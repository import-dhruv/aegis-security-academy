# Chapter 14: Reconnaissance and Attack Surface Mapping

> **Learning objectives.** Build an authorized asset inventory; enumerate subdomains, DNS, certificates, technologies, endpoints, APIs, and cloud exposures; use recon tools correctly; reduce false positives; and keep all scanning within owned infrastructure, authorized targets, or local labs.

> **Authorization reminder:** every technique in this chapter must be applied only to assets you own, authorized program targets, or your lab. Certificate transparency and passive sources are observational; active scanning requires authorization.

## 14.1 The Recon Mindset

Reconnaissance answers: *what exists, what is it made of, and how does it connect?* The goal is an **attack surface map** — a structured inventory of assets, technologies, endpoints, and trust relationships. Good recon is patient and mostly passive first; noisy scanning comes later and only when allowed.

```
Passive sources               Active techniques (authorized only)
-----------------             ----------------------------------
Certificate transparency      DNS brute forcing
Search engines                Port scanning
Historical archives           HTTP probing
Public code repos             Content discovery
DNS records                   Technology fingerprinting
```

## 14.2 Asset Discovery and Subdomain Enumeration

Sources:

- **Certificate Transparency (CT) logs:** every publicly issued TLS certificate is logged. Query crt.sh or certspotter to find subdomains. Passive and highly effective.
- **DNS:** zone transfers (if misconfigured), brute forcing with wordlists, and passive DNS datasets.
- **Search engines:** indexed URLs and subdomains.
- **Historical archives:** Wayback Machine and Common Crawl reveal old endpoints.
- **Public code:** repositories, JS bundles, and documentation may reference internal hostnames.
- **ASN/IP ownership:** based on authorized IP ranges.

## 14.3 Tools Study Format

For each tool: purpose, architecture, installation, commands, output, limitations. Verify installation and flags against official docs (versions change).

### Amass
- **Purpose:** comprehensive attack-surface mapping and subdomain enumeration using passive and active sources.
- **Architecture:** modular data sources; graph-based data model; can use external APIs.
- **Install:** `go install github.com/owasp-amass/amass/v4/...@latest` (verify at https://github.com/owasp-amass/amass).
- **Commands:** `amass enum -passive -d example.com`; `amass enum -active -d example.com` (active requires authorization).
- **Output:** list of subdomains and relationships; JSON/Graph formats.
- **Limitations:** many sources need API keys; active mode can be noisy.

### Subfinder
- **Purpose:** fast passive subdomain discovery.
- **Architecture:** Go-based, many source modules.
- **Install:** `go install github.com/projectdiscovery/subfinder/v2/cmd/subfinder@latest`.
- **Commands:** `subfinder -d example.com -o subs.txt` (passive by default).
- **Output:** deduplicated subdomains. **Limitations:** source coverage varies; API keys improve results.

### httpx
- **Purpose:** fast HTTP probing to find live hosts, status codes, titles, and tech.
- **Install:** `go install github.com/projectdiscovery/httpx/cmd/httpx@latest`.
- **Commands:** `httpx -l subs.txt -status-code -title -tech-detect -o live.txt`.
- **Output:** one line per live URL with metadata. **Limitations:** can overload targets; use `-rate` limits.

### dnsx
- **Purpose:** fast DNS querying and resolution/validation.
- **Install:** `go install github.com/projectdiscovery/dnsx/cmd/dnsx@latest`.
- **Commands:** `dnsx -l subs.txt -a -aaaa -cname -resp`.
- **Limitations:** resolver reliability; use reputable resolvers.

### Naabu
- **Purpose:** port scanning optimized for recon workflows.
- **Commands:** `naabu -host target -top-ports 100` (authorized only).
- **Limitations:** noisy; respect scope and rate limits.

### Nmap
- **Purpose:** the standard network discovery and security scanner.
- **Architecture:** host discovery, port scan, version detection, OS detection, NSE scripts.
- **Commands:** `nmap -sV -sC -oA scan target` (authorized only).
- **Output:** normal, XML, grepable. **Limitations:** heavy scans are detectable and may be disallowed; learn scan types (`-sS`, `-sT`, `-sU`).

### Katana
- **Purpose:** next-generation web crawler that extracts endpoints and links from JS.
- **Install:** `go install github.com/projectdiscovery/katana/cmd/katana@latest`.
- **Commands:** `katana -u https://target -o urls.txt`.
- **Limitations:** JS-heavy apps require headless mode; can be noisy.

### Waybackurls / Gau
- **Purpose:** fetch historical URLs from archives (Wayback Machine, Common Crawl).
- **Commands:** `echo target | waybackurls > old.txt`; `gau target > urls.txt`.
- **Limitations:** archived endpoints may be long dead; verify before testing.

### Feroxbuster / ffuf / Gobuster
- **Purpose:** content and parameter discovery (directories, files, virtual hosts).
- **Commands:**
  ```
  feroxbuster -u https://target -w wordlist.txt
  ffuf -u https://target/FUZZ -w wordlist.txt -mc 200,301
  gobuster dir -u https://target -w wordlist.txt
  ```
- **Output:** discovered paths with status/size. **Limitations:** false positives from catch-all responses; noisy; must be rate-limited and authorized.

### WhatWeb / Wappalyzer
- **Purpose:** technology fingerprinting (server, framework, CMS, libraries).
- **Commands:** `whatweb https://target`. Wappalyzer is a browser extension.
- **Limitations:** fingerprinting can be spoofed; verify with multiple signals (headers, cookies, file hashes, JS bundle names).

### Shodan / Censys / SecurityTrails
- **Purpose:** internet-wide search engines for exposed assets, banners, certificates, and DNS history.
- **Usage:** web UI/API; query by organization, ASN, certificate, or banner.
- **Limitations:** data may be stale; confirm current ownership before testing.

## 14.4 Building an Attack Surface Map

A practical pipeline (all on authorized assets):

```
1. Seed: example.com (from scope)
2. Passive: subfinder + amass passive + CT logs -> subs.txt
3. Resolve: dnsx -l subs.txt -a -> resolved.txt
4. Probe: httpx -l resolved.txt -status-code -title -o live.txt
5. Crawl: katana -l live.txt -o urls.txt; gau/waybackurls -> historical
6. Fingerprint: whatweb on live hosts; parse headers with httpx
7. Ports: naabu/nmap on in-scope hosts (rate-limited)
8. Content: ffuf/feroxbuster on key hosts
9. API discovery: inspect JS bundles for paths; look for /api, /graphql
10. Dedup and store: sort -u; tag each asset with source and scope status
```

## 14.5 JavaScript Analysis

Modern apps reveal APIs in JS bundles:

```
katana -u https://target -o urls.txt
grep -Eo '"/api/[A-Za-z0-9_/{}-]+"' urls.txt | sort -u
```

Use browser DevTools → Sources / Network to find chunks, source maps, and endpoints. Look for hardcoded keys (report, do not abuse), feature flags, GraphQL schemas, and hidden admin paths.

## 14.6 Cloud Asset Exposure

- Use CT logs and DNS to find cloud-hosted subdomains.
- Look for object-storage endpoints (`s3.amazonaws.com`, `storage.googleapis.com`) in JS.
- Identify cloud provider from headers, IPs, and CNAMEs (Chapter 19).
- **Never probe cloud assets outside the program's scope.**

## 14.7 False-Positive Reduction

- Verify that a host actually resolves and responds.
- Check that a discovered subdomain is in scope (ownership!).
- Confirm status codes and content with a second request; catch-all 200s are common.
- Deduplicate by host + path + parameters.
- Record source and timestamp for each asset.

## 14.11 Mastery Deep Dive: Passive-First Reconnaissance

> **Authorization boundary.** Passive sources (certificate logs, public DNS, search engines, archives, public code) are observational. Active techniques — HTTP probing, port scanning, content discovery — require an asset you own, a local lab, or a current written program authorization. Every command below is presented for those contexts only. Verify tool flags against current official documentation; versions change.

### 14.11.1 The Passive-First Doctrine

Reconnaissance quality is determined before the first packet you send. Passive-first means exhausting observational sources to build a high-confidence candidate list, then using active techniques only to validate what matters. The reasons are practical as well as ethical:

| Concern | Passive-first benefit |
| — | — |
| Authorization | Observations do not probe a system; they require no permission beyond reading public data |
| Noise | Fewer requests mean less risk of disturbing production or tripping rate limits |
| Signal | Correlating multiple independent sources filters stale or misconfigured records |
| Cost | Public data is free; API quotas and scanning time are not |
| Scope discipline | Ownership clues appear in passive records before you send a single request |

The output of the passive phase is not "a list of subdomains." It is a **provenance-tagged set of candidate assets**, where every entry records which source produced it and when. Provenance is what lets you later explain why you touched an asset and discard dubious entries.

### 14.11.2 Certificate Transparency in Depth

Every publicly trusted TLS certificate is recorded in Certificate Transparency (CT) logs. This makes CT one of the richest passive sources for hostnames, including hosts not linked anywhere publicly.

```bash
# Query crt.sh for a domain and extract unique names from SAN fields.
curl -s 'https://crt.sh/?q=%25.example-lab.test&output=json' \
  | jq -r '.[].name_value' \
  | sed 's/^\*\.//' \
  | tr '[:upper:]' '[:lower:]' \
  | sort -u > ct_subs.txt

# Show the most recently logged certificates with issuer and dates.
curl -s 'https://crt.sh/?q=%25.example-lab.test&output=json' \
  | jq -r '.[] | [.logged_at, .issuer_name, .name_value] | @tsv' \
  | sort -r | head -20
```

**How to interpret the output:**

- Each `name_value` may contain multiple newline-separated SANs; `jq -r` expands them. Deduplicate aggressively.
- Leading `*.` entries indicate wildcard certificates. They tell you a wildcard exists but do **not** enumerate actual subdomains — treat them as hints, not hosts.
- Repeated names with different `logged_at` dates show certificate renewal history. A name that stopped appearing months ago may be retired.
- An issuer you do not recognize may indicate a separate team or a third-party service. This is an ownership question, not a testing target.

**Limitations:** internal hostnames never appear; certificates may include names the owner no longer uses; and CT data is not proof that a host resolves today. Always resolve and validate later (14.12.2).

### 14.11.3 DNS, ASN/IP, WHOIS, and RDAP Intelligence

DNS records tell you how names map to infrastructure. All commands here are observational lookups against public resolvers or registries.

```bash
# Record types and what they reveal.
dig +short example-lab.test A            # IPv4 addresses
dig +short example-lab.test AAAA         # IPv6 addresses
dig +short example-lab.test CNAME        # alias to another name (ownership clue)
dig +short example-lab.test MX           # mail provider; often third-party
dig +short example-lab.test NS           # authoritative nameservers
dig +short example-lab.test TXT          # verification tokens, SPF, domain ownership
dig +short example-lab.test SOA          # zone metadata

# Zone transfer: attempt ONLY on a zone you own or are authorized to test.
dig @ns1.example-lab.test example-lab.test AXFR

# RDAP is the modern replacement for WHOIS.
whois example-lab.test | grep -iE 'registrant|organization|country|abuse'
curl -s 'https://rdap.org/domain/example-lab.test' | jq '.entities[]?.vcardArray'
```

**Interpretation table:**

| Observation | Likely meaning | Next passive step |
| — | — | — |
| CNAME to `*.cloudfront.net` | CDN in front of origin | Look for origin-host hints in DNS history and CT |
| CNAME to a SaaS domain | Third-party service | Treat as ownership-ambiguous; flag for clarification |
| MX to a mail provider | External email service | Usually out of scope; do not test |
| TXT with `google-site-verification` | Domain controlled by program (probably) | Corroborate with other sources |
| Multiple A records across ASNs | Load balancing or multi-cloud | Query ASN ownership data for authorized ranges |
| NS on a registrar's DNS | Simple hosting setup | Check whether subdomains use different NS |

**ASN/IP ownership (passive):** if the program publishes IP ranges, look them up in public routing registries and BGP data to understand which autonomous systems announce them. This is useful for confirming that an address block belongs to the program before any active step. Never expand from one in-scope IP to "the whole ASN" without explicit written scope.

### 14.11.4 Search-Engine and Code-Repository Dorking

Public indexes leak hostnames, endpoints, and documentation. The technique is query construction, not luck.

```text
Google/Bing operator patterns (use only to collect public references):

site:example-lab.test                         -> indexed pages
site:example-lab.test -www                    -> other subdomains
site:example-lab.test inurl:/api/             -> API paths
site:example-lab.test ext:pdf OR ext:docx     -> documents with hostnames
site:example-lab.test "test" "internal"       -> environment hints
"example-lab.test" -site:example-lab.test     -> third-party mentions
inurl:gitlab.example-lab.test                 -> code-hosting references

GitHub code search (public code only, read-only):
"example-lab.test"                            -> hardcoded config references
"api.example-lab.test"                        -> endpoint strings
"example-lab.test" filename:.env              -> exposed configuration (REPORT, do not abuse)
"example-lab.test" language:JavaScript        -> JS bundles with paths
```

**Rules for dorking ethically:**

- Collect *pointers*; do not follow a discovered credential into a system. If you find a live secret in public code, report it through the authorized channel and do not use it.
- Do not scrape aggressively; respect provider rate limits and terms of service.
- Verify that anything you plan to probe is in scope. A leaked hostname may belong to a vendor.
- Record the exact query string and date in your notes so results are reproducible.

### 14.11.5 Provenance Table for the Passive Phase

| Source | Command / query | Output file | Timestamp | Trust level |
| — | — | — | — | — |
| CT logs | `curl crt.sh ...` | `ct_subs.txt` | | Medium (may be stale) |
| Search index | `site:example-lab.test` | `search_subs.txt` | | Low (index lag) |
| GitHub code | `"example-lab.test"` | `code_subs.txt` | | Low (may be third party) |
| DNS TXT/NS | `dig ...` | `dns_obs.txt` | | High (current) |
| Historical archives | `gau`, `waybackurls` | `historical_urls.txt` | | Low (verify liveness) |

Every later step consumes this table. If an active result cannot be traced back to a provenance row, discard it.

## 14.12 Mastery Deep Dive: Discovery, Validation, and Fingerprinting

### 14.12.1 Subdomain Discovery as a Pipeline

No single tool finds everything. Run complementary collectors, then merge and deduplicate.

```bash
# 1. Passive collectors (no direct target traffic).
subfinder -d example-lab.test -o subfinder.txt
amass enum -passive -d example-lab.test -o amass_passive.txt

# 2. Merge with earlier passive sources and normalize.
cat subfinder.txt amass_passive.txt ct_subs.txt search_subs.txt \
  | tr '[:upper:]' '[:lower:]' \
  | sed 's#^https\?://##; s#/.*$##' \
  | sort -u > subs_all.txt

wc -l subs_all.txt
```

**Interpreting tool behavior:**

- `subfinder` is fast and source-driven; its output is usually clean but limited by configured API keys. An empty or small result set means "few sources responded," not "no subdomains exist."
- `amass enum -passive` builds a relationship graph and can reveal related domains, but many data sources require API keys configured in its config file.
- `amass enum -active` performs direct queries and is **only for authorized assets**. In a lab or owned domain, compare passive vs. active output to quantify what each mode adds.
- Deduplication must normalize case and strip URL prefixes; otherwise the same host appears multiple times and distorts counts.

### 14.12.2 Resolution and HTTP Probing

Raw candidate names include dead records and wildcards. Resolve, then probe — gently.

```bash
# Resolve and classify DNS answers.
dnsx -l subs_all.txt -a -aaaa -cname -resp -o dns_resolved.txt

# Extract only hosts with a successful A/AAAA answer.
awk '{print $1}' dns_resolved.txt | sort -u > resolved_hosts.txt

# Probe politely for live HTTP services.
httpx -l resolved_hosts.txt \
  -status-code -title -server -tech-detect \
  -rate-limit 20 -timeout 5 \
  -o live_hosts.txt
```

**How to read `httpx` output:** each line is a URL plus metadata such as `[200] [Example Login] [nginx]`. Interpret it as follows:

- `200` with a consistent title: likely a real application; high priority.
- `301/302`: follow the redirect target and record it; redirects often reveal canonical hosts or SSO portals.
- `403/401`: authentication required; still in scope if the host is authorized. Note it for later manual testing.
- `404` with identical content length across many hosts: a catch-all or default virtual host, not a real service. Discard unless the program specifically includes it.
- Duplicate titles across many hosts: often a shared template or a wildcard DNS catch-all. Verify before treating them as distinct assets.
- Timeouts: may indicate IPv6 records that do not route or firewalled hosts. Do not increase rate limits to compensate.

### 14.12.3 Port and Service Discovery With Nmap (Authorized Only)

Use port scanning only on hosts you own, in a lab, or explicitly authorized for active scanning — and only if the program permits it.

| Scan type | Flag | What it does | When to use |
| — | — | — | — |
| TCP SYN | `-sS` | Half-open scan; fast and relatively stealthy | Default on authorized Linux targets |
| TCP connect | `-sT` | Full connect; no raw-socket privileges | When `-sS` is unavailable |
| UDP | `-sU` | Probes UDP services; slow and noisy | Only with explicit permission and a reason |
| Service/version | `-sV` | Banner and probe-based version detection | After finding open ports |
| Default scripts | `-sC` | Safe NSE scripts | Standard follow-up on owned hosts |
| OS detection | `-O` | TCP/IP fingerprinting | Rarely needed for web targets |
| All ports | `-p-` | Full 1-65535 range | Small, owned scopes only |

```bash
# Lab / owned host: standard service discovery.
nmap -sS -sV -sC -oA nmap_lab 192.0.2.10

# Authorized in-scope host with a narrow port set and gentle timing.
nmap -sS -sV -p 80,443,8443 -T2 -oA nmap_inscope app.example-lab.test

# Summarize open ports from grepable output.
grep '^Ports:' nmap_inscope.gnmap
```

**Output interpretation:**

```text
PORT     STATE  SERVICE   VERSION
22/tcp   open   ssh       OpenSSH 8.x
80/tcp   open   http      nginx
443/tcp  open   ssl/http  nginx
8443/tcp closed https-alt
```

- `open` plus a version means a service is reachable; verify the version against vendor advisories rather than assuming it is vulnerable.
- `filtered` means a firewall dropped probes; do not interpret this as closed or keep hammering it.
- `closed` means the port responded with a reset. Note it but do not rescan repeatedly.
- A discrepancy between `https-alt` on 8443 and the actual service highlights why version labels are hints, not facts.
- Never run aggressive timing (`-T4`/`-T5`) or NSE scripts that send large payloads on production without explicit approval.

### 14.12.4 Technology Fingerprinting

Fingerprinting is correlation, not a single tool's verdict.

```bash
# HTTP-level clues.
httpx -l live_hosts.txt -header 'Server' -header 'X-Powered-By' \
  -header 'Set-Cookie' -follow-redirects -o headers.txt

# Fingerprint web technologies.
whatweb https://app.example-lab.test --verbose

# Favicon hashing (useful for matching frameworks and finding similar apps).
curl -s https://app.example-lab.test/favicon.ico | md5sum
```

| Signal | What it suggests | Reliability | Corroborate with |
| — | — | — | — |
| `X-Powered-By: PHP` | PHP application | Medium | File extensions, cookie names |
| `Set-Cookie: JSESSIONID` | Java servlet container | High | Error page format, header order |
| JS bundle names like `app.[hash].js` | Modern SPA build | High | Source maps, framework runtime markers |
| `Server: nginx` | Reverse proxy or web server | Low (spoofable) | Error pages, header ordering |
| Favicon hash match | Same framework or template family | Medium | HTML structure, asset paths |
| `__NEXT_DATA__` in HTML | Next.js application | High | `/_next/` asset paths |

Fingerprinting drives prioritization: a known framework narrows the list of likely vulnerabilities and tells you which documented configuration checks are relevant. Always validate the inference in the browser or in responses before acting on it.

### 14.12.5 Visual Recon and Screenshotting

HTTP metadata misses what a human sees: portals, error pages, brand names, and environment labels.

```bash
# Screenshot live hosts (lab or authorized in-scope only).
httpx -l live_hosts.txt -screenshot -screenshot-dir shots/ \
  -rate-limit 10 -o screenshot_meta.txt

# Dedicated screenshotters (verify current install/docs):
# gowitness scan file -f live_hosts.txt --threads 2 --screenshot-path shots/
# eyeballer -i live_hosts.txt -o shots/
```

**What to look for in screenshots:**

- Environment labels ("STAGING", "UAT", "internal only") that may change scope status.
- Login portals revealing SSO providers or product names.
- Default web server pages indicating an unconfigured host.
- Error pages exposing framework or stack traces.
- Branding that suggests a third-party or acquired service — a scope question, not a target.

Store screenshots with a naming convention `<host>_<date>.png` and link them from the asset inventory. A screenshot is often the fastest way to explain to a program why you believed a host was in scope.

## 14.13 Mastery Deep Dive: Endpoints, Parameters, and Templates

### 14.13.1 Layered Endpoint Discovery

Endpoints come from four layers; use all of them.

```bash
# 1. Live crawl from discovered hosts (authorized only).
katana -l live_hosts.txt -o crawled_urls.txt

# 2. Historical archives (passive).
echo "example-lab.test" | gau > gau_urls.txt
echo "example-lab.test" | waybackurls > wayback_urls.txt

# 3. Merge and normalize, keeping paths and parameters.
cat crawled_urls.txt gau_urls.txt wayback_urls.txt \
  | sed 's/#.*$//' | sort -u > urls_all.txt

# 4. Extract parameter names for the endpoint ledger.
grep -o '?[^#]*' urls_all.txt \
  | tr '&' '\n' | sed 's/^?//' | cut -d= -f1 | sort -u > params.txt
```

**Interpretation:** archived URLs are *leads*, not live endpoints. Many return 404 or redirect. Validate with a gentle HEAD/GET probe and record status. Parameter names are especially valuable because they reveal the application's vocabulary (`id`, `user_id`, `role`, `redirect`, `next`, `file`, `token`) and guide manual testing in Chapter 15.

### 14.13.2 Content and Parameter Discovery With ffuf

Content discovery finds unlinked paths and parameters. It is active and must be rate-limited and authorized.

```bash
# Directory/file discovery with sensible filters.
ffuf -u https://app.example-lab.test/FUZZ \
  -w /usr/share/wordlists/dirb/common.txt \
  -mc 200,204,301,302,307,401,403 \
  -fc 404 -rate 10 -timeout 10 \
  -o ffuf_dirs.json -of json

# Parameter discovery on a known endpoint.
ffuf -u 'https://app.example-lab.test/api/search?FUZZ=test' \
  -w params.txt -mc all -fc 404 -rate 5 \
  -o ffuf_params.json -of json

# Virtual host discovery against an owned IP.
ffuf -u http://192.0.2.10/ -H 'Host: FUZZ.example-lab.test' \
  -w subs_all.txt -mc 200 -rate 10
```

**Filtering and false-positive control:**

| Response pattern | Likely cause | Action |
| — | — | — |
| Every path returns 200 with identical size | Catch-all / SPA fallback | Filter by `-fs <size>`; verify a few manually |
| Many 403s for random paths | Access control default | Check whether 403 bodies are identical; often noise |
| 301 to a single canonical host | Redirect normalization | Follow once; do not treat as discovery |
| Different sizes for identical statuses | Real distinct content | Investigate manually |
| Rate-limit responses (429) | Too fast | Stop, lower `-rate`, and consider approval |

Always confirm a discovery with a second manual request before recording it as an asset. A `ffuf` hit is a hypothesis, not a fact.

### 14.13.3 JavaScript Analysis for Hidden Endpoints

Modern applications reveal their API surface in JavaScript bundles. This is passive when you fetch bundles that the application already serves to browsers, but still keep volumes low and stay in scope.

```bash
# Extract JS URLs from crawl output.
grep -Eo 'https?://[^"'"'"' ]+\.js(\?[^"'"'"' ]*)?' urls_all.txt | sort -u > js_urls.txt

# Download bundles for local analysis (authorized target only).
mkdir -p js_bundles
while read -r u; do
  curl -s "u" -o "js_bundles/(echo "$u" | md5sum | cut -c1-12).js"
done < js_urls.txt

# Extract API-like paths and interesting keywords.
grep -RhoE '"/(api|v[0-9]+|graphql|admin|internal)/[A-Za-z0-9_/?=&{}-]+"' js_bundles/ \
  | sort -u > js_paths.txt
grep -RhinE 'apiKey|secret|token|aws|s3\.|graphql|featureFlag' js_bundles/ | head -40
```

**What to look for and what to do:**

- **Endpoint strings:** add to the endpoint ledger; validate gently.
- **Feature flags:** may reveal hidden functionality; note the flag name.
- **Hardcoded keys or credentials:** report through the authorized channel; **never use them**. Do not test whether they work.
- **Source maps (`*.js.map`):** may expose original source structure; read locally, do not publish.
- **GraphQL schema introspection:** if the program permits, record types and queries; keep requests minimal.
- **Minified chunks:** dynamic imports often reveal route names; search for `import(` and chunk manifests.

### 14.13.4 Nuclei Templates: Safe Automation

Nuclei runs templated checks. Its value is consistency and speed, but templates must be chosen carefully and run gently.

**Anatomy of a safe, informational template (lab/authorized use only):**

```yaml
id: lab-server-header-info

info:
  name: Lab - Server header observation
  author: lab-student
  severity: info
  description: Records a Server response header for inventory purposes only.

requests:
  - method: GET
    path:
      - "{{BaseURL}}/"
    matchers-condition: and
    matchers:
      - type: status
        status:
          - 200
      - type: word
        part: header
        words:
          - "Server:"
    extractors:
      - type: regex
        part: header
        regex:
          - '(?i)server:\s*(.+)'
```

```bash
# Run a custom template against a single authorized host, gently.
nuclei -u https://app.example-lab.test \
  -t templates/lab-server-header-info.yaml \
  -rl 5 -timeout 5 -o nuclei_results.txt

# Run a small, reviewed template set against an owned inventory.
nuclei -l resolved_hosts.txt -t templates/lab-templates/ -rl 5 -o nuclei_all.txt
```

**Template discipline:**

- Read every template before running it. Community templates can include intrusive payloads.
- Prefer `info` and `low` severity detection templates during inventory building; save exploitation-style checks for explicit authorization.
- Use `-rl` (rate limit) and a narrow target list; never point templates at a whole ASN.
- Interpret results as leads. A template match is a pattern match, not a validated finding; manual confirmation is mandatory.
- Record template ID, version, and run date in your notes so results are reproducible.

### 14.13.5 API and GraphQL Discovery Notes

- Look for `/api/`, `/v1/`, `/graphql`, `/openapi.json`, `/swagger.json`, and `/docs` in crawled and archived URLs.
- API documentation is a map of intended behavior; save a local copy for your endpoint ledger.
- Compare REST, GraphQL, and mobile representations of the same object; differences often reveal extra fields (a Chapter 15 testing idea).
- For GraphQL under authorization, record available queries and types without sending expensive introspection queries repeatedly.
- Never probe undocumented internal APIs unless the program explicitly includes them.

## 14.14 Mastery Deep Dive: Prioritization, Inventory, and Continuous Monitoring

### 14.14.1 A Prioritization Scoring Model

Not all assets deserve equal attention. Score them with a transparent rubric:

| Criterion | Weight | Score 0-5 questions |
| — | — | — |
| In-scope certainty | 0.25 | 5 = explicit; 3 = resolved wildcard; 0 = ambiguous |
| Liveness and interactivity | 0.20 | 5 = 200 with forms/API; 1 = static page |
| Attack surface richness | 0.20 | 5 = many endpoints/parameters; 1 = few |
| Technology familiarity | 0.15 | 5 = known stack; 1 = unfamiliar |
| Freshness | 0.10 | 5 = recently added/changed; 1 = long stable |
| Data/privilege sensitivity | 0.10 | 5 = auth, payments, admin; 1 = marketing |

Worked example: Host A is explicitly in scope (5), interactive (5), rich (4), familiar (5), fresh (2), sensitive (5). Score = `5(0.25)+5(0.20)+4(0.20)+5(0.15)+2(0.10)+5(0.10) = 4.55`. Host B is ambiguous (0) but otherwise scores 5s: `0(0.25)+5(0.20)+5(0.20)+5(0.15)+5(0.10)+5(0.10) = 3.75`. Host A wins, and the ambiguity gate prevents Host B from being tested at all until clarified. This is intentional: scope certainty is weighted most heavily.

### 14.14.2 The Canonical Asset Inventory

Your inventory is the deliverable of recon. Use a schema that supports decisions:

```markdown
| Asset | Source(s) | In-scope? | IP / ASN | Status | Tech | Endpoints | Priority | Notes |
| — | — | — | — | — | — | — | — | — |
| app.example-lab.test | CT, subfinder, DNS | Yes (explicit) | 192.0.2.10 | 200 | nginx, SPA | 48 | 4.55 | Login + API |
| beta.example-lab.test | CT only | Amber (asked 2026-11-01) | CNAME to SaaS | 302 | unknown | 3 | blocked | Awaiting answer |
| support.example-lab.test | DNS, CT | No (excluded) | third party | 200 | helpdesk | - | red | Never test |
```

Required columns and why they matter:

- **Source(s):** provenance for every asset; supports false-positive review.
- **In-scope?:** the decision, with date of any clarification.
- **IP / ASN:** ownership evidence; helps detect third-party hosting.
- **Status:** HTTP state from `httpx`; tells you if the asset is live.
- **Tech:** fingerprint with confidence notes.
- **Endpoints:** count from the endpoint ledger; drives prioritization.
- **Priority:** computed score; orders your testing queue.
- **Notes:** screenshots, open questions, and observations.

### 14.14.3 Continuous Monitoring

Attack surfaces change. A monitoring loop turns recon from a one-time event into a habit. In your own environment, lab, or authorized program:

```text
Weekly (or on a schedule you can sustain):

1. Re-run passive collectors (CT, subfinder, amass passive, gau).
2. Merge with the previous snapshot:  sort -u previous.txt new.txt > merged.txt
3. Diff to find changes:              comm -13 previous.txt new.txt > added.txt
                                      comm -23 previous.txt new.txt > removed.txt
4. Probe only newly added, in-scope hosts gently with httpx.
5. Update the inventory with new rows and dates.
6. Re-read the program policy; scope changes invalidate old decisions.
```

**What changes signal:** a new subdomain often means a new feature; a changed CNAME may mean a migration; a removed host may be decommissioned (do not test it). New certificates frequently precede new services by days, making CT monitoring the earliest warning source.

Store snapshots with date-stamped filenames (`subs_2026-11-01.txt`) so you can reconstruct what you knew at any point. Never "monitor" by running continuous active scans; monitoring should be passive-first with gentle validation of changes.

### 14.14.4 False-Positive and Scope Re-Verification Checklist

```text
[ ] Host resolves to a real address today (dnsx result recorded).
[ ] HTTP response is not a catch-all; status/body verified manually.
[ ] The host is in scope under a specific clause, not inference.
[ ] CNAME / ASN ownership checked; third-party hosts flagged.
[ ] Duplicate entries normalized (case, scheme, trailing slash).
[ ] Archived endpoints revalidated before use.
[ ] Template/tool hits manually confirmed.
[ ] Source and timestamp recorded for every retained asset.
[ ] Rate limits respected and no program restriction violated.
```

### 14.14.5 Common Recon Mistakes

1. **Trusting one source.** Source diversity is the only defense against stale data.
2. **Equating a wildcard certificate with a live host.** Certificates enumerate names, not services.
3. **Skipping deduplication.** Duplicate hosts inflate inventory counts and waste testing time.
4. **Scanning first, scoping later.** Every active step must follow a scope decision.
5. **Ignoring catch-all responses.** A 200 for every path poisons content-discovery results.
6. **Using default aggressive tool settings.** Rate limits are part of professional conduct.
7. **Treating fingerprinting as truth.** Headers are spoofable; correlate multiple signals.
8. **Collecting secrets without a reporting path.** A found credential is a report, not a tool.
9. **Never revisiting the inventory.** Recon decays; schedule monitoring.
10. **Confusing "found" with "validated."** Discovery produces leads; validation produces assets.

## 14.15 Mastery Deep Dive: Lab Drills, Documentation, and Assessment

### 14.15.1 Practice Environment

Build a lab before practicing active techniques:

- A domain you own, with DNS you control, for passive-vs-active comparisons.
- A local vulnerable application (for example, a deliberately vulnerable web app in a container) for crawling, ffuf, and nuclei practice.
- A local DNS zone for zone-transfer and record-type experiments.
- Optional: a local testnet/fork if you also study Web3 targets.

Never point practice scans at systems you do not own or that are not explicitly authorized. The lab is where you are free to make mistakes; production is not.

### 14.15.2 Lab Exercises With Deliverables

1. **CT vs. DNS comparison.** For your owned domain, collect CT names and live DNS names. Deliverable: a table showing names found by only one source and an explanation of each discrepancy.
2. **Tool correlation.** Run `subfinder` and `amass enum -passive` on your domain. Deliverable: a Venn-style list of unique and shared results with a hypothesis for each difference.
3. **HTTP triage.** Probe your resolved hosts with `httpx`. Deliverable: a classification of each host into live app / redirect / auth-required / catch-all / dead, with evidence.
4. **Nmap interpretation.** Scan your lab VM with `-sV -sC`. Deliverable: an annotated output explaining each open, filtered, and closed port and why version labels are hypotheses.
5. **Fingerprint correlation.** Fingerprint your lab app with `whatweb`, headers, and favicon hash. Deliverable: a confidence table for each inferred technology.
6. **Content discovery false positive.** Run `ffuf` against the lab app with a small wordlist. Deliverable: identification of a catch-all response and the exact filter that removed it.
7. **JS endpoint mining.** Host a small SPA in the lab. Deliverable: a list of endpoints found only in JS, with the bundle and line reference for each.
8. **Safe template writing.** Write one informational nuclei template for your lab app. Deliverable: the YAML, the run command with rate limit, and an explanation of why it cannot cause harm.
9. **Monitoring diff.** Take two passive snapshots of your owned domain a week apart (or use archived snapshots). Deliverable: a `comm`-based diff and an interpretation of each change.
10. **Priority scoring.** Score five lab/authorized assets with the 14.14.1 rubric. Deliverable: a ranked queue with a one-line justification per asset.

### 14.15.5 Knowledge Check

1. Why does a wildcard certificate not prove that a subdomain is live?
2. You see a CNAME from an in-scope hostname to a third-party SaaS provider. What is the correct next step?
3. `ffuf` returns 200 for every path with the same response size. What is happening and how do you handle it?
4. Name two signals that corroborate a `Server: nginx` header inference.
5. A community nuclei template contains an intrusive payload. What do you do?
6. Why is scope certainty weighted most heavily in the prioritization rubric?
7. You find a hardcoded API key in a public JS bundle of an authorized target. What do you do?

<details>
<summary><strong>Answers</strong></summary>

1. A certificate records a name that was issued a certificate; the name may no longer resolve, may point to a different service, or may never have hosted an application. Resolve and probe gently to establish liveness.
2. Treat it as ownership-ambiguous. Do not probe it; ask the program in writing whether the host is in scope and record the answer. Branding or a wildcard is not proof of ownership.
3. A catch-all or SPA fallback is returning the same content for all paths. Verify a couple manually, then filter by response size (`-fs`) or status and re-run at a gentle rate.
4. Error page format and header ordering are common corroborating signals; cookie names and framework-specific asset paths also help. Correlate at least two independent clues.
5. Do not run it. Read the template, choose a safe informational alternative, or write your own checked template with a rate limit. A template match is still only a lead requiring manual validation.
6. Because testing an ambiguous asset can become an authorization violation regardless of how valuable it appears. Scope certainty is a gating condition, not a tradeable preference.
7. Report it through the authorized channel without using it, testing whether it works, or sharing it. Include where it was found and its apparent type; let the owner rotate it.

</details>

## 14.16 Mastery Deep Dive: The Recon-to-Testing Handoff

### 14.16.1 Turning Inventory Into Hypotheses

Recon has no value until it produces testable ideas. For each high-priority asset in your inventory, write a short handoff note that a tester (often you, a day later) can act on without redoing the work:

```markdown
# Handoff Note: <host>

Priority score: <value from 14.14.1>
Scope decision: <explicit / resolved wildcard + date of clarification>
Observed tech: <signals with confidence>
Interesting endpoints: <top five with source>
Parameter vocabulary: <notable names>
Open questions: <scope or ownership items>
Suggested first hypotheses:
  H1: <what boundary might be broken and why>
  H2: <alternative hypothesis>
Do-not-test: <excluded branches, third-party hosts, data types>
```

The "suggested first hypotheses" field is the critical one. It forces you to convert observations into claims. For example: "The JS bundle references `/api/admin/export` on an in-scope host; the app uses bearer tokens; hypothesize function-level authorization may be missing — test with a normal user token in an authorized session." That is a direct bridge into the Chapter 15 methodology.

### 14.16.2 Recon Quality Gates

Before declaring recon complete, require all of the following:

```text
[ ] At least three independent passive sources were queried and logged.
[ ] Every retained asset has a source, timestamp, and scope decision.
[ ] Active steps were limited to owned/lab/authorized hosts and rate-limited.
[ ] HTTP probing results were classified (live, redirect, auth, catch-all, dead).
[ ] Fingerprints were corroborated by two or more signals.
[ ] Archived and JS-derived endpoints were revalidated for liveness.
[ ] Any discovered credentials were reported, never used.
[ ] The priority rubric was applied and a ranked queue exists.
[ ] A monitoring snapshot was saved for future diffing.
[ ] Handoff notes were written for the top-priority assets.
```

If any gate fails, recon is incomplete. This is preferable to discovering mid-test that your "attack surface" was a single tool's output and that half of it is out of scope.

### 14.16.3 Knowledge Check: Handoff

1. Why does a handoff note include a "do-not-test" field?
2. What makes a suggested hypothesis actionable rather than vague?

<details>
<summary><strong>Answers</strong></summary>

1. Because recon discovers excluded and third-party hosts as well as valid ones. Recording them prevents a later session, or a peer, from mistaking a discovery for permission.
2. It names the asset, the observed signal, the suspected boundary, and the first safe test, so testing can begin without repeating recon or guessing.

</details>

## 14.9 Key Takeaways

- Recon is structured inventory building, not random scanning.
- Passive sources (CT, archives, search engines) come first; active scanning only when authorized.
- Each tool has a specific role; interpret output critically and reduce false positives.
- Scope verification is part of every recon step.
