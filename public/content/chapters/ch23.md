# Chapter 23: Fuzzing and Automated Vulnerability Discovery

> **Learning objectives.** Choose a fuzzing strategy; build harnesses; manage corpora and crashes; use sanitizers and coverage feedback; and run small projects with AFL++, libFuzzer, OSS-Fuzz, Jazzer, and Schemathesis.

## 23.1 What Fuzzing Is

Fuzzing is automated testing with generated inputs. A fuzzer repeatedly feeds inputs to a target and watches for crashes, hangs, or assertion failures. It is exceptionally good at finding memory-safety and parser bugs that humans would never construct manually.

```
   seed inputs -> mutate/generate -> run target -> observe
        ^                                |
        +---- feedback (coverage) -------+
```

## 23.2 Fuzzing Strategies

- **Mutation-based:** start with seed inputs and mutate (bit flips, byte changes, splices). AFL++ excels here.
- **Generation-based:** generate inputs from a specification/grammar. Useful for structured formats.
- **Coverage-guided:** instrument the target and prioritize inputs that reach new code paths (AFL++, libFuzzer).
- **Grammar-based:** generate syntactically valid inputs from a grammar (great for protocols/compilers).
- **Differential fuzzing:** feed the same input to two implementations and compare outputs (finds logic bugs).
- **API fuzzing:** generate sequences of API calls (e.g., Schemathesis from OpenAPI specs).
- **Protocol fuzzing:** target network protocol parsers with structured messages.

## 23.3 Crash Triage

1. **Reproduce** with the exact input.
2. **Minimize** (AFL++/libFuzzer have built-in minimizers) to the smallest crashing input.
3. **Classify** the crash type (segfault, assertion, hang, OOM).
4. **Root-cause** with a debugger and sanitizer reports.
5. **Assess exploitability** honestly — many crashes are not security-relevant.
6. **Report** with a reproducer and analysis.

## 23.4 Corpus Management

A good seed corpus is small, diverse, and covers different code paths. Deduplicate by coverage. Store interesting inputs (those that add coverage) in the queue. A poor corpus wastes enormous time.

## 23.5 Sanitizers

- **AddressSanitizer (ASan):** use-after-free, buffer overflows, double free.
- **UndefinedBehaviorSanitizer (UBSan):** integer overflow, misaligned access.
- **MemorySanitizer (MSan):** uninitialized reads.
- **ThreadSanitizer (TSan):** data races.

Sanitizers turn subtle bugs into detectable failures and are standard in modern fuzzing.

## 23.6 Reproducibility and Harnesses

A **harness** is a small program that takes fuzzer input and calls the target API. Good harnesses:

- Are fast and deterministic.
- Avoid unnecessary I/O and randomness.
- Reset state between inputs.
- Cover the parser/code of interest.
- Include assertions for "impossible" states.

```c
// libFuzzer-style harness
int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
    parse_packet(data, size);   // target function
    return 0;
}
```

## 23.7 Tools

- **AFL++:** coverage-guided fuzzer for C/C++ and more; https://aflplus.plus/
- **libFuzzer:** in-process coverage-guided fuzzer; part of LLVM.
- **OSS-Fuzz:** Google's continuous fuzzing service for open-source projects; https://google.github.io/oss-fuzz/
- **Jazzer:** coverage-guided fuzzer for Java/JVM; https://github.com/CodeIntelligenceTesting/jazzer
- **Schemathesis:** property-based API fuzzing from OpenAPI/GraphQL schemas; https://schemathesis.readthedocs.io/

## 23.8 Small Practical Projects

1. Write a simple C parser with a deliberate bug; fuzz with AFL++ and triage the crash with ASan.
2. Build a libFuzzer harness for a lab library; run for 10 minutes; minimize one crash.
3. Use Jazzer on a small Java class that parses input.
4. Use Schemathesis against a lab OpenAPI app; triage any server errors (distinguish client vs. server fault).
5. Implement differential fuzzing between two JSON parsers on your system and investigate differences.

## 23.9 Ethical Boundaries

Fuzz only software you own, open-source projects you are contributing to, or authorized lab targets. Fuzzing a production service can constitute a DoS. Respect rate limits and program rules.

## 23.12 Mastery Deep Dive: Fuzzing Taxonomy and Strategy Selection

### 23.12.1 The Five Strategies Compared

Choosing a strategy is the highest-leverage decision in a fuzzing campaign. Each strategy answers "where do inputs come from?" differently, and each fits different targets.

| Strategy | Input source | Best for | Weakness |
|----------|--------------|----------|----------|
| **Mutation** | Flip/duplicate/splice bytes of seeds | Binary formats, file parsers with samples | Struggles with complex structure without good seeds |
| **Generation** | Build inputs from a spec/model | Well-specified formats | Needs a correct model; can miss "weird" real inputs |
| **Coverage-guided** | Mutate; keep inputs that hit new code | Almost any instrumentable target | Needs instrumentation; can get stuck on magic bytes |
| **Grammar/structure-aware** | Generate valid syntax from a grammar | Compilers, interpreters, structured protocols | Grammar must match the real parser |
| **Differential** | Same input → two implementations, compare | Logic bugs, conformance | Needs two comparable implementations |

Selection rule of thumb: start with **coverage-guided mutation** on a small, diverse seed corpus; if coverage plateaus at a parser's "magic byte" checks, add **grammar** awareness or a **dictionary**; if you are hunting logic (not memory) bugs, reach for **differential**; if you have a schema/spec, consider **generation** or **API fuzzing**. Mastery means diagnosing *why* a campaign stalled and switching strategies, not just pointing a tool at a target.

### 23.12.2 Coverage Instrumentation and the Feedback Loop

Coverage-guided fuzzing works because the target is **instrumented**: the compiler inserts counters at basic blocks or edges. The fuzzer observes which inputs reach new code and keeps them as seeds, building a corpus that systematically explores the program.

The feedback loop:

```
   seed corpus -> mutate -> run instrumented target -> coverage map
        ^                                              |
        +---- keep inputs with NEW edges/counters ------+
```

Instrumentation modes in AFL++ include **llvm_mode** (`afl-clang-fast`, fast, uses sanitizer coverage), **QEMU mode** (for binaries without source), and **frida mode**. libFuzzer uses LLVM's `-fsanitize=fuzzer` inline instrumentation. **Coverage-guided** does not mean "random": it is a search guided by a fitness signal (new edges), which is why it finds deep bugs far faster than blind random testing.

Understanding the signal helps you debug a stalled campaign: if the coverage map never grows, either the harness is too shallow, seeds are poor, or a checksum/magic gate blocks progress (a dictionary or grammar fix helps).

### 23.12.3 Corpus Management and Minimization

A corpus is only useful if it is **diverse** and **small**. Practical rules:

- Start with 5–20 seeds that exercise distinct code paths — not 10,000 near-identical files.
- Let the fuzzer **deduplicate by coverage**: AFL++'s `afl-cmin` and libFuzzer's `-merge=1` reduce a corpus to the minimal set that preserves total coverage.
- Periodically **minimize** the corpus; a bloated corpus slows every execution.

```bash
<LAB> afl-cmin -i seeds/ -o seeds_min/ -- ./target @@
<LAB> ./fuzz_target -merge=1 corpus_min/ corpus/    # libFuzzer

<LAB> # cmin output: "N files selected from M" -> keep the selected set
```

Interpretation: if `afl-cmin` reduces 2,000 seeds to 80 with no coverage loss, your original corpus was 96% redundant — the fuzzer was wasting cycles re-running equivalent inputs. Keep the minimized set and let the fuzzer grow it with *interesting* (new-coverage) inputs.

### 23.12.4 What Fuzzing Excels At and What It Misses

Knowing the limits of fuzzing prevents wasted campaigns and false confidence. Fuzzing is exceptional at **parsers and input-validation code**: image decoders, protocol parsers, file loaders, and deserializers, where untrusted bytes flow into complex branching logic and manual reasoning is infeasible. It reliably finds memory-safety errors (OOB, UAF, double free) and assertion failures, especially with sanitizers. It is also good at "unknown unknowns" — inputs no human would think to construct, such as a length field set to `0xFFFFFFFF`.

Fuzzing is weak at:

- **Deep semantic logic** that requires many correlated conditions (e.g., "a valid session, then a privileged operation, then a state transition"). Coverage alone does not encode *relationships* between fields; stateful or grammar-aware fuzzing is needed.
- **Cryptographic weaknesses, authentication bypasses, and business-logic flaws** — there is no crash signal when the program does the wrong thing "successfully." Differential testing or explicit oracles help.
- **Rare environment-dependent paths** requiring specific timing, file-system state, or external services.
- **Code that is not instrumented or reachable** through the harness — coverage cannot guide exploration of code the harness never calls.

Security rule: a clean fuzzing campaign is evidence that *a specific harness on a specific build* found no crashes in *a specific time budget* — not proof the software is bug-free. Pair fuzzing with code review, static analysis, and threat modeling. Mastery includes stating these limits explicitly when reporting results.

## 23.13 Mastery Deep Dive: Fuzzer Toolchains and Command Walks

### 23.13.1 AFL++ Setup and Command Walkthrough

AFL++ is a mutation-based, coverage-guided fuzzer for C/C++ (and more via modes). A full lab run:

```bash
<LAB> # 1. Build with AFL++ instrumentation
<LAB> afl-clang-fast -g -O1 -o target target.c

<LAB> # 2. Prepare seeds
<LAB> mkdir seeds && printf '<LAB>' > seeds/seed1

<LAB> # 3. Run (one core) - @@ is replaced by the input file path
<LAB> afl-fuzz -i seeds/ -o findings/ -t 1000 -- ./target @@

<LAB> # 4. Parallel campaign across cores
<LAB> afl-fuzz -i seeds/ -o findings/ -M main -- ./target @@
<LAB> afl-fuzz -i seeds/ -o findings/ -S worker1 -- ./target @@
```

Reading the AFL++ status screen:

| Field | Meaning | Healthy sign |
|-------|---------|--------------|
| `cycles done` | Full passes over the queue | Increasing steadily |
| `corpus count` | Interesting inputs kept | Growing early, then stable |
| `saved crashes` | Unique crashing inputs | 0 is fine; >0 means triage |
| `exec speed` | Executions/sec | Higher is better; a cliff means hangs |
| `coverage` | Edge coverage % | Increases as new paths found |
| `stab. / stability` | Determinism of coverage | High (>90%); low suggests nondeterminism |
| `pend/favored` | Queue reduction progress | Favored inputs drive most mutations |

`afl-fuzz` writes `findings/default/queue/` (interesting inputs), `findings/default/crashes/` (crashes), and `findings/default/hangs/` (timeouts). Reproduce with `<LAB> ./target findings/default/crashes/id:...`.

### 23.13.2 libFuzzer Setup and Command Walkthrough

libFuzzer is an **in-process** fuzzer: it calls the harness function repeatedly in one process, which is extremely fast. Build with Clang:

```bash
<LAB> clang -g -O1 -fsanitize=fuzzer,address -o fuzz_target harness.c
<LAB> mkdir corpus && printf '<LAB>' > corpus/seed
<LAB> ./fuzz_target -max_total_time=120 -artifact_prefix=<LAB>_ corpus/
```

Interpreting output lines:

```
INFO: Seed corpus: files: 1 min:4B max:4B total:4B
#2      INITED cov: 12 ft: 14 corp: 1/1b exec/s: 0 rss: 25Mb
#5000   pulse  cov: 45 ft: 90 corp: 8/2Kb exec/s: 2500 rss: 30Mb
==12345==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x...
artifact_prefix='<LAB>_'; Test unit written to <LAB>_crash-...
```

Interpretation: `INITED` shows initial coverage/corpus; `pulse` lines show periodic stats (`cov` edges, `ft` features, `corp` corpus size, `exec/s` speed). The `ERROR` line is a real finding; libFuzzer writes a minimized reproducer file. Re-run deterministically with `<LAB> ./fuzz_target <LAB>_crash-...`.

Useful flags: `-max_len=N` (cap input size), `-dict=dict.txt` (tokens), `-rss_limit_mb=N` (OOM guard), `-timeout=N`, `-fork=N` (parallelism), `-merge=1` (corpus minimization).

### 23.13.3 honggfuzz and Other Engines

**honggfuzz** is a fast, feedback-driven fuzzer supporting multiple platforms and both source instrumentation and hardware-assisted feedback (Intel PT) for black-box binaries:

```bash
<LAB> hfuzz-clang -g -O1 -fsanitize=address -o target target.c
<LAB> honggfuzz -i seeds/ -o findings/ -n 4 -- ./target ___FILE___
```

`___FILE___` is honggfuzz's input-file placeholder. It reports unique crashes in `findings/` with `CRASH`-prefixed filenames. Other engines worth knowing: **AFL** (original), **libFuzzer** (in-process), **honggfuzz** (multi-platform), **Jazzer** (JVM), **go-fuzz** (Go), **Schemathesis** (APIs), **Peach/WinAFL** (structured/Windows). Mastery is understanding that the *engine* is interchangeable; the *harness* and *strategy* are what determine success.

### 23.13.4 Harness Design Deep Dive

The harness is the bridge between fuzzer bytes and target code. A poor harness wastes the entire campaign.

```c
// <LAB> libFuzzer harness for a packet parser
#include <stdint.h>
#include <stdlib.h>
#include "packet.h"

int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
    // 1. Reset global state so runs are independent
    parser_reset();
    // 2. Enforce invariants the real system guarantees
    if (size < 4 || size > 4096) return 0;
    // 3. Call the target; free any outputs
    Packet *p = parse_packet(data, size);
    if (p) packet_free(p);
    return 0;   // 0 = no crash
}
```

Good-harness checklist:

- **Deterministic**: same input → same behavior; no time/random dependence.
- **Fast**: no disk I/O, no network, no heavy logging in the hot path.
- **State-resetting**: globals reinitialized each call (otherwise false crashes and hidden bugs).
- **Target-focused**: call the parser/API of interest directly, not `main`.
- **Assertive**: add checks for impossible states (`assert(index < len)`) to catch logic bugs early.
- **Memory-clean**: free allocations so ASan/leak detection stays meaningful.
- **Invariant-respecting**: reject inputs the real system could never produce (but do not over-constrain).

Common harness mistakes: calling `main` (slow, I/O-heavy, exits), forgetting to reset globals, over-filtering inputs so interesting paths are unreachable, and leaving randomness that makes crashes unreproducible.

### 23.13.5 Running Campaigns at Scale

Once a single-core campaign works, scale it deliberately rather than launching dozens of fuzzers blindly.

- **Parallelism** — AFL++ uses `-M main` / `-S workerN` to coordinate instances sharing a corpus directory; libFuzzer uses `-fork=N` or `-jobs=N -workers=N`. Each worker explores different mutations while periodically syncing interesting inputs.
- **Dictionaries** — supply format tokens (`-x`/`-dict`) to get past magic-byte gates.
- **Time budgeting** — run short smoke tests (minutes) to validate harness health, then longer campaigns (hours) for depth. Diminishing returns show up as a flat coverage curve; when coverage stops growing for an extended period, add seeds/grammar or switch strategy instead of burning CPU.
- **Resource hygiene** — monitor RSS and exec speed; a dropping exec/s often means the target is leaking memory or hanging. Set `-rss_limit_mb` and `-timeout` to bound runs.
- **Crash deduplication** — store artifacts with a hash of the sanitizer stack trace so identical root causes are grouped; triage one representative per group.
- **Distributed fuzzing** — for large projects, tools like AFL++ in combination with a shared corpus store or OSS-Fuzz's cluster infrastructure run many instances across machines. The principles are identical: shared corpus, unique seeds per worker, centralized triage.

Interpretation of scale: more cores multiply *throughput*, not insight. A focused, well-instrumented campaign on one core often outperforms a sprawling one with a poor harness. Scale after the loop is proven, not before.

## 23.14 Mastery Deep Dive: Sanitizers, Triage, and Advanced Strategies

### 23.14.1 Sanitizers in Depth with Example Findings

Sanitizers instrument the program to detect bug classes that would otherwise be silent.

| Sanitizer | Detects | Typical report |
|-----------|---------|----------------|
| ASan | OOB read/write, UAF, double free | `heap-buffer-overflow`, `use-after-free` |
| UBSan | Integer overflow, misaligned access, invalid shifts | `signed integer overflow` |
| MSan | Use of uninitialized values | `use-of-uninitialized-value` |
| TSan | Data races | `WARNING: ThreadSanitizer: data race` |
| LSan | Leaks | `detected memory leaks` |

Annotated ASan report:

```
==LAB==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x602000000014
READ of size 1 at 0x602000000014 thread T0
    #0 0x401234 in parse <LAB>/parser.c:37
    #1 0x401400 in LLVMFuzzerTestOneInput <LAB>/harness.c:12
0x602000000014 is located 0 bytes to the right of 20-byte region
allocated by thread T0 here:
    #0 0x4a1234 in malloc
    #1 0x401180 in parse <LAB>/parser.c:20
```

Interpretation: class (`heap-buffer-overflow`), access (`READ of size 1`), exact source line (`parser.c:37`), and the allocation site (`parser.c:20`). "0 bytes to the right of a 20-byte region" means an off-by-one read just past a 20-byte buffer — root cause visible immediately. Build with `-fsanitize=address,undefined` and `-g` for symbolized, instructive reports. Note: ASan and MSan cannot be combined; TSan is separate.

### 23.14.2 Crash Triage, Minimization, and Root Cause

A repeatable triage protocol:

1. **Reproduce** — run the exact artifact; confirm it crashes consistently.
2. **Minimize** — shrink while preserving the crash:
   ```bash
   <LAB> ./fuzz_target -minimize_crash=1 -exact_artifact_path=min.bin crash.bin
   <LAB> afl-tmin -i crash.bin -o min.bin -- ./target @@
   ```
3. **Classify** — read the sanitizer report or GDB backtrace; assign a CWE.
4. **Root-cause** — identify the faulty line and the flawed assumption (e.g., "trusted a length field without validating it against the buffer size").
5. **Assess** — is it a security bug, a mere DoS, or a harness artifact? (A crash caused by your harness misuse is not a target bug.)
6. **Report/dedupe** — many fuzzer "crashes" are the same root cause; group them.

Interpretation of minimization: a 4 KB input shrinking to 9 bytes usually reveals a specific field (e.g., a length byte set to `0xFF`) as the trigger, making the root cause obvious. Honest assessment matters — a null deref in a rarely used path is low severity; an OOB write reachable from untrusted input is high.

### 23.14.3 Differential Fuzzing

Differential fuzzing searches for *logic* bugs, not crashes: feed the same input to two implementations (or two versions) and flag divergent outputs.

```python
# <LAB> - conceptual differential harness
def differential(data):
    out_a = impl_a(data)     # e.g., two JSON parsers
    out_b = impl_b(data)
    if normalize(out_a) != normalize(out_b):
        save(data, out_a, out_b)   # investigate divergence
```

Applications: comparing two parsers for spec conformance, testing a new implementation against a reference, finding compiler miscompilations, or checking that a patched version behaves identically on valid inputs. The challenge is *normalization* (equivalent outputs may differ in formatting) and deciding which implementation is correct. Differential fuzzing excels where memory-safety fuzzing is blind: a parser that accepts invalid input silently is a logic bug no sanitizer will flag.

### 23.14.4 Grammar and Structure-Aware Fuzzing

When inputs must satisfy a grammar (e.g., a protocol with magic bytes, length fields, and checksums), blind mutation rarely passes the first gate. Two solutions:

1. **Dictionaries** — give the fuzzer tokens. In libFuzzer, `-dict=tokens.dict` where the file contains `"magic"`, `"\x01\x02"`, etc.; AFL++ uses `-x dict.txt`. This helps the fuzzer discover magic-byte checks.
2. **Generators/grammars** — produce syntactically valid inputs directly. Tools: **Grammarinator** (ANTLR grammars → generators), **protobuf-based** structured mutation (`libprotobuf-mutator`), **AFL++ custom mutators**.

```text
# <LAB> tokens.dict for a toy format
"GET "
"HTTP/1.1"
"Content-Length: "
"\x00\x01\x02\x03"
```

Structure-aware fuzzing lets the fuzzer spend its budget exploring *semantic* edge cases (huge length values, nested structures, negative indices) instead of guessing magic bytes. For APIs, **Schemathesis** generates requests from an OpenAPI/GraphQL schema and checks for server errors (5xx) and contract violations — fuzzing at the API layer rather than the byte layer.

### 23.14.5 API and Protocol Fuzzing

Network protocol and API fuzzing require special care because they involve state and side effects.

- **Stateless bytes** (file parsers) are the easiest: each input is independent.
- **Stateful protocols** need sequences: a login, then a sequence of operations. Model the state machine, or use a tool that learns it.
- **APIs**: generate valid requests from a schema, vary parameters, and check response contracts. Distinguish **client faults** (4xx) from **server faults** (5xx, hangs, crashes) — only the latter are findings.

```bash
<LAB> schemathesis run --hypothesis-profile=ci \
        -b <LAB_BASE_URL> <LAB_OPENAPI_SPEC> --checks all
```

Interpretation: Schemathesis reports endpoints where a generated input caused a 5xx or violated the schema; triage each to see whether it is a real server bug or an over-permissive schema. Confine API/protocol fuzzing to lab deployments or explicitly authorized programs — fuzzing a production service is effectively a DoS.

### 23.14.6 Troubleshooting a Stalled Campaign

A campaign that finds nothing is often a configuration problem, not a secure target. Work through this diagnostic checklist:

1. **Is the harness healthy?** Run it once with a valid seed and confirm it reaches the intended function. Add a temporary `abort()` at a known-deep line and verify the fuzzer reaches it — if it does not, your harness or seeds are the problem.
2. **Is coverage growing?** If `cov` is flat after thousands of executions, the target is gated (magic bytes, checksums, size checks). Add a dictionary or grammar.
3. **Is exec speed reasonable?** Very low exec/s suggests heavy I/O, logging, or a slow target; remove I/O from the hot path and simplify the harness.
4. **Is there nondeterminism?** Low "stability" (AFL++) or crashes that vanish on replay indicate global state, randomness, or concurrency. Reset state and remove randomness (seed RNG deterministically).
5. **Are sanitizers active?** Confirm the binary is actually instrumented (`nm ./fuzz_target | grep asan`, or an ASan startup banner). A target built without sanitizers hides subtle bugs.
6. **Are inputs too constrained?** Over-aggressive early `if (size < N) return` checks can make every mutation invalid. Relax to the minimum the target truly requires.
7. **Is the bug class reachable at all?** Some code paths need configuration or environment the harness never sets; extend the harness to cover them.

Mastery is the ability to move from "the fuzzer found nothing" to a specific, testable hypothesis about why, and to fix the harness or strategy accordingly — rather than concluding the target is secure.

## 23.15 Mastery Deep Dive: Lab, Measurement, and Practice

### 23.15.1 Building a Fuzzing Lab and Measuring Coverage

A productive fuzzing lab includes:

- **Isolated VM/container** with compiler toolchain (Clang, AFL++), sanitizer runtimes, and debuggers.
- **CPU and RAM headroom** — fuzzing is resource-intensive; dedicate cores, monitor RSS.
- **Version control** for harnesses, seeds, dictionaries, and findings.
- **Coverage reporting** — for libFuzzer, `-dump_coverage=1` plus `llvm-profdata`/`llvm-cov` produces a line/branch coverage HTML report showing which code paths were never reached. That "uncovered" list tells you where to add seeds or improve the harness.
- **Crash storage** with deduplication and metadata (fuzzer, seed, timestamp, sanitizer class).

```bash
<LAB> ./fuzz_target -runs=0 -dump_coverage=1 corpus/          # emit .profraw
<LAB> llvm-profdata merge -sparse default.profraw -o cov.profdata
<LAB> llvm-cov show ./fuzz_target -instr-profile=cov.profdata > coverage.txt
```

Interpretation: functions with 0% coverage are unexplored — either unreachable through your harness or gated by a condition your seeds never satisfy. This turns coverage from a vanity metric into a roadmap.

### 23.15.2 Detection and Defense Checklists

Defensive side (reducing the bugs fuzzing finds in your own software):

- [ ] Continuous fuzzing in CI (OSS-Fuzz or internal); regression-test every found crash
- [ ] Sanitizer builds in CI (ASan/UBSan) alongside fuzzing
- [ ] Bounds/overflow checks on all length and size arithmetic
- [ ] Fuzz targets for every parser and untrusted-input entry point
- [ ] Triage SLAs: reproduce, minimize, fix, add regression seed

Operational detection (while fuzzing):

- [ ] Monitor exec speed and RSS to catch hangs/OOMs early
- [ ] Deduplicate crashes by root cause to avoid wasted triage
- [ ] Watch for "stability" warnings indicating nondeterminism in the target
- [ ] Rate-limit and scope any network fuzzing; never fuzz production

### 23.15.3 Common Mistakes

1. **Fuzzing `main`** instead of a focused harness — slow and exits on first input.
2. **No state reset** — globals carry over, producing false crashes and masking real ones.
3. **Poor seeds** — a single tiny seed against a complex format means the fuzzer spends hours rediscovering structure.
4. **Ignoring sanitizer build flags** — without `-g`/`-fsanitize`, crashes are hard to interpret.
5. **Treating every crash as a security bug** — many are harness artifacts, OOMs, or asserts; dedupe and assess.
6. **Fuzzing too broadly at once** — start with one parser and one strategy; expand after you have a working loop.
7. **Forgetting authorization** — fuzzing a third-party production service is disruptive and likely unlawful; keep it in the lab or in-scope.

### 23.15.4 Verify in Your Lab

1. Write `<LAB>` a small C parser with a deliberate off-by-one (e.g., loop `<= len`).
2. Build it with AFL++ instrumentation; seed with 2–3 valid inputs; run for 2 minutes.
3. Build the same target with `-fsanitize=fuzzer,address`; run libFuzzer and read the ASan report.
4. Minimize one crash to its smallest reproducer and identify the faulty line.
5. Add a dictionary for the format; observe whether coverage increases.
6. Use `afl-cmin`/`-merge=1` to shrink the corpus while preserving coverage.
7. Run a differential test between two implementations of the same function and investigate any divergence.

### 23.15.5 What Mastery Looks Like

You have mastered this material when you can:

- Choose a strategy based on the target and diagnose why a campaign stalled.
- Build fast, deterministic, state-resetting harnesses with sanitizers.
- Run AFL++, libFuzzer, and a structured/API fuzzer, and interpret each tool's feedback.
- Triage crashes to root cause with minimization, sanitizers, and a debugger — and honestly assess severity.
- Measure coverage, identify unreached code, and improve the corpus or grammar accordingly.
- Integrate fuzzing into a repeatable, authorized research workflow with deduplication and regression tests.

### 23.15.6 Knowledge Check (Answers Included)

**Q1.** Coverage has plateaued on a parser that requires an 8-byte magic header. What is the fastest fix?
**A1.** Add the magic bytes to a fuzzer dictionary (`-dict`/`-x`) or use a structure-aware generator so the fuzzer can get past the magic gate.

**Q2.** Why must a libFuzzer harness reset global state between calls?
**A2.** libFuzzer calls the harness in one process; without a reset, state leaks across inputs, causing false/non-reproducible crashes and hiding real bugs.

**Q3.** An ASan report says "0 bytes to the right of a 20-byte region." What is the likely bug?
**A3.** An off-by-one access just past a 20-byte allocation — check the loop bound (`<=` vs `<`) at the reported line.

**Q4.** When would you choose differential fuzzing over coverage-guided memory fuzzing?
**A4.** When hunting logic/conformance bugs (e.g., two parsers that should agree) rather than memory corruption; a wrong-but-non-crashing result is invisible to sanitizers.

**Q5.** Why is fuzzing a production API dangerous even without malicious intent?
**A5.** High-volume generated requests can exhaust resources (effectively a DoS) and touch real user data; keep fuzzing in lab or explicitly in-scope environments.

## 23.10 Key Takeaways

- Fuzzing explores input spaces far beyond manual testing, especially with coverage feedback.
- Strategy choice depends on the target: raw bytes, grammar, API sequences, or differential behavior.
- Sanitizers, minimization, and reproducibility turn crashes into actionable findings.
- Fuzz within authorized boundaries; a production fuzzing run can be disruptive.
