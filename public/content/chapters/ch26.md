# Chapter 26: Building a Professional Bug Bounty Workflow

> **Learning objectives.** Run a repeatable ten-phase workflow; use checklists, templates, and research logs; and turn ad-hoc testing into a disciplined practice.

## 26.1 The Ten Phases

### Phase 1: Program Selection

- Choose programs whose scope matches your skills.
- Prefer clear policies and safe-harbor language.
- Read recent public disclosures to gauge triage quality (where allowed).
- Confirm current scope and rules before each session.

### Phase 2: Scope Analysis

- List in-scope assets and exclusions.
- Resolve wildcard ambiguity by asking if needed.
- Note restrictions (automation, DoS, accounts, data).
- Record the policy version and date in your journal.

### Phase 3: Asset Inventory

- Perform passive recon first (Chapter 14).
- Build a CSV inventory: asset, source, in-scope?, technology, notes.
- Probe live hosts within rate limits.

### Phase 4: Application Mapping

- Create accounts and map roles.
- Capture all workflows in a proxy.
- Build endpoint and parameter lists; note auth requirements.

### Phase 5: Manual Testing

- Work through the authorization matrix and test hypotheses.
- Prioritize high-value areas (Chapter 15).
- Record every test, even negative results.

### Phase 6: Vulnerability Validation

- Confirm with minimal, safe PoC using your own accounts.
- Check for false positives.
- Establish reproducibility (multiple runs).

### Phase 7: Impact Assessment

- Determine realistic worst case.
- Map CWE and suggest severity/CVSS.
- Note prerequisites honestly.

### Phase 8: Evidence Collection

- Save exact requests/responses, timestamps, and test-account IDs.
- Redact any sensitive data (there should be none from real users).
- Keep PoCs minimal and repeatable.

### Phase 9: Report Writing

- Use the Chapter 25 structure.
- Review against the program's submission requirements.
- Submit one issue per report unless a chain is inseparable.

### Phase 10: Submission and Triage

- Track status in your journal.
- Respond promptly and professionally to requests.
- After resolution, request permission before any public disclosure.

```
[ ] Unauthenticated access
[ ] Low-privilege vs. high-privilege
[ ] Object ID swapped with own second account
[ ] Method variations (GET/POST/PUT/DELETE/PATCH)

```

## 26.8 Mastery Deep Dive: Engagement Management End to End

> **Authorized testing only.** Everything below assumes an explicit scope, program rules, and lab/test accounts. When in doubt, stop and ask the program before acting.

A workflow is not a checklist you memorize — it is a state machine you can run under pressure. This deep dive turns the ten phases into an operable engagement: how to set up, select targets, timebox, track state, and finish cleanly.

### 26.8.1 Pre-Engagement Setup and Scope Lock

Before the first request, capture a "scope lock" document: program name, policy URL, exact in-scope assets, exclusions, wildcard interpretation, allowed techniques, prohibited techniques, account policy, disclosure terms, safe-harbor statement, and the UTC timestamp you read it. Email or platform-message any ambiguity and save the reply. Re-read the policy at every session — policies change. Define the engagement goal in one sentence ("find broken object-level authorization on the v2 API") so you can say no to tangents.

### 26.8.2 Timeboxing and Target Selection

Split available time into fixed blocks: 45–60 minutes of focused testing, 10 minutes of notes, 5 minutes of triage of your own findings. Score candidate targets on a simple matrix: in-scope certainty, likely impact, your prior familiarity, and signal density (new/changed code). Pick the highest-score target for the block. Timeboxing prevents endless recon and guarantees evidence capture. A targets CSV:

| Asset | In scope | Impact guess | Familiarity | Signal | Score |
|-------|----------|--------------|-------------|--------|-------|
| api.lab.test/v2 | yes | High | medium | new endpoint | 8 |
| cdn.lab.test | yes | Medium | low | static | 4 |

### 26.8.3 The Ten Phases as a State Machine

Think of phases as states with entry and exit criteria, not a linear script. You can loop from Phase 5 (manual testing) back to Phase 4 (mapping) when you discover a new parameter, or from Phase 7 (impact) back to Phase 6 (validation) when evidence is weak. The rule: never skip Phase 6 validation or Phase 8 evidence — those are the gates that protect your reputation. Track the current phase per target in your journal.

### 26.8.4 Definition of Done for Each Phase

| Phase | Done when |
|-------|-----------|
| Selection | Scope lock written, goal sentence recorded |
| Scope analysis | Ambiguities resolved or asked about |
| Inventory | CSV complete, live hosts probed within limits |
| Mapping | All roles and workflows captured in proxy |
| Manual testing | Every hypothesis tested, negatives logged |
| Validation | PoC reproduced 3× in lab, false positives checked |
| Impact | CWE assigned, severity reasoned, prerequisites honest |
| Evidence | Requests/responses, timestamps, redacted artifacts saved |
| Reporting | Template complete, peer-reviewed |
| Submission | Status tracked, replies logged, disclosure request filed |

## 26.9 Mastery Deep Dive: Lab and Tooling Setup

### 26.9.1 Browser Profiles and Isolation

Use separate browser profiles per role and per target: one for attacker/test account A, one for victim/test account B, one for unauthenticated browsing. Install only testing extensions (proxy switcher, decoder, header editor) in the test profile. Clear state between sessions or use container tabs. Label profiles visibly so you never submit a request with the wrong identity — a common cause of broken reproducibility.

### 26.9.2 Proxy Configuration (Burp/ZAP)

Set the test browser's proxy to your local listener, enable intercept off by default, and confirm traffic reaches the proxy before testing. Organize a project per engagement with scoped target definitions so out-of-scope hosts are excluded from passive crawling. Keep a dedicated scope rule set and verify it before each session. Save the proxy project encrypted; it contains tokens and request histories.

```text
Browser -> 127.0.0.1:8080 (proxy) -> lab target
Scope include: *.lab-*.test
Scope exclude: *.vendor.com, *.cdn-thirdparty.test
```

### 26.9.3 VMs, Containers, and Network Isolation

Run a dedicated VM or container for lab work: separate network namespace, no personal logins, minimal installed software. Keep a hosts-file alias between the real hostname and a local label so logs stay readable. Snapshot the VM before destructive tests and restore afterward. Never route personal or production traffic through the lab proxy.

### 26.9.4 Notes and Knowledge Base Systems

Use one note system with a consistent schema: date, target, phase, hypothesis, request, response, result, next action. Tag by vulnerability class, asset, and outcome. Keep a separate "class notes" page per CWE with what worked, what failed, and canonical payloads. Link each finding note to its evidence files. The goal: six months later you can find the exact test that worked without re-deriving it.

## 26.10 Mastery Deep Dive: Automation Without Losing Understanding

### 26.10.1 What to Automate and What to Keep Manual

Automate the boring, repeatable, high-volume work: asset discovery, endpoint enumeration, header checks, baseline diffs. Keep manual the judgment-heavy work: authorization matrices, business logic, chained impact, and report writing. Rule of thumb: if you cannot explain what the tool does in one sentence, do not run it — you cannot interpret its output. Every automated hit must be manually validated.

### 26.10.2 Building a Recon Pipeline

A minimal, understandable pipeline: passive sources → DNS resolution → live host check → port/service tags → screenshot → diff against last week. Store each stage's output as a file, not only in memory, so you can inspect intermediate results.

```bash
# Illustrative lab-only pipeline; replace with authorized targets
cat in_scope.txt | resolve_hosts > resolved.txt
cat resolved.txt | probe_live > live.txt
cat live.txt | tag_services > inventory.csv
```

### 26.10.3 Rate Limiting and Safe Automation

Throttle requests to a rate the program permits; default to conservative values and back off on 429/503 responses. Never run denial-of-service, fuzzing that writes data, or credential stuffing unless explicitly authorized. Cap concurrent threads. Log every automated run with timestamps and target lists so you can prove what you touched.

### 26.10.4 Validating Tool Output

Tools produce false positives; your value is filtering them. For each hit, reproduce manually, check preconditions, check whether the behavior is intended, and confirm the asset is in scope. Record the validation decision. A finding that fails validation still teaches something — log why, so the tool can be tuned.

## 26.11 Mastery Deep Dive: Tracking Findings and Personal Knowledge Base

### 26.11.1 Finding Lifecycle States

Track each finding through explicit states: `Hypothesis → Testing → Confirmed-lab → Report-drafted → Submitted → Triaging → Accepted/Info/Duplicate → Fixed → Disclosed/Closed`. Each transition needs a trigger (e.g., "third successful reproduction" for Confirmed-lab). A board or spreadsheet with columns for state, asset, CWE, severity, and last action prevents findings from rotting.

### 26.11.2 The Hypothesis Journal

Write hypotheses before testing, not after. Format: "If the server trusts `X`, then changing `X` to `Y` should produce `Z`; if I observe `Z`, the boundary is broken." This forces falsifiability. Log negative results with the same rigor as positives — they map the system and prevent re-testing dead ends.

### 26.11.3 Structuring a Searchable Knowledge Base

Organize by vulnerability class with four fields per entry: trigger pattern, safe test payload, false-positive traps, and a worked lab example. Add an "environment" page per technology (GraphQL, JWT, cloud metadata) with version quirks. Use consistent tags so a query like "SSRF + cloud" retrieves everything relevant. Review and prune quarterly.

### 26.11.4 Metrics That Matter (and Vanity Metrics)

| Useful metric | Why | Vanity metric | Why not |
|---------------|-----|---------------|---------|
| Accepted findings / submissions | Quality | Total bug count | Rewards noise |
| Time to reproduce in triage | Report clarity | Hours online | Presence ≠ output |
| New techniques learned per week | Growth | Tools installed | Collection ≠ skill |
| Negative hypotheses documented | Rigor | Bounties earned | Lagging, noisy signal |

Track a weekly dashboard of the left column and ignore the right.

## 26.12 Mastery Deep Dive: Collaboration, Handoffs, and Communication

### 26.12.1 Working With Other Researchers

Share techniques, not live targets' private data. In team engagements, divide by asset or vulnerability class and keep a shared log of who tested what to avoid duplicate effort. Establish a rule for overlapping findings: first reporter owns the write-up; others add evidence with permission. Credit collaborators explicitly.

### 26.12.2 Handoff Templates

When passing a target or finding, use a structured handoff:

```text
Target / asset:
Scope confirmed (policy + date):
What I tested:
What I ruled out:
Open hypotheses:
Evidence location:
Next suggested action:
Safety notes (rate limits, accounts, destructive tests to avoid):
```

### 26.12.3 Communicating With Program Owners

Ask scope questions early and in writing; keep them short and specific. For status requests: "Checking on `#ID` submitted `date` — any evidence you need from me?" For scope clarification: "Does `*.lab.test` include `staging.lab.test` under the current policy?" Professional brevity gets faster answers than long explanations.

### 26.12.4 Avoiding Burnout and Maintaining Momentum

Bounty work is variable and rejection-heavy. Protect against burnout with fixed session lengths, a mandatory weekly day off, and a "win log" of accepted findings and learned techniques. Separate self-worth from queue outcomes. When motivation drops, switch to skill-building (lab, write-up, tool) rather than grinding the same target. Seek feedback from peers when stuck for more than two sessions.

## 26.13 Mastery Deep Dive: Continuous Improvement and Operating Rhythm

### 26.13.1 The Weekly Operating Rhythm

| Day | Focus |
|-----|-------|
| Monday | Review scope changes, pick target, write hypotheses |
| Tue–Thu | Focused testing blocks + same-day evidence capture |
| Friday | Report writing, submissions, KB updates |
| Saturday | Skill building: lab, reading, tool improvement |
| Sunday | Rest; optional light review |

### 26.13.2 The Retrospective Loop

At week's end ask: what worked, what failed, what will I change next week? Convert each answer into one concrete action (update a checklist, tune a tool, read a chapter). Review the previous week's actions before setting new ones — closure matters more than volume.

### 26.13.3 Checklists

**Daily:** scope re-check; profile/identity verified; proxy scoping verified; hypotheses written; negative results logged; evidence saved.
**Weekly:** reports peer-reviewed; KB updated; metrics dashboard filled; pending triage replies answered; targets rescored.
**Monthly:** policy re-read for all active programs; toolchain updated; one deep technique studied; disclosure permissions confirmed.

### 26.13.4 What Mastery Looks Like and Knowledge Checks

> **Mastery looks like:** you can run an engagement from scope lock to coordinated disclosure without skipping a gate; your notes let a stranger reproduce your work; and you stop, rather than guess, when the rules are unclear.

1. **Q:** Why write hypotheses before testing? **A:** It forces falsifiable expectations and documents intent.
2. **Q:** Which phase gates must never be skipped? **A:** Validation (6) and evidence (8).
3. **Q:** Why separate browser profiles? **A:** To avoid identity mix-ups that break reproducibility and cause out-of-scope requests.
4. **Q:** Name two vanity metrics. **A:** Total bug count, hours online.
5. **Q:** What belongs in a handoff template? **A:** Scope confirmation, what was tested/ruled out, open hypotheses, evidence location, safety notes.
6. **Q:** How often should you re-read program policies? **A:** Every session, plus a monthly full review.

## 26.14 Mastery Deep Dive: Recon and Mapping Depth

The ten phases compress reconnaissance into two lines, but the quality of your hypotheses is bounded by the quality of your map. This section goes deeper on building that map without losing scope discipline.

### 26.14.1 Passive Recon Sources and Their Limits

Start with sources that require no direct contact: certificate transparency logs, DNS history, archived pages, public code repositories, and the program's own documentation. Each has limits — CT logs include expired domains, DNS history includes stale records, and public repos may contain dead endpoints. Record the source and collection date for every asset so you can distinguish current from historical. Never treat a passive hit as in-scope until you verify it against the current policy. Passive work is also where you learn naming conventions (`api-v2`, `admin`, `internal`) that generate hypotheses later.

### 26.14.2 Building an Authorization Matrix

Create a grid with roles as rows and endpoint groups as columns. Populate each cell with `allow`, `deny`, or `unknown` by testing with a distinct account for each role. This single artifact finds more authorization bugs than any scanner.

| Role | /users | /admin | /invoices/{id} | /export |
|------|--------|--------|----------------|---------|
| Anonymous | deny | deny | deny | deny |
| Low-priv | allow | unknown | own only | own only |
| High-priv | allow | allow | all | all |

Every `unknown` is a test task. Every cell where a low-priv role gets `allow` on an admin function is a finding candidate. Rebuild the matrix after each major product change.

### 26.14.3 Technology Fingerprinting and Hypothesis Generation

Identify framework, language, server, and WAF from headers, cookies, error shapes, and static assets. Then map technology to likely weaknesses: a JSON-heavy SPA suggests IDOR/BOLA and mass assignment; XML endpoints suggest XXE; a `JWT` cookie suggests algorithm confusion; cloud-hosted storage suggests SSRF/metadata exposure. Fingerprinting is not an end — it is a way to choose the next hypothesis. Keep a per-technology note page that lists "classes to test here" and "false positives I have seen."

### 26.14.4 Attack-Surface Diffing and Change Detection

Re-crawl in-scope assets weekly and diff against the previous inventory: new endpoints, changed parameters, new subdomains, changed headers. Change is where bugs live. Store diffs as unified text so you can see exactly what moved. Prioritize diffs that touch authentication, authorization, or file handling. A quiet program may still yield findings when a deploy introduces one new parameter.

## 26.15 Mastery Deep Dive: Evidence, Reporting, and Closure

### 26.15.1 Evidence Package Structure

Bundle evidence in a predictable folder layout so any reviewer can navigate it:

```text
finding-ID/
  00-summary.txt
  01-requests/        raw request/response pairs
  02-screenshots/     redacted PNGs with captions
  03-video/           30-90s narrated clip
  04-timestamps.txt   UTC log with test-account aliases
  05-cleanup.txt      what you reverted
```

Name files with the finding ID and date. Include a `README` mapping each artifact to a report step. This structure lets you reconstruct a finding months later during triage questions.

### 26.15.2 Peer Review of Your Own Reports

Swap drafts with a peer and ask three questions only: can you reproduce from the steps alone? Is any real data present? Does the impact claim match the evidence? Reviewers should not rewrite your prose — they should try to break your chain. Record their questions and answer them in the report before resubmitting. A report that survives a skeptical peer usually survives triage.

### 26.15.3 Handling Triage Threads at Scale

Treat each thread as a small project: acknowledge within a day, answer only what was asked, attach the specific artifact requested, and close with a short summary. Maintain a triage inbox table with columns: finding ID, last message from program, your next action, due date, status. Never let a thread sit unanswered for a week. If a program is slow, one polite check-in every 10–14 days is acceptable.

### 26.15.4 Engagement Closure and Cleanup

Closure is a phase, not an afterthought. Delete test accounts you created, remove seeded data, revoke tokens, restore VM snapshots, and confirm no automation is still running. Mark each finding's final state. Note lessons in your knowledge base: which hypothesis worked, which false positive cost time, which tool needs tuning. Request disclosure permission in writing and file it with the evidence package. A clean closure makes the next engagement faster and keeps you in the program's good graces.

## 26.16 Mastery Deep Dive: Judgment Under Uncertainty

Process handles routine work; judgment handles the moments when the rules do not answer cleanly. These are the decisions that separate a safe professional from a reckless one.

### 26.16.1 Decision Checklist Under Uncertainty

When you are unsure whether an action is allowed, run this sequence: (1) quote the exact policy line; (2) identify the asset in question; (3) ask whether the action changes data, affects another party, or exceeds published rates; (4) if any answer is uncertain, stop and ask the program in writing; (5) record the answer and the timestamp. Never resolve ambiguity in the direction of "probably fine." A five-minute question protects a career.

### 26.16.2 Knowing When to Stop Testing a Target

Set stop conditions before a session: a hard time cap, a request-count cap, and a scope boundary. Stop when the cap is reached, when you have three confirmed findings queued for reporting (write them before hunting more), or when a target becomes unstable. Continuing past a stop condition turns disciplined research into noise and risk. Write the stop reason in your journal so the next session starts fresh.

### 26.16.3 Handling Sensitive Discoveries

If you stumble on real user data, credentials, or an active compromise, do not explore further. Do not copy, screenshot, or exfiltrate the material. Notify the program immediately with the minimum detail needed to act, and let them direct next steps. Keep the discovery confidential. Your value is the alert, not the data. The same discipline applies to out-of-scope assets: stop, report, do not probe.

### 26.16.4 Knowledge Checks III

1. **Q:** What is the first step when unsure if an action is allowed? **A:** Quote the exact policy line and identify the asset.
2. **Q:** How should ambiguity be resolved? **A:** Stop and ask in writing; never assume "probably fine."
3. **Q:** Name three stop conditions. **A:** Time cap, request cap, scope boundary (or three queued findings).
4. **Q:** What do you do with accidentally exposed real data? **A:** Stop, do not copy it, notify the program with minimal detail.

### 26.16.5 Common Workflow Mistakes

| Mistake | Symptom | Correction |
|---------|---------|------------|
| Testing before the scope lock | Wasted work on out-of-scope hosts | Write the lock first, every session |
| Recon without a hypothesis | Large inventory, no findings | Convert each asset into a testable "if/then" |
| Notes written at end of day | Lost detail, weak evidence | Log each request as you make it |
| Automating before understanding | Uninterpretable hits | Explain the tool in one sentence first |
| Chasing a target past its stop cap | Fatigue, sloppy evidence | Honor time and request caps |
| Reporting before peer review | "Cannot reproduce" replies | Run the three-question review |
| No cleanup | Lingering accounts and data | Close with the cleanup checklist |

Each mistake has a checkpoint earlier in this chapter: the scope lock (26.8.1), hypothesis journal (26.11.2), tool-validation rule (26.10.1), stop conditions (26.16.2), peer review (26.15.2), and closure (26.15.4). The workflow is only as strong as its least-kept step — review this table when a session feels unproductive; the cause is usually a skipped checkpoint, not bad luck.

## 26.6 Key Takeaways

- A documented workflow turns luck into repeatable results.
- Scope, safety, and logging are part of the workflow, not overhead.
- Review weekly and refine your process.
