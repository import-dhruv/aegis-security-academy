# Chapter 22: Reverse Engineering

> **Learning objectives.** Distinguish static and dynamic analysis; explain disassembly and decompilation; recognize ELF, PE, and Mach-O formats; identify functions and behavior; and analyze safe sample binaries.

## 22.1 What Reverse Engineering Is

Reverse engineering is the process of understanding a binary's structure and behavior without source. It is used for malware analysis, vulnerability research, interoperability, and understanding legacy systems. This chapter uses only safe sample binaries you create or intentionally vulnerable lab programs.

## 22.2 Static vs. Dynamic Analysis

- **Static analysis:** examining the binary without running it — disassembly, decompilation, strings, imports, symbols, resources.
- **Dynamic analysis:** running the binary in a controlled environment and observing behavior — API calls, file/network activity, memory, debugger state.

Use both: static gives structure, dynamic confirms behavior.

## 22.3 Binary Formats

- **ELF (Linux):** headers, program headers (segments), section headers, symbol tables, relocations. Tools: `readelf`, `objdump`, `file`.
- **PE (Windows):** DOS header, PE header, sections (.text, .data), import/export tables. Tools: PE Explorer, `dumpbin`.
- **Mach-O (macOS/iOS):** load commands, segments, sections, symbol tables. Tools: `otool`, `class-dump`.

Understanding sections helps locate code (`.text`), initialized data (`.data`), uninitialized data (`.bss`), and imported functions (which hint at behavior).

## 22.4 Disassembly and Decompilation

- **Disassembly:** machine code → assembly mnemonics (Ghidra, IDA, radare2, objdump).
- **Decompilation:** assembly → higher-level C-like pseudocode (Ghidra, Hex-Rays, JADX for Java).

Decompiler output is *approximate*: compiler optimizations, stripped symbols, and obfuscation degrade it. Always cross-check with disassembly.

Common patterns to recognize:

- Function prologue: `push rbp; mov rbp, rsp` (or just `endbr64` on modern compilers).
- Calls to `strcmp`, `strlen`, `malloc`, `free`, `system`.
- String references to URLs, file paths, keys.
- Branches around validation checks (a `cmp` followed by `jne` may be an authorization or license check).

## 22.5 Function Identification

- Entry point (`_start`, `main`) found from the ELF header or symbols.
- Names from symbol tables (if not stripped).
- Cross-references (xrefs) to strings and imports reveal relevant functions.
- Calling conventions determine argument passing (Chapter 2).

## 22.6 Malware Analysis Fundamentals (Safe Context)

In an isolated lab (never on your main machine):

1. **Static triage:** `file`, hashes, strings, imports/sections, packer detection.
2. **Dynamic observation:** run in a sandboxed VM with network isolation; observe processes, files, registry, and network.
3. **Behavioral classification:** what does it do (keylogging, encryption, C2 communication)?
4. **Indicators of compromise (IoCs):** hashes, IPs, domains, file paths.

Do not build or deploy malware. Analysis is defensive and educational. Use dedicated lab VMs with snapshots.

## 22.7 Software Behavior Analysis

For a legitimate binary you own:

- Trace configuration file reads/writes.
- Identify network endpoints and protocols.
- Understand cryptographic operations (look for known constants).
- Map error paths and validation logic.

## 22.8 Protocol Reverse Engineering

When a protocol is undocumented, observe messages between client and server (Wireshark), identify structure (length fields, delimiters, opcodes), and infer state machines. Fuzzing the parsed fields can reveal bugs. This is used in IoT and proprietary client analysis — only in authorized contexts.

## 22.9 Tools

- **Ghidra:** free, powerful decompiler; headless mode for automation.
- **IDA Free / IDA Pro:** industry-standard disassembler.
- **radare2/rizin:** scriptable CLI framework.
- **GDB / lldb:** debuggers.
- **objdump, readelf, nm, strings, file:** binutils essentials.

## 22.10 Exercises

1. Compile a small C program with symbols; open it in Ghidra and identify `main`, `printf`, and local variables.
2. Strip the binary (`strip`) and repeat; note what information is lost.
3. Use `strings` to find embedded literals and trace one back to its code reference.
4. Use `objdump -d` and manually decode a short function.
5. Run the binary under GDB, break at a function, and inspect arguments.

## 22.11 Key Takeaways

- Reverse engineering combines static structure with dynamic behavior.
- Binary formats (ELF/PE/Mach-O) organize code and data; tools expose their structure.
- Decompilation is approximate; verify against disassembly and runtime observation.
- Analyze only safe samples and binaries you own or are authorized to examine.
