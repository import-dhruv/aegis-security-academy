# Chapter 22: Reverse Engineering

> **Learning objectives.** Distinguish static and dynamic analysis; explain disassembly and decompilation; recognize ELF, PE, and Mach-O formats; identify functions and behavior; and analyze safe sample binaries.

## 22.1 What Reverse Engineering Is

Reverse engineering is the process of understanding a binary's structure and behavior without source. It is used for malware analysis, vulnerability research, interoperability, and understanding legacy systems. This chapter uses only safe sample binaries you create or intentionally vulnerable lab programs.

## 22.2 Static vs. Dynamic Analysis

- **Static analysis:** examining the binary without running it — disassembly, decompilation, strings, imports, symbols, resources.
- **Dynamic analysis:** running the binary in a controlled environment and observing behavior — API calls, file/network activity, memory, debugger state.

Use both: static gives structure, dynamic confirms behavior.

## 22.3 Binary Formats

- **ELF (Linux):** headers, program headers (segments), section headers, symbol tables, relocations. Tools: `readelf`, `objdump`, `file`.
- **PE (Windows):** DOS header, PE header, sections (.text, .data), import/export tables. Tools: PE Explorer, `dumpbin`.
- **Mach-O (macOS/iOS):** load commands, segments, sections, symbol tables. Tools: `otool`, `class-dump`.

Understanding sections helps locate code (`.text`), initialized data (`.data`), uninitialized data (`.bss`), and imported functions (which hint at behavior).

## 22.4 Disassembly and Decompilation

- **Disassembly:** machine code → assembly mnemonics (Ghidra, IDA, radare2, objdump).
- **Decompilation:** assembly → higher-level C-like pseudocode (Ghidra, Hex-Rays, JADX for Java).

Decompiler output is *approximate*: compiler optimizations, stripped symbols, and obfuscation degrade it. Always cross-check with disassembly.

Common patterns to recognize:

- Function prologue: `push rbp; mov rbp, rsp` (or just `endbr64` on modern compilers).
- Calls to `strcmp`, `strlen`, `malloc`, `free`, `system`.
- String references to URLs, file paths, keys.
- Branches around validation checks (a `cmp` followed by `jne` may be an authorization or license check).

## 22.5 Function Identification

- Entry point (`_start`, `main`) found from the ELF header or symbols.
- Names from symbol tables (if not stripped).
- Cross-references (xrefs) to strings and imports reveal relevant functions.
- Calling conventions determine argument passing (Chapter 2).

## 22.6 Malware Analysis Fundamentals (Safe Context)

In an isolated lab (never on your main machine):

1. **Static triage:** `file`, hashes, strings, imports/sections, packer detection.
2. **Dynamic observation:** run in a sandboxed VM with network isolation; observe processes, files, registry, and network.
3. **Behavioral classification:** what does it do (keylogging, encryption, C2 communication)?
4. **Indicators of compromise (IoCs):** hashes, IPs, domains, file paths.

Do not build or deploy malware. Analysis is defensive and educational. Use dedicated lab VMs with snapshots.

## 22.7 Software Behavior Analysis

For a legitimate binary you own:

- Trace configuration file reads/writes.
- Identify network endpoints and protocols.
- Understand cryptographic operations (look for known constants).
- Map error paths and validation logic.

## 22.8 Protocol Reverse Engineering

When a protocol is undocumented, observe messages between client and server (Wireshark), identify structure (length fields, delimiters, opcodes), and infer state machines. Fuzzing the parsed fields can reveal bugs. This is used in IoT and proprietary client analysis — only in authorized contexts.

## 22.9 Tools

- **Ghidra:** free, powerful decompiler; headless mode for automation.
- **IDA Free / IDA Pro:** industry-standard disassembler.
- **radare2/rizin:** scriptable CLI framework.
- **GDB / lldb:** debuggers.
- **objdump, readelf, nm, strings, file:** binutils essentials.

## 22.13 Mastery Deep Dive: Executable Formats and Loading

### 22.13.1 ELF, Section by Section

The **ELF** (Executable and Linkable Format) file is interpreted two ways: as a *linkable* file (section headers) and as a *loadable* image (program headers/segments). Mastery means knowing both views.

The **ELF header** (`readelf -h`) records class (32/64-bit), data encoding (endianness), `e_type` (ET_EXEC, ET_DYN for PIE/shared libs), `e_entry` (entry point), and offsets to the program/section header tables.

**Program headers** (`readelf -l`) describe **segments** consumed by the loader: `PT_LOAD` (mapped into memory with flags R/W/X), `PT_INTERP` (path to the dynamic loader, e.g., `/lib64/ld-linux-x86-64.so.2`), `PT_DYNAMIC` (dynamic linking info), `PT_PHDR`. The mapping has practical consequences: the `.text` section lives in an R-X `PT_LOAD`, `.data`/`.bss` in an RW `PT_LOAD`. An `RWE` segment (read-write-executable) is a red flag.

**Section headers** (`readelf -S`) describe sections used by tools and the linker:

| Section | Contents | Why it matters |
|---------|----------|----------------|
| `.text` | Executable code | Disassembly target |
| `.rodata` | Read-only constants/strings | Find literals, keys, URLs |
| `.data` | Initialized writable globals | Global variables |
| `.bss` | Uninitialized globals (no file bytes) | Size reserved at load |
| `.symtab` | Full symbol table (often stripped) | Names of functions/variables |
| `.dynsym` | Dynamic symbols (kept for imports/exports) | Imported API calls |
| `.rel.* / .rela.*` | Relocations | Pointers patched by loader |
| `.got / .plt` | Global Offset Table / Procedure Linkage Table | Indirection for dynamic calls; GOT overwrite target |
| `.strtab / .shstrtab` | Strings for symbol/section names | — |

Inspect all views in one pass:

```bash
<LAB> file ./sample                # ELF 64-bit LSB pie executable, x86-64
<LAB> readelf -h ./sample | grep -E 'Type:|Entry point'
<LAB> readelf -lW ./sample | grep -E 'LOAD|INTERP|DYNAMIC'
<LAB> readelf -SW ./sample | egrep '\.text|\.rodata|\.data|\.bss|\.dynsym'
<LAB> readelf -dW ./sample | grep NEEDED   # shared libraries needed
```

Interpretation: `Type: DYN` with an `INTERP` means a PIE executable. `NEEDED` entries (`libc.so.6`, `libcrypto.so`) reveal capabilities even when stripped — a binary linking `libcrypto` likely does cryptography.

### 22.13.2 PE, Section by Section

**PE** (Portable Executable, Windows) begins with a **DOS header** (`MZ`) containing `e_lfanew`, a file offset to the PE header. The **COFF/PE header** holds `Machine`, `NumberOfSections`, `TimeDateStamp`, and `Characteristics` (e.g., `IMAGE_FILE_DLL`). The **Optional Header** (PE32 vs PE32+) contains `ImageBase`, `AddressOfEntryPoint`, `SectionAlignment`, `FileAlignment`, `SizeOfImage`, and `DataDirectory` entries pointing to import/export/resource/relocation tables.

Common sections:

| Section | Typical role |
|---------|--------------|
| `.text` | Code |
| `.rdata` | Read-only data, import/export tables, strings |
| `.data` | Writable globals |
| `.bss` | Uninitialized data |
| `.rsrc` | Resources (icons, dialogs, manifests) |
| `.reloc` | Base relocations for ASLR |
| `.edata` (or `.rdata`) | Export table (DLLs) |

The **Import Table** (`dumpbin /imports`, or `pefile` in Python) lists DLLs and imported functions — a behavioral goldmine: `CreateRemoteThread`, `VirtualAllocEx`, `RegSetValueEx`, `URLDownloadToFile` are strong indicators. The **Export Table** lists functions a DLL exposes. `dumpbin /headers` and `objdump -x` (with mingw) are standard.

```bash
<LAB> python3 -c "import pefile; p=pefile.PE('sample.exe'); \
print([d.dll for d in p.DIRECTORY_ENTRY_IMPORT])"
```

### 22.13.3 Mach-O, Section by Section

**Mach-O** (macOS/iOS) starts with a **mach_header** (magic, cputype, filetype, flags, `ncmds`, `sizeofcmds`) followed by a sequence of **load commands**. Key load commands:

- `LC_SEGMENT_64` — defines a segment with sections (`__TEXT`, `__DATA`, `__LINKEDIT`).
- `LC_MAIN` — entry point (`LC_UNIXTHREAD` on older builds).
- `LC_LOAD_DYLIB` — dependency (e.g., `/usr/lib/libSystem.B.dylib`).
- `LC_SYMTAB` / `LC_DYSYMTAB` — symbol tables.
- `LC_CODE_SIGNATURE` — code signature.
- `LC_ENCRYPTION_INFO` — FairPlay encryption on App Store binaries.

Sections inside `__TEXT` include `__text` (code) and `__cstring` (string literals); inside `__DATA`, `__data`, `__bss`, `__la_symbol_ptr`/`__nl_symbol_ptr` (the Mach-O equivalent of GOT/PLT).

```bash
<LAB> otool -hv sample           # header: filetype, flags (e.g., MH_PIE)
<LAB> otool -l sample | grep -E 'LC_|segname|sectname' | head -60
<LAB> otool -L sample            # linked dylibs
<LAB> nm -gU sample | head       # external symbols
```

Interpretation: `MH_PIE` in flags means position-independent; `LC_ENCRYPTION_INFO cryptid=1` means encrypted (App Store); `__la_symbol_ptr` entries reveal imported functions like `_malloc` or `_CCCrypt`.

### 22.13.4 Loader, Imports, Relocations, and Dynamic Linking

When a program starts, the kernel maps the `PT_LOAD`/segments, then the **dynamic loader** resolves imports: for each imported symbol, the loader finds its address in a shared library and patches the GOT (ELF) or lazy symbol pointers (Mach-O) or IAT (PE). **Relocations** adjust absolute addresses when the image is loaded at a different base than the preferred one (ASLR/PIE).

Why this matters to analysis:

- Imports are a *behavioral fingerprint*. A binary importing `socket`, `connect`, `send` is networked; one importing `RegOpenKeyEx`/`RegSetValueEx` touches the registry.
- **Lazy binding** means some imports are resolved only on first call; in a debugger you can see the PLT stub jump into the resolver the first time, then directly to the resolved address thereafter.
- **Stripped** binaries still expose `.dynsym`/imports because the loader needs them — this is why function *names* often survive even when the full symbol table is removed.

### 22.13.5 Case Study: Following a String to Behavior

To make the format concepts concrete, here is a compact end-to-end trace you can reproduce on a harmless lab binary you compile yourself. Suppose `strings -a sample` reveals the literal `http://<LAB_DOMAIN>/update`. The goal is to find the code that uses it and decide what it does.

Step 1 — find the string's virtual address. `strings -t x sample` prints file offsets; for a typical ELF the `.rodata` section is mapped nearly 1:1, but confirm with `readelf -SW` (section address vs. offset). Step 2 — find cross-references: in radare2, `iz~<LAB_DOMAIN>` lists the string with its address, then `axt @ <address>` shows instructions that reference it. In Ghidra, double-click the string in **Defined Strings** and inspect **References**. Step 3 — read the referencing function in the listing: a typical pattern is

```asm
lea rax, [rip+0x2fd1]      ; load address of the URL string
mov rdi, rax               ; arg1 = URL
call 401040 <curl_easy_setopt@plt>
...
call 401050 <socket@plt>
call 401060 <connect@plt>
```

Interpretation: the string is passed to `curl_easy_setopt`, then a socket is opened — this function performs an HTTP request. Following xrefs *backward* to `main` shows who triggers it and under what condition (a timer? a command-line flag?). This "string → xref → function → caller chain" is the single most common reverse-engineering workflow, and it works on ELF, PE, and Mach-O alike. The mastery skill is not memorizing tool commands but being able to trace data flow from an observable artifact to the behavior that produces it.

## 22.14 Mastery Deep Dive: Disassembly, Decompilation, and Tool Workflows

### 22.14.1 Disassembly vs. Decompilation and Their Limits

**Disassembly** translates machine code bytes to assembly mnemonics — deterministic and faithful. **Decompilation** attempts to reconstruct higher-level C-like pseudocode — helpful but lossy. Sources of error:

- **Compiler optimizations** reorder, inline, and fuse operations; loops become pointer arithmetic; variables vanish into registers.
- **Stripping** removes names, so the decompiler guesses.
- **Obfuscation/packing** hides code until runtime.
- **Data vs. code ambiguity**: x86 variable-length instructions can be misaligned, producing wrong disassembly if you start at the wrong byte.

Rule: *always confirm decompiler conclusions in the disassembly listing and, when in doubt, in the debugger.* Pseudocode like `if (i == 0x1337) goto LABEL_5;` must be verified against the actual `cmp`/`jne` and the register contents at runtime.

### 22.14.2 Ghidra Workflow with Headless Automation

Interactive workflow:

1. Create project, import `<LAB> sample`, run Auto-Analysis.
2. In **Defined Strings**, find URLs/paths/keys; double-click to jump to xrefs.
3. In the **Symbol Tree**, navigate `Functions`; use the **Decompiler** pane to read `main` and callees.
4. Right-click → **References → Find References to** a string to see all code paths using it.
5. Rename functions/variables and add comments; export findings.

Headless mode for repeatable analysis:

```bash
<LAB> /opt/ghidra/support/analyzeHeadless /tmp/ghidra_proj labproj \
        -import <LAB_SAMPLE> -postScript FindStrings.java -scriptPath ./scripts
```

`analyzeHeadless` runs analyzers and your Java/Python (Jython) script without the GUI — ideal for batch triage. Interpretation: the script's stdout lists decoded strings and xref counts, letting you rank samples before manual work.

### 22.14.3 radare2 / rizin Workflow

```bash
<LAB> r2 -A ./sample
[0x00401000]> afl                 # list functions
[0x00401000]> fs symbols; f        # list flags/symbols
[0x00401000]> iz                   # strings in data sections
[0x00401000]> s main; pdf          # disassemble function
[0x00401000]> s sym.vuln; pdc      # pseudo-decompilation
[0x00401000]> axt @ str.url        # xrefs to a string
[0x00401000]> ?v 0x10              # numeric helpers
```

Interpretation: `afl` gives the function inventory; `iz` surfaces strings with their virtual addresses; `axt` shows who references a string (the quickest route from "interesting URL" to "the function that uses it"). rizin (`rz-`) is the maintained fork with a similar command set. These tools are scriptable and excellent when you need automation or work over SSH.

### 22.14.4 Symbols, Stripping, and Function Identification

Binaries may carry:

- **`.symtab`** — full symbols (removed by `strip`).
- **`.dynsym` / imports** — retained for dynamic linking.
- **Debug info** (`-g`, DWARF / PDB) — richest, often absent in release.

When stripped, identify functions by:

- **Entry point** from ELF header / `LC_MAIN` / PE `AddressOfEntryPoint`, then follow calls.
- **Known library calls** — `main` often calls `__libc_start_main` with its address as an argument.
- **Signatures** — FLIRT (IDA) / Ghidra Function ID match compiler-generated patterns.
- **Prologues/epilogues** — `push rbp; mov rbp,rsp` / `endbr64`.
- **String xrefs** — a function referencing "password" is likely an auth check.

```bash
<LAB> nm ./sample | grep ' [tT] '     # defined text symbols (before strip)
<LAB> strip --strip-all ./sample -o ./sample.stripped
<LAB> readelf -sW ./sample.stripped | grep -c FUNC   # compare counts
<LAB> strings -a ./sample | grep -Ei 'http|pass|key'
```

Interpretation: after stripping, `.symtab` is gone but `.dynsym` remains; the drop in `FUNC` symbol count quantifies what you lost and justifies switching to xref-based identification.

### 22.14.5 Debugging and Breakpoints

3. **Software breakpoints** replace a byte with `0xCC` (`int3`); **hardware breakpoints** use debug registers (watchpoints for data access). Use hardware watchpoints to catch *when a variable is written*:

```bash
<LAB> gdb ./sample -q
(gdb) break *0x401126        # breakpoint at exact address
```

## 22.15 Mastery Deep Dive: Malware Behavior Analysis in an Isolated Lab

> Everything here is defensive/educational analysis of samples you create or receive through a controlled feed, performed inside an isolated sandbox. Never build or deploy real malware.

### 22.15.1 Safe Analysis Environment and Containment

A malware lab is defined by **containment boundaries**:

- **Isolated VM** with a snapshot taken before execution; no shared folders, no clipboard sharing, no bridged adapter to production networks.
- **Host-only or NAT network** with internet access only if needed, routed through a controlled sinkhole/DNS sink; better, fully offline with fake DNS.
- **No real credentials** on the guest; disposable identity.
- **Monitoring tools** pre-installed: Procmon/Process Explorer (Windows), `sysmon`, `tcpdump`, `Wireshark`, `regshot`, ProcDot, `volatility3`.
- **Revert to snapshot** after every run; keep the guest clock consistent for timeline analysis.
- **Legal/ethical:** handle samples per your organization's policy; never execute on a host that holds sensitive data.

### 22.15.2 Static Triage of a Suspicious Sample

A rapid triage checklist:

```bash
<LAB> file sample.bin
<LAB> sha256sum sample.bin
<LAB> strings -a -n 6 sample.bin | grep -Ei 'http|exe|dll|reg|software\\|cmd|powershell'
<LAB> python3 -c "import pefile; p=pefile.PE('sample.exe'); print(p.DIRECTORY_ENTRY_IMPORT)" 2>/dev/null
<LAB> python3 -m magic sample.bin 2>/dev/null || true
```

Packer/obfuscation indicators: very few imports, high entropy (>7.0), sections named `UPX0`/`.aspack`, small file with large virtual size, `LoadLibrary`/`GetProcAddress` used to resolve APIs dynamically. Check with `ent` (entropy) and `PEiD`/`DIE` (Detect It Easy). Interpretation: a high-entropy, low-import sample is likely packed; unpack in the lab (e.g., `upx -d` on your own sample) before deeper analysis.

### 22.15.3 Behavioral Analysis: Persistence, Lateral, and Network Indicators

Run the sample in the sandbox while recording a baseline diff:

```bash
<LAB> regshot  # take snapshot 1, run sample, take snapshot 2, compare
<LAB> tcpdump -i any -w capture.pcap
<LAB> sysmon -accepteula -i config.xml   # detailed event logging
```

What to look for and how to interpret:

| Behavior | Artifact / indicator | Where to observe |
|----------|----------------------|------------------|
| Persistence | New `Run` key, scheduled task, service, startup folder | Procmon/regshot diff |
| Lateral movement | `net use`, SMB connections, `psexec`-like service creation | Sysmon Event ID 1, network |
| C2 communication | Periodic beacons to a domain/IP, DNS TXT queries, unusual ports | Wireshark, DNS logs |
| Defense evasion | `cmd /c`, PowerShell `-enc`, disabling Defender | Process command lines |
| Credential access | Reads of `lsass.exe` memory, `Mimikatz`-like strings | Sysmon, process access events |
| Encryption/ransom | Mass file renames, high CPU, extension changes | File-system diff |

Indicators of compromise (IoCs) to extract: SHA256 hashes, C2 domains/IPs, mutex names, dropped file paths, registry keys, user-agent strings. These feed detections (YARA/Sigma/Suricata).

### 22.15.4 Writing YARA Rules

**YARA** matches patterns in files/memory — a detection language, not an exploit tool. A rule has metadata, strings, and a condition:

```yara
rule Lab_Suspicious_Indicator {
    meta:
        description = "<LAB> educational detection for a test sample"
        author = "lab"
        severity = "medium"
    strings:
        $url = "http://<LAB_DOMAIN>/beacon" ascii nocase
        $mutex = " LAB_MUTEX_1337" wide
        $api1 = "CreateRemoteThread" ascii
        $api2 = "VirtualAllocEx" ascii
        $mz = { 4D 5A }              // MZ header bytes
    condition:
        mz at 0 and (url or mutex) and 2 of (api*)
}
```

Interpretation: `mz at 0` requires a PE, `url or mutex` requires one sample-specific indicator, and `2 of (api*)` requires two of the process-injection API strings. Use `yara -r rule.yar <LAB_DIR>` to scan. Good rules balance **specificity** (few false positives) and **generality** (catch variants); test against a benign corpus to measure false-positive rate.

### 22.15.5 Memory Forensics Basics

When a sample leaves few disk artifacts, analyze a RAM image with **Volatility 3**:

```bash
<LAB> vol3 -f mem.dump windows.info
<LAB> vol3 -f mem.dump windows.pslist
<LAB> vol3 -f mem.dump windows.netscan
<LAB> vol3 -f mem.dump windows.malfind --pid <LAB_PID>
<LAB> vol3 -f mem.dump windows.dlllist --pid <LAB_PID>
```

Interpretation: `pslist` shows processes (hidden ones may appear only via `psscan`); `netscan` reveals sockets even if the sample closed them; `malfind` flags executable memory regions with `PAGE_EXECUTE_READWRITE` protection and no backing file — classic injected code; `dlllist` shows loaded modules, including unexpectedly injected DLLs. Dumping the flagged region and scanning it with YARA links memory evidence to your detection rules.

### 22.15.6 Protocol Reverse Engineering

For an undocumented protocol (in an authorized lab):

1. Capture traffic with Wireshark between client and server you control.
2. Identify framing: fixed magic bytes, length fields, delimiters, endianness.
3. Segment a message: `[magic:4][length:2 LE][opcode:1][payload:variable][checksum:4]`.
4. Vary one field at a time and observe responses to infer the state machine.
5. Replay modified messages with Scapy, then fuzz the parsed fields (Chapter 23).

Interpretation: a length field that does not match observed payload sizes suggests a parser bug candidate; opcodes that trigger distinct responses map the state machine. Always confine this to systems you own or are authorized to test.

### 22.15.7 Handling Packed and Obfuscated Samples

Packing compresses or encrypts a binary so that its real code appears only at runtime. Static analysis of a packed sample usually shows a small stub, very few imports (often just `LoadLibrary`/`GetProcAddress` or `mmap`/`mprotect`), and high entropy. Your analysis strategy must adapt:

1. **Detect** — check entropy (`ent sample`): values near 8.0 suggest encryption/compression. Look for section names like `UPX0`, `.aspack`, `.nsp`, or an overlay. Tools: `DIE` (Detect It Easy), `PEiD`, `exescan`.
2. **Unpack in the lab** — for a known packer on a sample you own, `upx -d sample` works; for custom packers, run the sample in the sandbox and dump the unpacked image from memory.
3. **Dump memory** — with GDB on Linux (`dump binary memory dumped.bin 0xSTART 0xEND`) or a Volatility `windows.dumpfiles`/`malfind` dump on Windows. Once unpacked, re-run the full static triage on the dumped image.
4. **Watch the unpacking stub** — set a breakpoint on `VirtualAlloc`/`mmap`/`mprotect` (memory allocation/protection changes) and on `WriteProcessMemory`; when the stub writes executable code, you have found the original entry point (OEP). From the OEP, standard analysis applies.

Interpretation: unpacking is not an end; it converts an opaque sample into an analyzable one. If a sample uses multiple layers or anti-debug tricks (e.g., `IsDebuggerPresent`, timing checks), you may need to patch those checks in the lab or use a debugger that hides itself. The key principle remains: all of this happens inside your isolated VM against a sample you are authorized to analyze.

### 22.15.8 Producing an Analysis Report and Timeline

The deliverable of reverse engineering is a decision, not a pile of notes. A good report contains:

- **Executive summary** — what the binary is and what it does, in business language.
- **Scope and containment** — where the analysis ran, what authority you had, what snapshot was restored.
- **Technical findings** — each behavior with an artifact (hash, path, IP, registry key) and the evidence that supports it (xref screenshot, Procmon line, packet capture).
- **IoCs** — structured list: hashes, domains, IPs, mutexes, file paths, YARA rule.
- **Timeline** — a sequence of events from execution: `T+0s sample launched → T+2s reads registry → T+5s DNS query to <LAB_DOMAIN> → T+7s TCP connect`. Tools like ProcDot can visualize this from Sysmon/PCAP data.
- **Mitigation recommendations** — detection rules and hardening steps.

A disciplined timeline prevents a common failure: concluding "it connects to the internet" without establishing *when* and *what triggered it*. Correlating process-creation events, file writes, and network flows by timestamp turns scattered observations into a causal story. Mastery includes writing a report another analyst can reproduce from your evidence alone.

## 22.16 Mastery Deep Dive: Verification and Practice

### 22.16.1 Detection and Defense Checklists

Defensive hardening (for software you build):

- [ ] Strip release binaries; enable CFI/control-flow guard where available
- [ ] Avoid RWE segments/permissions; enforce W^X
- [ ] Sign binaries and verify signatures at runtime
- [ ] Minimize dangerous imports; use allow-listed APIs
- [ ] Remove debug symbols and hard-coded secrets from release builds
- [ ] Maintain SBOM and baseline hashes to detect tampering

Detection engineering (for defenders):

- [ ] YARA rules for known samples/families; Sigma rules for behavioral events
- [ ] Sysmon/EDR telemetry for injection, persistence, and C2 patterns
- [ ] Network sinkhole/DNS logging to catch beaconing
- [ ] Memory capture capability for incident response
- [ ] Baseline file/registry state for diffing

### 22.16.2 Common Mistakes

1. **Trusting decompiler pseudocode without checking disassembly** — leads to wrong conclusions about branches and data flow.
2. **Running a sample on the host or a networked VM** — containment failure; always snapshot and isolate.
3. **Skipping the baseline** — without a pre-run snapshot you cannot distinguish sample activity from background noise.
4. **Writing over-broad YARA rules** that match half your benign corpus — measure false positives.
5. **Ignoring packed/obfuscated samples** — unpack in the lab first or you analyze only the unpacker stub.
6. **Confusing imports with behavior** — an import only shows *capability*, not that the code path executes; confirm dynamically.

### 22.16.3 Verify in Your Lab

1. Compile `<LAB>` a small C program; analyze with `file`, `readelf`, `objdump`, and Ghidra.
2. Strip it; compare symbol counts and note which identification methods still work.
3. Find a string (`<LAB>`), trace its xrefs in r2 to the using function, and confirm in GDB.
4. Create a harmless test "sample" that writes a file and makes a DNS query to `<LAB_DOMAIN>`; analyze it in an isolated VM with regshot + tcpdump.
5. Write a YARA rule that detects your test sample but not a benign binary; scan a small corpus.
6. Capture a memory image during execution and locate the process with `vol3 windows.pslist`.

### 22.16.4 What Mastery Looks Like

You have mastered this material when you can:

- Walk through ELF/PE/Mach-O headers and explain what the loader does with each structure.
- Move fluently between disassembly, decompiler output, and debugger state, cross-checking each.
- Identify functions in a stripped binary using xrefs, imports, and signatures.
- Run a contained behavioral analysis and produce IoCs with evidence for each.
- Write and validate targeted YARA rules and perform basic memory forensics.
- Maintain a defensible, reproducible analysis record with scope and containment documented.

### 22.16.5 Knowledge Check (Answers Included)

**Q1.** Why do imported function names often survive stripping?
**A1.** The loader needs them for dynamic linking, so `.dynsym`/import tables remain even when the full `.symtab` is removed.

**Q2.** A PE imports `VirtualAllocEx`, `WriteProcessMemory`, and `CreateRemoteThread`. What capability does this suggest, and what is the caveat?
**A2.** Process injection (allocating/writing memory in another process and starting a thread there). Caveat: imports show capability, not proof of use — confirm dynamically.

**Q3.** What does a Volatility `malfind` hit with `PAGE_EXECUTE_READWRITE` and no backing file indicate?
**A3.** A private executable memory region, often injected code; dump it and scan with YARA.

**Q4.** Why must decompiler output be cross-checked against disassembly?
**A4.** Decompilation is lossy: optimizations, stripped symbols, and obfuscation can produce misleading or incorrect pseudocode.

**Q5.** What two properties make a YARA rule useful rather than noisy?
**A5.** Specificity (matches the intended sample, few false positives) and generality (catches variants), validated against a benign corpus.

## 22.11 Key Takeaways

- Reverse engineering combines static structure with dynamic behavior.
- Binary formats (ELF/PE/Mach-O) organize code and data; tools expose their structure.
- Decompilation is approximate; verify against disassembly and runtime observation.
- Analyze only safe samples and binaries you own or are authorized to examine.
