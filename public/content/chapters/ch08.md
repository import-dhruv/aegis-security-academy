# Chapter 8: Web Security Architecture

> **Learning objectives.** Trace a complete HTTP request from browser to database and back; explain each component's role and security boundary; describe methods, headers, cookies, authentication flows, and authorization models; and read request-lifecycle diagrams.

## 8.1 The Modern Web Stack

A request from a browser to a modern web application passes through many systems:

```
   [Browser]
      |  DNS resolution, TCP+TLS
      v
   [CDN / Edge]        (cache, WAF, TLS termination, DDoS protection)
      |
      v
   [Reverse Proxy]     (routing, TLS, header rewriting)
      |
      v
   [Load Balancer]     (distribute across app instances)
      |
      +---> [App Server A] ---> [Cache (Redis)]
      +---> [App Server B] ---> [Database]
      +---> [App Server C] ---> [Object Store]
```

Each hop is a potential **security boundary** — a place where one component trusts (or should not trust) another. Vulnerabilities often arise at boundaries:

- Between browser and CDN: cache keys, headers.
- Between proxy and app: forwarded headers, original IP, host.
- Between app and database: injection, excessive privileges.
- Between services: authentication, tenant isolation.

## 8.2 Request--Response Lifecycle

A complete trace:

1. **DNS resolution:** browser resolves `www.example.com` to an IP.
2. **Connection:** TCP handshake, then TLS handshake (certificate validation).
3. **Request:** browser sends method, path, headers, cookies, body.
4. **Edge/CDN:** may serve cached content or forward; WAF may block.
5. **Reverse proxy:** terminates TLS, adds/removes headers, routes.
6. **App server:** framework parses request, runs middleware (auth, CSRF, logging), routes to handler.
7. **Handler:** validates input, checks authorization, executes business logic, queries database.
8. **Database:** returns data; app builds response.
9. **Response:** headers (cookies, CSP) and body travel back through proxy/CDN.
10. **Browser:** parses HTML, executes JS, renders, makes subresource requests.

Every step is an opportunity for a researcher to ask: *what does this component assume, and can I violate that assumption?*

## 8.3 HTTP Methods, Headers, Status Codes

**Methods** (Chapter 4) define intent. Security relevance:

- GET should be safe and idempotent; state changes via GET enable CSRF and prefetch leaks.
- PUT/DELETE may be enabled unintentionally, allowing file/record manipulation.
- TRACE can enable XSS variants (XST) and should be disabled.
- Method override headers (`X-HTTP-Method-Override`) can bypass naive method restrictions.

**Headers** of security interest:

| Header | Purpose |
|--------|---------|
| `Host` | Virtual host routing; trust issues → host-header injection |
| `X-Forwarded-For` / `X-Real-IP` | Client IP behind proxy; spoofable if not sanitized |
| `Origin` | Cross-origin request source; used in CSRF/CORS checks |
| `Referer` | Previous page; information leakage, sometimes used for CSRF defense |
| `Content-Type` | Body format; parsing differences → smuggling |
| `Content-Length` / `Transfer-Encoding` | Body framing; disagreement → request smuggling |
| `Authorization` | Bearer/basic credentials |
| `Cookie` / `Set-Cookie` | Session state |
| `Content-Security-Policy` | Restricts script/content sources → XSS mitigation |
| `Strict-Transport-Security` | Forces HTTPS → downgrade protection |

**Status codes** tell you about state: 200 vs. 403 vs. 404 differences reveal authorization logic; 302 vs. 200 reveals redirects; 500 with stack traces leaks internals.

## 8.4 Cookies and Sessions

Cookies carry session state. Cookie attributes (Chapter 6) and server-side session handling together define session security. Key properties:

- **Predictability:** session IDs must be cryptographically random (at least 128 bits).
- **Transport:** `Secure` flag; HSTS.
- **Access:** `HttpOnly` blocks JS theft.
- **Scope:** `Domain`/`Path` must not be overly broad (subdomain trust issues).
- **Lifecycle:** rotation on privilege change, idle/absolute timeouts, invalidation on logout.
- **CSRF:** `SameSite` plus tokens.

## 8.5 Authentication Flows

Authentication mechanisms include:

- **Form-based login:** credentials → session cookie.
- **Bearer tokens:** JWT/Opaque tokens in `Authorization` header.
- **API keys:** often long-lived and over-privileged.
- **Mutual TLS:** certificate-based, common in service-to-service.
- **SSO / federation:** SAML, OIDC (Chapter 7).

Security questions to ask: Can authentication be bypassed via parameter manipulation? Are credentials compared safely? Is there rate limiting? Is MFA enforced and can it be bypassed? Are sessions invalidated on password change? Are default credentials present?

## 8.6 Authorization Models

- **DAC:** owner decides (Unix files).
- **MAC:** central policy (SELinux).
- **RBAC:** roles (admin, user) with permissions.
- **ABAC:** attributes (department, clearance, time).
- **ReBAC:** relationships (owner, member of group).
- **PBAC:** policy-based (e.g., Cedar, OPA).

Web apps typically implement a mix. The researcher's focus: is authorization checked at the **object** level (can user A read *this* record?) and **function** level (can user A call *this* admin endpoint?), on every request, server-side? Missing checks produce IDOR/BOLA and BFLA (Chapters 9 and 17).

## 8.7 Security Boundaries Diagram

```
 +------------------ Browser ------------------+
 | Untrusted: URL, form fields, JS, files,      |
 | cookies, headers, websocket frames           |
 +--------------------+-------------------------+
                      |  (all input is untrusted)
 +--------------------v-------------------------+
 |              Edge / Proxy / CDN              |
 |  Cache keys, header trust, TLS, WAF          |
 +--------------------+-------------------------+
                      |
 +--------------------v-------------------------+
 |               Application Tier               |
 |  Validation | AuthN | AuthZ | Logic | Errors |
 +--------------------+-------------------------+
                      |  (parameterize, least privilege)
 +--------------------v-------------------------+
 |          Data Tier (DB, cache, files)         |
 +----------------------------------------------+
```

The core principle: **never trust data crossing a boundary without validation appropriate to that boundary.** A value safe for display may be unsafe for a shell command; a value safe in a URL may be unsafe in SQL.

## 8.8 Case Study: Tracing a Login

A user submits a login form:

1. Browser POSTs `/login` with `username`, `password`, CSRF token.
2. CDN forwards; proxy sets `X-Forwarded-For`.
3. Framework validates CSRF token, rate-limits by IP and username.
4. Handler looks up user, verifies password hash (e.g., Argon2id/bcrypt).
5. On success: rotate session ID, set cookie with `HttpOnly; Secure; SameSite=Lax`.
6. Redirect to `/dashboard`; browser follows with cookie.
7. `/dashboard` middleware verifies session and loads user; handler checks authorization.

A researcher testing this flow would ask: Is the CSRF token checked on all state-changing methods? Can rate limits be bypassed with header spoofing? Is the session ID regenerated? Can a stale session access `/dashboard` after logout? Can `username` be injected into SQL? Does the redirect allow an open redirect via a `next` parameter?

3. For a lab app, identify where authorization is enforced and where it is assumed.
4. Compare responses for an authorized vs. unauthorized object access (403 vs. 404) and explain what the difference reveals.

## 8.12 Mastery Deep Dive: HTTP Semantics in Depth

### 8.12.1 Methods and their security consequences

Method choice encodes intent, but servers often accept more methods than developers realize. GET must be safe and idempotent — state changes on GET are CSRF/prefetch hazards (link scanners, browser prefetch, `<img>` tags). PUT/DELETE may be enabled by a framework's defaults even if the UI never uses them; test method overrides (`X-HTTP-Method-Override: DELETE`, `_method=DELETE`) against endpoints that only check the visible method. TRACE reflects input and can enable cross-site tracing (XST) when combined with client-side scripts; disable it. `CONNECT` on a forward proxy is a different capability and is frequently abused in SSRF chains.

### 8.12.2 Status codes as an oracle

| Code | Meaning | What it reveals |
|------|---------|-----------------|
| 200 | OK | Success; compare bodies for authz differences |
| 201 | Created | Resource created — useful for idempotency tests |
| 204 | No Content | Often a successful preflight or action |
| 301/302 | Redirect | Target may allow open redirect / token leakage |
| 304 | Not Modified | Conditional request succeeded; cache behavior signal |
| 400 | Bad Request | Parser rejected framing/encoding |
| 401 | Unauthorized | Auth missing/invalid |
| 403 | Forbidden | Authz denied — but confirm the data is truly absent |
| 404 | Not Found | May hide existence (good) or reveal it via timing |
| 405 | Method Not Allowed | Method restrictions exist |
| 412 | Precondition Failed | `If-Match`/`If-None-Match` in play (ETag oracle) |
| 429 | Too Many Requests | Rate limit exists — find its key |
| 500 | Server Error | Verbose ones leak stack traces, SQL, paths |

Differences between 403 and 404, and between response *lengths* and timings, are authorization oracles. A "404" that returns a full body for an existing-but-forbidden object is a bug, not a control.

### 8.12.3 Headers of security interest

Beyond the classic set, learn these: `Vary` (cache key correctness), `Cache-Control`/`Age`/`Expires` (caching), `ETag`/`Last-Modified` (conditional requests and cache validators), `X-Content-Type-Options: nosniff` (stops MIME sniffing), `Referrer-Policy` (leak control), `X-Frame-Options`/`frame-ancestors` (clickjacking), `Cross-Origin-Resource-Policy`/`Cross-Origin-Opener-Policy`/`Cross-Origin-Embedder-Policy` (cross-origin isolation), `Permissions-Policy` (feature gating), and `Expect: 100-continue` (framing interactions). On the request side: `Origin`, `Referer`, `Host`, `X-Forwarded-*`, `Forwarded`, `Content-Type`, `Content-Length`, `Transfer-Encoding`, `Authorization`, `Cookie`, and `Upgrade`.

### 8.12.4 Conditional requests and ETags

Clients send `If-None-Match: "<etag>"` or `If-Modified-Since`; the server replies 304 if unchanged. ETags can be **strong** (`"v1"`) or **weak** (`W/"v1"`). Security relevance: ETags are cache validators that can act as oracles — if an ETag changes when another user's data changes, it leaks state. ETags derived from sensitive content can leak that content's hash. Range requests (`Range: bytes=0-99`, response 206 Partial Content) can be used for compression-oracle attacks (BREACH-style) and for bypassing naive filters by splitting payloads across ranges.

### 8.12.5 Caching and cache keys

A cache stores responses keyed by a subset of the request. Common key inputs: method, scheme, host, path, query, sometimes `Accept-Encoding` or specific headers; cookies are often excluded by default for "public" content. `Cache-Control: public, max-age=60, s-maxage=300` (shared caches) vs `private, no-store`. A **cache poisoning** flaw exists when an input that influences the response is *not* in the key. A **cache deception** flaw exists when a cache stores a personalized response because a URL looks static (e.g., `/user/123/avatar.png` returning private data). `Vary: Origin`, `Vary: Accept-Encoding`, and correct `Cache-Control: private/no-store` are key defenses. Always verify `X-Cache`, `CF-Cache-Status`, and `Age` headers to understand cache state.

## 8.13 Mastery Deep Dive: Proxies, CDNs, and Load Balancers

### 8.13.1 Forwarded headers and trust chains

Reverse proxies add `X-Forwarded-For`, `X-Real-IP`, `X-Forwarded-Proto`, and `Forwarded`. Applications use these for rate limiting, logging, access control, and generating absolute URLs. If the app trusts client-supplied forwarded headers (because it cannot tell they were not added by the proxy), an attacker can spoof the apparent IP (`X-Forwarded-For: 1.2.3.4`) to evade IP-based controls or poison logs. Detection: send a lab request with a forged forwarded header and see whether rate-limit counters, "your IP" displays, or admin checks change. Defense: configure trusted-proxy counts, overwrite (not append) forwarded headers at the edge, and key controls on the socket peer address where possible.

### 8.13.2 Host routing and virtual hosts

A single IP serves many virtual hosts; the `Host`/`:authority` value selects the application. If an app trusts `Host` to build links or make authz decisions, host-header injection is possible. `X-Forwarded-Host` and absolute-form request lines (`GET http://<LAB_HOST>/ HTTP/1.1`) are alternate vectors. Test in a lab by supplying a controlled Host and observing generated URLs (password resets, redirects). Defense: maintain an allow-list of canonical hosts at the edge and in the app; reject unknown Hosts; never build security decisions from Host.

### 8.13.3 Where desync is born

Mixing HTTP/1.1 and HTTP/2, multiple proxies, TLS terminators, and differing header-normalization rules creates opportunities for two components to disagree on request boundaries or header values. Duplicate `Content-Length`, conflicting `Transfer-Encoding`, header folding, and `:authority` → `Host` translation are classic triggers. The defense is end-to-end HTTP/2 where possible, rejecting ambiguous framing, normalizing/deduplicating headers, and disabling malformed-request tolerance. (Chapter 10 covers exploitation mechanics in authorized labs.)

## 8.14 Mastery Deep Dive: TLS and Transport Security

### 8.14.1 The TLS 1.3 handshake

TLS 1.3 (RFC 8446) reduces round trips: the client sends `ClientHello` with supported versions, cipher suites, key shares, and SNI; the server replies `ServerHello` with its key share, then encrypted extensions and its certificate (encrypted with the handshake keys); the client verifies the certificate, sends its Finished message, and the server confirms. Earlier versions (TLS 1.2) expose more handshake metadata and support legacy renegotiation. Security properties: forward secrecy via ephemeral Diffie–Hellman, authenticated server identity, and integrity via AEAD ciphers (AES-GCM, ChaCha20-Poly1305). TLS 1.3 removed RSA key transport, CBC, and compression, eliminating many legacy attacks.

### 8.14.2 Certificate validation

The client checks: the chain terminates at a trusted CA, the leaf matches the hostname (SAN/CN), the certificate is within validity dates, and it is not revoked (OCSP/CRL) — plus name constraints and key usage. Failures here enable MITM: self-signed acceptance, hostname mismatch, wildcard overreach (`*.example.com` matching more than intended), and expired certs. Mobile apps and thin clients that disable validation or pin incorrectly are common findings. Certificate Transparency logs (crt.sh) are recon gold: they reveal subdomains you are authorized to test.

### 8.14.3 HSTS and downgrade protection

`Strict-Transport-Security: max-age=31536000; includeSubDomains; preload` instructs browsers to use only HTTPS for the host. It mitigates SSL-stripping downgrade attacks after the first trusted HTTPS visit. The `preload` list hard-codes the policy in browsers but requires meeting strict criteria and is effectively irreversible — verify all subdomains support HTTPS first. HSTS does not protect first contact or HTTP-only subdomains not covered by `includeSubDomains`. Combine with secure cookie flags and redirect HTTP→HTTPS.

### 8.14.4 TLS termination implications

When a CDN/load balancer terminates TLS, traffic from the proxy to the app may be plaintext HTTP. The app then cannot know the client used HTTPS unless it consults `X-Forwarded-Proto` (which can be spoofed — see 8.13.1). This affects `Secure` cookie setting, redirect logic, and HSTS emission. mTLS (mutual TLS) authenticates both sides and is common service-to-service; ensure the app verifies the client certificate rather than trusting a header that claims it did.

## 8.15 Mastery Deep Dive: Cookies, CORS, and CSP Deep Dive

### 8.15.1 Cookie parsing quirks

Browsers and servers disagree on cookie parsing: characters like `;` separating attributes, handling of `__Host-` prefixes, and duplicate cookie names (order matters — RFC 6265 says later same-name cookies may win in the `Cookie` header). Cookie shadowing across subdomains and path-scope quirks can place two cookies with the same name in one request. This matters for session fixation and for poisoning session state. Test only on lab hosts you control, and prefer `__Host-` prefixed cookies (requires `Secure`, `Path=/`, no `Domain`) to prevent subdomain injection.

### 8.15.2 CORS: the full decision tree

When a cross-origin request carries credentials (`credentials: 'include'`), the server must respond with an explicit origin (not `*`) and `Access-Control-Allow-Credentials: true`. The browser compares `Origin` exactly. Preflight results are cached per origin+URL for `Access-Control-Max-Age`. Request headers that trigger preflight include `Authorization` and `Content-Type: application/json`. CORS is a *read* permission: it does not protect endpoints from non-browser clients, and absence of CORS does not prevent CSRF-style request sending. Detection pattern: reflect a lab-controlled `Origin` and observe `Access-Control-Allow-Origin` + credentials; if reflected with credentials, any origin can read authenticated data.

### 8.15.3 CSP directive reference

| Directive | Controls |
|-----------|----------|
| `default-src` | Fallback for most fetch directives |
| `script-src` | Scripts; nonces/hashes/`strict-dynamic` |
| `style-src` | CSS; `unsafe-inline` sometimes needed for legacy |
| `img-src` / `font-src` / `media-src` | Subresources |
| `connect-src` | fetch/XHR/WebSocket destinations |
| `frame-src` / `frame-ancestors` | Embedded frames / who may frame us |
| `object-src` | Plugins — set to `'none'` |
| `base-uri` | `<base>` hijack — set to `'none'` |
| `form-action` | Where forms may submit |
| `report-uri` / `report-to` | Violation reporting |

Defense design: start in `Report-Only`, gather violations, then enforce. Avoid allowing `data:`, `blob:`, or JSONP-hosting origins in `script-src`. Combine with Trusted Types (`require-trusted-types-for 'script'`) to eliminate DOM XSS sinks. Verify by loading a harmless inline script in a lab and confirming it is blocked and reported.

## 8.16 Mastery Deep Dive: HTTP/2 and HTTP/3

### 8.16.1 What changes on the wire

HTTP/2 (RFC 9113) is binary and multiplexed over one TCP connection, with header compression (HPACK) and pseudo-headers (`:method`, `:authority`, `:scheme`, `:path`). HTTP/3 (RFC 9114) runs over QUIC/UDP with QPACK compression and improved loss recovery. The request *semantics* are unchanged, but the representation differs — which is exactly where translation bugs live. HPACK uses a dynamic table shared across a connection; QPACK avoids head-of-line blocking with different table synchronization.

### 8.16.2 Security implications

Pseudo-headers replace the request line; translation to HTTP/1.1 at a proxy must map `:authority` → `Host` and `:path` → request target consistently. Duplicate or conflicting pseudo-headers, illegal characters in header names, and differing treatment of uppercase header names are desync triggers. Multiplexing means many streams share a connection — request-smuggling variants can use stream-specific framing. HTTP/3's UDP/QUIC changes which middleboxes can inspect traffic, but not the application-layer trust model.

### 8.16.3 Practical notes

Use `curl --http2`/`--http3` or browser DevTools to inspect protocol (`Alt-Svc` header advertises h3). When testing headers, remember that some proxies normalize or strip them on protocol downgrade. Detection of translation issues requires dedicated labs and careful byte-level observation; never point these tests at third-party systems.

## 8.17 Mastery Deep Dive: Header Parsing Inconsistencies

Different servers treat whitespace, line folding, duplicate headers, and chunk extensions differently. Examples: `Content-Length: 5 ` vs `Content-Length: 5`; two `Content-Length` headers (`6` and `5`); `Transfer-Encoding: chunked` followed by a second `Transfer-Encoding` value; `Content-Length` with leading `+` or leading zeros; obs-fold (header continuation lines). A front-end that uses the first value and a back-end that uses the last can be desynchronized. Other inconsistencies: URL parsing of `//evil.com`, encoded `.`/`%2f` in paths, and backslash handling differ across stacks and can defeat path/authorization checks. Mastery is knowing that *parsers are code*, and code disagrees.

### 8.18.1 What mastery looks like — checklist

- [ ] I can explain method/idempotency security and name ten status codes and their oracle value.
- [ ] I can describe cache keys, poisoning vs. deception, and the headers that prevent each.
- [ ] I can explain forwarded-header spoofing and Host-routing trust.

- [ ] I can contrast HTTP/2/3 pseudo-headers with HTTP/1.1 and explain translation desync.
- [ ] I can name concrete parser inconsistencies and how they enable smuggling/bypasses.

### 8.18.2 Common mistakes

- Trusting `X-Forwarded-For` without knowing the proxy chain.
- Using `X-Frame-Options` and ignoring `frame-ancestors` CSP (or vice versa) without understanding coverage.
- Assuming CORS protects an API from unauthorized use by non-browser clients.
- Setting HSTS with `preload` before verifying every subdomain supports HTTPS.
- Ignoring `Vary`/`Cache-Control` and accidentally caching personalized responses.

### 8.18.3 Knowledge checks (answers below)

1. A response reflects `X-Forwarded-Host` but the cache key ignores that header. What flaw class is this, and what is the fix?
2. Why can't `Access-Control-Allow-Origin: *` be used with credentials?
3. What does `includeSubDomains` on HSTS change, and what is the risk of `preload`?
4. Which two headers, when both present with conflicting values, can cause request smuggling?

**Answers.** (1) Cache poisoning; include the influential header in the key or strip/normalize it at the edge and avoid reflecting it. (2) The spec forbids it: a wildcard would let any origin read credentialed responses; browsers reject the combination. (3) It extends HSTS to all subdomains; `preload` is effectively irreversible and breaks any HTTP-only subdomain. (4) `Content-Length` and `Transfer-Encoding`.

### 8.18.4 Lab exercises

1. On a lab host, set a misleading `X-Forwarded-For` and observe whether rate-limit/logging behavior changes; then configure trusted-proxy settings and retest.
2. Deploy a strict CSP in report-only mode, trigger a harmless inline script, and read the violation report.
3. Send conditional requests with `If-None-Match` and observe 304 vs 200; check whether an ETag leaks state across lab accounts.
4. Inspect a site you own with `curl -I` and with `--http2`; compare how headers are represented and whether any are normalized away.

## 8.19 Mastery Deep Dive: Caching Architectures in Practice

### 8.19.1 The layers of caching

A response may be cached at several layers, each with its own key and rules:

| Layer | Typical key | Control |
|-------|-------------|---------|
| Browser cache | URL + method + `Vary` | `Cache-Control`, `ETag` |
| Service worker | Request + scope | Worker script logic |
| CDN / edge | Host + path + query (+ configured headers/cookies) | CDN cache rules |
| Reverse proxy | URL + selected headers | Proxy cache config |
| Application | Object/query key | App cache (Redis/Memcached) |

A poisoning flaw at one layer can be neutralized by another, so test each layer independently. `Age`, `X-Cache`, `CF-Cache-Status`, and repeated `Date` headers reveal which layer served a response.

### 8.19.2 Determining the cache key experimentally

To learn a cache key in a lab: pick a URL, add a random query param `?cb=random1`, request twice, and see if the second is a HIT (the param may be excluded from the key, or the content may simply ignore it). Then vary one candidate at a time (a header like `X-Forwarded-Host`, a cookie, `Accept-Encoding`) and observe whether responses differ. A value that changes the body but is *not* in the key is a poisoning vector. Always confirm with a second, clean request that the poisoned response is served to a "normal" visitor.

### 8.19.3 Cache deception in depth

Cache deception tricks a cache into storing a personalized response by using a URL that appears static. Techniques: append a semicolon/path parameter that the app ignores but the cache treats as part of a static path; request `/lab/account/settings/anything.css` where routing ignores the suffix; exploit `?` vs `;` differences between app and cache. The fix: define cache rules on the *canonical, normalized* path, set `Cache-Control: private, no-store` on personalized pages, and never cache responses that depend on cookies. Verify by requesting a "static-looking" URL for user A and then as user B and confirming no cross-user data appears.

## 8.20 Mastery Deep Dive: Authentication at the Edge and Header Trust

### 8.20.1 The PROXY protocol and IP trust

Load balancers often use the PROXY protocol to pass the real client IP: a line like `PROXY TCP4 203.0.113.5 10.0.0.1 12345 443\r\n` precedes the HTTP request. If the application accepts PROXY-protocol lines from clients directly (not only from the trusted LB), an attacker can spoof their IP. Trust boundaries must be explicit: accept forwarded/proxy headers only from known proxy addresses, and overwrite rather than append. Detection in a lab: send a forged forwarded/proxy header and see whether access logs, rate limits, or geo/ACL decisions change.

### 8.20.2 Origin validation at the edge

Edge platforms often enforce `Origin`-based rules for CORS and CSRF. Verify that validation is exact (scheme + host + port), that `null` is rejected, and that the rule cannot be bypassed with a look-alike domain (`trusted.com.evil.com`) or a subdomain of the attacker's choosing. Combine with `SameSite` cookies and server-side tokens — an edge rule alone is a single point of failure. Test each layer independently in a lab and confirm that disabling the edge rule does not expose the app (defense in depth).

### 8.20.3 Header normalization and smuggling boundaries

Proxies differ on whether they merge duplicate headers, strip obs-fold, lowercase names, or reject invalid characters. These behaviors determine whether a smuggling payload succeeds (Chapter 10). A hardened edge should: reject requests with both `Content-Length` and `Transfer-Encoding`, reject duplicate or conflicting framing headers, normalize whitespace, and refuse malformed chunk extensions. Verify by replaying a battery of malformed requests in a lab and confirming consistent 400 responses and no cross-request contamination. The goal is a single, unambiguous interpretation of every request before it reaches application code.

## 8.21 Mastery Deep Dive: Practical HTTP Recon and Verification

### 8.21.1 Reading responses like a protocol analyst

Use `curl -i --http2 -v` against a lab host to observe the raw exchange: TLS version and cipher, ALPN negotiation (`h2`/`http/1.1`), the exact request headers, and the response header order. Header *order* and duplication can reveal which component set them (edge vs app). Compare responses to identical requests with one header varied (`Accept-Encoding: gzip`, different `User-Agent`, `X-Forwarded-Proto`) to discover normalization and cache behavior. Record `Server`/`X-Powered-By`/framework cookies as fingerprinting signals, then verify they are removed in a hardened build.

### 8.21.2 Conditional and range oracles

ETags and `Last-Modified` are not just cache validators — they can be oracles. If an ETag changes when another user's data changes, it leaks state; if an ETag is derived from sensitive content, its hash can be probed. Range requests (`Range: bytes=0-0`, response `206 Partial Content`) combined with compression can form compression oracles (BREACH-style) that leak secrets when a secret is reflected in a compressed response. Lab validation: request a range and compare response sizes with a guessed prefix included; statistically distinguish the correct guess. Defense: disable compression on responses that reflect secrets, separate secrets from user-controlled input, and prefer randomized padding or lengths.

### 8.21.3 Verification checklist for transport and headers

After hardening, verify: HTTP redirects to HTTPS; HSTS present with an appropriate `max-age`; cookies carry `Secure`, `HttpOnly`, and `SameSite`; CSP is enforced (not just report-only) with nonce/hash and `object-src 'none'`; `X-Content-Type-Options: nosniff` and `Referrer-Policy` set; forwarded headers are not trusted from clients; unknown Hosts are rejected; and ambiguous framing requests get a 400. Use an automated header scanner plus manual `curl` checks, and re-run after each deployment. Common mistake: setting a header at the app but having the CDN strip or override it — always verify the response as the client sees it.

## 8.10 Key Takeaways

- Requests traverse many components; each hop is a trust boundary with its own failure modes.
- Headers like Host, forwarded-IP, and framing headers shape security decisions and are frequently abused.
- Sessions and authorization must be enforced server-side on every request.
- Tracing the full lifecycle is the foundation of systematic web testing.
