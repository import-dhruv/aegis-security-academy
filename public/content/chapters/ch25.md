# Chapter 25: Writing High-Quality Vulnerability Reports

> **Learning objectives.** Write a report that triage can verify quickly; map severity and CWE; handle duplicates and disagreements professionally; and learn from 20 fictional examples.

## 25.1 Anatomy of a High-Quality Report

A good report answers every triage question before it is asked. Use this structure:

1. **Title** — concise: vulnerability type + affected asset.
2. **Executive summary** — one paragraph: what, where, impact.
3. **Affected asset & scope confirmation** — exact URL/endpoint and proof it is in scope.
4. **Classification** — CWE, suggested severity, CVSS vector (if useful).
5. **Preconditions** — accounts, roles, user interaction needed.
6. **Steps to reproduce** — numbered, exact requests, minimal.
7. **Proof of concept** — request/response, screenshots, video if helpful.
8. **Expected vs. actual behavior** — what should happen vs. what does.
9. **Security impact** — realistic worst case, not hype.
10. **Evidence** — logs, timestamps, test-account identifiers.
11. **Remediation** — concrete fix.
12. **References** — CWE/OWASP links.

**Principles:** be accurate, concise, reproducible, and honest about limitations. Use your own test accounts and synthetic data. Never include real user data in a report.

## 25.2 Severity and CVSS

Use CVSS as a common language, but understand that programs apply business context. A finding's severity depends on impact, exploitability, privileges, user interaction, and scope. Map CWE precisely: CWE-79 (XSS), CWE-89 (SQLi), CWE-918 (SSRF), CWE-639 (IDOR/BOLA), CWE-862 (missing authorization), CWE-352 (CSRF), CWE-22 (path traversal), CWE-502 (deserialization), CWE-200 (information exposure). When unsure, describe the impact clearly and let triage assign severity.

## 25.3 Triage Outcomes and Communication

- **Informative vs. valid:** informative means no clear security impact; valid means a security boundary is crossed.
- **Duplicate:** the same issue was reported; read the original if public and learn.
- **Not applicable / out of scope:** the asset or behavior is excluded.
- **Accepted:** valid; reward decision follows.
- **Severity disagreements:** respond with additional impact analysis, not emotion. Ask what evidence would change the assessment.
- **Follow-ups:** be polite, concise, and timely. Do not spam triage.

## 25.4 Twenty Fictional Example Reports

> These reports are fictional teaching examples for a fictitious program. They illustrate structure and reasoning; they are not real vulnerabilities.

### Example Report 1: IDOR exposes another user's order details on `api.shop-lab.test`

- **Classification:** Broken Access Control (BOLA/IDOR) — CWE-639 — High — CVSS:4.0 base 7.1 (network, low complexity, low privileges, high confidentiality)
- **Affected asset:** `api.shop-lab.test` (fictional, in scope per teaching policy)
- **Executive summary:** Order objects are fetched by a sequential ID without verifying the authenticated owner.
- **Preconditions:** Two authorized test accounts (A and B) in the program's lab environment.
- **Steps to reproduce:** 1. Log in as account A and GET /api/orders/1042 (A's own order). 2. Note the response. 3. Using A's token, GET /api/orders/1043 (B's order, ID obtained from B's own account). 4. Observe B's order details returned.
- **Proof of concept:** GET /api/orders/1043 with Authorization: Bearer <A-token> returns B's order JSON.
- **Expected behavior:** the server rejects the request or enforces the permission.
- **Actual behavior:** GET /api/orders/1043 with Authorization: Bearer <A-token> returns B's order JSON.
- **Security impact:** Any authenticated user can read other users' order data (names, addresses, totals) by incrementing an ID.
- **Remediation:** Enforce object-level authorization: SELECT ... WHERE id=? AND owner_id=current_user; use centralized policy checks.
- **Triage note:** Valid. Distinct accounts used; no real user data accessed.

## 25.7 Mastery Deep Dive: Report Anatomy Line by Line

> **Authorized testing only.** Every example in this deep dive assumes a lab environment or an explicit program scope. Use accounts you own, synthetic data, and harmless markers. Never touch real user data.

A report is a product with one impatient consumer: a triage analyst with roughly ninety seconds and a queue of hundreds. The gap between a report accepted in minutes and one that languishes is rarely the bug — it is how quickly the reader can confirm validity, scope, and impact. This section dissects each field and explains the decision behind it.

### 25.7.1 Title and Executive Summary

**Title.** Use `Vulnerability class on affected asset — short qualifier`. Good: `Stored XSS in product review field on app.shop-lab.test`. Bad: `Critical bug!!!` or `Found something weird`. Triagers route by class and asset; a precise title does that routing for them. Keep it under roughly 70 characters, use the asset's exact in-scope name, and omit severity adjectives — severity is the program's call, and a self-labelled "Critical" that triage downgrades reads as hype.

**Executive summary.** Two to four sentences answering *what, where, who can trigger it, and worst-case impact*, written so a reader who stops here still understands the finding. Fill this template:

> On `{{asset}}`, the `{{endpoint/parameter}}` fails to `{{root cause}}`. An attacker with `{{preconditions}}` can `{{capability}}` against `{{victim population}}`. Demonstrated in the lab with `{{harmless technique}}`; no real user data accessed.

Lead with the "why it matters" line. Define jargon inline. Write for the triager first and the engineer second: the top third of the report must answer "valid, in scope, novel, how severe?" while the appendix answers "how do I fix it?"

### 25.7.2 Affected Asset, Scope, and Preconditions

**Affected asset.** Give the exact URL, endpoint, IP, or host plus the scope entry it maps to — quote the policy line. For wildcards, explain the match. Record the program name and the policy version/date you tested against. If several assets are affected, name the primary one in the title and list the rest here.

**Preconditions.** State every condition: accounts and roles, authentication state, required user interaction, seeded lab data, network position, tool versions. Honest preconditions build credibility; omitted ones cause "could not reproduce" replies. A compact table works well:

| Precondition | Detail |
|--------------|--------|
| Accounts | A (victim) and B (attacker), both lab-only |
| Role | Authenticated low-privilege |
| Interaction | Victim views the seeded review |
| Data | Synthetic marker string only |

### 25.7.3 Steps to Reproduce and Proof of Concept

**Steps.** Number them, start from a clean state, and make each step copy-pasteable with the exact method, path, headers, and body. End each step with an observable checkpoint. Three to six steps is the sweet spot; more means you are documenting exploration, not reproduction. Never write "then exploit as usual" — spell out the request.

**PoC.** The smallest artifact that proves a boundary was crossed. Prefer a single request/response pair. Use harmless markers (`LAB-XSS-7f3a`), a callback to a listener you control, or a synthetic record ID. Show the raw request and a redacted response:

```http
GET /api/orders/1043 HTTP/1.1
Host: api.shop-lab.test
Authorization: Bearer <A-token-lab>
```

```json
{"id":1043,"owner":"user-B-lab","total":"41.00"}
```

For CSRF, supply an HTML form, not a live phishing page. For SSRF, use a controlled listener, not a real cloud metadata endpoint. If you include video, keep it 30–90 seconds, narrate the precondition, and caption each step.

### 25.7.4 Impact, Remediation, and References

**Impact.** Describe the realistic worst case and label what is proven versus inferred. A small table is persuasive:

| Capability gained | Prerequisite | Confidence |
|-------------------|--------------|------------|
| Read another user's order JSON | Valid low-priv token | Demonstrated in lab |
| Enumerate all order IDs | Sequential IDs | Inferred from sample |

Quantify using your own test tenant (e.g., "three seeded records accessible"), never real user counts. Avoid "total compromise" unless you can justify every link in the chain.

**Remediation.** Give a concrete root-cause fix with a snippet or config change, then defense in depth marked as such. Prefer centralized authorization, parameterized queries, allow-lists, and hardened parsers. Cite CWE and OWASP, and include a CVSS calculator link with your exact vector so triage can recompute.

**References.** List the CWE page, the relevant OWASP guide chapter, and the vector. Three high-quality links beat ten generic ones.

### 25.7.5 Writing for Triagers and Engineers

You write for two readers. The triager asks: valid? in scope? novel? severity? The engineer asks: how do I reproduce and fix it? Serve both with a three-part structure: TL;DR at top, body for triage, appendix for engineering detail (versions, raw traces, alternative payloads). Use consistent terminology — pick "BOLA/IDOR" and stick to it. Anticipate objections: if a reader might think "that's just informative," add one sentence explaining the crossed boundary. Keep the tone neutral; adjectives are noise.

> **Mastery signal:** a triager can reproduce your finding in under two minutes without asking a single clarifying question, and an engineer can implement your suggested fix without further research.

## 25.8 Mastery Deep Dive: CVSS 3.1 Worked Calculations

CVSS is a communication protocol, not a truth oracle. Programs layer business context on top of it. Mastery means computing a defensible base score, explaining temporal and environmental modifiers, and saying plainly where the model does not fit.

### 25.8.1 Base Metrics and the Subscores

The 3.1 base score derives from Exploitability and Impact. Exploitability = `8.22 × AV × AC × PR × UI`. Values: AV N/A/L/P = 0.85/0.62/0.55/0.2; AC L/H = 0.77/0.44; PR (scope unchanged) N/L/H = 0.85/0.62/0.27, (scope changed) 0.85/0.68/0.50; UI N/R = 0.85/0.62. Impact uses `ISCBase = 1 − (1−C)(1−I)(1−A)` with H/L/N = 0.56/0.22/0. Scope U: `Impact = 6.42 × ISCBase`. Scope C: `Impact = 7.52×(ISC−0.029) − 3.25×(ISC−0.02)^15`. Then `Base = Roundup(min(Exploit+Impact, 10))` for U, or `Roundup(min(1.08×(Exploit+Impact), 10))` for C.

**Worked IDOR (from Example 1):** `AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N`. Exploitability = 8.22×0.85×0.77×0.62×0.85 = 2.84. ISC = 0.56, Impact = 6.42×0.56 = 3.60. Sum = 6.44 → **6.5 (Medium)**. Now add demonstrated write access (`I:H`): ISC = 1−(0.44×0.44) = 0.8064, Impact = 5.18, sum = 8.02 → **8.1 (High)**. One extra impact metric moves the score — choose metrics from evidence, not aspiration.

### 25.8.2 Temporal and Environmental Metrics

Temporal metrics (E, RL, RC) capture current state: Exploit Code Maturity (X/H/F/P/U), Remediation Level (X/O/T/W/U), Report Confidence (X/C/R/U). Formula: `Roundup(Base × E × RL × RC)`. Environmental metrics (CR, IR, AR, MAV, MAC, MPR, MUI, MS) adjust for your context; use them when a program asks, otherwise leave X. A critical asset can raise a 6.5 to 7.4 with CR:H — but only with written justification. Always show the full vector so the score is reproducible.

### 25.8.3 Worked Example: Stored XSS With Changed Scope

Vector: `CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:C/C:L/I:L/A:N`.

- Exploitability = 8.22×0.85×0.77×0.85(PR:N)×0.62(UI:R) = 2.84
- ISC = 1−(0.78×0.78×1) = 0.3916; Scope-C Impact = 7.52×(0.3916−0.029) − negligible = 2.73
- Sum = 5.57 → ×1.08 = 6.01 → **6.1 (Medium)**

If the same flaw requires a logged-in low-privilege account, PR:L (scope C = 0.68) drops Exploitability to 2.27 and the score to **5.4**. Learn to show both so triage can pick the applicable precondition.

### 25.8.4 When CVSS Misleads

CVSS ignores business context, attack chains, and whether data is already public. State the limitation in one sentence and give triage the impact narrative. A 3.7 informational finding on an admin API can matter more than a 7.5 on a marketing page. Never argue severity from the number alone — argue from the crossed boundary and the evidence.

## 25.9 Mastery Deep Dive: CVSS 4.0 and What Changed

CVSS 4.0 reframes impact around the *vulnerable system* and the *subsequent system*, adds Attack Requirements, and separates base scoring from supplemental "threat" metrics.

### 25.9.1 New Metrics You Must Know

- **Attack Requirements (AT:N/P):** does the attack need preconditions beyond the vulnerable system's normal state?
- **Vulnerable System Impact (VC/VI/VA):** confidentiality/integrity/availability of the component with the flaw.
- **Subsequent System Impact (SC/SI/SA):** impact on systems that trust or consume the vulnerable one.
- **Supplemental (not in base score):** Safety (S), Automatable (AU), Recovery (R), Urgency (U).

### 25.9.2 Worked CVSS 4.0 Example

Vector: `CVSS:4.0/AV:N/AC:L/AT:N/PR:N/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:N` → **9.3 (Critical)**. Interpretation: network-reachable, low complexity, no special attack requirements, unauthenticated, no interaction, full impact on the vulnerable system, none downstream. If the compromised component feeds a downstream trust boundary (`SC:H/SI:H`), the score rises toward **10.0**. Always recompute with the official calculator and state which version you used.

### 25.9.3 CVSS 3.1 vs. 4.0

| Aspect | 3.1 | 4.0 |
|--------|-----|-----|
| Impact model | Single C/I/A triad | Split vulnerable + subsequent systems |
| Scope | S:U/S:C toggle | Replaced by AT + system split |
| Privileges/UI | Apply to vulnerable component | Re-read for subsequent context |
| Supplemental metrics | None in base | Safety, Automatable, Recovery, Urgency |
| Typical use | Still dominant in programs | Growing adoption; ask the program |

### 25.9.4 Choosing Which Version to Report

Use whatever the program requests. If unspecified, provide the version you computed and, for high-value findings, both scores. Never mix vectors from different versions in one report. Note that 4.0's supplemental metrics communicate urgency but do not change the base number — say so explicitly to avoid confusion.

## 25.10 Mastery Deep Dive: CWE Mapping and Severity Decision Trees

### 25.10.1 CWE Mapping Table

| Class | CWE | Root cause | Common mislabel |
|-------|-----|------------|-----------------|
| Reflected/stored XSS | 79 | Missing context-aware output encoding (116) | Calling all XSS "stored" |
| SQL injection | 89 | Query built from untrusted input | Confusing with 89's sibling 90 |
| BOLA/IDOR | 639 | Missing object-level authorization | Using 862 (function-level) |
| Missing function authz | 862 | Route lacks role check | Using 639 for object IDs |
| SSRF | 918 | Server fetches user-supplied URL | Calling it open redirect (601) |
| CSRF | 352 | No anti-CSRF token / SameSite | Confusing with 601 |
| Path traversal | 22 | Uncanonicalized file path | Using 23 (write) for reads |
| Insecure deserialization | 502 | Untrusted serialized data | Using 1321 prototype pollution |
| Mass assignment | 915 | Binding raw input to model | Calling it 639 |
| XXE | 611 | External entities enabled | Using 918 |
| Sensitive data exposure | 200 | Missing protection | Overused as a catch-all |
| Race condition | 362 | Non-atomic check-then-use | Mislabeling as logic flaw (840) |

### 25.10.2 Root Cause vs. Symptom

XSS is the symptom; missing output encoding (CWE-116) is often the root cause. Map to the class triage recognizes (79) while explaining the deeper cause in remediation. Same pattern: IDOR (639) is a symptom of a missing centralized authorization policy. A precise CWE helps triage route the ticket; a precise root-cause explanation helps engineering fix the whole class, not one endpoint.

### 25.10.3 Severity Decision Tree

```text
Is a security boundary crossed (authz, trust, data confidentiality)?
├─ No ────────────────────────────────> Informative / N/A
└─ Yes
   ├─ Unauthenticated or low-priv, no user interaction?
   │  └─ High/Critical if impact is broad (C/I/A on many objects)
   └─ Requires high priv or user interaction?
      ├─ Impact limited to one object / self ─> Low/Medium
      └─ Chains to scope change or other users ─> Medium/High
   ├─ Does it cross a trust boundary (tenant, role, origin)? ─> raise
   └─ Is impact only metadata with no secret value? ─> lower
```

Use the tree to *justify*, not to auto-assign. Record which branch you took in the report.

### 25.10.4 Impact Framing Without Real Data

State assumptions, count only your own records, and never claim real users were affected.

| Weak phrasing | Strong phrasing |
|---------------|-----------------|
| "All user data is exposed" | "In my lab tenant, three synthetic order records were readable via sequential IDs" |
| "Account takeover is trivial" | "With a valid low-priv token, another test account's session data was readable; takeover depends on session reuse" |
| "This is a critical 0day" | "Boundary crossed: object-level authorization; plausible impact is cross-user data disclosure" |

## 25.11 Mastery Deep Dive: Harmless PoCs and Evidence Hygiene

### 25.11.1 Designing Safe, Reproducible PoCs

Rules: test only in-scope assets; use accounts you own; seed synthetic data with unique markers; never perform destructive actions or persist artifacts beyond what is needed; respect rate limits; never involve real third parties. A safe PoC proves the *capability* without maximizing damage. Checklist:

- [ ] Marker values are unique strings you control (e.g., `LAB-7f3a`)
- [ ] No real user record, token, or PII appears
- [ ] No write/delete beyond a reversible lab change
- [ ] Requests stay within published rate limits
- [ ] Cleanup performed after evidence capture

### 25.11.2 Screenshot and Video Hygiene

Crop to the relevant panel; redact session cookies, CSRF tokens, Authorization headers, and any real-looking identifier. Blur incidental PII. Annotate with arrows and short captions that name the checkpoint. Keep raw evidence locally; submit only the sanitized copy. Never show a screenshot containing another real user's data — if one appears accidentally, discard and re-capture in a clean lab state.

### 25.11.3 Data Handling and Scope Discipline

Keep finding notes in an encrypted, access-controlled store. Delete test data at engagement end. Never copy production data into a report or a local tool. Keep a scope diary: policy URL, version, read timestamp, and any clarification received from the program. If a host turns out to be out of scope, stop immediately and purge anything collected from it.

### 25.11.4 Redaction Checklist

- [ ] Tokens, cookies, API keys, and passwords removed
- [ ] Real names, emails, phone numbers, addresses removed or blurred
- [ ] Internal hostnames/IPs replaced with lab aliases if sensitive
- [ ] URLs canonicalized to the in-scope asset name
- [ ] Timestamps retained (they help triage) but account IDs pseudonymized

## 25.12 Mastery Deep Dive: Triage Conversations and Disposition Outcomes

### 25.12.1 Duplicates, Informative, and Not Applicable

**Duplicate:** same root cause and asset already reported. Script: "Thanks — I see this maps to `#X`. Does my case add a distinct precondition or impact? If not, happy to close." **Informative:** no clear security boundary crossed. Script: "Understood. Could you share what evidence would establish impact here? I can test a second account / write path and resubmit if that is useful." **Not applicable:** asset or behavior excluded. Script: "Thanks for clarifying — I tested `asset` believing it matched `policy line`. I'll withdraw and keep it out of future sessions." Stay curious, never entitled.

### 25.12.2 Handling Severity Pushback With Scripts

> "I appreciate the review. My reasoning was `X` because `Y` (lab evidence). Would `Z` — for example, demonstrating write access with a second test account — change the assessment? Happy to provide it."

Avoid arguing from CVSS alone, never accuse triage of missing something, and do not escalate publicly. Ask what evidence would change the decision; either provide it or accept the outcome gracefully.

### 25.12.3 Disclosure Timeline and Coordination

| Phase | Typical window | Your action |
|-------|----------------|-------------|
| Submit | Day 0 | Send complete report, buffered evidence |
| Triage | Days 1–7 | Answer questions promptly, add evidence |
| Remediation | 30–90 days | Keep confidential; check in politely |
| Disclosure | Per program / ~90 days | Request written permission before publishing |

Honor embargoes. If a fix is delayed, ask for a status update rather than threatening disclosure. Coordinate on CVE assignment and publication date with the vendor.

### 25.12.4 Common Mistakes and What Mastery Looks Like

| Mistake | Consequence | Fix |
|---------|-------------|-----|
| Hype language | Credibility loss | Neutral, factual wording |
| Real data in PoC | Policy violation | Synthetic markers only |
| Vague steps | "Cannot reproduce" | Exact requests, checkpoints |
| Missing preconditions | Downgrade | Full precondition table |
| Arguing severity | Queue friction | Evidence-based follow-up |
| Early disclosure | Trust damage | Ask permission, honor embargo |

> **Mastery looks like:** accepted on first submission, reproduced by triage without questions, fixed at the root cause, and disclosed only with written coordination.

## 25.13 Mastery Deep Dive: Templates, Worked Example, and Knowledge Checks

### 25.13.1 Fill-in Report Template

```text
TITLE: <Class> on <asset> — <qualifier>
SUMMARY: <what / where / who / worst case; 2-4 sentences>
AFFECTED ASSET: <exact URL/endpoint> — scope line: "<quote>"
POLICY VERSION / DATE: <...>
CLASSIFICATION: CWE-<n>, suggested severity, CVSS <version> vector
PRECONDITIONS: accounts | roles | UI | lab data | tools
STEPS:
 1. <exact request> -> <observable checkpoint>
 2. ...
 3. ...
POC: <minimal request/response or marker artifact>
EXPECTED: <...>
ACTUAL: <...>
IMPACT: <proven vs inferred; own-tenant counts only>
REMEDIATION: <root-cause fix> ; defense-in-depth: <...>
EVIDENCE: <redacted screenshots/video, timestamps, test IDs>
REFERENCES: CWE | OWASP | CVSS calculator
DISCLOSURE: <program terms acknowledged>
```

### 25.13.2 Fully Worked Example

**Title:** BOLA in webhook test endpoint reveals another tenant's signing secret on `api.lab-saas.test`.

- **Classification:** CWE-639, High, `CVSS:4.0/AV:N/AC:L/AT:N/PR:L/UI:N/VC:H/VI:N/VA:N/SC:N/SI:N/SA:N` (~7.1).
- **Affected asset:** `api.lab-saas.test` — scope line: "*.lab-saas.test APIs are in scope."
- **Summary:** The webhook test endpoint accepts a tenant-supplied `webhookId` and returns the target's signing secret without checking ownership. An authenticated low-privilege user can read another tenant's secret, enabling forged webhook events against that tenant.
- **Preconditions:** Two lab tenants A and B; low-priv token for A; synthetic secret `LAB-SECRET-B-9c2`.
- **Steps:** 1. As A, `POST /api/webhooks/test {"webhookId":"wb-A"}`, note A's secret. 2. Using A's token, `POST /api/webhooks/test {"webhookId":"wb-B"}`. 3. Observe `LAB-SECRET-B-9c2` returned.
- **Expected:** 403 for a webhook A does not own. **Actual:** 200 with B's secret.
- **Impact:** Proven: cross-tenant secret disclosure for seeded markers. Inferred: forged signed events if the secret is reused in production.
- **Remediation:** Query `WHERE id=? AND tenant_id=current_tenant`; centralize object-level authorization; rotate exposed secrets.
- **Evidence:** Two redacted responses, UTC timestamps, pseudonymized test IDs.
- **Triage note:** Valid. Only synthetic markers accessed; no real tenant data.

### 25.13.3 Common Report Mistakes

Forgotten scope quote; severity in title; real-looking data; steps that skip auth setup; no expected/actual contrast; remediation that is only a WAF rule; missing version numbers; no disclosure acknowledgement. Each maps to a checklist item above — the template exists to make omission obvious.

### 25.13.4 Knowledge Checks With Answers

1. **Q:** Why avoid severity words in the title? **A:** Severity is the program's decision; self-labelling invites bias and conflicts if downgraded.
2. **Q:** Which CWE for a function-level missing role check? **A:** CWE-862, not 639 (which is object-level).
3. **Q:** Compute the base score for `AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N`. **A:** 6.5 (Medium).
4. **Q:** What does `S:C` do in CVSS 3.1? **A:** Applies the 1.08 multiplier and the scope-C impact formula.
5. **Q:** Name two CVSS 4.0 supplemental metrics. **A:** Safety, Automatable, Recovery, Urgency (any two).
6. **Q:** What should a harmless XSS PoC use? **A:** A unique harmless marker string in your own account, not a real cookie stealer.
7. **Q:** How do you handle a duplicate professionally? **A:** Ask whether your case adds distinct evidence, then accept gracefully.
8. **Q:** When may you publish? **A:** Only after written permission per the program's terms/embargo.

## 25.14 Mastery Deep Dive: Advanced Scoring and Triage Edge Cases

The fundamentals cover ordinary findings. Masters handle the awkward ones: environment-specific scores, chains, and reports that need a second pass before submission.

### 25.14.1 Environmental Scoring Worked Example

Environmental metrics let you score against a *specific* deployment, not an abstract one. Take the IDOR from 25.8 (base 6.5) and suppose your authorized lab host demonstrably holds high-value records: set CR:H (1.5), IR:H (1.5), AR:X (1.0). Confidentiality becomes `min(0.56×1.5, 1) = 0.84`; integrity becomes `0.84`. ISC = `1 − (1−0.84)(1−0.84) = 0.9744`; Impact = `6.42×0.9744 = 6.26`; sum with exploitability 2.84 = 9.1 → **9.2**. This number is only defensible if you can show the data is high-value — otherwise leave CR/IR at X. MAV/MAC/MPR/MUI adjust exploitability: if the lab host is reachable only from an internal network, `MAV:A` lowers the score. Always show modified vectors explicitly.

### 25.14.2 Chained Vulnerabilities and Score Caps

CVSS scores one weakness at a time. A chain — open redirect (4.7) plus a token placed in a URL — enables session theft, but you should report both findings and describe the chain in the higher finding's impact, not inflate one vector to cover both. Never "borrow" impact from a second bug to raise a score. If two issues share a root cause and cannot be separated, say so explicitly in the report title ("chain inseparable because..."). Triagers dislike both artificially split reports and artificially merged ones; explain your choice.

### 25.14.3 Report Review and Self-Critique Rubric

Before submitting, score your own draft out of 12:

| Criterion (0/1/2) | Question |
|-------------------|----------|
| Title | Class + asset + qualifier, no hype? |
| Summary | Understandable standalone? |
| Scope | Exact policy line quoted? |
| Preconditions | Complete and honest? |
| Steps | Copy-pasteable with checkpoints? |
| PoC | Minimal, harmless, unique marker? |
| Impact | Proven vs inferred separated? |
| Remediation | Root cause, not just WAF rule? |
| CVSS/CWE | Versioned vector, precise CWE? |
| Evidence | Redacted, timestamps present? |
| Disclosure | Program terms acknowledged? |
| Tone | Neutral, no adjectives? |

A score below 10 means revise. If any criterion is 0, the report will likely get a "cannot reproduce" or "informative" reply.

### 25.14.4 Knowledge Checks II (Advanced)

1. **Q:** When are environmental metrics appropriate? **A:** When a specific deployment's data value or reachability is demonstrated; otherwise leave X.
2. **Q:** Why not merge two bugs into one inflated vector? **A:** CVSS models a single weakness; merging hides root causes and misleads prioritization.
3. **Q:** What does `MAV:A` change? **A:** Modified attack vector becomes adjacent, reducing exploitability.
4. **Q:** Which self-rubric score should block submission? **A:** Below 10/12, or any 0 on scope, steps, or PoC safety.
5. **Q:** How should you describe a chain? **A:** Report each finding, then narrate the combined impact in one report without borrowing metrics.

## 25.5 Key Takeaways

- Structure reports for fast verification.
- Demonstrate impact with your own accounts and synthetic data.
- Map CWE/CVSS carefully but prioritize clear impact description.
- Treat triage as a professional collaboration.
