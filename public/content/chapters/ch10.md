# Chapter 10: Advanced Web Exploitation Concepts

> **Learning objectives.** Reason about multi-step attack chains; analyze authentication, authorization, and business logic deeply; understand desync, cache, race, prototype-pollution, OAuth/JWT, WebSocket, GraphQL, and multi-tenant failure modes; and document complex findings.

## 10.1 Thinking in Chains

Simple vulnerabilities are found by testing one parameter. Advanced research asks: *what can I combine?* A chain links individually low-severity issues into a high-impact outcome:

```
Open redirect -> OAuth token leakage -> account takeover
XXE -> SSRF -> internal admin endpoint -> secret disclosure
XSS -> CSRF bypass -> state change -> privilege escalation
Race condition -> coupon reuse -> financial loss
```

Chains often cross boundaries between components, which is why they are missed by scanners that test one endpoint at a time. To reason about chains, map **trust**, **state**, and **capabilities**:

- What can each component observe or influence?
- What state persists across requests (sessions, cache, DB)?
- What capability does each finding grant (read, write, execute, identity)?

## 10.2 Authentication Bypass Research

Areas to investigate in authorized targets:

- **Credential handling:** rate limits, lockout, timing differences (user enumeration), password reset flows, token entropy and expiry.
- **Logic paths:** login with unexpected content types, duplicate JSON keys, array-vs-string type juggling (`{"user":["admin"]}`), parameter pollution (`?user=a&user=admin`).
- **MFA:** can it be skipped by altering a response, reusing a code, or accessing a "trusted" device endpoint directly?
- **Session lifecycle:** fixation, rotation on login/privilege change, invalidation on logout/password change.
- **OAuth/OIDC:** state/PKCE validation, redirect_uri matching, token validation.

A key principle: **enforcement must be server-side and on every path.** A check that exists only in the browser or only on the primary login route is not a control.

## 10.3 Authorization Logic Analysis

Build a matrix of roles × actions × objects:

| Role | Read own | Read others | Update own | Admin function |
|------|----------|-------------|------------|----------------|
| anon | no | no | no | no |
| user | yes | no | yes | no |
| admin | yes | yes | yes | yes |

Test every cell with a controlled account. Pay special attention to:

- Endpoints that accept a role or tenant parameter from the client.
- Bulk operations and export endpoints (often forgotten).
- Differences between REST and GraphQL paths to the same data.
- "Internal" endpoints protected only by network position.

## 10.4 Desync and Request Smuggling Theory

Modern stacks mix HTTP/1.1 and HTTP/2, TLS terminators, and multiple proxies. Desynchronization arises when components parse the same byte stream differently. Beyond CL.TE/TE.CL (Chapter 9), advanced variants include:

- **CL.0 / desync:** a front-end treats a request as ended by Content-Length while the back-end keeps the connection open.
- **HTTP/2 → HTTP/1.1 downgrade smuggling:** header translation differences (e.g., how `:authority`, `content-length`, or `transfer-encoding` are converted).
- **Header name/value confusion:** duplicated headers, whitespace, or line-folding differences.

Safe validation requires dedicated labs (PortSwigger's smuggling labs) with harmless marker prefixes, controlled timing, and absolutely no production targets. The impact — hijacking other users' requests or bypassing front-end security controls — makes this a high-severity research area, but also one where accidental harm is easy. Stay in the lab.

## 10.5 Cache Behavior Analysis

To analyze caching:

1. Identify cacheable responses via `Cache-Control`, `Age`, `X-Cache`, `CF-Cache-Status`.
2. Determine the cache key (URL path, query, headers, cookies).
3. Find inputs that influence the response but are not in the key.
4. Test in your own lab whether a crafted header changes a cached response for a normal visitor.

The classic pattern: a response reflects `X-Forwarded-Host` into a script URL, and the cache ignores that header. Poison the cache once; every visitor receives the malicious response. Defenses: include influential headers in the key, strip untrusted headers at the edge, and avoid reflecting headers into responses.

## 10.6 Race Condition Research

Advanced race research uses synchronization to widen the timing window:

- Send many requests in parallel with a barrier (e.g., threads released simultaneously).
- Use HTTP/2 single-packet attacks to reduce network jitter.
- Look for TOCTOU between check and use: coupon redemption, balance checks, one-time tokens, file operations, invite acceptance.

A robust lab demonstration shows a state that should be impossible (e.g., a coupon used three times). Remediation is atomicity: database transactions with row locks, idempotency keys, and unique constraints.

## 10.7 Prototype Pollution Deep Dive

Sources: `JSON.parse` merged via recursive `merge`, `Object.assign`, query-string parsers, and libraries with unsafe deep-merge.

Gadgets: after polluting `Object.prototype`, downstream code that checks `obj.isAdmin` or iterates properties can behave unexpectedly. Real chains are highly application-specific.

Investigation in a lab:

```javascript
JSON.parse('{"__proto__":{"polluted":"yes"}}') // creates own __proto__ key in JSON.parse
// then a vulnerable deep-merge copies it into Object.prototype
console.log({}.polluted) // "yes" if pollution occurred
```

Remediation: reject `__proto__`, `constructor`, `prototype` keys; use `Object.create(null)`; use `Map`; freeze prototypes; validate with schema libraries.

## 10.8 Advanced SSRF

Bypass techniques studied in labs include:

- Alternative IP formats: decimal (`2130706433` = 127.0.0.1), octal, IPv6 mapped (`::ffff:127.0.0.1`).
- DNS rebinding: a hostname resolves to a public IP during validation and a private IP at fetch time.
- Open redirects and URL parsing quirks to bypass allow-lists (`http://allowed.com@127.0.0.1/`).
- Non-HTTP protocols (`gopher://`, `file://`, `dict://`) where supported.
- Redirect chains where validation occurs only on the first hop.

Defense-in-depth: resolve DNS and pin the validated IP, block private/link-local/loopback ranges (IPv4 and IPv6), disable redirects, enforce egress firewalling, and require IMDSv2 on cloud instances.

## 10.9 OAuth and JWT Implementation Flaws

OAuth pitfalls: missing `state`, absent PKCE for public clients, loose `redirect_uri` matching (prefix/suffix bypass), token leakage via referrers or browser history, and accepting tokens from the wrong issuer.

JWT pitfalls: `alg:none`, RS256→HS256 confusion, weak HMAC secrets, accepting tokens with missing/expired `exp`, ignoring `aud`/`iss`, and confusing "decoded" with "verified."

In a lab, demonstrate a measurable impact (e.g., forging a token for another test user). Never attack real authentication systems.

## 10.10 WebSocket and GraphQL Security

**WebSockets:** the server must validate `Origin` (browsers do not enforce SOP for WebSockets); messages need authentication, authorization, size limits, and rate limits. Test in labs for CSWSH (cross-site WebSocket hijacking) and missing per-message authorization.

**GraphQL:** introspection disclosure, excessive query depth/complexity (DoS), resolver-level authorization gaps, batching attacks that evade rate limits, and mutations that bypass REST checks. Test every resolver with a second test account; use complexity limits and persisted queries as defenses.

## 10.11 Multi-Tenant Isolation Failures

SaaS applications must isolate tenants at every layer: database rows, object storage prefixes, cache keys, search indices, logs, and background jobs. Failures include:

- Missing tenant filter in a query.
- Cache keyed only by object ID, not tenant ID.
- File paths using predictable tenant-unique names.
- Async jobs that trust a tenant ID from the message payload.

These are high-severity because they expose multiple customers' data. Test only with your own two tenants in an authorized program.

## 10.12 Chained Case Study (Fictional)

A lab application has three issues:

1. A profile field reflects user input into a page without encoding (XSS) but the session cookie is HttpOnly.
2. A password-reset flow uses a predictable token and no rate limit.
3. The password-reset endpoint trusts a `Host` header to build the reset link.

Individually: XSS (limited by HttpOnly), weak token (low if rate-limited?), Host injection (low). Chained: XSS in a victim's session reads a CSRF token, triggers a password reset with a poisoned Host so the link points to the attacker's server, and the weak token is brute-forced — producing account takeover. The chain demonstrates why impact assessment must consider downstream capabilities, not just the isolated bug.

## 10.13 Reporting Complex Chains

- Describe each link clearly and the capability it grants.
- Provide a step-by-step PoC with exact requests.
- Show the final impact with your own test accounts.
- Map each link to CWE where applicable.
- Note prerequisites (e.g., victim interaction) honestly.

## 10.14 Key Takeaways

- Advanced research is about chaining capabilities and questioning component boundaries.
- Desync, caching, races, and prototype pollution arise from subtle implementation details.
- OAuth/JWT/GraphQL/WebSocket security depends on rigorous validation at each step.
- Multi-tenant isolation must be verified at every layer with controlled test tenants.
