# Chapter 15: Manual Bug Hunting Methodology

> **Learning objectives.** Follow a professional end-to-end testing workflow; map architecture, roles, requests, trust boundaries, and authorization checks; prioritize high-value testing; and learn from a detailed fictional case study.

## 15.1 The Professional Loop

```
Read policy -> Map app -> Create accounts -> Capture traffic
   -> Identify trust boundaries -> Test hypotheses -> Validate safely
   -> Assess impact -> Write report -> Submit -> Learn
```

Tools accelerate this loop, but the thinking is manual. A researcher who only runs scanners finds what everyone finds.

## 15.2 Reading the Program and Application

Before touching a request:

- Read the scope and rules (Chapter 13).
- Understand the product: what does it do, who are its users, what data is sensitive?
- Identify roles: anonymous, free user, paid user, admin, partner, service account.
- Read public documentation and help pages — they reveal intended behavior.

## 15.3 Mapping the Application

Create a map with:

- **Assets:** web app, API, mobile, subdomains.
- **Workflows:** registration, login, password reset, checkout, sharing, admin.
- **Endpoints:** method, path, parameters, auth required.
- **Data model:** users, objects, relationships, roles.
- **Trust boundaries:** where data crosses from client to server, service to service.

Use Burp Suite / OWASP ZAP to capture every request in a lab or authorized target. Organize the site map and annotate each request's purpose.

## 15.4 Test Accounts and Roles

Create the minimum accounts needed (typically 2--3): user A, user B, and if possible a privileged account in your own lab. Keep credentials in your journal. Label all data you create with a marker (e.g., `TEST-A-2026`).

## 15.5 Capturing and Understanding Requests

For each workflow, record:

```
Method, path, query params, headers, cookies, body
Expected behavior
What is authenticated vs. unauthenticated
Which parameters influence server state
```

Pay attention to hidden fields, client-side validation, and values that come from the server but are echoed back by the client (e.g., price, user ID, role).

## 15.6 Identifying Trust Boundaries

Ask where the server trusts the client:

- Does it trust a `user_id` in the request to decide whose data to show?
- Does it trust a price computed by the browser?
- Does it trust `Origin`/`Host`/forwarded headers?
- Does it trust that multi-step flows happen in order?

Each trust assumption is a hypothesis to test safely in scope.

## 15.7 Mapping Authorization Checks

Build a role × action matrix (Chapter 10). For each endpoint:

1. Call it unauthenticated — should fail.
2. Call as user A on user A's object — should succeed.
3. Call as user A on user B's object — must fail.
4. Call as user A on an admin function — must fail.

Any deviation is a candidate finding. Compare HTTP status, response body, and side effects.

## 15.8 Parameter Investigation

For each parameter, classify its role: identifier, filter, state, content, redirect target, file path, command fragment, price, role. Then:

- Change its type (string → array/number/null).
- Remove it entirely.
- Duplicate it (HTTP parameter pollution).
- Try values from your other accounts.
- Observe error messages and timing.

## 15.9 Comparing Roles and API Responses

APIs often return more data than the UI displays. Compare:

- REST response vs. GraphQL response vs. mobile app response.
- List endpoint vs. detail endpoint.
- Export/bulk endpoints (frequently missing authorization).

## 15.10 Edge Cases and Business Logic

Test:

- Empty, very long, unicode, and encoded inputs.
- Negative numbers, zero, decimal values, extreme values.
- Repeated, out-of-order, and skipped steps.
- Reusing one-time tokens.
- Concurrent requests (in labs).
- Currencies, quantities, and discounts.

## 15.11 Prioritizing Testing

Prioritize by likely impact and likelihood:

1. Authorization on object references and admin functions.
2. Authentication and session handling.
3. File upload, URL fetch, and command execution features.
4. Business logic involving money or privileges.
5. Injection sinks with reflected input.
6. Client-side sinks (XSS) and redirect targets.

Avoid repetitive low-value testing (version banners, missing headers without impact, generic 404s). Depth beats breadth.

## 15.12 End-to-End Fictional Case Study

**Scenario:** "ShopLab," a fictional authorized program, has a web app and REST API. Researcher Priya creates two accounts (A and B) with test markers.

**Step 1 — Policy.** Scope includes `*.shoplab.example` and the API; excludes `support.shoplab.example`. No DoS, no data access beyond test accounts.

**Step 2 — Mapping.** Priya captures login, product listing, cart, checkout, and order history. She notices `GET /api/orders/{id}` and `POST /api/cart/apply-coupon`.

**Step 3 — Authorization test.** Using account A's token, she requests order ID belonging to account B (ID learned from her own B account). The response returns B's order details — **BOLA/IDOR** (valid, medium/high).

**Step 4 — Business logic.** She applies a coupon code and observes the discount computed server-side. Sending quantity `-1` produces a negative total — **business logic flaw** (valid, high).

**Step 5 — Auth flow.** Password reset sends a token; repeated requests use tokens that do not expire quickly and lack rate limiting in the lab environment, enabling brute force (valid, medium).

**Step 6 — Chain.** She demonstrates that a crafted reset link with a poisoned Host header (from a separate observation) would point to an attacker-controlled host — but the program excludes Host-header issues as informative, so she notes it as supporting context rather than a separate report.

**Step 7 — Validation.** All tests use her own two accounts and synthetic data. She stops when she sees a field containing another real user's name in a response and does not access it further.

**Step 8 — Reporting.** She writes three separate reports: BOLA, negative-quantity logic flaw, and weak password-reset tokens. Each has clear steps, PoC requests, impact, and remediation.

**Lessons:** systematic mapping found three issues; scope knowledge prevented an out-of-scope report; discipline with data kept the work ethical.

## 15.13 Building a Personal Methodology

Over time, codify your approach:

- A standard recon checklist.
- A standard test-account setup.
- A per-endpoint test matrix.
- A journal template (Chapter 29 and handbook).
- A report template.

Consistency makes results reproducible and speeds up each engagement.

## 15.16 Mastery Deep Dive: The Repeatable Manual Testing Loop

> **Authorization boundary.** Everything in this deep dive assumes an owned application, a local lab, or an explicitly in-scope program asset. Use only your own synthetic accounts and data. Never test real user accounts, never perform destructive actions, and stop if you encounter real user data.

### 15.16.1 The Loop as a State Machine

Elite testing is not a checklist you run once; it is a loop you can re-enter deliberately. Treat each endpoint as a small state machine:

```text
OBSERVE  ->  MODEL  ->  HYPOTHESIZE  ->  TEST  ->  INTERPRET  ->  DECIDE
  ^                                                                  |
  |__________________________________________________________________|
                    (new information feeds the next cycle)

OBSERVE    capture the request/response and its context
MODEL      decide what the endpoint does, who may call it, what it trusts
HYPOTHESIZE write a falsifiable statement: "if X, then boundary Y is broken"
TEST       change ONE variable; keep everything else fixed
INTERPRET  compare against baseline; explain the difference mechanistically
DECIDE     promote to finding, refine hypothesis, or close and move on
```

The discipline is in **changing one variable at a time**. If you change the method, the parameter, and the cookie simultaneously, a difference tells you nothing. Mastery is the ability to say "this single change caused this single response difference, therefore the server behaves this way."

**Common mistake.** Treating a scanner finding as the start of the loop. A scanner output is an *observation*; it still needs modeling, a hypothesis, and manual validation before it becomes a candidate.

### 15.16.2 Threat Modeling a Target

Before testing a request, build a small threat model. It converts a pile of endpoints into a set of priorities.

```markdown
# Mini Threat Model Template

Application / in-scope asset:
Purpose (what business process does it support?):
Actors: anonymous, free user, paid user, partner, admin, service account
Assets: accounts, orders, messages, files, tokens, configuration
Trust boundaries:
  1. Client -> server (HTTP parameters, headers)
  2. Service -> service (internal APIs, webhooks)
  3. User -> user (sharing, collaboration, messaging)
  4. Admin -> user (support tools, moderation)
  5. Third party -> app (OAuth callbacks, payments)
Most sensitive asset:
Most likely weakness (based on architecture):
Out-of-scope assumptions from the policy:
```

**Worked example (fictional "ShopLab" lab app).** The actors are anonymous browsers, registered buyers, and a lab admin. Assets include carts, orders, coupon state, and session tokens. The critical trust boundaries are client-to-server (quantity and price fields), user-to-user (order IDs), and third-party-to-app (payment callback). The most sensitive asset is order data; the most likely weakness is trusting client-supplied object IDs. This model predicts that `GET /api/orders/{id}` is the first endpoint to test — which is exactly where a systematic tester finds the IDOR.

Threat modeling also tells you what *not* to spend time on: a static marketing page with no state and no sensitive data has a thin threat model and low expected value, even though it is in scope.

### 15.16.3 Trust-Boundary Mapping

A trust boundary is a place where data crosses from one authority domain to another. Each boundary generates test ideas:

| Boundary | Question to ask | Safe test idea (own accounts / lab) |
| — | — | — |
| Client to server | Does the server trust client-supplied identifiers? | Request your second account's object using your first account's token |
| Client to server | Does the server trust client-computed values? | Change quantity/price in a copy of your own cart request |
| User to user | Can one user's action affect another's state? | Share a resource to your own second account and inspect what is exposed |
| Service to service | Are internal calls authenticated? | In the lab, call an internal endpoint directly; observe whether it trusts headers |
| Third party to app | Is a callback verified? | In the lab, replay a callback with altered parameters |
| Admin to user | Are privileged actions restricted by role? | Call an admin route with a normal user token (own accounts) |
| Header trust | Are `Host`, `Origin`, or forwarded headers trusted? | Note as hypothesis; only test if the program permits such issues |

Each row is a *hypothesis generator*, not a conclusion. The map keeps your testing systematic rather than random.

### 15.16.4 The Hypothesis Ledger

Write hypotheses before testing and record the outcome. This is the single habit that most separates advanced researchers from intermediates.

```markdown
| ID | Endpoint | Hypothesis (falsifiable) | Prior | Test performed | Result | Conclusion |
| — | — | — | — | — | — | — |
| H1 | GET /api/orders/{id} | Server uses client id without ownership check | high | A's token + B's id | B's order returned | Confirmed BOLA |
| H2 | POST /api/cart/apply-coupon | Server trusts client quantity sign | medium | quantity=-1 | Negative total | Confirmed logic flaw |
| H3 | /search?q= | Reflection is unencoded in HTML context | low | marker string | Encoded | Rejected; keep as context |
```

**Why priors matter.** Recording `high`, `medium`, or `low` before the test prevents hindsight bias. After ten engagements you can check: were your "high" hypotheses confirmed more often than "low"? If not, your intuition needs recalibration, and the ledger shows you exactly where.

### 15.16.5 Timeboxing and When to Move On

Time is the only non-renewable resource in testing. Use explicit boxes and stop rules.

```text
Per-endpoint box:   10-20 minutes for first-pass modeling and key hypotheses
Per-hypothesis box: 2-3 focused tests, then re-evaluate
Per-asset box:      one deep session, then reassess priority score

Move on when:
  - Three distinct hypotheses on the endpoint are rejected -> low yield
  - A finding is confirmed -> document it now, then continue
  - You are repeating the same test with different payloads -> loop detected
  - Duplicate rate on the asset spikes -> likely saturated
  - You feel the urge to bend a scope or safety rule -> stop immediately
```

A "loop detected" signal is important: if you have tried twenty XSS payloads with no change in behavior, the issue is probably your model of the output context, not your payload list. Go back to OBSERVE and inspect where the input actually lands.

## 15.17 Mastery Deep Dive: The Per-Class Test Matrix

### 15.17.1 Building the Matrix

A test matrix crosses **roles**, **actions**, and **representations**. It turns "test authorization" into a concrete grid you can complete.

| Dimension | Values to include |
| — | — |
| Roles | anonymous, user A, user B, privileged/lab admin, service token |
| Actions | read, create, update, delete, export, bulk operations, admin actions |
| Object IDs | your own, your second account's, nonexistent, malformed |
| Representations | web UI, REST API, GraphQL, mobile client, export/bulk endpoint |
| States | fresh token, expired token, logged-out, after password change |

For every cell, ask: "What *should* happen?" Then test the one case that violates the expectation. The matrix is a coverage instrument; it prevents the common failure of testing only the happy path.

### 15.17.2 Authentication and Authorization Workflow

This is the highest-value area for human researchers. Work in this order, using only your own accounts:

```text
Step 1  Establish baselines.
        - Capture a request as anonymous, as user A, and as user B.
        - Record status codes and response bodies for allowed and denied cases.

Step 2  Test authentication boundaries.
        - Call an authenticated endpoint with no token -> must fail.
        - Call with a malformed/expired token -> must fail.
        - After logout, replay the old token -> must fail (if policy permits testing).

Step 3  Test object-level authorization (BOLA/IDOR).
        - Learn your own object IDs from your own accounts only.
        - Call endpoint with A's token and B's object ID -> must fail.
        - Compare A-on-A (success) with A-on-B (must fail) in Comparer.

Step 4  Test function-level authorization (BFLA).
        - Call admin/export/bulk routes with a normal user token -> must fail.
        - Check whether the UI hides a route that the API still allows.

Step 5  Test privilege and role transitions.
        - Try to set your own role field to admin in a copy of your request.
        - Check mass assignment: add fields the UI does not expose.

Step 6  Test representation inconsistencies.
        - Compare REST detail, GraphQL query, and export responses for the same object.

Step 7  Document the minimal boundary violation.
        - One object, one field, synthetic data, own accounts, clear status diff.
```

**Safe PoC principle.** To prove an authorization flaw, reading *one* synthetic object belonging to your second account is sufficient. Dumping a list, iterating IDs, or touching real accounts is not necessary and likely violates the program's data rules.

**Annotated example (lab):**

```http
GET /api/orders/1042 HTTP/1.1
Host: app.example-lab.test
Authorization: Bearer <A-TOKEN>
```

Response returns order `1042` belonging to your account B. Baseline `GET /api/orders/1041` with A's token returned A's own order with `200`. The single changed variable is the ID. Conclusion: object-level authorization is missing. Record the two responses as evidence with the marker values visible.

### 15.17.3 Parameter and Input Analysis

For each parameter, classify its role, then apply a small, fixed set of transformations.

| Parameter role | Example | Transformations to try (own accounts / lab) |
| — | — | — |
| Identifier | `id`, `user_id`, `order_id` | Swap with your other account's ID; nonexistent value; malformed type |
| Filter | `status`, `role`, `type` | Unexpected enum values; empty; array instead of string |
| State | `step`, `stage`, `approved` | Skip or repeat a step; set final state directly |
| Content | `message`, `name` | Marker string to observe reflection context; encoding variants |
| Redirect target | `next`, `return_to` | Alternative in-scope URL; external URL (report, do not chain to real users) |
| File path | `file`, `path`, `template` | In-scope relative paths; traversal indicators in the lab |
| Price / quantity | `price`, `qty`, `discount` | Zero, negative, decimal, extreme values in your own cart |
| Role / permission | `role`, `is_admin` | Elevation attempt on your own account only |
| Token | `token`, `nonce` | Reuse after use; expiry observation; never brute force real tokens |

**Type confusion and parameter pollution:** change a string to an array (`?id[]=1`), send `null`, duplicate a parameter (`?role=user&role=admin`), and remove the parameter entirely. Each tests a different assumption about how the server parses input. Note the response difference; do not assume the first framework's behavior.

### 15.17.4 Business-Logic Testing

Business logic flaws are invisible to scanners because they require understanding *intended* behavior. Model the workflow as a state machine:

```text
cart created -> item added -> coupon applied -> address set -> payment -> order created
```

Then test transitions:

- **Skipping steps:** jump directly to a later state in the lab or with your own cart.
- **Replaying steps:** apply the same coupon twice; reuse a one-time token.
- **Reversing steps:** cancel after payment; modify a cart after checkout.
- **Negative and extreme values:** quantity `-1`, price `0`, discount greater than total.
- **Concurrency (lab only):** send two simultaneous requests to observe race behavior; never do this against production without explicit approval.
- **Currency and rounding:** fractional values and currency mismatches in your own test transactions.
- **Trust in client-computed totals:** change the total in a copy of your request and observe whether the server recalculates.

**Impact framing.** A negative quantity that produces a negative total is interesting; a negative total that is actually accepted by the order workflow and could be exploited at scale is a material business-logic finding. Test the *downstream effect* within your own account before claiming impact, and state clearly what you did and did not verify.

### 15.17.5 Vulnerability-Class Quick Matrix

| Class | Where to look | Minimal safe PoC | Common false positives |
| — | — | — | — |
| BOLA / IDOR | Object IDs in paths/params | Read one synthetic object from your second account | IDs that are public by design |
| BFLA | Admin/export routes | Call privileged route with normal user token | Route that merely hides UI but enforces server-side |
| Broken auth | Tokens, reset flows | Replay expired token; reuse reset token in lab | Logout that is client-side only but server-enforced |
| Reflected/stored XSS | Reflection points | Harmless marker like `TEST-<id>` showing unencoded output | Self-only reflection; browser auto-escaping |
| SQL injection | Query params, filters | Boolean/error-based observation with benign markers in lab | Generic error pages; WAF blocks without proof |
| SSRF | URL-fetch features | Point to an in-scope/internal lab endpoint or your Collaborator | DNS resolution without a real request; allowlisted destinations |
| File upload | Upload forms | Upload a benign marker file; observe storage and content type | Filename reflection without execution |
| Open redirect | `next`, `return_to` | Redirect to an in-scope alternative URL | Allowed internal redirects |
| CSRF | State-changing GET/POST | Lab demonstration with missing token on own account | SameSite cookies preventing real exploitation |
| Missing rate limit | Login, OTP, reset | Low-volume observation in lab/authorized test account | Theoretical brute force without evidence |
| Sensitive exposure | APIs, exports | Show extra field returned for your own account | Data that is intentionally public |
| Mass assignment | JSON bodies | Add an unexpected field to your own request | Field ignored by server |

## 15.18 Mastery Deep Dive: Toolcraft and Evidence Standards

### 15.18.1 Burp Proxy Discipline

Configure Burp before you begin:

```text
[ ] Target scope set to the exact in-scope hosts (no broad wildcard).
[ ] "And URL Is in Target Scope" filter enabled in Proxy/HTTP history.
[ ] Intercept off by default; turn on only for specific requests.
[ ] History annotated with workflow names (login, checkout, admin).
[ ] A dedicated browser profile used only for this engagement.
[ ] Test accounts logged in with clear labels (A / B / admin-lab).
```

A clean history is a testing asset. Annotate requests as you go; an unannotated history of 2,000 requests is unusable after a day. Use Burp's notes/highlights or an external ledger keyed by request number.

### 15.18.2 Repeater for Differential Testing

Repeater is where hypotheses are tested. The pattern:

1. Send a baseline request as user A on A's object; note status, length, body.
2. Copy to a second tab; change exactly one variable (B's object ID).
3. Compare responses: status, length, and a distinctive body field.
4. Repeat with A's token removed to distinguish authentication from authorization failures.
5. Save the final pair to your evidence bundle.

**Interpretation trap.** A `403` might mean correct authorization enforcement, a WAF, or a missing header. Always check the response body and headers; compare against a known-denied baseline rather than assuming.

### 15.18.3 Intruder With Restraint

Intruder is powerful and easy to misuse. Rules for professional use:

- Use it only for small, controlled sets (a handful of values from your own accounts or a short wordlist).
- Set a request throttle or delay; never maximize threads on a production target.
- Prefer a small custom list over a huge generic list; volume adds noise, not insight.
- Log the exact payload set in your journal for reproducibility.
- For large or long-running tasks, prefer a lab environment and get program approval for anything else.

Typical safe use: testing a small set of HTTP methods, a few parameter-name variations, or your own object IDs across an endpoint. Unsafe use: brute-forcing real credentials, enumerating thousands of IDs, or fuzzing with destructive payloads.

### 15.18.4 Comparer for Response Differences

Comparer turns "the responses look different" into evidence. Use it for:

- A's object vs. B's object (authorization).
- Success vs. failure responses (what distinguishes a valid token).
- Responses before and after a single parameter change.
- Timing observations (with caution; network jitter is noisy).

When presenting evidence, a two-panel diff with the changed field highlighted is far more persuasive than a prose claim that "the response was different."

### 15.18.5 Collaborator for Out-of-Interaction Detection

Burp Collaborator (or an equivalent authorized OOB service) detects interactions such as DNS lookups or HTTP callbacks triggered by a feature like URL fetching or webhook processing.

**Safe use (lab or authorized in-scope only):**

1. Generate a unique Collaborator payload.
2. Place it in the parameter under test (e.g., a URL field in your own account's request).
3. Watch for DNS/HTTP interactions and record timestamps.
4. Interpret: a DNS lookup alone proves the server resolved the domain; an HTTP request proves it fetched it. Distinguish the two carefully.
5. Never use Collaborator to exfiltrate data or target third-party systems.

**Common false positive.** Some mail/security scanners resolve links automatically, producing interactions unrelated to the vulnerability. Correlate the interaction timestamp with your exact request and repeat once to confirm.

### 15.18.6 Evidence Capture Standards

A finding is only as good as its evidence. Capture, per finding:

```markdown
# Evidence Bundle Template

Finding ID / title:
Authorized scope reference (policy URL + date):
Date/time and timezone:
Test accounts used (labels only):
Markers used (e.g., TEST-A-2026):
Affected endpoint (method + path + host):
Baseline request and response (raw, redacted):
Modified request and response (raw, redacted):
Single variable changed:
Observed difference (status, length, body field):
Screenshot filenames (local paths):
Tool/version and exact command or Burp module used:
Data-safety statement: "Only synthetic data and own accounts used;
  no real user data accessed."
Reproduction steps (numbered, no creativity required):
```

**Redaction rules:** mask session tokens and real personal data; keep synthetic markers visible. Do not paste raw production tokens into a report. Store evidence locally with restricted access and delete it when retention is no longer needed.

**Chain of custody:** record when each artifact was captured and by which tool. If you modify a screenshot, keep the original. This is not bureaucracy; it lets triage trust that the artifact shows what you claim.

## 15.19 Mastery Deep Dive: Avoiding False Positives and Knowing When to Stop

### 15.19.1 A False-Positive Taxonomy

| False positive pattern | Why it looks like a bug | How to rule it out |
| — | — | — |
| Tool pattern match | Scanner flags a signature | Manually replay; check actual context and encoding |
| Catch-all response | Every path returns 200 | Compare bodies/lengths; verify a random path |
| Self-only effect | Reflection appears in your own browser only | Check whether another role/account sees it |
| Intended behavior | A field is public by design | Read docs and policy; ask the program |
| Client-side-only control | UI hides a feature | Check whether the server enforces it (own accounts) |
| Cached response | Old response persists | Use unique markers and cache-busting parameters |
| Environment artifact | Staging behaves differently | Confirm the asset's scope and environment |
| Misclassified impact | Missing header with no effect | Demonstrate a concrete security consequence |

### 15.19.2 The Validation Ladder

Promote a candidate through five rungs; stop if any rung fails:

```text
1. TOOL HIT        "A tool reported something." -> observation only
2. MANUAL REPLAY   "I can reproduce it by hand with one variable changed."
3. BOUNDARY        "A specific trust boundary is demonstrably crossed."
4. IMPACT          "A concrete consequence follows (own synthetic data)."
5. SAFETY CHECK    "No real data, no destructive effect, no scope violation."
```

Only a finding that reaches rung 5 is ready to write up. This ladder is the most reliable cure for the two dominant failure modes: submitting theoretical issues and overstating impact.

### 15.19.3 Severity Calibration in Business Context

Technical severity is only the starting point. Calibrate with three questions:

1. **Who is affected?** Self-only effects are typically informational; other users or the organization raise severity.
2. **What is the precondition?** Authentication required? A rare configuration? A user must click? Each precondition lowers practical severity.
3. **What is the business consequence?** Account takeover, data exposure, and integrity violations outrank cosmetic issues.

Use the program's own severity matrix where published (Chapters 11 and 12). State your reasoning in the report but accept the program's final classification; arguing taxonomy without new evidence is unproductive.

### 15.19.4 When to Move On

Move on when any of these is true:

- The hypothesis was rejected three times with clean tests.
- The finding is confirmed and documented — capture it now, then continue.
- The asset's priority score drops after new information (e.g., it is revealed as third-party).
- You are repeating tests without changing your model of the application.
- The session's timebox is exhausted.
- You feel pressure to bend a rule; stop regardless of progress.

**Annotated example.** After two hours on a search endpoint, you have tested reflection contexts, parameter pollution, and encoding variants with no difference from baseline. Rather than trying a hundred more payloads, you close the hypothesis with the note "server appears to encode all reflected input; revisit if framework changes" and move to the order API. This is not giving up; it is reallocating attention to a higher-yield hypothesis.

### 15.19.5 Note-Taking During engaged Testing

Keep three linked artifacts open:

- **Session journal** (policy version, accounts, scope decisions, timeboxes).
- **Hypothesis ledger** (ID, hypothesis, prior, test, result).
- **Finding drafts** (evidence bundle template started the moment a candidate reaches rung 3).

Starting the draft early matters: details such as the exact marker string and request order are easiest to capture while the context is fresh. A finding written from memory the next day is usually weaker.

## 15.20 Mastery Deep Dive: Lab Drills, Routines, and Assessment

### 15.20.1 Lab Setup and Drills

Use a locally hosted deliberately vulnerable application plus two or three synthetic accounts. Suggested drills:

1. **Baseline drill.** For ten endpoints, write the expected behavior for each role before sending any request.
2. **Authorization matrix drill.** Complete the full role × action grid on your own accounts; produce a matrix showing allowed/denied results.
3. **One-variable drill.** Take five parameters and, for each, perform exactly one transformation; document the response difference.
4. **Comparer drill.** Produce a two-panel diff for a confirmed authorization issue and write the one-sentence conclusion it supports.
5. **Business-logic drill.** Find one state-machine flaw in the lab workflow and describe the minimal PoC and the business consequence.
6. **Collaborator drill.** Demonstrate an out-of-band interaction and correctly distinguish DNS lookup from HTTP fetch.
7. **False-positive drill.** Deliberately misclassify a self-only reflection, then write the note that rules it out.
8. **Report drill.** From a lab finding, produce a complete triage-ready report using the evidence bundle template.

### 15.20.2 A Weekly Practice Routine

```text
Monday      Read one public disclosure or writeup; extract the hypothesis
            the researcher formed, not just the payload they used.
Tuesday     Reproduce the technique in the lab; write the hypothesis in
            your own words and confirm or reject it.
Wednesday   Run the authorization matrix drill on one lab module.
Thursday    Toolcraft: one Burp module used deliberately with notes.
Friday      Write one triage-ready report from a lab finding; peer-review it.
Weekend     Light review: update templates, calibrate priors, plan next week.
```

Every drill produces an artifact. Artifacts compound; opinions do not.

### 15.20.3 What Mastery Looks Like

```text
[ ] I start each target with a written threat model and trust-boundary map.
[ ] I write falsifiable hypotheses with priors before testing.
[ ] I change one variable at a time and can explain each response difference.
[ ] I complete role × action × representation matrices systematically.
[ ] I use Burp modules deliberately: Proxy for capture, Repeater for
    differential tests, Comparer for evidence, Intruder with restraint,
    Collaborator only for authorized OOB detection.
[ ] I promote findings through the five-rung validation ladder.
[ ] My evidence bundles are redacted, timestamped, and reproducible.
[ ] I distinguish self-only effects from real impact and avoid false positives.
[ ] I timebox, move on when signals say to, and never bend a safety rule.
[ ] A peer can replay my report without asking me a question.
```

### 15.20.4 Knowledge Check

1. Why must you change only one variable at a time in Repeater?
2. What is the difference between BOLA and BFLA, and how does the matrix test each?
3. A search parameter reflects your marker unencoded in your own browser, but no other role ever sees it. Which rung of the validation ladder fails and why?
4. A Collaborator payload produces a DNS lookup but no HTTP request. What can you conclude, and what can you not conclude?
5. You get a `403` when testing an admin route with a normal user token. Name two alternative explanations you should rule out.
6. After three clean rejected hypotheses on an endpoint, what should you do?
7. What belongs in a data-safety statement in an evidence bundle?

<details>
<summary><strong>Answers</strong></summary>

1. Because a difference caused by multiple simultaneous changes cannot be attributed to any one of them; you would not know which behavior you actually learned about.
2. BOLA (object-level) is about accessing another user's object and is tested by swapping object IDs between your own accounts. BFLA (function-level) is about invoking a privileged action and is tested by calling admin/export/bulk routes with a normal user token.
3. The impact/boundary rung: an effect visible only in your own session does not cross a trust boundary affecting other users. It is typically self-only and informational at best.
4. You can conclude the server resolved the domain (something triggered a DNS lookup). You cannot conclude it fetched content, followed a redirect to your host, or processed the response; that would require an HTTP interaction.
5. The `403` could come from a WAF or middleware, or from a missing expected header/session state. Compare with a known-denied baseline and inspect body and headers before concluding authorization is enforced.
6. Close the hypothesis with a clear note and move to the next highest-priority hypothesis or asset. Repeated payload guessing without a changed model is a loop, not progress.
7. A statement that only synthetic data and your own labeled accounts were used, that no real user data was accessed, and ideally the stop-on-real-data decision if one occurred.

</details>

## 15.21 Mastery Deep Dive: Pitfalls, Collaboration, and Continuous Improvement

### 15.21.1 Cognitive Biases in Manual Testing

Technical skill is necessary but not sufficient; your reasoning process must be guarded against predictable errors.

| Bias | How it appears in testing | Countermeasure |
| — | — | — |
| Confirmation bias | Trying payloads only because you want the hypothesis to be true | Write a falsification test: "what result would prove this wrong?" |
| Anchoring | Fixating on the first endpoint you examined | Force a fresh priority ranking after each new observation |
| Sunk cost | Continuing a dead endpoint because of time invested | Use predefined timeboxes and stop rules |
| Availability | Testing only bug classes you recently read about | Maintain the per-class matrix and rotate through it |
| Authority bias | Assuming a tool or senior researcher is correct | Re-derive conclusions from raw responses yourself |
| Optimism about impact | Claiming a large consequence from a narrow PoC | Apply the validation ladder and state what you did not verify |

**Annotated example.** You believe a parameter is vulnerable to injection and have sent fifteen variations. A confirmation-biased tester keeps varying payloads. A disciplined tester asks: "If the server is properly parameterized, what would I see?" The answer might be identical, well-formed responses with no timing or content change — which is what you observe. The hypothesis is rejected in one step, and the time goes to a better target.

### 15.21.2 Collaboration and Peer Review

Bug bounty looks solitary but improves dramatically with structured collaboration that respects confidentiality:

- **Peer-review your reports before submission.** Ask a trusted peer to replay your steps from the evidence bundle alone. If they ask a question you answered only in your head, fix the report.
- **Discuss methodology, not undisclosed findings.** Unless the program permits it, do not share details of an open report. Talk about techniques, lab setups, and reasoning patterns instead.
- **Learn from triage comments.** A request for information reveals exactly where your report was ambiguous. Add that lesson to your personal checklist.
- **Avoid "bug piling."** Coordinating with others to submit the same issue repeatedly wastes triage resources and damages trust.

### 15.21.3 The Continuous Improvement Loop

At the end of every engagement, perform a five-minute retrospective:

```text
1. Which hypothesis produced the most value? Why?
2. Which assumption was most wrong? How did I discover that?
3. Where did I lose time? (tool, recon gap, unclear scope, loop)
4. What safety or scope decision was hardest, and was it handled correctly?
5. What single change will I make to my templates or checklist next time?
```

Track these retrospectives in a single document. After several engagements, patterns emerge: perhaps your best findings always come from comparing API representations, or perhaps most of your time goes to content discovery that never yields a finding. Use the pattern to reallocate time — this is deliberate practice applied to your own workflow (Chapter 11).

### 15.21.4 Integrating the Full Pipeline

The chapters in this part form one continuous pipeline. Use this consolidated checklist to confirm you have covered it:

```text
PROGRAM SELECTION  - scored the program; safe harbor and scope verified
SCOPE ANALYSIS     - written scope map; questions asked and answered
RECON              - passive-first, correlated sources, ranked inventory
PRIORITIZATION     - transparent scoring; highest-value assets first
MANUAL TESTING     - threat model, trust boundaries, hypothesis ledger
VALIDATION         - five-rung ladder; own accounts; synthetic data only
EVIDENCE           - redacted, timestamped, reproducible bundle
REPORTING          - impact first, exact steps, program taxonomy used
TRIAGE             - one precise clarification response; respect decisions
DISCLOSURE         - confidential until permission; coordinate timing
IMPROVEMENT        - retrospective logged; templates updated
```

Skipping any stage does not save time; it moves the cost downstream into rejected reports, scope incidents, or unrepeatable results. The researcher who treats all eleven stages as one system is the one who improves steadily.

### 15.21.5 Knowledge Check: Integration

1. Your evidence bundle is perfect, but the asset turns out to be hosted by a third party. Which pipeline stage failed, and what should have prevented it?
2. A peer cannot replay your report without asking questions. Which stages need revisiting?
3. Name one concrete output for each of: scope analysis, recon, manual testing, validation, and improvement.

<details>
<summary><strong>Answers</strong></summary>

1. Scope analysis (and the ownership verification in Chapter 13). A written scope map with ownership checks and a recorded clarification should have prevented testing the asset at all.
2. Evidence capture and reporting. Rebuild the bundle with raw redacted requests, exact reproduction steps, and markers; then have the peer replay it before submission.
3. Scope analysis: a written scope map with green/amber/red decisions. Recon: a provenance-tagged, prioritized asset inventory plus handoff notes. Manual testing: a hypothesis ledger and completed test matrix. Validation: a finding that passed all five rungs. Improvement: a retrospective entry with one concrete template change.

</details>

## 15.14 Key Takeaways

- Manual testing is a structured loop of mapping, hypothesizing, validating, and reporting.
- Authorization and business logic are the highest-value areas for human researchers.
- Compare roles, endpoints, and data representations to reveal inconsistencies.
- Ethical discipline (own accounts, synthetic data, stop on real data) is part of the method.
