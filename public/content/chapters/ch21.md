# Chapter 21: Binary Exploitation and Memory Safety

> **Learning objectives.** Explain C memory model, stack/heap layout, and common memory-corruption bugs; describe modern mitigations and bypass concepts; understand fuzzing and crash analysis; and practice only in isolated labs.

## 21.1 Foundations in C

C gives direct memory access with no automatic bounds checks, which is why memory corruption is possible.

```c
void copy(char *input) {
    char buf[64];
    strcpy(buf, input);   // no bounds check -> overflow
}
```

Key constructs: pointers (`*`), address-of (`&`), arrays (contiguous memory), `malloc`/`free`, null terminators, and undefined behavior. Off-by-one errors and signed/unsigned confusion are frequent.

## 21.2 Memory Layout (Revisited)

```
 High
 +------------------+
 | Environment/Args |
 +------------------+
 | Stack  (down)    |  frames, locals, return addresses
 +------------------+
 |       ...        |
 +------------------+
 | Heap   (up)      |  malloc allocations
 +------------------+
 | BSS / Data       |
 +------------------+
 | Text (r-x)       |
 +------------------+
 Low
```

A stack frame (x86-64, simplified):

```
 rsp -> [ locals ... ]
        [ saved rbp ]
        [ return address ]  <- overwritten by stack overflow
```

## 21.3 Vulnerability Classes

**Stack buffer overflow:** writing past a stack buffer overwrites saved registers and the return address, allowing control of RIP (CWE-121).

**Heap overflow:** writing past a heap allocation corrupts allocator metadata or adjacent objects (CWE-122).

**Integer overflow:** arithmetic wraps, producing a smaller-than-needed allocation; subsequent copy overflows (CWE-190).

**Format string:** passing user input as a printf format string (`printf(user)`) allows reads/writes via `%x`/`%n` (CWE-134).

**Use-after-free (UAF):** using a pointer after its memory is freed; the memory may be reallocated with attacker data (CWE-416).

**Double free:** freeing the same pointer twice corrupts allocator state (CWE-415).

**Out-of-bounds read/write:** accessing outside allocated bounds (CWE-125/787).

## 21.4 Mitigations

- **ASLR (Address Space Layout Randomization):** randomizes addresses; bypass needs an info leak.
- **DEP/NX:** marks stack/heap non-executable; bypass via ROP.
- **Stack canaries:** a random value before the return address; detected on return; bypass needs a leak or overwrite of the canary.
- **CFI (Control-Flow Integrity):** restricts indirect branches to valid targets.
- **RELRO / Full RELRO:** makes the GOT read-only, limiting GOT overwrite attacks.
- **Safe languages:** Rust, Go, and memory-safe runtimes eliminate entire classes.

**ROP (Return-Oriented Programming):** chaining short instruction sequences ending in `ret` (gadgets) from existing code to perform actions despite NX. Understanding ROP conceptually is important; exploitation is a specialized skill best learned in dedicated labs (e.g., picoCTF, OverTheWire, Hacking: The Art of Exploitation-style exercises).

## 21.5 Fuzzing and Crash Analysis

Fuzzers generate inputs to find crashes (Chapter 23). For native code:

- **AFL++** and **libFuzzer** provide coverage-guided fuzzing.
- **AddressSanitizer (ASan)** detects memory errors at runtime.
- **Valgrind** detects memory leaks and invalid accesses.

Crash triage: reproduce, minimize the input, determine the root cause with GDB, and assess exploitability. Many crashes are not exploitable; honest assessment is part of research quality.

## 21.6 Debugging Workflow

```
gdb ./vulnerable
(gdb) set args <input>
(gdb) break main
(gdb) run
(gdb) info registers
(gdb) x/40gx $rsp      # examine stack
(gdb) bt               # backtrace
(gdb) continue
```

Use `checksec` to inspect mitigations, `objdump`/`readelf` to inspect binaries, and Ghidra (Chapter 22) for decompilation.

## 21.7 Secure Coding

- Use bounded functions (`strncpy`, `snprintf`) carefully; prefer safe libraries.
- Check allocation sizes for overflow; use `size_t` and validate.
- Initialize pointers; set to NULL after free.
- Use compiler protections (`-fstack-protector-strong`, `-D_FORTIFY_SOURCE=2`, `-Werror`).
- Prefer memory-safe languages where possible.

## 21.8 Ethical Boundaries

Binary exploitation against systems you do not own is illegal. Practice only with intentionally vulnerable programs in isolated VMs. Do not develop or use persistence, stealth, or destructive capabilities against real targets. The goal is understanding and defense.

## 21.12 Mastery Deep Dive: Architecture and Assembly Essentials

### 21.12.1 x86-64 Registers, Operand Sizes, and Endianness

You cannot reason about a crash without speaking the machine's language. In x86-64 (AMD64) the general-purpose registers are 64-bit: `rax, rbx, rcx, rdx, rsi, rdi, rbp, rsp, r8–r15`. Sub-registers alias them: `eax` is the low 32 bits of `rax`, `ax` the low 16, `al` the low 8. Writing to a 32-bit register zero-extends to 64 bits — a subtle rule that matters when interpreting disassembly.

| Register | Conventional role |
|----------|-------------------|
| `rsp` | Stack pointer (top of current stack frame) |
| `rbp` | Frame pointer (stable base of frame, when used) |
| `rip` | Instruction pointer (not directly addressable) |
| `rdi, rsi, rdx, rcx, r8, r9` | Argument registers 1–6 (SysV AMD64) |
| `rax` | Return value; also syscall number |
| `rbx, rbp, r12–r15` | Callee-saved (must be preserved) |

**Endianness** is the byte order of multi-byte values. x86-64 and ARM in typical mobile/embedded configurations are **little-endian**: the value `0x41424344` is stored in memory as bytes `44 43 42 41`. This is why a 4-byte overwrite of a return address with `0x0000000000401234` appears on the stack as `\x34\x12\x40\x00...`. When you read `x/8gx $rsp` in GDB, the displayed word `0x00007fffffffe3c0` represents the 8 bytes `c0 e3 ff ff ff 7f 00 00` in memory.

Common mistake: reversing byte order incorrectly when crafting an input. If a lab payload must place an address at a known offset, you supply it little-endian (lowest byte first) for x86-64/ARM LE targets, big-endian for the rare BE target.

### 21.12.2 The x86-64 Calling Convention and a Worked Stack Frame

Under the System V AMD64 ABI (Linux/macOS), the caller places the first six integer/pointer arguments in `rdi, rsi, rdx, rcx, r8, r9`; further arguments go on the stack. The return value is in `rax`. `rsp` must be 16-byte aligned at the call site. Callee-saved registers (`rbx, rbp, r12–r15`) must be restored before returning.

A typical non-optimized function prologue/epilogue:

```asm
push   rbp            ; save caller's frame pointer
mov    rbp, rsp       ; new frame base
sub    rsp, 0x40      ; reserve 64 bytes for locals
...
mov    rsp, rbp       ; teardown
pop    rbp
ret                   ; pops return address into RIP
```

With `buf[64]` at the bottom of that reserved region, the frame looks like:

```
    Higher addresses
    +----------------------+
    | caller's stack       |
    +----------------------+
    | return address (8B)  |  <- rbp+8 ; overwritten by overflow
    +----------------------+
    | saved rbp (8B)       |  <- rbp   ; overwritten next
    +----------------------+
    | local buf[64]        |  <- rbp-0x40 ; overflow starts here
    +----------------------+
    | (red zone 128B)      |  <- rsp-0x80 (Leaf functions may use)
    +----------------------+
    Lower addresses
```

Worked offset: to reach the saved return address from the start of `buf`, you cross 64 bytes of `buf` + 8 bytes of saved `rbp` = **72 bytes**. The first 8 bytes after that overwrite the low bytes of the return address. This is the arithmetic behind every stack-overflow offset — always derive it from the disassembly and frame layout, never guess.

When a compiler omits the frame pointer (`-fomit-frame-pointer`, default at `-O2`), locals are addressed relative to `rsp`, and the saved return address sits at `rsp + frame_size`. GDB still shows it; `info frame` reports the return address directly.

### 21.12.3 ARM / AArch64 Essentials and Calling Convention

Mobile and embedded targets are usually ARM. **AArch64 (ARM64)** has 31 general-purpose registers `x0–x30`:

- `x0–x7` — arguments/return values (`x0` also carries the return value).
- `x8` — indirect result location (large structs).
- `x9–x17` — caller-saved temporaries.
- `x19–x28` — callee-saved.
- `x29` — frame pointer (`fp`).
- `x30` — link register (`lr`), holds the return address.
- `sp` — stack pointer.

AArch64 instructions are fixed 32-bit, typically `ADD/SUB`, `LDR/STR` (with `signed` variants `LDRSB/LDRSW`), `B/BL/BR`, and conditional `CBZ/CBNZ/TBZ`. Unlike x86, AArch64 does not push the return address on the stack for a simple `BL`; it lives in `x30` until the function saves it. This changes exploit mechanics: a stack overflow must often overwrite a *saved* `x30` that the prologue stored on the frame.

```
AArch64 prologue (frame size 64):
  stp x29, x30, [sp, #-64]!   ; save fp and lr, decrement sp
  mov x29, sp
  sub sp, sp, #64             ; locals
  ...
  ldp x29, x30, [sp], #64     ; restore
  ret                         ; branches to x30
```

Here the saved `lr` is at `[x29, #8]`; overwriting it controls the return. On 32-bit ARM the return address lives in `r14` (`lr`) and arguments in `r0–r3`.

### 21.12.4 Reading Disassembly: A Guided Interpretation

Given this annotated listing from `objdump -d` on a lab binary:

```asm
401126 <vuln>:
  401126:  push   rbp
  401127:  mov    rbp,rsp
  40112a:  sub    rsp,0x40
  40112e:  lea    rax,[rbp-0x40]      ; address of buf
  401132:  mov    rdi,rax             ; arg1 = buf
  401135:  call   401030 <gets@plt>   ; unbounded input -> overflow
  40113a:  nop
  40113b:  leave
  40113c:  ret
```

Interpretation, step by step: `lea rax,[rbp-0x40]` computes the address of the 64-byte `buf`; it is moved into `rdi` (first argument) and `gets@plt` is called. `gets` reads until newline with no bounds — this is the vulnerability. The `leave` instruction is shorthand for `mov rsp,rbp; pop rbp`, after which `ret` pops the return address. So overflowing `buf` by 72 bytes overwrites saved `rbp`, and by 80 bytes overwrites the return address. Mastery means deriving this offset from the listing in under a minute.

## 21.13 Mastery Deep Dive: Memory Corruption Mechanics in the Lab

> All exploitation steps below are for intentionally vulnerable programs you compile yourself, run inside an isolated VM, with mitigations toggled deliberately for learning. They are not instructions for attacking real systems.

### 21.13.1 Stack Overflow: Offset Discovery and Control of RIP

The canonical lab exercise: compile a vulnerable program with protections off, find the offset, and observe control of instruction pointer.

```c
// <LAB> - intentionally vulnerable, compile with: gcc -fno-stack-protector -no-pie -z execstack -O0 lab.c -o lab
#include <stdio.h>
#include <string.h>
void vuln() { char buf[64]; gets(buf); printf("%s\n", buf); }
int main() { vuln(); return 0; }
```

Determine the offset empirically with a cyclic (De Bruijn) pattern rather than guessing:

```bash
<LAB> python3 -c 'print("A"*72 + "BBBBBBBB")' > payload.bin
<LAB> gdb ./lab -q -ex 'run < payload.bin' -ex 'info registers rip'
```

If `rip` becomes `0x4242424242424242` (`BBBBBBBB`), the offset to saved return address is exactly 72 bytes. Generating a unique cyclic pattern and using GEF's `pattern search` automates this for larger buffers; the principle is identical — find which 4–8 bytes land in `rip`.

Interpretation of the result: with the return address overwritten, execution will attempt to jump to whatever address you supplied. Without further primitives, that address is either invalid (segfault) or points to code you control. This sets up the two classic continuations: shellcode (needs executable stack) or ROP (needs existing gadgets).

### 21.13.2 Shellcode Concepts (Lab-Only) and Why NX Exists

**Shellcode** is a small position-independent machine-code payload. In a lab you might use a payload that simply calls `exit()` or spawns a local shell — the pedagogical point is control flow, not deployment. For x86-64 Linux, a minimal `execve("/bin/sh",0,0)` stub is ~27 bytes; you place it in the buffer and point the return address at the buffer's address.

Two obstacles appear immediately:

1. **ASLR** randomizes the stack address, so you do not know where the buffer is. In the lab you disable ASLR (`setarch $(uname -m) -R ./lab`) or leak an address.
2. **NX/DEP** marks the stack non-executable, so jumping to the buffer faults. Compile with `-z execstack` only for the demonstration, then recompile *with* NX and watch the same payload fail — this is the clearest way to understand the mitigation's value.

We never deliver real payloads to third parties. The learning objective is to see that control of `rip` plus an executable, known-address buffer equals code execution — and then to appreciate how each mitigation removes one leg of that stool.

### 21.13.3 Format String Vulnerabilities: Reads and Writes

A format string bug occurs when user input is used as the format: `printf(user)` instead of `printf("%s", user)`. The `printf` family consumes arguments from registers/stack according to conversion specifiers in the string. Because the caller supplied no real arguments, the function reads whatever happens to be in argument slots — a **memory disclosure** primitive.

```c
// <LAB>
void f(char *user) { printf(user); }   // vulnerable
// safe: printf("%s", user);
```

Probe sequence on a lab build:

```bash
<LAB> ./lab "%p.%p.%p.%p"      # leaks stack/register values
<LAB> ./lab "%08x.%08x.%08x"   # same, hex, useful for stack dumps
<LAB> ./lab "%s"               # treats a leaked pointer as a string -> may crash
<LAB> ./lab "%n"               # WRITE primitive: stores bytes-written to a pointer arg
```

Interpretation: each `%p`/`%x` walks one argument slot; after the register slots (`rsi, rdx, rcx, r8, r9` on x86-64) it walks the stack, so you can dump stack contents and find pointers, canaries, or addresses. `%n` writes the count of characters printed so far to the pointer in the corresponding argument slot — on a 64-bit build `%hn`/`%n` with a controlled pointer is an arbitrary-write primitive. Positional specifiers (`%7$p`) let you target a precise slot without printing everything.

Defense: never let input be the format string; compile with `-Wformat-security -Werror` and enable `_FORTIFY_SOURCE=2`; use constant formats with arguments.

### 21.13.4 Heap Internals: UAF, Double Free, and Overflow

Heap exploits target the allocator's metadata and reuse behavior, not the stack. Using **glibc malloc** as the model:

- An allocated chunk has a header with `size` (and flags) just before the returned pointer; free chunks are linked in bins (tcache, fastbins, small/large bins, unsorted bin).
- **tcache** (thread-local cache) is a fast, singly-linked list of small free chunks; since glibc 2.32 it is keyed/corrupted-checked, but older lab images show classic behaviors clearly.

**Use-after-free (UAF):** free an object but keep a dangling pointer; if a subsequent allocation reuses that chunk with attacker-controlled data, the dangling pointer now aliases that data. A classic example is a "note" object whose `free()` is called but whose pointer remains in an array; allocating a new note of the same size can place controlled bytes where the old object's function pointer lived.

```c
// <LAB> - simplified UAF pattern
struct Obj { void (*callback)(void); char data[24]; };
struct Obj *o = malloc(sizeof(struct Obj));
free(o);                       // o is now dangling
struct Obj *o2 = malloc(sizeof(struct Obj)); // likely reuses same chunk
strcpy(o2->data, "<LAB>");     // o->data now aliases controlled bytes
o->callback();                 // UAF: calls whatever is now at offset 0
```

**Double free:** calling `free(p)` twice inserts the same chunk into a free list twice; the allocator's linked-list metadata can then be made to point at an arbitrary address, so a later allocation returns a pointer you choose — a stepping stone to arbitrary write. Modern glibc detects "double free or corruption (!prev)" and aborts; learning includes reading that exact abort message.

**Heap overflow:** writing past a chunk corrupts the next chunk's header (`size` field) or, for in-use adjacent objects, adjacent object fields. The `printf` of glibc's abort message (`free(): invalid next size (fast)`) is a diagnostic you will learn to recognize.

**Defenses:** use safe wrappers, prefer `calloc` with checked multiplication, set pointers to `NULL` after free, compile with ASan (`-fsanitize=address`), and where possible use memory-safe languages.

### 21.13.5 Integer Overflows and Off-by-One

An **integer overflow** (CWE-190) makes an allocation too small. Classic pattern: `int n = user; if (n+1 > MAX) reject; buf = malloc(n+1); read(fd, buf, n);` — if `n = INT_MAX`, `n+1` wraps negative, the check passes, and `malloc` returns a tiny buffer that `read` then floods. Signed/unsigned confusion is the cousin: comparing a `size_t` to a negative `int` converts the int to a huge unsigned value.

An **off-by-one** writes exactly one byte past a buffer. With a null terminator it can overwrite the least-significant byte of a saved pointer or a chunk's size low byte — small change, large consequence.

Defense checklist: use `size_t` for sizes, check `n > SIZE_MAX / elem_size` before multiplying, use compiler flags `-fsanitize=integer` (where available), and prefer bounded APIs (`snprintf`, `fgets`, `memcpy_s` alternatives).

## 21.14 Mastery Deep Dive: Exploit Techniques and Mitigations

### 21.14.1 ROP Chain Construction Concepts

When NX prevents executing the stack, **Return-Oriented Programming (ROP)** reuses existing executable code. A **gadget** is a short instruction sequence ending in `ret` (or `jmp`/`call` through a register). Examples: `pop rdi; ret`, `pop rsi; ret`, `mov rax, rdi; ret`. Chaining gadgets by placing their addresses in sequence on the stack creates a program: each `ret` pops the next gadget address.

Conceptual chain for a lab AMD64 target calling `system("/bin/sh")`:

```
stack (growing down shown bottom-up):
  [ gadget: pop rdi; ret ]      <- overwritten return address
  [ address of "/bin/sh" ]      <- popped into rdi
  [ gadget: ret ]               <- alignment padding (16-byte stack alignment)
  [ address of system@plt ]
```

Tooling in the lab: `ROPgadget --binary ./lab | grep 'pop rdi'`, `ropper`, or pwntools' `ROP` object. The hard part is usually *finding* gadgets and composing them given constraints (bad characters, stack alignment on modern glibc's `movaps` instructions). Mastery means understanding the *grammar* — set arguments in registers per calling convention, align the stack, call the function — not memorizing a specific exploit. We keep this conceptual and confined to lab binaries.

### 21.14.2 Mitigation Matrix: How Each Changes Exploitation

| Mitigation | What it stops | What the attacker needs instead |
|-----------|--------------|---------------------------------|
| ASLR | Known addresses | An info leak to compute base addresses |
| NX / DEP | Executing stack/heap | ROP / code reuse |
| Stack canary | Straight stack overflow to RIP | Leak the canary, or overflow a non-canary path (e.g., function pointer) |
| RELRO (partial/full) | GOT overwrites | Full RELRO makes GOT read-only; target other writable function pointers |
| PIE | Fixed code addresses | Leak a code pointer to defeat PIE, then ROP |
| CFI / CET (shadow stack, IBT) | ROP / indirect branch hijack | Weakened or misconfigured CFI; data-oriented attacks |
| FORTIFY_SOURCE / fortified libc | Known dangerous calls | Harder; often just aborts |
| Safe languages | Entire memory-safety classes | Logic bugs, unsafe blocks, FFI boundaries |

Key insight: mitigations **compose**. NX forces ROP; ASLR forces a leak; PIE forces a code leak; canaries force a leak or alternate target; CFI constrains control-flow hijack. A realistic exploit chain reads like: leak a libc pointer → compute libc base → find `system` and `/bin/sh` → build ROP → align stack → trigger overflow. Mastery is understanding this dependency graph.

Check your lab binary's posture:

```bash
<LAB> checksec --file=./lab
# RELRO: Full RELRO | Stack: Canary found | NX: NX enabled | PIE: PIE enabled
```

### 21.14.3 Info Leaks and Defeating ASLR (Concepts)

ASLR randomizes stack, heap, and library base addresses, but relative offsets within a module stay fixed. If you leak *one* pointer from a module (e.g., a saved return address on the stack points into libc), you can subtract its known offset to recover the module base, then compute any other address in that module. Format-string `%p` leaks and uninitialized-memory disclosures are classic sources.

The same arithmetic applies to PIE: leak a code pointer, subtract its link-time offset, recover the PIE base. This is why an apparently minor "information disclosure" can be a critical link in a chain; severity assessment must consider exploit chaining, not just isolated impact.

### 21.14.4 Honest Exploitability Assessment

Not every crash is exploitable. A rigorous triage asks:

1. **What was corrupted?** A return address, a function pointer, or only non-control data?
2. **Is the write controlled in content, size, and location?** A one-byte null overwrite of a chunk size is weaker than arbitrary-length data at an arbitrary offset.
3. **Do mitigations block the path?** Canary present and no leak → likely DoS only.
4. **Is the crash deterministic?** Timing/concurrency-dependent crashes are hard to weaponize.
5. **What is the realistic impact in context?** A local DoS in a client app is very different from a pre-auth RCE in a network service.

Mastery includes *saying "not exploitable" with confidence* and documenting why. Inflating every crash into a critical finding destroys credibility.

## 21.15 Mastery Deep Dive: Debugger Workflow, Crash Analysis, and Verification

### 21.15.1 GDB / GEF Workflow with Annotated Output

A disciplined debug session:

```bash
<LAB> gdb -q ./lab
(gdb) checksec                     # (GEF) mitigation summary
(gdb) break vuln
(gdb) run < payload.bin
Breakpoint 1, 0x000000000040112e in vuln ()
(gdb) disassemble vuln             # confirm frame size and gets call
(gdb) x/16gx $rsp                  # inspect locals/stack
0x7fffffffe0a0: 0x4141414141414141 0x4141414141414141
(gdb) info frame                   # shows saved rip and frame base
(gdb) continue
Program received signal SIGSEGV, Segmentation fault.
0x4242424242424242 in ?? ()        # rip controlled -> overflow confirmed
(gdb) bt                           # backtrace shows corrupted frame chain
(gdb) x/8gx $rsp-0x20              # inspect stack near crash
```

Interpretation checklist: `checksec` tells you which mitigations you must reason about; `disassemble` gives the frame layout for offset math; `x/16gx` shows your pattern bytes in memory; `info frame` pinpoints the saved return address; the SIGSEGV at `0x4242...` confirms control; `bt` failing or showing garbage indicates the frame chain is destroyed. With GEF, `pattern create` / `pattern search` replaces manual pattern work, and `canary` / `checksec` are one command.

### 21.15.2 Ghidra Workflow for Vulnerability Research

1. Import the lab binary; let auto-analysis complete.
2. In the **Symbol Tree**, find `main`; follow calls to identify `vuln`.
3. Open **Decompiler** view: locate `gets`, `strcpy`, `printf`, `malloc`, `free`. For each, ask "where does the data come from and how long is it?"
4. Use **Defined Strings** and **References** (xrefs) to find hard-coded paths/keys and the functions that use them.
5. Rename variables and add comments; produce a call graph.
6. Cross-check anything suspicious in the **Listing** (disassembly) view — decompiler output can hide aliasing and optimization artifacts.

Deliverable habit: maintain a findings table with `address | function | suspicious API | source→sink | verdict`. This turns analysis into a reproducible audit instead of wandering.

### 21.15.3 Crash Triage and Minimization

When a fuzzer or manual test crashes a lab target:

```bash
<LAB> ./lab crash.bin                # 1. reproduce
<LAB> afl-tmin -i crash.bin -o min.bin -- ./lab @@   # 2. minimize (AFL++)
<LAB> gdb ./lab -q -ex 'run < min.bin' -ex 'bt'      # 3. root cause
<LAB> valgrind --tool=memcheck ./lab < min.bin       # 4. independent check
```

Interpretation: minimization shrinks a 10 KB crashing file to, say, 12 bytes, revealing the exact field/offset responsible. GDB's backtrace plus a sanitizer report identifies the faulty line. Valgrind confirms invalid reads/writes even when execution does not crash. Classify as: out-of-bounds read/write, UAF, double free, null deref, assertion, stack overflow, or infinite loop/hang. Each class maps to a CWE and a fix.

### 21.15.4 The Fuzzing Connection and Sanitizers

Fuzzing (Chapter 23) is the *discovery* engine; sanitizers make its signals loud. Build the lab target with instrumentation:

```bash
<LAB> clang -g -O1 -fsanitize=fuzzer,address -o fuzz_target harness.c
<LAB> ./fuzz_target -max_total_time=60 corpus/
# ==12345==ERROR: AddressSanitizer: heap-buffer-overflow on address ...
#  WRITE of size 4 at ... thread T0
#     #0 0x... in parse harness.c:42
```

Interpretation of an ASan report: the header gives class and access type; the stack trace pinpoints the source line; the "allocated by" trace shows where the buffer came from. ASan adds redzones around allocations and quarantines freed chunks, converting silent corruption into an immediate, diagnostic abort. UBSan reports signed-integer overflow and misaligned access; MSan reports use of uninitialized values; TSan reports data races. Each widens the net beyond what a segfault alone would catch.

### 21.15.5 Detection and Defense Checklists

Defense (build-time and code):

- [ ] Stack protector: `-fstack-protector-strong` (or `-fstack-protector-all` for critical code)
- [ ] NX/DEP enabled; no `-z execstack` in release
- [ ] PIE enabled (`-fPIE -pie`)
- [ ] Full RELRO (`-Wl,-z,relro,-z,now`)
- [ ] FORTIFY_SOURCE=2 with optimization enabled
- [ ] CFI / CET where toolchain supports it (`-fcf-protection`, `-fsanitize=cfi`)
- [ ] Bound checks on all lengths; safe allocation arithmetic; null-after-free
- [ ] Prefer Rust/Go for new security-critical components
- [ ] Continuous fuzzing + sanitizers in CI

Detection (runtime/operations):

- [ ] Crash telemetry with symbolized stack traces (e.g., Breakpad/Crashlytics)
- [ ] Alert on repeated crashes in one module (possible exploitation attempts)
- [ ] Monitor for ROP-like behavior where CET/shadow stacks are available
- [ ] W^X enforcement; no writable+executable mappings

### 21.15.6 Common Mistakes

1. **Overflowing the wrong offset** because you forgot saved `rbp` or stack alignment. Always confirm with a pattern in GDB.
2. **Forgetting endianness** when writing addresses — supply little-endian on x86-64/ARM LE.
3. **Assuming a crash equals control.** A null deref is not RIP control.
4. **Testing with mitigations off and concluding exploits are easy.** Re-enable them and observe the same payload fail; that comparison *is* the lesson.
5. **Ignoring ASan because "the program didn't crash."** Silent corruption is often more dangerous.
6. **Skipping the 16-byte stack alignment** on AMD64 glibc — `movaps` in `system` will fault and look like a mysterious crash.

### 21.15.7 Verify in Your Lab

1. Compile `<LAB>` vulnerable program twice: with `-fno-stack-protector -no-pie -z execstack` and with full hardening.
2. Run `checksec` on both; record the differences.
3. Find the return-address offset with a cyclic pattern; confirm RIP control in GDB.
4. Recompile with canaries + NX; confirm the same input now aborts ("stack smashing detected") or faults at a non-executable address.
5. Build a format-string demo; leak three `%p` values and identify one pointer.
6. Trigger a UAF and an ASan report; read the "freed by" and "allocated by" traces.
7. Fuzz the parser briefly with libFuzzer+ASan and minimize one crash.

### 21.15.8 What Mastery Looks Like

You have mastered this material when you can:

- Derive a stack offset from disassembly and confirm it empirically.
- Explain each mitigation's mechanism and the primitive needed to bypass it.
- Distinguish control-flow corruption from data-only corruption and assess exploitability honestly.
- Build a ROP chain conceptually and explain why stack alignment and leaks matter.
- Use GDB/GEF and Ghidra together, interpreting output rather than memorizing keystrokes.
- Reproduce, minimize, and root-cause a crash with sanitizers and a debugger.

### 21.15.9 Knowledge Check (Answers Included)

**Q1.** A 64-byte `buf` sits at `rbp-0x40` in a standard frame. How many bytes to overwrite the saved return address?
**A1.** 72: 64 bytes of buffer + 8 bytes of saved `rbp`; the next 8 bytes are the return address.

**Q2.** Why does NX force ROP rather than shellcode on the stack?
**A2.** NX marks the stack non-executable, so a jump to injected bytes faults. ROP instead reuses existing executable code (gadgets), needing no new executable memory.

**Q3.** What single primitive most directly defeats ASLR?
**A3.** An information leak of a pointer from a randomized module; subtracting its fixed offset reveals the module base.

**Q4.** A program prints `printf(user_input)`. Name a read primitive and a write primitive it enables.
**A4.** `%p`/`%x` leak stack/register values (read); `%n` writes to the address taken from an argument slot (write).

**Q5.** glibc aborts with "double free or corruption (!prev)". What happened?
**A5.** The same chunk was freed twice (or adjacent chunk metadata was corrupted), and the allocator's consistency check detected the invalid free-list state.

## 21.10 Key Takeaways

- Memory corruption arises from C's direct memory access and undefined behavior.
- Stack, heap, integer, format-string, UAF, and double-free bugs have distinct mechanisms.
- Mitigations (ASLR, NX, canaries, CFI) raise the bar; bypasses require information or reuse.
- Fuzzing plus sanitizers is an effective discovery combination; all practice belongs in labs.
