# Chapter 21: Binary Exploitation and Memory Safety

> **Learning objectives.** Explain C memory model, stack/heap layout, and common memory-corruption bugs; describe modern mitigations and bypass concepts; understand fuzzing and crash analysis; and practice only in isolated labs.

## 21.1 Foundations in C

C gives direct memory access with no automatic bounds checks, which is why memory corruption is possible.

```c
void copy(char *input) {
    char buf[64];
    strcpy(buf, input);   // no bounds check -> overflow
}
```

Key constructs: pointers (`*`), address-of (`&`), arrays (contiguous memory), `malloc`/`free`, null terminators, and undefined behavior. Off-by-one errors and signed/unsigned confusion are frequent.

## 21.2 Memory Layout (Revisited)

```
 High
 +------------------+
 | Environment/Args |
 +------------------+
 | Stack  (down)    |  frames, locals, return addresses
 +------------------+
 |       ...        |
 +------------------+
 | Heap   (up)      |  malloc allocations
 +------------------+
 | BSS / Data       |
 +------------------+
 | Text (r-x)       |
 +------------------+
 Low
```

A stack frame (x86-64, simplified):

```
 rsp -> [ locals ... ]
        [ saved rbp ]
        [ return address ]  <- overwritten by stack overflow
```

## 21.3 Vulnerability Classes

**Stack buffer overflow:** writing past a stack buffer overwrites saved registers and the return address, allowing control of RIP (CWE-121).

**Heap overflow:** writing past a heap allocation corrupts allocator metadata or adjacent objects (CWE-122).

**Integer overflow:** arithmetic wraps, producing a smaller-than-needed allocation; subsequent copy overflows (CWE-190).

**Format string:** passing user input as a printf format string (`printf(user)`) allows reads/writes via `%x`/`%n` (CWE-134).

**Use-after-free (UAF):** using a pointer after its memory is freed; the memory may be reallocated with attacker data (CWE-416).

**Double free:** freeing the same pointer twice corrupts allocator state (CWE-415).

**Out-of-bounds read/write:** accessing outside allocated bounds (CWE-125/787).

## 21.4 Mitigations

- **ASLR (Address Space Layout Randomization):** randomizes addresses; bypass needs an info leak.
- **DEP/NX:** marks stack/heap non-executable; bypass via ROP.
- **Stack canaries:** a random value before the return address; detected on return; bypass needs a leak or overwrite of the canary.
- **CFI (Control-Flow Integrity):** restricts indirect branches to valid targets.
- **RELRO / Full RELRO:** makes the GOT read-only, limiting GOT overwrite attacks.
- **Safe languages:** Rust, Go, and memory-safe runtimes eliminate entire classes.

**ROP (Return-Oriented Programming):** chaining short instruction sequences ending in `ret` (gadgets) from existing code to perform actions despite NX. Understanding ROP conceptually is important; exploitation is a specialized skill best learned in dedicated labs (e.g., picoCTF, OverTheWire, Hacking: The Art of Exploitation-style exercises).

## 21.5 Fuzzing and Crash Analysis

Fuzzers generate inputs to find crashes (Chapter 23). For native code:

- **AFL++** and **libFuzzer** provide coverage-guided fuzzing.
- **AddressSanitizer (ASan)** detects memory errors at runtime.
- **Valgrind** detects memory leaks and invalid accesses.

Crash triage: reproduce, minimize the input, determine the root cause with GDB, and assess exploitability. Many crashes are not exploitable; honest assessment is part of research quality.

## 21.6 Debugging Workflow

```
gdb ./vulnerable
(gdb) set args <input>
(gdb) break main
(gdb) run
(gdb) info registers
(gdb) x/40gx $rsp      # examine stack
(gdb) bt               # backtrace
(gdb) continue
```

Use `checksec` to inspect mitigations, `objdump`/`readelf` to inspect binaries, and Ghidra (Chapter 22) for decompilation.

## 21.7 Secure Coding

- Use bounded functions (`strncpy`, `snprintf`) carefully; prefer safe libraries.
- Check allocation sizes for overflow; use `size_t` and validate.
- Initialize pointers; set to NULL after free.
- Use compiler protections (`-fstack-protector-strong`, `-D_FORTIFY_SOURCE=2`, `-Werror`).
- Prefer memory-safe languages where possible.

## 21.8 Ethical Boundaries

Binary exploitation against systems you do not own is illegal. Practice only with intentionally vulnerable programs in isolated VMs. Do not develop or use persistence, stealth, or destructive capabilities against real targets. The goal is understanding and defense.

## 21.9 Exercises

1. Compile a small C program with and without stack protector; inspect with `checksec`.
2. In a lab, trigger a stack overflow in a provided vulnerable binary and observe the crash in GDB.
3. Use ASan to detect a heap overflow and read its report.
4. Explain how ASLR and NX together make exploitation harder and what an info leak provides.
5. Fuzz a small parser with AFL++ in a lab and triage one crash.

## 21.10 Key Takeaways

- Memory corruption arises from C's direct memory access and undefined behavior.
- Stack, heap, integer, format-string, UAF, and double-free bugs have distinct mechanisms.
- Mitigations (ASLR, NX, canaries, CFI) raise the bar; bypasses require information or reuse.
- Fuzzing plus sanitizers is an effective discovery combination; all practice belongs in labs.
