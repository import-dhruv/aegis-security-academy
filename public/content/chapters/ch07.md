# Chapter 7: Backend, Databases, and APIs

> **Learning objectives.** Explain REST, GraphQL, and gRPC; distinguish authentication from authorization; describe OAuth 2.0, OIDC, and JWT; explain SQL/NoSQL fundamentals, ORMs, and query security; and recognize common backend security mistakes.

## 7.1 Backend Architecture

A backend receives requests, applies business logic, talks to data stores, and returns responses.

```
 Client --> [Load Balancer] --> [App Server] --> [Database]
                                   |
                                   +--> [Cache / Queue / Object Store]
```

Core concerns: routing, request parsing, validation, authentication, authorization, business logic, data access, error handling, and logging. Security flaws can live in any of these.

## 7.2 API Styles

### REST

REST (Representational State Transfer) uses HTTP semantics: resources identified by URLs, methods expressing actions, status codes expressing outcomes. It is stateless — each request carries everything needed.

```
GET    /api/v1/users/123
POST   /api/v1/users
PUT    /api/v1/users/123
DELETE /api/v1/users/123
```

Good REST design is predictable, but REST is a convention, not a protocol; implementations vary, which is why API inventories and schemas matter.

### GraphQL

GraphQL exposes a typed schema and lets clients request exactly the fields they need:

```graphql
query {
  user(id: 123) {
    name
    email
    posts { title }
  }
}
```

Security considerations: introspection can reveal the full schema; deeply nested queries can cause DoS (depth/complexity limits); resolvers must authorize each field; batching can bypass naive rate limits. See Chapter 17.

### gRPC

gRPC is a high-performance RPC framework using HTTP/2 and Protocol Buffers. It is strongly typed and common in microservices. Security relies on mTLS, proper service-to-service authorization, and careful handling of reflection (which can expose service definitions).

## 7.3 Authentication vs. Authorization

- **Authentication (AuthN):** who are you? Credentials, tokens, biometrics, certificates.
- **Authorization (AuthZ):** what are you allowed to do? Roles, permissions, policies, ownership checks.

A huge share of vulnerabilities is authorization failures, not broken cryptography. Always ask: "for *this specific object and action*, does the server verify that the authenticated user is entitled?"

**Session management:** generate high-entropy session IDs; rotate on login; set secure cookie attributes; expire idle and absolute sessions; invalidate on logout. Predictable or reused session IDs are critical flaws.

## 7.4 OAuth 2.0 and OpenID Connect

**OAuth 2.0** is an authorization framework, not an authentication protocol. It lets an application obtain limited access to a resource on behalf of a user. Common flows:

- **Authorization Code** (with PKCE for public clients) — recommended.
- **Implicit** — deprecated due to token exposure in URLs/fragments.
- **Client Credentials** — machine-to-machine.
- **Resource Owner Password Credentials** — deprecated; avoid.

Flow (Authorization Code + PKCE):

```
Client -> /authorize?client_id&redirect_uri&response_type=code&code_challenge
User logs in; consent
Provider -> redirect_uri?code=...
Client -> /token with code + code_verifier
Provider -> access_token (+ refresh_token, id_token if OIDC)
```

**OpenID Connect (OIDC)** layers identity on OAuth 2.0, adding an `id_token` (a signed JWT) and a UserInfo endpoint.

Common implementation flaws:

- Missing/incorrect `state` parameter → CSRF on the authorization flow.
- Weak or absent PKCE → authorization-code interception.
- `redirect_uri` validation mistakes → open redirect / token leakage.
- Trusting the `id_token` without validating signature, issuer, audience, and expiry.
- Scope confusion and insufficient validation of token claims.

## 7.5 JWT (JSON Web Tokens)

A JWT has three Base64URL-encoded parts: `header.payload.signature`.

```
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjMifQ.SflKxwRJSMe...
```

The server should verify: signature algorithm, signature, `exp`, `nbf`, `iat`, `iss`, `aud`, and application-specific claims.

Common mistakes (Chapter 10 covers testing):

- **`alg: none` acceptance** — a token with no signature accepted due to flawed verification.
- **Algorithm confusion** — RS256 expected but HS256 accepted, using the public key as the HMAC secret.
- **Weak secrets** — HS256 with a guessable secret.
- **Missing claim validation** — expired tokens accepted; `aud` ignored.
- **Client-side trust** — decoding without verification, or trusting token contents for authorization without checking the signature.

JWTs are not encrypted by default: anyone holding a token can read the payload. Do not put secrets in them.

## 7.6 SQL and Databases

**SQL** queries relational databases. A vulnerable concatenation:

```python
query = "SELECT * FROM users WHERE name = '" + user + "'"
```

Input `alice' OR '1'='1` changes the query's meaning — **SQL injection** (Chapter 9). The fix is parameterized queries:

```python
cur.execute("SELECT * FROM users WHERE name = %s", (user,))
```

Relational systems:

- **PostgreSQL** — feature-rich, extensible; roles and schema privileges; row-level security.
- **MySQL/MariaDB** — widely deployed; users and grants.

**NoSQL (MongoDB):** uses documents (BSON/JSON). Injection can occur in query operators: passing `{"$ne": null}` where a string is expected. ORMs and query builders help but are not magic; unsafe use of raw queries reintroduces risk.

Database security fundamentals:

- Least-privilege database accounts (the web app should not be `root`/`sa`).
- Separation of tenants, ideally at the database or row level with enforced policies.
- No sensitive data in logs or error messages.
- Encryption at rest and in transit; careful key management.
- Backups tested for restore.

**ORM security:** Object-Relational Mappers (SQLAlchemy, Hibernate, Django ORM) parameterize most queries, but raw SQL escape hatches, dynamic column names, and unsafe `order_by` parameters can still be injectable.

## 7.7 Other Backend Concepts

- **API gateways:** centralize auth, rate limiting, routing, and observability. Misconfiguration can expose internal routes.
- **Rate limiting:** per-IP, per-account, per-token; protects credentials and expensive endpoints. Missing or bypassable limits enable brute force and DoS.
- **Input validation:** allow-list preferred; validate type, length, range, format, and encoding at trust boundaries. Reject unexpected content types and duplicate parameters.
- **Serialization/deserialization:** converting objects to/from bytes. Deserializing untrusted data with languages that instantiate classes (Java, Python pickle, .NET) can lead to remote code execution. Prefer data-only formats (JSON) with strict schemas.
- **Mass assignment/auto-binding:** binding request fields directly to object properties can let an attacker set `isAdmin=true` (Chapter 17).

## 7.8 Common Backend Security Mistakes

1. Trusting client-side authorization ("the UI hides the button").
2. String-concatenated queries and commands.
3. Missing object-level ownership checks (IDOR/BOLA).
4. Over-privileged service accounts and database users.
5. Verbose errors revealing stack traces, SQL, or paths.
6. Secrets in source code, logs, or environment exposed via debug endpoints.
7. Inconsistent parsing between gateway, app, and database.
8. Deserializing untrusted objects.
9. No rate limits on authentication and expensive endpoints.
10. Assuming internal traffic is trustworthy.

2. Decode (but do not trust) a sample JWT at jwt.io; identify header and payload fields and explain which must be validated.
3. Diagram an OAuth Authorization Code + PKCE flow and mark the points where CSRF or redirect attacks could occur.
4. Create two users in a lab app and test whether user A can access user B's objects by changing an ID (authorized lab only).
5. Configure a MongoDB lab to reject query-operator injection by validating input types.

## 7.12 Mastery Deep Dive: The Full Request Lifecycle

A backend is a pipeline of transformations, and every stage is a place where a security decision is made — or skipped. Internalize the lifecycle and you can predict where validation is missing without needing source code.

### 7.12.1 Stages and the decisions they make

```
DNS -> TCP -> TLS -> HTTP parse -> edge/CDN -> reverse proxy
   -> framework routing -> middleware chain -> handler -> data access
   -> response construction -> serialization -> transport -> browser parse
```

Stage-specific questions:

- **HTTP parse:** which parser handles duplicate headers, duplicate JSON keys, chunked bodies, and unusual content types? Parsers differ on `{"a":1,"a":2}` — last-wins vs first-wins — which can smuggle a privileged value past a validator that saw the other one.
- **Middleware chain:** does authentication run *before* the route body? Is the CSRF check applied to every state-changing method, or only the "main" one? Middleware order is security logic.
- **Handler:** are all inputs (path, query, body, headers, cookies) validated, or only the obvious ones? Is authorization checked per object?
- **Data access:** are queries parameterized? Does the DB account have least privilege?
- **Response:** are errors generic? Are secrets or stack traces omitted? Are security headers set?

### 7.12.2 Trust boundaries inside one process

Even within a single application, treat each layer as a boundary: framework → service → repository → database. Type confusion at a boundary (string vs array, number vs string, object vs scalar) is a rich source of bugs. For example, a validator that checks `isinstance(x, str)` but a downstream library accepts a list can be bypassed with `{"user":["admin"]}`. Log and reject unexpected types at every boundary.

### 7.12.3 Statefulness and idempotency

HTTP is stateless, but applications are not: sessions, caches, counters, and queues hold state across requests. Ask which state is authoritative (usually the DB), which is derived (cache, client token), and what happens when they disagree. Idempotency keys (a client-supplied unique token for a mutation) are a defense against both retries and race-condition abuse; their absence is a discoverable weakness.

## 7.13 Mastery Deep Dive: SQL and NoSQL Query Mechanics

### 7.13.1 How the database evaluates your input

A parameterized query sends the SQL text and the data separately, so the DBMS treats the placeholder strictly as a value. Concatenation builds one string, so the DBMS re-parses the attacker's characters as syntax. Understanding the grammar lets you craft payloads that are *syntactically valid* for the target DBMS. Always fingerprint the engine (`@@version` on MSSQL, `version()` on PostgreSQL, `version()`/`@@version` on MySQL) in a lab.

### 7.13.2 Injection taxonomy with lab-safe payload patterns

All payloads below are for an application you own or an explicit lab.

| Class | Mechanism | Lab example pattern |
|-------|-----------|---------------------|
| In-band union | Append a second result set with matching column count | `' UNION SELECT 1,version(),3-- ` |
| Error-based | Force a type/conversion error that echoes data | `' AND 1=CAST((SELECT version()) AS int)-- ` |
| Boolean blind | Infer truth from a response difference | `' AND (SELECT SUBSTR(version(),1,1))='8`-- ` |
| Time blind | Infer truth from delay | `'; IF (1=1) WAITFOR DELAY '0:0:5'-- ` (MSSQL) |
| Out-of-band | Exfiltrate via DNS/HTTP callback you control | `... TO 'attacker.<LAB_HOST>'` (lab listener) |

Steps for disciplined detection: submit `'` and `"` and observe errors/behaviors; comment out the rest of the statement (`-- `, `#`, `/* */`); balance columns with `ORDER BY n`; then use a union or boolean probe. Extract only a known sentinel value (e.g., `@@version`) to prove impact — never real user data. Verify remediation by re-running the exact payload and confirming it is now treated as a literal value (no delay, no error, no extra rows).

### 7.13.3 NoSQL operator injection

Document databases accept query objects. If the app passes a string directly into a query operator context, an attacker can send an object instead:

```javascript
// Vulnerable: expects a string, receives an object
db.users.find({ username: req.body.username, password: req.body.password });
// Request body (lab):
// {"username":"admin","password":{"$ne":"__never__"}}  -> matches any password
```

Detection: submit `{"ne":null}`, `{"gt":""}`, `{"$regex":".*"}` where a plain value is expected and observe authentication bypass or data leakage. Defenses: enforce scalar types at the boundary, use schema validation, and never pass raw request objects to query builders.

### 7.13.4 ORM escape hatches

ORMs parameterize normal filters but expose raw-SQL and dynamic-identifier APIs. Injectable patterns include `order_by(user_input)`, `SELECT ... WHERE name = ${raw}`, and stored procedures that concatenate. Column/table names cannot be parameterized, so allow-list them from a fixed map. Verify by comparing a safe query against an "order by" parameter set to a random string — a 500 or SQL error indicates the value reached SQL syntax.

## 7.14 Mastery Deep Dive: Authentication vs. Authorization Architecture

### 7.14.1 Session lifecycle and fixation

A secure session lifecycle: generate ≥128 bits from a CSPRNG at login (never reuse the pre-login ID — that is **session fixation**), bind it to the user, rotate on privilege change, enforce idle and absolute timeouts, and invalidate server-side on logout and password change. Test fixation in a lab: obtain a session ID before login, log in, and check whether the same ID remains valid; if it does, an attacker who can set that ID in a victim's browser can hijack the session. Also confirm invalidation is server-side — deleting only the client cookie is not logout.

### 7.14.2 Password storage

| Algorithm | Property | Guidance |
|-----------|----------|----------|
| bcrypt | Adaptive work factor, salt built in | Use cost ≥12; truncate issue at 72 bytes |
| Argon2id | Memory-hard, resists GPU/ASIC | Preferred; tune memory/iterations/parallelism |
| scrypt | Memory-hard | Acceptable alternative |
| SHA-256 / MD5 | Fast, unsalted by default | Never use for passwords |

Verification: inspect a lab database dump — hashes should be salted and slow to verify; identical passwords must produce different hashes. During auth testing, look for plaintext comparison, unsalted hashes, and password-reset tokens that double as authentication.

### 7.14.3 Authorization models in practice

RBAC (roles), ABAC (attributes), and ReBAC (relationships) are implementation strategies; the security property is the same: for *every request*, on the *server*, decide whether this principal may perform this action on this object. Centralize the check (a policy layer or middleware) and deny by default. Test with a role × action × object matrix and a second account (Chapters 9–10). Missing checks on bulk/export endpoints and on "internal" endpoints are the highest-yield findings.

### 7.14.4 CSRF defenses and their limits

Layer defenses: synchronizer tokens (per-session random token in body/header), `SameSite=Lax/Strict` cookies, `Origin`/`Referer` validation, and re-authentication for sensitive actions. Double-submit cookies are acceptable if signed. Bypass patterns to check in labs: token validated only on POST (try method override), token missing on JSON endpoints with permissive CORS, `Origin` checked only when present (remove it via a cross-origin navigation technique), and `SameSite=None` cookies. CORS is not a CSRF defense — simple requests do not preflight.

### 7.14.5 Rate limiting and brute force

Rate limits must key on the right principal: per-account (stops credential stuffing against one user), per-IP (stops distributed spraying, but NAT/VPN and `X-Forwarded-For` spoofing matter), and per-token. Detect gaps: no lockout/backoff on login, OTP endpoints with unlimited attempts, and limits keyed only on a spoofable header. Verify a fix by scripting the exact number of allowed attempts plus one and confirming the 429. Use exponential backoff and CAPTCHA only as secondary layers.

## 7.15 Mastery Deep Dive: JWT Deep Dive

### 7.15.1 Structure and verification checklist

A JWS (signed JWT) is `base64url(header).base64url(payload).base64url(signature)`. Verification must: parse the header and **pin the algorithm**, verify the signature with the correct key, then validate claims — `exp` (not expired), `nbf` (not before), `iat` (reasonable), `iss` (expected issuer), `aud` (this application), and any application claims (tenant, role, scope). A JWE (encrypted JWT) has five parts; JWTs are *signed, not encrypted* by default, so payload data is readable by anyone holding the token.

### 7.15.2 Algorithm and key confusion (labs only)

| Flaw | Mechanism | Lab-safe verification |
|------|-----------|-----------------------|
| `alg:none` | Verifier accepts "none" and ignores signature | Change header to `{"alg":"none"}`, drop signature; see if the app accepts it |
| RS256→HS256 | Verifier uses the RSA *public* key as an HMAC secret when HS256 is requested | Sign a modified token with HMAC using the lab's public key as secret; see if accepted |
| `jku`/`jwk` injection | Verifier fetches keys from a URL in the header | Point `jku` at a lab server you control hosting your own key; only in an authorized lab |
| `kid` path/SQL injection | `kid` used to look up a key file or DB row without validation | Set `kid` to a known lab path or `' UNION SELECT ...`; observe behavior |
| Weak HMAC secret | HS256 with a guessable secret | Offline crack a token you own against a wordlist; labs only |

Defenses: hard-code the expected algorithm and key (never trust `alg`/`jku`/`jwk` from the token), validate all claims, use asymmetric signing for multi-service systems, keep keys out of source, rotate keys with `kid` allow-listing, and prefer opaque tokens where you can centralize revocation. Confirm a fix by replaying each lab token and observing rejection (401) with a generic error.

### 7.15.3 Detection and common mistakes

Recognize JWTs by the three base64url segments starting with `eyJ`. Decode (do not trust) at jwt.io to view claims; identify `alg`, `iss`, `aud`, and expiry. Common mistakes: treating "decoded" as "verified," trusting client-side role claims for authorization, accepting expired tokens, ignoring `aud` (a token for another service works here), and no revocation path after compromise. Detection on the defender side: log rejected signature/claim failures and alert on spikes, and monitor for tokens with unexpected `alg` values.

## 7.16 Mastery Deep Dive: OAuth 2.0 and OIDC

### 7.16.1 Flows and where they break

Authorization Code + PKCE is the recommended flow for public clients. The security-critical bindings are: `state` ties the authorization request to the browser session (CSRF protection); PKCE (`code_challenge` = S256 of `code_verifier`) proves the party redeeming the code is the one that started the flow (code-interception protection); `redirect_uri` must be exactly registered; the token must be validated for issuer/audience/signature/expiry.

```
1. Client: GET /authorize?client_id=C&redirect_uri=https://app/cb&response_type=code
           &scope=openid profile&state=RANDOM&code_challenge=HASH&code_challenge_method=S256
2. Provider: authenticates user, obtains consent
3. Provider: 302 -> https://app/cb?code=XYZ&state=RANDOM
4. Client: verifies state == RANDOM; POST /token with code + code_verifier
5. Provider: validates PKCE; returns access_token, refresh_token, id_token (OIDC)
6. Client: validates id_token signature, iss, aud, exp, nonce
```

### 7.16.2 Attack patterns and defenses (labs only)

| Flaw | Lab test | Defense |
|------|----------|---------|
| Missing `state` | Start a flow, drop `state`; see if the callback is accepted | Require and cryptographically bind `state` (or PKCE with `nonce`) |
| No PKCE | Public client without `code_challenge` | Require S256 PKCE for all public clients |
| Loose `redirect_uri` | Try `https://app/cb.evil.com`, suffix/prefix, `@`, `#`, path traversal | Exact string match; no wildcards; validate parsed URL |
| Token leakage | Check for tokens in URL fragments/history/referrers | Use code flow, `Referrer-Policy: no-referrer`, short code lifetimes |
| Wrong issuer token | Submit a valid token from another issuer/lab tenant | Validate `iss` and `aud` against expected values |
| `id_token` trusted without verification | Forge/alter claims in a lab token | Full JWS verification + `nonce`, `iat`, `azp` checks |

### 7.16.3 OIDC specifics

OIDC adds `id_token` (a signed JWT identity assertion) and the UserInfo endpoint. Validate `iss`, `aud` (must contain your `client_id`), `exp`, `iat`, `nonce` (binds to the auth request), and `azp` for multiple audiences. Do not use access-token contents for authorization decisions — they are for the resource server. Discovery documents (`.well-known/openid-configuration`) and JWKS endpoints tell you the expected algorithms and keys; fetch them over TLS and cache with pinning.

### 7.17.2 Common mistakes

- Reusing the pre-authentication session ID (fixation) or deleting only the client cookie on logout.
- Trusting JWT claims without verifying the signature, algorithm, issuer, and audience.
- Using RSA public key material as an HMAC secret, or honoring token-supplied `jku`/`jwk`.
- Gating CSRF protection on a header that is only sometimes present.
- Rate limiting by a spoofable `X-Forwarded-For` without trusting a known proxy chain.

### 7.17.3 Knowledge checks (answers below)

1. Why does a prepared statement stop SQLi even when the input contains quotes and comments?
2. A token has a valid signature but `aud` is a different service. Accept or reject, and why?
3. What does PKCE's `code_verifier` prove that `state` alone does not?
4. Why is deleting the session cookie insufficient for logout?

**Answers.** (1) The SQL text and data are sent separately; the DBMS treats placeholders strictly as values, so meta-characters cannot alter the parse tree. (2) Reject — `aud` binds the token to its intended resource server; a token for another audience must not be trusted here. (3) `state` binds the browser session to the flow (CSRF); PKCE proves the party redeeming the code possesses the secret derived at initiation, defeating authorization-code interception. (4) The server-side session record remains valid; an attacker possessing the ID can reuse it.

2. Decode a JWT you control;forge an `alg:none` variant and confirm a hardened verifier rejects it.
3. Implement a small OAuth Authorization Code + PKCE client; demonstrate that dropping `state` breaks the session binding and that lax `redirect_uri` matching permits a callback to an attacker-controlled path in the lab.
4. Build a lab login with per-account and per-IP rate limits; attempt the forward-header bypass and confirm the fixed version resists it.

## 7.18 Mastery Deep Dive: Advanced Database Topics

### 7.18.1 Stored procedures and second-order injection

A stored procedure is not automatically safe: if it builds SQL by concatenation internally, passing it a parameter does not help. Investigate procedures in a lab by checking whether their inputs are concatenated into dynamic SQL (`EXEC`, `sp_executesql` with concatenated strings). **Second-order injection** occurs when input is stored safely (escaped on insert) but later retrieved and concatenated into a different query — the payload sleeps in the database until a "safe-looking" value is reused. Test by storing a marker with quotes in one lab field and observing where it appears in later queries (search, export, report generation). Defense: parameterized queries at *every* use site, not just the input site.

### 7.18.2 Database privileges and isolation

The application's DB account should have only the privileges it needs: `SELECT/INSERT/UPDATE/DELETE` on specific tables, no `DROP`, no `FILE`, no `xp_cmdshell`, no DDL. Row-Level Security (PostgreSQL RLS) and separate schemas per tenant provide defense in depth: even if an authorization check is missed, the database returns no rows outside the tenant. Inspect grants in a lab (`\du` in psql, `SHOW GRANTS` in MySQL) and verify the app account cannot read sensitive system tables. Connection pooling means a "session" variable set by one request may persist — avoid storing per-user state in database session variables.

### 7.18.3 Out-of-band and advanced extraction

When the application does not reflect results, lab testers use out-of-band (OOB) techniques: SQL that triggers a DNS or HTTP callback to a listener you control (e.g., MSSQL `xp_dirtree` to a UNC path, PostgreSQL `COPY ... TO PROGRAM` where permitted — only in an isolated lab). These prove exfiltration capability without reading real data. For blind inference, binary-search a value with conditional delays or boolean responses: one bit per request yields the value with logarithmic requests. Defense: least privilege (no outbound filesystem/network from the DB), network egress controls, WAF as a temporary layer, and parameterized queries that make the entire class unreachable.

## 7.19 Mastery Deep Dive: Session and Token Architectures

### 7.19.1 Opaque tokens vs. JWTs

| Property | Opaque session token | JWT |
|----------|----------------------|-----|
| Storage | Server-side session store | Client-side, self-contained |
| Revocation | Easy (delete server record) | Hard (needs denylist or short expiry) |
| Data exposure | None (random string) | Payload readable by holder |
| Scaling | Needs shared store (Redis) | Stateless, no store needed |
| Revocation on logout | Immediate | Delayed until expiry unless tracked |

Hybrid designs use short-lived JWTs plus a server-side refresh-token store with rotation and reuse detection: if a refresh token is used twice, revoke the whole family. Detect reuse-detection gaps in a lab by replaying an old refresh token and observing whether the session is invalidated.

### 7.19.2 SAML and federation attacks (labs only)

SAML SSO uses signed XML assertions. Classic implementation flaws: accepting assertions without verifying the signature, signature-wrapping (placing a signed node elsewhere and an unsigned malicious assertion where the app reads it), not validating `audience`/`recipient`/`InResponseTo`, and accepting assertions from any IdP. In a lab, demonstrate by modifying an assertion's attributes and observing whether access is granted. Defense: use a mature SAML library, verify the signature over the correct node, validate all conditions and timestamps, and bind the assertion to the auth request. This pairs with the XXE and JWT topics covered elsewhere.

### 7.19.3 Device binding and step-up authentication

High-value actions often require re-authentication or MFA ("step-up"). Implementation flaws: the step-up flag is client-supplied (`mfa=passed`), the OTP endpoint lacks rate limits, codes are reusable, or a "trusted device" cookie is forgeable. Defense: track step-up state server-side in the session, expire it quickly, bind it to the action, and require fresh verification for sensitive operations. Verify by replaying a step-up request after its expiry and confirming rejection.

## 7.10 Key Takeaways

- Backends mediate every trust boundary between client and data; authorization must be enforced server-side, per object.
- OAuth 2.0 is authorization; OIDC adds identity; both are easy to implement incorrectly.
- JWTs require full signature and claim validation; they are signed, not encrypted.
- Parameterized queries, strict deserialization, least privilege, and rate limiting prevent entire vulnerability classes.
