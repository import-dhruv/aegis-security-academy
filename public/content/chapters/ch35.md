# Chapter 35: Practical Assessments

> **Learning objectives.** Apply your knowledge across seven progressive assessments. Each includes scenarios and a separate solutions section. Do not read solutions until you have attempted the tasks.

## 35.1 Assessment 1: Beginner Security Assessment

**Tasks**

1. Define confidentiality, integrity, and availability with one example each.
2. Convert `0x2A` to decimal and binary.
3. Explain the difference between a process and a thread.
4. Given `10.0.0.0/8`, state the number of addresses and the private-range purpose.
5. List four HTTP security headers and their purpose.
6. What is the difference between a vulnerability, a threat, and a risk?
7. Name three rules from a typical bug bounty policy that protect data.
8. Explain why `SameSite=Lax` helps against CSRF.

## 35.2 Assessment 2: Intermediate Web Security Assessment

**Scenario:** An authorized lab app has these behaviors:

- `GET /api/invoice/8821` returns invoice data; changing `8821` to `8822` returns another user's invoice.
- The search parameter `q` is echoed unencoded into a `<div>`.
- Password reset tokens are 6-digit numbers and do not expire.
- The app sets `Set-Cookie: session=...; Secure` without HttpOnly.

**Tasks**

1. Identify each issue and map it to a CWE.
2. For each, describe a safe validation approach using your own accounts.
3. Rank by severity and justify.
4. Write a remediation for each.
5. List two false positives that could mimic the XSS finding.

## 35.3 Assessment 3: Advanced Application Security Assessment

**Scenario:** A lab application sits behind a reverse proxy. You observe:

- Both `Content-Length` and `Transfer-Encoding` headers on a POST.
- A cache ignores `X-Forwarded-Host` but reflects it into a script URL.
- Two parallel requests both succeed in redeeming a single-use coupon.
- A settings merge copies `__proto__` keys.

**Tasks**

1. Explain the mechanism of each issue in detail.
2. Describe a safe lab validation for each.
3. For the desync issue, explain how front-end/back-end disagreement arises.
4. Propose a defense-in-depth strategy covering all four.
5. Describe how you would report these as separate findings.

## 35.4 Assessment 4: API Security Challenge

**Scenario:** A lab REST API and GraphQL endpoint expose the same user records. Observations:

- `GET /api/v1/users/17` works with user A's token for user B's ID.
- `PUT /api/profile` accepts `{"role":"admin"}` and persists it.
- GraphQL introspection is enabled and a `users` query returns email fields not in REST.
- No rate limit exists on `/api/login`.

**Tasks**

1. Name the OWASP API Top 10 category for each issue.
2. Explain how an inconsistent REST/GraphQL authorization surface arises.
3. Design a test plan with two user accounts and two tenants.
4. Provide remediations including schema-level controls.
5. Explain why mass assignment is distinct from BOLA.

## 35.5 Assessment 5: Cloud Security Challenge

**Scenario:** In your own lab cloud account you find:

- An S3 bucket policy with `Principal: "*"` and read access.
- An EC2 instance with IMDSv1 enabled and an app with an SSRF parameter.
- A CI workflow that runs untrusted PR code with cloud credentials.
- A container running as root with the Docker socket mounted.

**Tasks**

1. For each issue, explain the attack path an adversary would take.
2. Prioritize by impact and likelihood.
3. Provide concrete remediations.
4. Explain how you would audit the account safely with Prowler/ScoutSuite.
5. Describe the shared-responsibility boundary relevant to each.

## 35.6 Assessment 6: AI Security Challenge

**Scenario:** An authorized lab AI support assistant uses RAG over documents and has tools: `read_doc`, `send_email`, and `issue_refund`. Hidden context contains the support MACRO list. You can seed documents in your own tenant and there is a second tenant.

**Tasks**

1. Design a test for indirect prompt injection via a seeded document.
2. Design a test for cross-tenant RAG leakage using marker documents.
3. Explain how to test tool-call authorization for `issue_refund`.
4. Distinguish which observations would be harmless jailbreaks versus genuine vulnerabilities.
5. Map your findings to OWASP LLM Top 10 2026 and Agentic Top 10 2026 categories.
6. Describe a deterministic architecture change that would prevent the most severe issue.

## 35.7 Assessment 7: Final Independent Research Assessment

**Task:** Choose a technology you own or an open-source project. Perform a mini research project:

1. Write a threat model: assets, adversaries, trust boundaries.
2. Perform reconnaissance and map the attack surface.
3. Select one vulnerability class and research its root cause in this technology.
4. Build a safe lab reproduction or a minimal static-analysis test.
5. Produce a finding (or a documented refutation) with evidence.
6. Write a report and, if appropriate, a responsible disclosure plan.
7. Reflect on what you would do differently with more time.

**Deliverables:** threat model, attack-surface map, research notes, reproducer, report, and disclosure plan.

## Solutions

### Solutions to Assessment 1

1. Confidentiality: only authorized access (e.g., encryption); Integrity: data unmodified (e.g., hashes/signatures); Availability: accessible when needed (e.g., redundancy).
2. `0x2A` = 42 decimal = `0010 1010` binary.
3. A process has its own address space; a thread shares it with siblings in the process and has its own stack/registers.
4. `10.0.0.0/8` has 2^24 addresses (16,777,216); it is RFC1918 private space, not routable on the public internet.
5. CSP restricts content sources; HSTS forces HTTPS; X-Content-Type-Options prevents MIME sniffing; X-Frame-Options/frame-ancestors prevents clickjacking; Referrer-Policy controls referrer leakage.
6. A vulnerability is a weakness; a threat is an actor/event that can exploit it; risk is the likelihood × impact given threats and controls.
7. Use only test accounts; do not access other users' data; no DoS/destructive testing; stay in scope.
8. SameSite=Lax prevents cookies being sent on most cross-site requests, so a forged cross-site request is unauthenticated.

### Solutions to Assessment 2

1. IDOR/BOLA (CWE-639); Reflected XSS (CWE-79); weak password-reset token/expiry (CWE-640); missing HttpOnly (CWE-1004/614).
2. Create accounts A and B; swap invoice IDs with A's token; submit a harmless marker in `q` and observe rendering; request two resets and examine token structure/expiry in the lab; inspect Set-Cookie attributes.
3. IDOR high (direct data exposure); XSS medium-high (session theft limited by Secure but not HttpOnly); reset token medium/high (account takeover); missing HttpOnly medium (amplifies XSS).
4. Object-level authorization checks; context-aware output encoding; high-entropy single-use expiring tokens with rate limits; add HttpOnly to cookies.
5. Encoded reflection (`&lt;`), CSP blocking execution, payload in a text node/attribute that is not executable.

### Solutions to Assessment 3

1. Smuggling: conflicting framing headers cause parser disagreement. Cache poisoning: unkeyed reflected header. Race: non-atomic check-then-act. Prototype pollution: unsafe recursive merge.
2. Use dedicated labs with harmless markers and controlled listeners; parallel requests for the race; a pollution marker checked on unrelated objects.
3. The front-end may honor Content-Length while the backend honors Transfer-Encoding (or vice versa), leaving a prefix that becomes the start of a second request interpreted by the backend.
4. Normalize/reject ambiguous framing; include influential headers in cache keys and strip untrusted headers; make state changes atomic with transactions and idempotency keys; reject dangerous object keys and use Object.create(null).
5. Separate reports per distinct root cause; link them in a chain only if the impact cannot be shown independently.

### Solutions to Assessment 4

1. BOLA (API1); Mass assignment / BOPLA (API3); Improper inventory/excessive exposure (API9/API3); Unrestricted resource consumption / broken auth (API4/API2).
2. Different teams or code paths implement REST and GraphQL resolvers; authorization is often added to one but not the other, or the schema exposes fields the REST DTO filters.
3. Two accounts and two tenants; compare object access, role fields, introspection output, and login throttling across both interfaces.
4. Centralized object-level authorization; explicit writable-field allow-lists; disable introspection or authenticate it; schema-level field authorization; rate limits per token/IP.
5. BOLA is about *which object* you can access; mass assignment is about *which fields* you can set on an object you can access.

### Solutions to Assessment 5

1. Public bucket → anonymous data read/write; IMDSv1 + SSRF → instance credential theft; untrusted PR code with credentials → pipeline compromise and cloud account takeover; root container + Docker socket → host compromise.
2. Pipeline credentials and SSRF→IMDS are typically highest; public bucket depends on data sensitivity; root container is high if exploitable.
3. Block public access and use least-privilege bucket policies; enable IMDSv2 and egress controls; isolate PR builds, use OIDC short-lived credentials, pin actions; run non-root and never mount the Docker socket.
4. Use read-only credentials in a dedicated lab profile; run Prowler/ScoutSuite; review findings; verify each manually before remediating.
5. Provider secures infrastructure; customer secures data, IAM, configs, and workloads (and, for containers/Kubernetes, the guest and orchestration configuration).

### Solutions to Assessment 6

1. Seed a document containing a harmless instruction marker; ask the assistant to summarize; observe whether it attempts an unintended tool call.
2. Seed tenant A with a unique marker; query as tenant B for related terms; check whether A's marker enters context or the answer.
3. With a low-privilege user, attempt to trigger `issue_refund` with another account's identifier; check whether a deterministic policy gate rejects it.
4. Jailbreak text with no side effect is harmless; a tool call, data read, or tenant crossing is a genuine security finding.
5. Indirect injection → LLM01:2026; tool misuse → ASI02; privilege abuse → ASI03; cross-tenant RAG → LLM09:2026; hidden context → LLM08:2026; unbounded consumption if loops → LLM06:2026.
6. Enforce authorization in a deterministic policy gate outside the model, with minimal tool scopes and human approval for high-impact actions.

### Solutions to Assessment 7

Evaluate against: clarity of threat model, correctness of trust-boundary identification, rigor of reproduction, honesty about false positives and limitations, quality of report, and responsibility of disclosure plan. A refuted hypothesis with clear evidence is a successful research outcome — negative results are part of research.

## 35.8 Key Takeaways

- Assessments test reasoning, not memorization.
- Always use owned systems, labs, and synthetic data.
- Documenting a refutation is as valuable as confirming a finding.
