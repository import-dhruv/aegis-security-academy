# Chapter 6: JavaScript and Web Programming

> **Learning objectives.** Explain how HTML, CSS, JavaScript, the DOM, and browser APIs fit together; describe the browser security model (SOP, CORS, cookies, storage); contrast frontend frameworks and backend Node.js; and explain how web-development knowledge reveals vulnerabilities.

## 6.1 The Web Platform

A web page is a document rendered by a browser. Three technologies form its core:

- **HTML (HyperText Markup Language)** describes structure and content: headings, paragraphs, links, forms, images.
- **CSS (Cascading Style Sheets)** describes presentation: layout, colors, fonts, responsive behavior.
- **JavaScript (JS)** adds behavior: event handling, network requests, DOM manipulation.

```html
<!doctype html>
<html>
<head><title>Lab</title></head>
<body>
  <form id="login">
    <input name="user" value="">
    <button type="submit">Go</button>
  </form>
  <div id="result"></div>
  <script src="/app.js"></script>
</body>
</html>
```

## 6.2 JavaScript Fundamentals

```javascript
const name = "alice";            // immutable binding
let count = 0;                   // mutable
var old = 1;                     // legacy, function-scoped

function greet(who) {
  return `Hello, ${who}`;
}

const user = { name: "alice", roles: ["user"] };
user.roles.push("admin");

[1, 2, 3].map(x => x * 2);        // [2, 4, 6]
```

Key concepts: prototypes and prototypal inheritance, closures, `this` binding, hoisting, event loop (call stack + task/microtask queues), `async`/`await` and Promises, modules (`import`/`export`), strict mode.

JavaScript is dynamically typed and forgiving, which is precisely why it produces subtle security bugs: type coercion (`"1" == 1`), prototype manipulation, and implicit globals.

## 6.3 The DOM and Browser Execution

The **DOM (Document Object Model)** is a tree representation of the page that JS can mutate.

```
document
 +-- html
     +-- head
     +-- body
         +-- form#login
         |   +-- input[name=user]
         |   +-- button
         +-- div#result
```

```javascript
const input = document.querySelector('input[name="user"]');
document.getElementById("result").textContent = input.value;
```

Using `innerHTML` with untrusted data creates **DOM-based XSS**:

```javascript
// VULNERABLE
document.getElementById("result").innerHTML = location.hash.slice(1);
```

`textContent` is safe because it creates a text node, not markup. The distinction between "data" and "code" is the heart of injection security.

The browser executes JS in a sandboxed environment with restricted access to the OS. It parses HTML incrementally, which creates interesting edge cases (mutation XSS, parser differentials) that advanced researchers study.

## 6.4 Browser Security Model

### Same-Origin Policy (SOP)

The **origin** is scheme + host + port. SOP forbids a page from one origin reading content from another origin. `https://a.com:443` and `https://b.com` are different origins; `http://a.com` and `https://a.com` are different. SOP is the foundation of web isolation.

### CORS (Cross-Origin Resource Sharing)

CORS is a controlled relaxation of SOP: a server can send `Access-Control-Allow-Origin` to permit cross-origin reads. Preflight requests (`OPTIONS` with `Access-Control-Request-Method`) check permissions before non-simple requests.

Misconfigurations: reflecting any origin with `Access-Control-Allow-Credentials: true` allows any site to make authenticated cross-origin requests — a serious flaw. `Access-Control-Allow-Origin: *` cannot be combined with credentials.

### Cookies and Sessions

Cookies are name/value pairs stored by the browser and sent with requests. Attributes:

- `HttpOnly` — JS cannot read it (mitigates XSS cookie theft).
- `Secure` — only over HTTPS.
- `SameSite=Lax|Strict|None` — controls cross-site sending (mitigates CSRF; `None` requires `Secure`).
- `Domain`, `Path`, `Expires`/`Max-Age`.

**Sessions** are server-side state keyed by a session cookie. Alternatives include stateless signed tokens (JWT). Session fixation, prediction, and insufficient expiry are common flaws.

### Web Storage

- `localStorage` — persistent, origin-scoped, up to ~5 MB, accessible to JS.
- `sessionStorage` — per-tab, cleared on tab close.
- `IndexedDB` — structured, asynchronous, larger storage.
- `document.cookie` — cookies accessible to JS (unless HttpOnly).

None of these are secure storage for secrets: any JS running on the origin (including XSS or a compromised third-party script) can read them.

### Fetch, AJAX, WebSockets, Service Workers

```javascript
fetch("/api/user", { credentials: "include" })
  .then(r => r.json())
  .then(data => console.log(data));
```

- **Fetch API / AJAX** enable asynchronous requests.
- **WebSockets** provide full-duplex communication; they are not governed by SOP in the same way, so the server must validate the `Origin` header.
- **Service workers** are persistent, programmable network proxies for an origin; they can intercept requests and cache responses. Compromised or malicious service workers can enable persistent attacks; scope is restricted by path.
- **PostMessage** allows cross-origin messaging; always validate `event.origin` and the message contents.

## 6.5 Frontend Frameworks

React, Angular, Vue, and Svelte abstract DOM manipulation into components and declarative rendering. They reduce (but do not eliminate) injection risk:

- React escapes interpolated values by default, but `dangerouslySetInnerHTML`, `href` with `javascript:`, and unsafe use of refs reintroduce XSS.
- Client-side routing and state introduce new surfaces: open redirects, client-side auth bypass (enforced only in UI), and token storage mistakes.
- **SSR/SSG** (Next.js, Nuxt, SvelteKit) blur the client/server boundary, creating hydration mismatches and server-side injection risks.

## 6.6 Node.js and Express

Node.js runs JavaScript on the server using the V8 engine and an event-driven, non-blocking I/O model.

```javascript
const express = require("express");
const app = express();
app.use(express.json());

app.get("/api/user/:id", (req, res) => {
  const id = req.params.id;
  // DANGER: missing authorization check -> IDOR
  db.query(`SELECT * FROM users WHERE id = ${id}`, (err, rows) => {
    res.json(rows);
  });
});
app.listen(3000);
```

This snippet shows two classic server-side flaws: string-concatenated SQL (injection) and missing authorization (IDOR). Express middleware ordering matters: authentication must run before protected routes. `express.json()` parses request bodies; without size limits it can enable DoS.

## 6.7 How Web Development Knowledge Reveals Vulnerabilities

A researcher who understands development can:

- Read JS bundles to discover hidden endpoints and parameters (Chapter 14).
- Recognize where a framework's escaping defaults are bypassed.
- Understand how a SPA enforces (or fails to enforce) authorization client-side.
- Trace a request from UI to API to database and identify trust boundaries.
- Recognize serialization/deserialization patterns (`JSON.parse`, `prototype` assignment) that enable prototype pollution.

Example: seeing `Object.assign({}, defaults, userInput)` where `userInput` can contain `__proto__` should trigger a prototype-pollution investigation (Chapters 9 and 10).

## 6.8 Exercises

1. Build an HTML page with a form and use JS to render form input with `textContent`; then deliberately switch to `innerHTML` with a harmless `<b>test</b>` payload in your lab and observe the difference.
2. Use browser DevTools to inspect cookies and their attributes on a site you own.
3. Set up two local origins (e.g., `localhost:3000` and `localhost:3001`) and observe SOP blocking a fetch; add CORS headers and observe the change.
4. Write a small Express app with an intentional IDOR and verify that adding an authorization check fixes it.
5. Inspect a JS bundle of an app you own and enumerate API paths referenced in it.

## 6.9 Key Takeaways

- Web pages are HTML + CSS + JS manipulating a DOM; injection arises when data becomes code.
- SOP isolates origins; CORS, cookies, storage, and postMessage are controlled relaxations with their own pitfalls.
- Frameworks reduce common bugs but introduce framework-specific bypasses and client/server boundary issues.
- Understanding the developer's mental model lets you predict where their assumptions fail.
