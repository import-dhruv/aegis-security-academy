# Chapter 19: Cloud and Infrastructure Security

> **Learning objectives.** Explain shared responsibility and core cloud services (AWS, GCP, Azure); analyze IAM, storage, metadata services, serverless, containers, Kubernetes, CI/CD, and supply-chain risks; and research cloud security without touching unauthorized infrastructure.

## 19.1 Cloud Fundamentals and Shared Responsibility

Cloud providers operate a **shared responsibility model**: the provider secures the *cloud* (physical infrastructure, hypervisor, networking), while the customer secures *in the cloud* (data, identity, configurations, workloads). The exact split varies by service model (IaaS, PaaS, SaaS).

Core providers:

- **AWS:** IAM, EC2, S3, Lambda, RDS, CloudFormation, VPC.
- **Google Cloud (GCP):** Cloud IAM, Compute Engine, Cloud Storage, Cloud Functions, GKE, VPC.
- **Microsoft Azure:** Entra ID (Azure AD), VMs, Blob Storage, Functions, AKS, VNets.

Most cloud breaches are caused by misconfiguration, over-privileged identities, or leaked credentials — not exotic provider vulnerabilities.

## 19.2 IAM and Credentials

**Identity and Access Management (IAM)** defines who can do what.

- **Users/groups/roles** and policies (allow/deny statements).
- **Access keys** (long-lived) vs. **temporary credentials** (STS, instance profiles) — prefer temporary.
- **Identity federation:** SSO via SAML/OIDC; workload identity federation for non-human identities.
- **Least privilege:** grant only required actions on specific resources.
- **MFA** for human accounts; key rotation; no keys in source code.

Common mistakes: wildcard actions/resources (`Action: "*"`), over-permissive trust policies, unused credentials, and access keys in public repos or mobile apps.

## 19.3 Storage Misconfigurations

Object storage (S3, Cloud Storage, Blob) is frequently exposed publicly. Risks:

- Public read/write buckets.
- Bucket policies with `Principal: "*"`.
- Enumerated bucket names exposing data.
- Missing encryption or versioning.

Research only in authorized accounts (your own lab or an in-scope program). Use provider tools and Prowler/ScoutSuite (Chapter 16). Never download or retain real user data.

## 19.4 Cloud Metadata Services

Compute instances expose a metadata service (e.g., AWS `169.254.169.254`) providing instance credentials. SSRF (Chapters 9 and 10) can reach it. Defenses:

- AWS IMDSv2 (token-based) instead of IMDSv1.
- Network controls (no egress to link-local).
- GCP: require `Metadata-Flavor: Google` header and disable legacy endpoints.

## 19.5 Serverless Security

Lambda/Functions introduce:

- Over-privileged execution roles.
- Event injection (untrusted data from queues, buckets, API gateways).
- Secrets in environment variables or code.
- Dependency and layer vulnerabilities.
- Denial-of-wallet (unbounded invocations).

Fix with least-privilege roles, input validation, secret managers, and concurrency/rate limits.

## 19.6 Container Security

Containers share the host kernel (Chapter 3). Risks:

- Vulnerable base images and dependencies.
- Running as root inside containers.
- Privileged containers and mounted Docker socket.
- Insecure container registries.
- Secrets baked into images.

Defenses: minimal images, non-root users, no privileged mode, seccomp/AppArmor, image scanning (Trivy/Grype), and signed images.

## 19.7 Kubernetes Security

Kubernetes orchestrates containers. Security areas:

- **RBAC:** least-privilege service accounts; avoid cluster-admin.
- **Network policies:** default-deny and allow required flows.
- **Pod security:** no privileged pods, read-only root filesystem, dropped capabilities.
- **Secrets management:** avoid plaintext secrets in manifests; use a secret manager.
- **API server exposure:** authenticate and authorize; restrict anonymous access.
- **Admission control:** enforce policies (e.g., Kyverno, OPA Gatekeeper).

Misconfigurations can allow pod escape, lateral movement, or cluster compromise. Test only in your own lab cluster.

## 19.8 CI/CD Security

Pipelines are high-value supply-chain targets:

- Protect branch rules and require reviews.
- Minimize secrets in pipelines; use OIDC short-lived credentials.
- Pin actions/dependencies to immutable versions.
- Sign build artifacts and produce SBOMs.
- Isolate build runners; avoid running untrusted PR code with secrets.

## 19.9 Secrets Management

Use dedicated managers (AWS Secrets Manager, GCP Secret Manager, HashiCorp Vault). Never hardcode secrets. Scan repos with Gitleaks (Chapter 16). Rotate any exposed secret immediately — treat it as compromised.

## 19.10 Infrastructure as Code (IaC)

IaC (Terraform, CloudFormation) enables repeatable, reviewable infrastructure. Security benefits: version control, policy checks (Checkov), drift detection. Risks: copied insecure templates and over-permissive defaults.

## 19.11 Network Security Groups and Logging

- Security groups / NACLs act as virtual firewalls; default-deny inbound.
- Enable cloud audit logs (CloudTrail, Cloud Audit Logs, Azure Monitor) and alert on suspicious activity.
- Centralize logs in a protected account.

## 19.12 Supply Chain Security

Cloud deployments depend on images, packages, and IaC modules. Verify integrity, scan dependencies, and gate deployments on policy checks. Chapter 20 covers this in depth.

## 19.13 Researching Cloud Security Safely

- Only assess accounts and resources you own or that are explicitly in scope.
- Use read-only auditing tools for assessment.
- Do not access data belonging to other customers.
- Do not exploit a finding against shared provider infrastructure.
- Report via the provider's VDP if you find a provider-side issue.

## 19.14 Exercises

1. Create a lab AWS account (free tier) and run Prowler; remediate one finding.
2. Configure a deliberately public S3 bucket in your lab and verify the scanner detects it; then lock it down.
3. Enable IMDSv2 on a lab EC2 instance and explain how it blocks SSRF credential theft.
4. Scan a lab container image with Trivy and update the base image to remove a CVE.
5. Write a Terraform snippet with an over-permissive IAM policy and run Checkov on it.

## 19.15 Key Takeaways

- Cloud security failures are usually configuration and identity failures.
- IAM least privilege, temporary credentials, and MFA are foundational.
- Metadata services, storage, serverless, containers, Kubernetes, and CI/CD each have distinct risks.
- Audit only what you own or what is explicitly in scope; never touch other tenants.
