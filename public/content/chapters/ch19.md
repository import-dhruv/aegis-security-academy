# Chapter 19: Cloud and Infrastructure Security

> **Learning objectives.** Explain shared responsibility and core cloud services (AWS, GCP, Azure); analyze IAM, storage, metadata services, serverless, containers, Kubernetes, CI/CD, and supply-chain risks; and research cloud security without touching unauthorized infrastructure.

## 19.1 Cloud Fundamentals and Shared Responsibility

Cloud providers operate a **shared responsibility model**: the provider secures the *cloud* (physical infrastructure, hypervisor, networking), while the customer secures *in the cloud* (data, identity, configurations, workloads). The exact split varies by service model (IaaS, PaaS, SaaS).

Core providers:

- **AWS:** IAM, EC2, S3, Lambda, RDS, CloudFormation, VPC.
- **Google Cloud (GCP):** Cloud IAM, Compute Engine, Cloud Storage, Cloud Functions, GKE, VPC.
- **Microsoft Azure:** Entra ID (Azure AD), VMs, Blob Storage, Functions, AKS, VNets.

Most cloud breaches are caused by misconfiguration, over-privileged identities, or leaked credentials — not exotic provider vulnerabilities.

## 19.2 IAM and Credentials

**Identity and Access Management (IAM)** defines who can do what.

- **Users/groups/roles** and policies (allow/deny statements).
- **Access keys** (long-lived) vs. **temporary credentials** (STS, instance profiles) — prefer temporary.
- **Identity federation:** SSO via SAML/OIDC; workload identity federation for non-human identities.
- **Least privilege:** grant only required actions on specific resources.
- **MFA** for human accounts; key rotation; no keys in source code.

Common mistakes: wildcard actions/resources (`Action: "*"`), over-permissive trust policies, unused credentials, and access keys in public repos or mobile apps.

## 19.3 Storage Misconfigurations

Object storage (S3, Cloud Storage, Blob) is frequently exposed publicly. Risks:

- Public read/write buckets.
- Bucket policies with `Principal: "*"`.
- Enumerated bucket names exposing data.
- Missing encryption or versioning.

Research only in authorized accounts (your own lab or an in-scope program). Use provider tools and Prowler/ScoutSuite (Chapter 16). Never download or retain real user data.

## 19.4 Cloud Metadata Services

Compute instances expose a metadata service (e.g., AWS `169.254.169.254`) providing instance credentials. SSRF (Chapters 9 and 10) can reach it. Defenses:

- AWS IMDSv2 (token-based) instead of IMDSv1.
- Network controls (no egress to link-local).
- GCP: require `Metadata-Flavor: Google` header and disable legacy endpoints.

## 19.5 Serverless Security

Lambda/Functions introduce:

- Over-privileged execution roles.
- Event injection (untrusted data from queues, buckets, API gateways).
- Secrets in environment variables or code.
- Dependency and layer vulnerabilities.
- Denial-of-wallet (unbounded invocations).

Fix with least-privilege roles, input validation, secret managers, and concurrency/rate limits.

## 19.6 Container Security

Containers share the host kernel (Chapter 3). Risks:

- Vulnerable base images and dependencies.
- Running as root inside containers.
- Privileged containers and mounted Docker socket.
- Insecure container registries.
- Secrets baked into images.

Defenses: minimal images, non-root users, no privileged mode, seccomp/AppArmor, image scanning (Trivy/Grype), and signed images.

## 19.7 Kubernetes Security

Kubernetes orchestrates containers. Security areas:

- **RBAC:** least-privilege service accounts; avoid cluster-admin.
- **Network policies:** default-deny and allow required flows.
- **Pod security:** no privileged pods, read-only root filesystem, dropped capabilities.
- **Secrets management:** avoid plaintext secrets in manifests; use a secret manager.
- **API server exposure:** authenticate and authorize; restrict anonymous access.
- **Admission control:** enforce policies (e.g., Kyverno, OPA Gatekeeper).

Misconfigurations can allow pod escape, lateral movement, or cluster compromise. Test only in your own lab cluster.

## 19.8 CI/CD Security

Pipelines are high-value supply-chain targets:

- Protect branch rules and require reviews.
- Minimize secrets in pipelines; use OIDC short-lived credentials.
- Pin actions/dependencies to immutable versions.
- Sign build artifacts and produce SBOMs.
- Isolate build runners; avoid running untrusted PR code with secrets.

## 19.9 Secrets Management

Use dedicated managers (AWS Secrets Manager, GCP Secret Manager, HashiCorp Vault). Never hardcode secrets. Scan repos with Gitleaks (Chapter 16). Rotate any exposed secret immediately — treat it as compromised.

## 19.10 Infrastructure as Code (IaC)

IaC (Terraform, CloudFormation) enables repeatable, reviewable infrastructure. Security benefits: version control, policy checks (Checkov), drift detection. Risks: copied insecure templates and over-permissive defaults.

## 19.11 Network Security Groups and Logging

- Security groups / NACLs act as virtual firewalls; default-deny inbound.
- Enable cloud audit logs (CloudTrail, Cloud Audit Logs, Azure Monitor) and alert on suspicious activity.
- Centralize logs in a protected account.

## 19.12 Supply Chain Security

Cloud deployments depend on images, packages, and IaC modules. Verify integrity, scan dependencies, and gate deployments on policy checks. Chapter 20 covers this in depth.

## 19.13 Researching Cloud Security Safely

- Only assess accounts and resources you own or that are explicitly in scope.
- Use read-only auditing tools for assessment.
- Do not access data belonging to other customers.
- Do not exploit a finding against shared provider infrastructure.
- Report via the provider's VDP if you find a provider-side issue.

## 19.14 Exercises

1. Create a lab AWS account (free tier) and run Prowler; remediate one finding.
2. Configure a deliberately public S3 bucket in your lab and verify the scanner detects it; then lock it down.
3. Enable IMDSv2 on a lab EC2 instance and explain how it blocks SSRF credential theft.
4. Scan a lab container image with Trivy and update the base image to remove a CVE.
5. Write a Terraform snippet with an over-permissive IAM policy and run Checkov on it.

## 19.17 Mastery Deep Dive: IAM Policy Evaluation Logic

Authorization in a cloud is not a single check — it is a deterministic evaluation of several policy layers. If you cannot recite the evaluation algorithm from memory, you cannot reason about privilege escalation, trust abuse, or why a "denied" action actually succeeded. This section builds that mental model.

### 19.17.1 The Evaluation Algorithm

Every AWS request is evaluated by a fixed precedence. Learn it as a flowchart, then memorize the one-line summary: **an explicit deny anywhere wins; a same-account allow must survive every allow-gate; cross-account needs an allow on both sides.**

1. **Start from implicit deny.** If no policy grants the action, it is denied. There is no "default allow."
2. **Search every applicable policy** (SCP, resource policy, identity policy, permission boundary, session policy).
3. **Explicit deny short-circuits.** A single `"Effect": "Deny"` that matches the principal, action, resource, and condition denies the request regardless of any allow.
4. **Evaluate gates for same-account requests.** An allow must be present in the identity policy **or** the resource policy, **and** must not be cut off by a permission boundary or session policy, **and** must be permitted by the SCP.
5. **Evaluate cross-account requests.** You need an allow in the identity policy of the calling account **and** an allow in the resource policy of the owning account, plus all the gates above.

> **Lab rule:** every example below uses fictional placeholders such as `<YOUR_LAB_ACCOUNT>` and `<YOUR_LAB_ROLE>`. Use only accounts and roles you own in a sandbox or an explicitly in-scope program. Never test authorization logic against a tenant you do not control.

### 19.17.2 The Six Policy Types and What Each Controls

| Policy layer | Attached to | Can grant? | Can deny? | Scope |
|--------------|-------------|-----------|-----------|-------|
| SCP (service control policy) | AWS Organizations OU/account | No (sets ceiling) | Yes | All principals in account, including root |
| Resource-based policy | Resource (S3 bucket, KMS key, IAM role trust) | Yes | Yes | That resource |
| Identity policy | User/role/group | Yes | Yes | That principal |
| Permissions boundary | Principal (user/role) | No (sets ceiling) | Yes | That principal's max rights |
| Session policy | Passed to `AssumeRole`/`GetFederationToken` | No (filters) | Yes | That one session |
| VPC endpoint policy | VPC endpoint | No (filters) | Yes | Traffic over that endpoint |

Key insight for assessments: a permissions boundary or SCP that *lacks* a permission does **not** grant it. It only caps what identity/resource policies may grant. The most common misreading is treating a boundary as an allow-list that "turns on" rights — it does not.

### 19.17.3 Identity vs. Resource Policies and the Same-Account OR

Within one account, an allow from **either** an identity policy **or** a resource policy is sufficient. This "OR" is why resource policies matter for cross-service access (e.g., an S3 bucket policy allowing a Lambda role to read) and why a broad resource policy can be dangerous.

```json
// Example identity policy (label: AllowReadLabBucket)
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject"],
    "Resource": "arn:aws:s3:::<YOUR_LAB_BUCKET>/*"
  }]
}
```

When you review a policy, annotate three dimensions for every statement: **who** (Principal/implicit principal), **what** (Action), and **under what conditions** (Condition). Attackers hunt for the intersection of a wildcard action, a broad resource ARN, and a missing condition key.

### 19.17.4 Trust Policies, STS, and AssumeRole

A role's **trust policy** is the resource-based policy that decides who may call `sts:AssumeRole`. It is a separate document from the role's identity policy. A realistic trust policy for a lab roles:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::<YOUR_LAB_ACCOUNT>:root" },
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": { "aws:PrincipalTag/team": "lab" }
    }
  }]
}
```

The mental model for escalation: **whoever can edit a role's trust policy can effectively become that role**, because they can add themselves as a principal. Therefore `iam:UpdateAssumeRolePolicy` and `iam:SetRolePolicy` are high-value permissions in an assessment, and confused-deputy bugs often arise when a service assumes a role with more rights than the caller.

To verify in your lab:

```bash
aws sts assume-role \
  --role-arn arn:aws:iam::<YOUR_LAB_ACCOUNT>:role/<YOUR_LAB_ROLE> \
  --role-session-name labcheck
# Inspect the returned Credentials; confirm Expiration is short-lived (~1h)
```

### 19.17.5 Workload Identity Federation (OIDC)

Long-lived keys are the root of most cloud credential leaks. **Workload identity federation** lets an external identity (GitHub Actions, GitLab, or an on-prem workload) exchange a signed token for short-lived cloud credentials — no static secret in the pipeline.

The chain in a GitHub Actions → AWS lab setup:

1. You create an **OIDC identity provider** in IAM that trusts `token.actions.githubusercontent.com`.
2. You create a role whose trust policy constrains `sub` to a specific repo and ref, and `aud` to `sts.amazonaws.com`.
3. The workflow requests an OIDC token and calls `AssumeRoleWithWebIdentity`.

The trust policy condition is the security boundary. A lab-safe example:

```json
"Condition": {
  "StringEquals": {
    "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
  },
  "StringLike": {
    "token.actions.githubusercontent.com:sub": "repo:<YOUR_LAB_ORG>/<YOUR_LAB_REPO>:ref:refs/heads/main"
  }
}
```

The mistake to look for in assessments: a trust policy that only checks `aud` and omits `sub`, which lets **any** repository in **any** org mint credentials for that role. That is a critical, real-world finding class.

### 19.17.6 Decision Table and Common Mistakes

| Observation | Likely cause | Fix |
|-------------|--------------|-----|
| Deny despite matching allow | Explicit deny in another policy | Find the `Deny` via IAM policy simulator / `aws iam simulate-principal-policy` |
| Allow unexpectedly granted | Resource policy OR across accounts | Tighten `Principal` and add `aws:SourceAccount` condition |
| Boundary present but action still denied | Boundary never granted it | Add the action to the boundary (it only caps) |
| Cross-account call fails | Missing allow on resource side | Add trusting account to resource policy |
| FedERATED role assumable by anyone | Trust policy missing `sub` check | Constrain `sub` and `aud` |

**Knowledge check.** A role has an identity policy allowing `s3:*`, a permission boundary allowing only `s3:GetObject`, and an SCP allowing `s3:*`. The principal calls `s3:PutObject`. Allowed or denied? **Answer:** Denied — the permission boundary caps the effective permission and does not include `PutObject`. The SCP ceiling permits it, but the boundary is the tighter gate.

## 19.18 Mastery Deep Dive: Instance Metadata and SSRF-to-Credential Chains

The cloud metadata service is a local HTTP endpoint that hands an instance its own identity and, often, temporary credentials. It sits at the intersection of SSRF and cloud IAM, and it is one of the highest-impact misconfiguration classes in the cloud.

### 19.18.1 IMDSv1 vs. IMDSv2 Mechanics

**IMDSv1** is a plain GET. Any process or SSRF sink that can reach `169.254.169.254` can read role credentials:

```http
GET /latest/meta-data/iam/security-credentials/<YOUR_LAB_ROLE> HTTP/1.1
Host: 169.254.169.254
```

The response is JSON containing `AccessKeyId`, `SecretAccessKey`, `SessionToken`, and `Expiration`. There is no authentication — the only "control" is network reachability.

**IMDSv2** adds a session token with a two-step flow:

```bash
# Step 1: obtain a token (PUT, never a GET)
TOKEN=$(curl -sX PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

# Step 2: use the token on subsequent GETs
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/
```

Why this matters for SSRF: a typical SSRF primitive issues a **GET** to an attacker-chosen URL. It usually cannot set arbitrary headers or perform a **PUT**. IMDSv2 therefore breaks the common SSRF→credential chain at the protocol level, not merely by hiding data.

**Hop limit** is the number of network hops a metadata packet may cross. The default tightened value is `1`. Important lab nuance: if your app runs in a container behind a Docker bridge, a hop limit of `1` can break legitimate IMDSv2 token retrieval because the request crosses the virtual bridge. The usual recommendation for containers is `2` — high enough for the bridge, low enough to block off-instance SSRF. Verify with:

```bash
aws ec2 modify-instance-metadata-options \
  --instance-id <YOUR_LAB_INSTANCE_ID> \
  --http-tokens required --http-put-response-hop-limit 2
```

### 19.18.2 Provider Comparison: Metadata Endpoints

| Provider | Endpoint | Required header | Legacy endpoint risk |
|----------|----------|-----------------|----------------------|
| AWS | `169.254.169.254` | IMDSv2: `X-aws-ec2-metadata-token` on GET; token via PUT | IMDSv1 has no header; disable with `http-tokens required` |
| GCP | `metadata.google.internal` / `169.254.169.254` | `Metadata-Flavor: Google` | v1 beta endpoints lacked the check; require the header |
| Azure | `169.254.169.254` | `Metadata: true` | Old endpoints returned data without the header; require it |

GCP-specific hardening: require the `Metadata-Flavor: Google` header and disable legacy endpoints at the project/org level. Azure: require `Metadata: true` and use managed identities rather than service-principal secrets.

### 19.18.3 SSRF-to-Credential Chain Anatomy (Lab Only)

In your own lab, trace the full chain so you understand each link a defender can break:

1. **Find an SSRF sink** in a lab app — a URL fetcher, PDF renderer, webhook tester, or image proxy that takes a user-supplied URL.
2. **Confirm outbound reachability** to the metadata IP from the app's network position (security groups/NACLs may block link-local).
3. **Attempt IMDSv1 read.** If it succeeds, the instance is a single SSRF away from role credentials.
4. **If IMDSv2 is enforced,** test whether the sink can be coerced into a PUT with a custom header. Most cannot — note this as a mitigated path.
5. **Interpret the response.** A `200` with JSON credentials means the chain is complete; a `401`/`403` means token enforcement is working.
6. **Simulate the impact** by listing what the role can access with the returned credentials in your own account (e.g., `aws s3 ls`), then stop. Never use credentials from any system you do not own.

```http
GET /fetch?url=http://169.254.169.254/latest/meta-data/ HTTP/1.1
Host: <YOUR_LAB_APP>
```
```
# Expected interpretations:
# 200 OK + "iam/"      -> metadata reachable, enumerate further (lab only)
# 401 Unauthorized     -> IMDSv2 token required; SSRF sink cannot supply PUT
# connection timeout   -> link-local egress blocked by network control
```

### 19.18.4 Detection and Fix Checklists

**Detection (in your own account):**

- CloudTrail/GuardDuty alert on `GetCallerIdentity` or metadata calls from unexpected processes (a sign of credential use from an odd host).
- VPC flow logs showing egress to `169.254.169.254` from application tiers that should never call metadata directly.
- Instance profile attached to an instance that does not need one.

**Fix checklist:**

- [ ] Enforce IMDSv2 (`HttpTokens: required`) on all lab instances.
- [ ] Set hop limit to `2` for containerized workloads, `1` otherwise.
- [ ] Block link-local egress from untrusted tiers with security groups / NACLs.
- [ ] Remove instance profiles from instances that do not need cloud API access.
- [ ] Scope the instance role to least privilege so a leaked credential has limited blast radius.

**What mastery looks like:** you can explain why a GET-only SSRF defeats IMDSv1 but not IMDSv2, why hop limit interacts with containers, and how to verify all three providers' endpoint requirements in a lab.

## 19.19 Mastery Deep Dive: Object Storage Misconfiguration Taxonomy

Public bucket incidents are the most common cloud data-exposure finding. The vocabulary differs by provider, but the underlying control model is the same: account-level guardrails, bucket-level policy, legacy ACLs, and time-limited signed URLs.

### 19.19.1 The Four-Layer Model

| Layer | AWS S3 | GCP Cloud Storage | Azure Blob |
|-------|--------|-------------------|------------|
| Account guardrail | S3 Block Public Access (4 flags) | Public Access Prevention | "Allow blob public access" = Disabled |
| Bucket/container policy | Bucket policy (`Principal: "*"`) | IAM allow to `allUsers` / `allAuthenticatedUsers` | RBAC role assignment to Everyone |
| Legacy ACL | ACLs (`Everyone` group) | ACLs (legacy; use uniform access) | Container ACL (`blob`/`container`) |
| Time-limited URL | Pre-signed URL | Signed URL / signed policy | SAS / user-delegation SAS |

**Block Public Access (AWS)** is the strongest single control: it overrides bucket policies and ACLs to force objects private. Its four flags are `BlockPublicAcls`, `IgnorePublicAcls`, `BlockPublicPolicy`, and `RestrictPublicBuckets`. Enable all four. The common assessment finding is a bucket policy granting `s3:GetObject` to `Principal: "*"` with Block Public Access disabled.

### 19.19.2 ACLs vs. Policies vs. IAM

A recurring confusion: ACLs and policies are *different authorization systems*. ACLs are legacy, coarse (READ/WRITE/FULL_CONTROL), and cannot express conditions. Policies are fine-grained and conditional. When **uniform bucket-level access** is on (GCP) or ACLs are disabled (AWS via Block Public Access), ACL grants are ignored entirely. In an assessment, always check which model is authoritative before concluding exposure.

### 19.19.3 Pre-signed URL / SAS Risks

Pre-signed URLs grant time-limited access without changing IAM. They are useful but easy to mishandle:

```bash
# Generate a lab pre-signed URL valid for 600 seconds
aws s3 presign s3://<YOUR_LAB_BUCKET>/<YOUR_LAB_OBJECT> --expires-in 600
```

Risks to look for:

- **Long or infinite expiry** — a leaked URL is a permanent credential.
- **Broad scope** — a SAS token granting `rwl` (read/write/list) at account level instead of a single blob.
- **URLs in logs, screenshots, or support tickets** — treat any exposed signed URL as a leaked capability.
- **No `response-content-disposition`** — can enable content sniffing/XSS when serving HTML from a bucket.

### 19.19.4 Detection, Fix, and Verify

**Detection queries (lab):**

```bash
# List buckets and their public-access settings
aws s3api list-buckets --query 'Buckets[].Name'
aws s3api get-public-access-block --bucket <YOUR_LAB_BUCKET>

# Find buckets with a public bucket policy
aws s3api get-bucket-policy-status --bucket <YOUR_LAB_BUCKET>
```

**Fix checklist:**

- [ ] Enable account-level Block Public Access / Public Access Prevention.
- [ ] Replace `Principal: "*"` with scoped principals plus condition keys (`aws:SourceVpc`, `aws:PrincipalAccount`).
- [ ] Disable legacy ACLs; migrate grants into policies.
- [ ] Bound signed-URL lifetimes; use user-delegation SAS in Azure.
- [ ] Enable versioning and default encryption (SSE-KMS) so accidental exposure is recoverable and auditable.

**Verify it in your lab:** create a bucket with a deliberately public policy, confirm an anonymous `curl` returns `403` once Block Public Access is enabled, then remove the policy and confirm it stays private.

> **Never** enumerate or download objects from buckets you do not own. An authorized assessment tests *your* resources; real user data is out of scope even when a bucket is misconfigured.

## 19.20 Mastery Deep Dive: Container and Kubernetes Attack Paths

Containers isolate processes with kernel features, not hardware boundaries. Kubernetes adds a control plane whose API is a rich privilege surface. Understanding the chain from a single pod to cluster compromise is essential for both attack and defense.

### 19.20.1 Container Escape Mechanics

A container escape breaks out of namespace/cgroup isolation to the host. Common lab-relevant causes:

- **Privileged containers** — `--privileged` grants nearly all capabilities and device access; a classic escape path.
- **Mounted Docker socket** — mounting `/var/run/docker.sock` lets a container talk to the host daemon and launch a privileged sibling container.
- **HostPath / host mounts** — writing to a mounted host path can drop a cron job or SSH key on the host.
- **Kernel exploits** — a vulnerable shared kernel plus a missing seccomp profile.
- **Exposed debugging ports** — unauthenticated Docker API on `2375/tcp`.

```bash
# Lab: inspect what a pod can see (authorized cluster only)
kubectl run lab-probe --image=<YOUR_LAB_IMAGE> --restart=Never -- \
  sh -c 'cat /proc/self/status | grep Cap; mount | grep host'
```

Interpretation: `CapEff` showing a full capability set, or host paths in `mount`, indicates a dangerously permissive workload.

### 19.20.2 Kubernetes RBAC and Service Account Tokens

Every pod mounts a service account (SA) token at `/var/run/secrets/kubernetes.io/serviceaccount/token`. If the SA is over-privileged, compromising the pod means compromising the API with those rights.

Assessment questions:

- Does the SA have `cluster-admin` or wildcard verbs (`apiGroups: ["*"], resources: ["*"], verbs: ["*"]`)?
- Can the SA `create pods` or `get secrets`? `create pods` is a known privilege-escalation primitive: a principal that can create a pod can often mount a more privileged SA and read its token.
- Is `automountServiceAccountToken` disabled for workloads that do not need API access?

```bash
# Lab: enumerate your own permissions
kubectl auth can-i --list --as=system:serviceaccount:<YOUR_LAB_NS>:<YOUR_LAB_SA>

# Lab: decode the mounted token to see its claims (base64 payload only)
cat /var/run/secrets/kubernetes.io/serviceaccount/token | cut -d. -f2 | base64 -d
```

### 19.20.3 Admission Control, Network Policies, and Pod Security

Defense-in-depth layers:

- **Admission controllers** (Kyverno, OPA Gatekeeper) reject non-compliant pods at creation time — e.g., block privileged containers, require read-only root filesystem, require non-root `runAsUser`.
- **Pod Security Standards** (`restricted`, `baseline`, `privileged`) enforce a namespace-level baseline. Set `pod-security.kubernetes.io/enforce: restricted`.
- **Network policies** implement default-deny ingress/egress and allow only required flows. Without them, any pod can reach any other pod and often the metadata service.

```yaml
# Lab: default-deny ingress in a namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: <YOUR_LAB_NS>
spec:
  podSelector: {}
  policyTypes: ["Ingress"]
```

### 19.20.4 etcd and Control-Plane Exposure

`etcd` stores all cluster state, including Secrets, unencrypted by default unless configured. Direct access to etcd (port 2379) or a backup of its data can yield every Secret in the cluster. In an authorized assessment, check:

- Is etcd exposed externally or only on localhost with TLS client auth?
- Are Secrets encrypted at rest with a KMS provider?
- Who can `get secrets` cluster-wide via RBAC?

**Detection + fix checklist:**

- [ ] Audit RBAC for wildcards and `cluster-admin` bindings (`kubectl get clusterrolebindings -o wide`).
- [ ] Set PSS `enforce: restricted` on all namespaces.
- [ ] Apply default-deny network policies.
- [ ] Disable SA token automount where unnecessary; use projected, short-lived tokens.
- [ ] Restrict etcd to localhost + mutual TLS; encrypt Secrets at rest.
- [ ] Scan images with Trivy/Grype and enforce signed images via admission policy.

**Case pattern.** A lab pod uses a default SA that can `create pods`. An attacker who compromises the web app creates a new pod mounting a `cluster-admin` SA, reads its token, and lists all Secrets. Fix: remove `create pods` from workload SAs, disable token automount, and add an admission policy blocking privileged pods.

## 19.21 Mastery Deep Dive: Serverless Event Injection and Denial of Wallet

Serverless shifts risk from the host to the **event** and the **execution role**. Functions are usually triggered by untrusted data and run with an identity that can call cloud APIs.

### 19.21.1 Event Injection Surfaces

Every event source is an input channel:

- **API Gateway / HTTP** — body, query, headers, path parameters.
- **Object storage events** — a newly uploaded file's name, content type, or metadata.
- **Queues (SQS/Pub/Sub)** — message bodies.
- **Streams (Kinesis)** — records.
- **Scheduled events** — cron-like triggers with fixed payloads.

The classic mistake is trusting the event's structure. A function that does `json.loads(event['body'])['user_id']` and uses that ID directly in a database query or cloud API call inherits the trust of the event.

```python
# Lab: defensive pattern — validate and authorize event data
def handler(event, context):
    body = json.loads(event.get("body", "{}"))
    uid = body.get("user_id")
    if not is_valid_uuid(uid):
        return {"statusCode": 400, "body": "invalid id"}
    # Authorization must be checked against the caller's identity,
    # not a user_id supplied in the event.
    if not authorized(context, uid):
        return {"statusCode": 403, "body": "forbidden"}
    ...
```

### 19.21.2 Denial of Wallet (Financial DoS)

Because you pay per invocation, an attacker who can trigger unbounded invocations can inflate your bill. Patterns:

- A public API endpoint with no rate limiting or WAF.
- A storage event that recursively triggers itself (a function writes to the bucket that triggers it).
- Huge payloads that maximize duration and memory.

Defenses: API Gateway throttling/usage plans, concurrency reservations (`ReservedConcurrentExecutions`), billing alarms, input size caps, idempotency and loop guards, and a WAF.

### 19.21.3 Secrets and Dependencies in Functions

- Environment variables are **not** a secret store; anyone with `lambda:GetFunctionConfiguration` can read them. Use a secrets manager with a scoped role.
- Layers and bundled dependencies age out; scan and patch them like any other supply-chain component.
- Execution roles are often wildly over-privileged (e.g., `s3:*` when only `GetObject` on one bucket is needed).

**Fix + detection checklist:**

- [ ] Validate and authorize every event field; never trust `user_id` from the payload.
- [ ] Apply throttling, concurrency caps, and billing alarms.
- [ ] Move secrets to a secret manager; remove them from env vars and code.
- [ ] Scope the execution role to specific actions and resources.
- [ ] Alert on invocation-rate anomalies and error-rate spikes.

## 19.22 Mastery Deep Dive: Cloud Logging and Detection Engineering

A misconfiguration you cannot see is a misconfiguration you cannot fix. Detection engineering turns provider logs into alerts that catch the findings in this chapter.

### 19.22.1 Core Log Sources by Provider

| Signal | AWS | GCP | Azure |
|--------|-----|-----|-------|
| Management/audit events | CloudTrail | Cloud Audit Logs | Azure Activity Log / Monitor |
| Data events (object reads) | CloudTrail data events | Data Access audit logs | Blob diagnostic logs |
| Network flow | VPC Flow Logs | VPC Flow Logs | NSG Flow Logs |
| Identity | IAM/CloudTrail | Cloud Identity logs | Entra ID sign-in/audit logs |
| Managed threat detection | GuardDuty | Security Command Center | Microsoft Defender for Cloud |

Enable **data events** explicitly — CloudTrail management events alone do not log S3 object reads, so a mass exfiltration may be invisible.

### 19.22.2 High-Value Detection Patterns

Write detections as hypotheses about behavior:

- **Credential use from a new location** — a role assumed from an unfamiliar IP or user agent.
- **`GetCallerIdentity` / `ListBuckets` bursts** — enumeration often precedes exploitation.
- **IAM policy changes** — `PutRolePolicy`, `UpdateAssumeRolePolicy`, `AttachRolePolicy` are high-signal escalation steps.
- **Public exposure** — `PutBucketPolicy` with `Principal: "*"`, or `PutBucketAcl` granting `AllUsers`.
- **IMDS probing** — flow logs to `169.254.169.254` from web tiers.

### 19.22.3 Detection-as-Code

Treat detections like software: version-controlled, tested, and reviewed. A simple Sigma-style logic for public bucket exposure (pseudo):

```yaml
title: S3 Bucket Made Public
source: cloudtrail
condition: eventName in [PutBucketPolicy, PutBucketAcl]
  and (requestParameters contains '"Principal":"*"'
       or grantee equals 'AllUsers')
```

**What mastery looks like:** for every attack path in this chapter, you can name the log event that would reveal it and the alert that would fire. Detection completeness is the measure of cloud security maturity.

## 19.23 Mastery Deep Dive: Cloud Assessment Playbook (Authorized Only)

A professional cloud assessment is disciplined and read-only first. The goal is evidence, not exploitation.

### 19.23.1 Methodology

1. **Scoping and rules of engagement.** Define exact accounts, subscriptions, and projects. Confirm written authorization. Agree on "no data access, no state changes."
2. **Credentials with least privilege.** Use a read-only role (`SecurityAudit`) in the lab account. Never use production admin credentials.
3. **Inventory.** Enumerate accounts, identities, roles, resources, and network topology.
4. **Automated read-only scan.** Run tools that only call `Describe`/`List`/`Get` APIs.
5. **Manual validation.** For each automated finding, confirm the configuration and assess real impact — a "public" bucket behind Block Public Access is not actually public.
6. **Prioritize.** Rank by exploitability and blast radius, not CVSS alone.
7. **Report.** Provide evidence, impact, and a specific fix for each finding.

### 19.23.2 Tool Comparison

| Tool | Style | Best for | Notes |
|------|-------|----------|-------|
| Prowler | CLI, checks-as-code | AWS/Azure/GCP CIS & benchmarks | Read-only; produces JSON/CSV/HTML |
| ScoutSuite | Multi-cloud python | Broad config review | Generates browsable HTML report |
| Steampipe | SQL interface over cloud APIs | Custom queries, drift, inventory | Query cloud like a database |
| Checkov | IaC + cloud scanning | Terraform/CloudFormation misconfigs | Shift-left; runs in CI |

### 19.23.3 Reporting and Ethics

- Report findings through the agreed channel; do not retain customer data.
- Never test a finding against shared provider infrastructure — report provider-side issues via the provider's VDP.
- Distinguish "misconfiguration in our scope" from "provider vulnerability" clearly.

## 19.24 Mastery Deep Dive: Twelve Realistic Misconfiguration Case Patterns

Each row is a pattern you should recognize instantly, with impact and fix.

| # | Pattern | Impact | Fix |
|---|---------|--------|-----|
| 1 | S3 bucket policy `Principal: "*"`, BPA off | Public data exposure | Enable BPA, scope principal |
| 2 | IAM user with long-lived access keys in code | Credential theft → account takeover | OIDC/roles, rotate, secrets manager |

## 19.25 Mastery Deep Dive: Verification, Checklists, and Knowledge Checks

### 19.25.1 "Verify It in Your Own Lab" Sequence

1. Create a free-tier lab account and a dedicated lab Kubernetes cluster.
2. Run Prowler in read-only mode; record baseline findings.
3. Deliberately expose one bucket, confirm the scanner detects it, then enable Block Public Access and confirm remediation.
4. Enforce IMDSv2 on one instance and demonstrate a GET-only SSRF can no longer retrieve credentials.
5. Deploy a pod with a wildcard RBAC role; use `kubectl auth can-i` to show the over-grant; tighten it and re-verify.
6. Add a billing alarm and a throttling policy to a lab function, then simulate a burst and confirm the cap.

### 19.25.2 What Mastery Looks Like

- [ ] You can recite the IAM evaluation algorithm and explain each gate.
- [ ] You can distinguish identity, resource, trust, SCP, boundary, and session policies.
- [ ] You can build and defend an OIDC federation trust policy.
- [ ] You can explain IMDSv1/v2, hop limit, and per-provider metadata headers.
- [ ] You can map a storage misconfiguration to its exact guardrail across AWS/GCP/Azure.
- [ ] You can describe a pod→cluster escalation chain and every control that breaks it.
- [ ] You can write a read-only assessment plan and a detection for each finding class.

### 19.25.3 Knowledge Checks (With Answers)

**Q1.** A bucket policy allows `Principal: "*"` but S3 Block Public Access is fully enabled. Is the bucket publicly readable? **A:** No — Block Public Access overrides the policy and forces objects private. This is why manual validation matters.

**Q2.** Why does IMDSv2 stop a GET-only SSRF even without network controls? **A:** It requires a PUT to a separate token endpoint plus a custom header on the GET; a typical SSRF sink can only issue a simple GET and cannot supply both.

**Q3.** A role's boundary allows `s3:GetObject` and its identity policy allows `s3:*`. What is the effective permission? **A:** `s3:GetObject` only — the boundary caps the identity policy.

**Q4.** An OIDC role trust policy checks only `aud`. What is the risk? **A:** Any repository/webhook able to mint a token with that audience can assume the role; `sub` must also be constrained to a specific repo/ref.

**Q5.** A pod's SA can `create pods`. Why is that escalation? **A:** It can create a new pod that mounts a more privileged SA and read its token, inheriting that SA's rights — a well-known Kubernetes privilege-escalation path.

## 19.26 Mastery Deep Dive: IAM Privilege Escalation Patterns (Authorized Lab)

Cloud privilege escalation is the art of turning a small set of permissions into a larger one by abusing legitimate API semantics. In an authorized lab, learning these patterns teaches you exactly which permissions are dangerous and why least privilege matters.

### 19.26.1 The Escalation Mindset

Ask three questions for any permission set: **Can I give myself more permissions?** (`iam:PutRolePolicy`, `AttachRolePolicy`, `UpdateAssumeRolePolicy`, `CreateAccessKey`, `AddUserToGroup`). **Can I make a more privileged identity act for me?** (`iam:PassRole`, `sts:AssumeRole`). **Can I run code as a privileged principal?** (`lambda:UpdateFunctionCode`, `ec2:RunInstances` with an instance profile, `glue:UpdateJob`).

| Permission (lab example) | Escalation path | Why it works | Mitigation |
|--------------------------|-----------------|--------------|------------|
| `iam:PutRolePolicy` | Attach admin policy to a role you can assume | You grant yourself the rights | Deny policy edits; use separate admin accounts |
| `iam:UpdateAssumeRolePolicy` | Add yourself to an admin role's trust policy | Trust is the gate to assuming | Protect trust-policy edits; SCP guardrail |
| `iam:CreateAccessKey` | Create a key for another user | You inherit that user's rights | Detect; restrict to self-service only |
| `iam:PassRole` + `ec2:RunInstances` | Launch instance with an admin instance profile, then read its metadata creds | The instance runs with the passed role | Restrict which roles can be passed; condition on service |
| `lambda:UpdateFunctionCode` | Replace a function's code; it runs with its execution role | Code execution inherits role rights | Protect function code; use separate deploy roles |
| `sts:AssumeRole` with broad trust | Assume an over-trusted role | Trust policy is too permissive | Constrain `Principal` and conditions |

### 19.26.2 Worked Lab Scenario: PassRole to Instance Profile

In your own account, create a low-privilege lab user with `ec2:RunInstances`, `ec2:DescribeInstances`, and `iam:PassRole` on a role that has, say, `s3:GetObject` on one lab bucket. Demonstrate:

1. The user launches an EC2 instance and passes the lab instance profile.
2. From the instance, the IMDSv2 token flow retrieves the role's temporary credentials (you control both sides).
3. Those credentials can read the one bucket — and nothing else.

This shows both the escalation primitive *and* why least privilege + IMDSv2 + a narrow role turn a theoretical escalation into a contained one. The defense is not to remove `PassRole` entirely (it is required for legitimate workloads) but to constrain it:

```json
"Condition": {
  "StringEquals": { "iam:PassedToService": "ec2.amazonaws.com" },
  "ArnEquals": { "iam:PolicyARN": "arn:aws:iam::<YOUR_LAB_ACCOUNT>:policy/<YOUR_LAB_POLICY>" }
}
```

### 19.26.3 Detection and Guardrails

- Alert on `PutRolePolicy`, `AttachRolePolicy`, `CreateAccessKey`, and `UpdateAssumeRolePolicy` by principals that do not normally perform them.
- Use an SCP as an org-level guardrail that denies disabling CloudTrail or deleting logs — escalation is meaningless if you cannot see it.
- Separate human admin accounts from workload accounts; most privesc paths require admin-adjacent permissions to exist in the first place.

**Knowledge check.** Why is `iam:PassRole` not automatically a vulnerability? **A:** It is required to attach roles to services; it becomes dangerous only when combined with the ability to run code on that service *and* the passed role is over-privileged. Scope the role and the `PassedToService` condition.

## 19.27 Mastery Deep Dive: Cloud Network Perimeter and Exfiltration Paths

Identity controls decide *who* can act; network controls decide *where* they can act from. Both are needed, and their interaction is a frequent source of mistakes.

### 19.27.1 Security Groups, NACLs, and the Three Perimeters

| Control | Statefulness | Scope | Typical use |
|---------|--------------|-------|-------------|
| Security group (AWS) / NSG (Azure) / firewall rule (GCP) | Stateful | Instance/interface | Primary allow-list for ports/sources |
| NACL (AWS) | Stateless | Subnet | Coarse subnet-level deny (must allow both directions) |
| VPC endpoint policy | N/A | Service access | Restrict which principals use a private endpoint |

Stateful means return traffic is automatically allowed; stateless NACLs require explicit rules for both inbound and outbound, which is why a misconfigured NACL can silently break a flow. In an assessment, trace both layers.

### 19.27.2 Private Endpoints and Data Exfiltration

**VPC endpoints / Private Link / Private Endpoint** keep traffic to cloud services on the provider's network, avoiding the public internet. A critical control is the endpoint policy plus an S3 bucket policy condition (`aws:SourceVpce`) so data can only leave via your approved endpoint. Without it, a leaked credential can exfiltrate from anywhere.

Exfiltration paths to understand in your lab:

- **Public bucket/object** — data copied to a public bucket an attacker reads.
- **Pre-signed URL** — a short-lived download link leaked to the internet.
- **DNS/HTTP egress** — data tunneled out through unrestricted outbound rules.
- **Cross-region/cross-account snapshots** — a database snapshot shared to another account.

```bash
# Lab: require that S3 access comes through your VPC endpoint
# Bucket policy condition (abbreviated):
# "Condition": { "StringEquals": { "aws:SourceVpce": "<YOUR_LAB_VPCE_ID>" } }
```

### 19.27.3 Provider Comparison

| Goal | AWS | GCP | Azure |
|------|-----|-----|-------|
| Private access to storage | S3 gateway endpoint + `aws:SourceVpce` | Private Google Access / VPC-SC | Private Endpoint + service policy |
| Egress control | Security group outbound + NAT firewall | Cloud NAT + firewall rules | NSG + Azure Firewall |
| Org-level guardrail | SCPs | Organization Policy Constraints | Azure Policy / management groups |

### 19.27.4 Detection and Fix Checklist

- [ ] Default-deny inbound on all security groups/NSGs; no `0.0.0.0/0` on management ports.
- [ ] Egress filtering to block link-local metadata and known exfil destinations.
- [ ] Private endpoints for storage/databases with source conditions.
- [ ] VPC flow logs enabled and alerted on unusual destinations.
- [ ] Alert on snapshot sharing to external accounts and on `PutBucketPolicy` changes.

**Knowledge check.** Why doesn't a private endpoint alone stop exfiltration by a leaked credential? **A:** A credential used from outside your VPC bypasses the endpoint path entirely; you need identity conditions (`aws:SourceVpce`, `aws:SourceVpc`) on the resource policy so only traffic via the approved endpoint is accepted.

## 19.15 Key Takeaways

- Cloud security failures are usually configuration and identity failures.
- IAM least privilege, temporary credentials, and MFA are foundational.
- Metadata services, storage, serverless, containers, Kubernetes, and CI/CD each have distinct risks.
- Audit only what you own or what is explicitly in scope; never touch other tenants.
