# Chapter 2: Computer Science Fundamentals

> **Learning objectives.** Explain number systems and how data is represented; describe CPU architecture, registers, cache, and the memory hierarchy; distinguish processes from threads and user mode from kernel mode; explain virtual memory, the stack and heap, pointers, compilers, and assembly; and connect each of these to concrete software security failures.

## 2.1 Why First Principles Matter

Every security vulnerability is ultimately a mismatch between an abstraction and reality. A developer writes `buffer[user_index]` believing the index is bounded; the machine has no such belief. A programmer assumes two operations are atomic; the scheduler interleaves them. A service assumes a client is honest; the client sends arbitrary bytes. To reason about security you must understand the layer *below* the abstraction you are using.

This chapter builds the mental model of a computer from bits upward. We will return to it for injection, memory corruption, race conditions, and reverse engineering.

## 2.2 Number Systems

Computers store information as **bits** (binary digits, 0 or 1). Humans use decimal (base 10); computers use binary (base 2) because two stable electrical states are easy to represent reliably.

- **Bit:** one binary digit.
- **Byte:** 8 bits; can represent 2^8 = 256 distinct values (0--255 unsigned, or -128 to 127 signed via two's complement).
- **Nibble:** 4 bits, one hexadecimal digit.
- **Word:** the natural unit of the CPU (e.g., 64 bits on a 64-bit machine).

**Binary (base 2)** uses digits 0--1. The value of binary `1011` is 1×2^3 + 0×2^2 + 1×2^1 + 1×2^0 = 8+0+2+1 = 11.

**Hexadecimal (base 16)** uses digits 0--9 and A--F (values 10--15). It is used because one hex digit maps exactly to four bits (a nibble), making binary compact and human-readable. `0x1F` = 1×16 + 15 = 31. Memory addresses, byte values, hashes, and color codes are conventionally written in hex.

Conversion examples:

```
Decimal 13  = Binary 1101      = Hex 0x0D
Decimal 255 = Binary 11111111  = Hex 0xFF
Decimal 4096= Binary 1000000000000 = Hex 0x1000
0xDEADBEEF  = 3735928559 (decimal)
```

**Two's complement** is how signed integers are represented. To negate a number: invert all bits, then add 1. In 8 bits, `0000 0001` = 1; invert → `1111 1110`; add 1 → `1111 1111` = -1. The range of an n-bit signed integer is -2^n-1 to 2^n-1-1. This matters for **integer overflow**: adding 1 to the 32-bit signed maximum 2 147 483 647 wraps to -2 147 483 648, which has caused real vulnerabilities (e.g., allocation size miscalculations).

**Floating point** (IEEE 754) represents fractions with a sign bit, exponent, and mantissa. It is approximate: `0.1 + 0.2 != 0.3` in binary floating point. Never use floats for security-sensitive arithmetic such as financial calculations or bounds checks.

## 2.3 Bits, Bytes, and Memory Units

| Unit | Size | Bytes |
|------|------|-------|
| Bit | 1 bit | 1/8 |
| Byte | 8 bits | 1 |
| Kilobyte (KB) | 10^3 bytes | 1,000 |
| Kibibyte (KiB) | 2^10 bytes | 1,024 |
| Megabyte (MB) | 10^6 | 1,000,000 |
| Mebibyte (MiB) | 2^20 | 1,048,576 |
| Gigabyte (GB) | 10^9 | 1,000,000,000 |
| Gibibyte (GiB) | 2^30 | 1,073,741,824 |

Storage vendors use decimal; operating systems often report binary. This is why a "500 GB" disk shows ~465 GiB.

## 2.4 CPU Architecture

The **central processing unit (CPU)** executes instructions. Its core components:

- **Arithmetic Logic Unit (ALU):** performs arithmetic and logical operations.
- **Control Unit:** decodes instructions and coordinates execution.
- **Registers:** tiny, extremely fast storage locations inside the CPU.
- **Cache:** small, fast memory close to the CPU.
- **Clock:** synchronizes operations; frequency in GHz.

The **fetch--decode--execute** cycle repeats continuously: fetch the next instruction from memory (addressed by the program counter), decode it, execute it, repeat. Modern CPUs use pipelining, out-of-order execution, and speculative execution to improve throughput — optimizations that have surprising security consequences (e.g., Spectre/Meltdown, which exploit speculative execution and cache timing).

### Registers

x86-64 general-purpose registers: `rax`, `rbx`, `rcx`, `rdx`, `rsi`, `rdi`, `rbp`, `rsp`, and `r8`--`r15`. Special registers include:

- **RIP (instruction pointer):** address of the next instruction. Attackers who control RIP control execution flow.
- **RSP (stack pointer):** top of the stack.
- **RBP (base pointer):** stable reference frame for a function's local variables.
- **Flags register:** stores condition codes from arithmetic (zero, carry, sign, overflow), used by conditional jumps.

Calling conventions specify how arguments are passed (in registers on x86-64 Linux: `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`) and how return values are passed (`rax`). Understanding this is essential for reverse engineering and exploitation.

### Memory Hierarchy

```
   +--------------------------------+
   | Registers      ~1 ns    <1 KB  |  fastest, most expensive
   +--------------------------------+
   | L1 Cache       ~1 ns    32-64 KB
   +--------------------------------+
   | L2 Cache       ~4 ns    256 KB-1 MB
   +--------------------------------+
   | L3 Cache       ~10 ns   8-64 MB (shared)
   +--------------------------------+
   | Main Memory    ~100 ns  GB     (DRAM)
   +--------------------------------+
   | SSD            ~100 us  GB-TB
   +--------------------------------+
   | HDD / Network  ~ms      TB+    slowest, cheapest
   +--------------------------------+
```

Each level is slower but larger and cheaper. **Locality** (temporal and spatial) makes caches effective. Cache behavior leaks information: cache-timing side channels can reveal memory access patterns, which is the basis of several microarchitectural attacks.

## 2.5 RAM and Virtual Memory

**RAM (Random Access Memory)** is volatile working storage. Programs do not see physical addresses directly; the OS and CPU's Memory Management Unit (MMU) provide **virtual memory**:

- Each process gets its own **virtual address space**, giving the illusion of a private, contiguous memory region.
- The MMU translates virtual addresses to physical addresses via **page tables**.
- Memory is divided into fixed-size **pages** (typically 4 KB).
- **Demand paging:** pages are loaded from disk only when needed; a page fault triggers loading (or an error).
- **Swapping:** pages can be moved to disk to free RAM.

Virtual memory provides **isolation** (one process cannot read another's memory by default) and **protection** (pages have permissions: read, write, execute, user/supervisor). Security boundaries in operating systems are implemented largely through these mechanisms.

## 2.6 Processes and Threads

A **process** is an instance of a running program with its own address space, file descriptors, and security context. A **thread** is a unit of execution within a process; threads share the address space and resources but have their own stack, registers, and program counter.

- Multiprocessing gives isolation; a crash in one process usually does not kill others.
- Multithreading gives efficiency and shared state — and introduces **race conditions** when shared data is accessed without synchronization.

The OS scheduler decides which thread runs on which CPU core. **Context switches** save and restore state. The classic race condition:

```c
// Two threads execute this concurrently on the same balance
balance = balance + 100;
```

This is three machine operations (load, add, store). An interleaving can lose an update. Security-relevant races appear in TOCTOU (time-of-check to time-of-use) bugs, token reuse, and double-spend patterns.

## 2.7 System Calls and Mode Switching

**System calls** are the controlled interface between user programs and the kernel. When a program needs to open a file, send network data, or allocate memory, it invokes a syscall (e.g., `open`, `sendto`, `mmap` on Linux).

**User mode** (ring 3) restricts what code can do: no direct hardware access, no arbitrary memory access. **Kernel mode** (ring 0) has full privileges. A syscall triggers a controlled transition (via `syscall` instruction or interrupt) from user to kernel mode. Drivers and kernel code run in ring 0; a bug there can compromise the whole system.

Security depends on this boundary. Exploitation often aims to escalate from user mode to kernel mode by abusing a kernel bug. Sandboxes (e.g., browser renderers) use the same idea at a finer granularity.

## 2.8 File Systems and Permissions

A **file system** organizes persistent data into files and directories. Linux uses inodes, a directory tree rooted at `/`, and mounts to attach storage. Common Linux file systems: ext4, XFS, Btrfs.

Unix permissions are a foundational access-control model. Each file has an owner and group, and three permission sets:

```
-rwxr-xr--  1 alice staff  4096 file
 ||||||  |
 ||| |  +--- others: read only
 ||  +------ group: read + execute
 | +-------- owner: read + write + execute
 +---------- regular file (d = directory, l = symlink)
```

- **Read (r=4):** view contents; on a directory, list names.
- **Write (w=2):** modify contents; on a directory, create/delete entries.
- **Execute (x=1):** run a file; on a directory, traverse into it.

Special bits: **setuid (s)** runs a program with the owner's privileges — a powerful mechanism and a classic source of privilege-escalation vulnerabilities. **setgid** and the **sticky bit** have analogous roles.

## 2.9 Memory Allocation: Stack and Heap

A process's memory layout (simplified, typical Linux):

```
   High address
   +---------------------------+
   | Stack   (grows downward)  |  local vars, return addresses
   +---------------------------+
   |            |              |
   |     free space            |
   |            |              |
   +---------------------------+
   | Heap    (grows upward)    |  malloc/new allocations
   +---------------------------+
   | BSS                       |  uninitialized globals
   +---------------------------+
   | Data                      |  initialized globals
   +---------------------------+
   | Text (code)  r-x          |  program instructions
   +---------------------------+
   Low address
```

**Stack:** LIFO region used for function call frames. Each frame holds local variables, saved registers, and the return address. Pushing/popping is fast. Overflowing a stack buffer can overwrite the return address — the classic **stack buffer overflow** (Chapter 21).

**Heap:** region for dynamically allocated memory (`malloc`/`free` in C, `new` in C++). Managing the heap is complex; errors produce **use-after-free**, **double free**, and **heap overflow** vulnerabilities. Modern allocators add checks, but the underlying risk remains.

**Pointers:** variables that hold memory addresses. In C, pointer arithmetic has no bounds checking. `*(p + i)` reads whatever is at that address. Pointer bugs are the root of most memory-corruption vulnerabilities.

## 2.10 Compilers, Interpreters, and Assembly

A **compiler** translates source code into machine code (or an intermediate representation) ahead of time (e.g., C → x86-64). An **interpreter** executes source code directly, statement by statement (e.g., Python). **Bytecode VMs** (Java, .NET, Python) compile to a portable intermediate form executed by a runtime.

**Assembly language** is a human-readable representation of machine instructions. Example x86-64:

```asm
mov rax, 1        ; put 1 in rax
add rax, 2        ; rax = 3
cmp rax, 3        ; compare
je  equal         ; jump if equal
```

Compilers optimize aggressively, which can introduce subtle behavior (e.g., optimizations assuming no undefined behavior). Security researchers read assembly to understand what code *actually* does, especially in binaries without source.

**Undefined behavior (UB):** operations the language specification does not define (e.g., signed integer overflow, out-of-bounds access in C). compilers may assume UB never happens and optimize accordingly; this can turn a benign-looking bug into an exploitable condition. Safe languages (Rust, Go) eliminate entire classes of memory UB.

## 2.11 Data Structures, Algorithms, and Complexity

Security researchers need algorithmic literacy:

- **Arrays/lists:** contiguous vs. linked; indexing vs. traversal.
- **Hash tables:** key→value mapping; collisions and hash-flooding DoS (attacker sends many colliding keys).
- **Trees/graphs:** hierarchies and relationships; used in DOM, DNS, dependency graphs.
- **Strings:** representation (length-prefixed vs. null-terminated) matters for off-by-one bugs.
- **Regular expressions:** powerful but can exhibit catastrophic backtracking (ReDoS), a classic DoS vector.

**Big-O notation** describes growth of resource use with input size n: O(1) constant, O(\log n) logarithmic, O(n) linear, O(n\log n) linearithmic, O(n^2) quadratic, 2^n exponential. A parser that is O(n^2) on attacker-controlled input can be a denial-of-service vector. Complexity analysis is therefore a security skill.

## 2.12 Operating System Architecture

An OS manages hardware and provides services:

- **Kernel:** core — process scheduling, memory management, file systems, device drivers, networking.
- **Monolithic kernel** (Linux): most services run in kernel mode; fast but large attack surface.
- **Microkernel:** minimal kernel; services run in user mode; smaller trusted computing base.
- **User space:** applications and system daemons; isolated via processes and permissions.
- **System call interface, device drivers, and kernel modules** are the boundary between trusted and untrusted code.

Key protection mechanisms:

- Privilege rings (user vs. kernel).
- Virtual memory and page permissions.
- Access control (Unix permissions, capabilities, SELinux/AppArmor MAC).
- Address space layout randomization (ASLR), NX/DEP, stack canaries (Chapter 21).

## 2.13 How These Concepts Influence Security

| Concept | Security consequence |
|---------|----------------------|
| Two's complement / fixed-width integers | Integer overflow → wrong bounds, allocations, or checks |
| Pointers + no bounds checking | Buffer overflows, use-after-free, arbitrary read/write |
| Virtual memory isolation | Process sandboxes; kernel bugs break isolation |
| Shared threads + scheduling | Race conditions, TOCTOU, double-spend |
| System call boundary | Privilege escalation via kernel/driver bugs |
| File permissions / setuid | Local privilege escalation |
| Compilers + UB | "Impossible" bugs become exploitable under optimization |
| Big-O complexity | Algorithmic DoS (ReDoS, hash flooding, parser bombs) |
| Cache hierarchy | Side-channel leakage (timing attacks) |

The recurring theme: **abstractions hide details, and attackers exploit the gap between the abstraction and the implementation.** Your job as a researcher is to look behind the abstraction.

## 2.15 Key Takeaways

- Data is bits; hex is a compact representation of binary; fixed-width arithmetic can overflow.
- The CPU executes a fetch--decode--execute cycle; caches and registers sit atop a memory hierarchy.
- Virtual memory gives isolation; syscalls and privilege rings enforce the user/kernel boundary.
- Processes are isolated; threads share state and create races.
- Stack and heap have distinct lifetime and failure modes; pointer bugs undermine memory safety.
- Security flaws arise where abstractions meet implementation reality.
