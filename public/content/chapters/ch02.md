# Chapter 2: Computer Science Fundamentals

> **Learning objectives.** Explain number systems and how data is represented; describe CPU architecture, registers, cache, and the memory hierarchy; distinguish processes from threads and user mode from kernel mode; explain virtual memory, the stack and heap, pointers, compilers, and assembly; and connect each of these to concrete software security failures.

## 2.1 Why First Principles Matter

Every security vulnerability is ultimately a mismatch between an abstraction and reality. A developer writes `buffer[user_index]` believing the index is bounded; the machine has no such belief. A programmer assumes two operations are atomic; the scheduler interleaves them. A service assumes a client is honest; the client sends arbitrary bytes. To reason about security you must understand the layer *below* the abstraction you are using.

This chapter builds the mental model of a computer from bits upward. We will return to it for injection, memory corruption, race conditions, and reverse engineering.

## 2.2 Number Systems

Computers store information as **bits** (binary digits, 0 or 1). Humans use decimal (base 10); computers use binary (base 2) because two stable electrical states are easy to represent reliably.

- **Bit:** one binary digit.
- **Byte:** 8 bits; can represent 2^8 = 256 distinct values (0--255 unsigned, or -128 to 127 signed via two's complement).
- **Nibble:** 4 bits, one hexadecimal digit.
- **Word:** the natural unit of the CPU (e.g., 64 bits on a 64-bit machine).

**Binary (base 2)** uses digits 0--1. The value of binary `1011` is 1×2^3 + 0×2^2 + 1×2^1 + 1×2^0 = 8+0+2+1 = 11.

**Hexadecimal (base 16)** uses digits 0--9 and A--F (values 10--15). It is used because one hex digit maps exactly to four bits (a nibble), making binary compact and human-readable. `0x1F` = 1×16 + 15 = 31. Memory addresses, byte values, hashes, and color codes are conventionally written in hex.

Conversion examples:

```
Decimal 13  = Binary 1101      = Hex 0x0D
Decimal 255 = Binary 11111111  = Hex 0xFF
Decimal 4096= Binary 1000000000000 = Hex 0x1000
0xDEADBEEF  = 3735928559 (decimal)
```

**Two's complement** is how signed integers are represented. To negate a number: invert all bits, then add 1. In 8 bits, `0000 0001` = 1; invert → `1111 1110`; add 1 → `1111 1111` = -1. The range of an n-bit signed integer is -2^n-1 to 2^n-1-1. This matters for **integer overflow**: adding 1 to the 32-bit signed maximum 2 147 483 647 wraps to -2 147 483 648, which has caused real vulnerabilities (e.g., allocation size miscalculations).

**Floating point** (IEEE 754) represents fractions with a sign bit, exponent, and mantissa. It is approximate: `0.1 + 0.2 != 0.3` in binary floating point. Never use floats for security-sensitive arithmetic such as financial calculations or bounds checks.

## 2.4 CPU Architecture

The **central processing unit (CPU)** executes instructions. Its core components:

- **Arithmetic Logic Unit (ALU):** performs arithmetic and logical operations.
- **Control Unit:** decodes instructions and coordinates execution.
- **Registers:** tiny, extremely fast storage locations inside the CPU.
- **Cache:** small, fast memory close to the CPU.
- **Clock:** synchronizes operations; frequency in GHz.

The **fetch--decode--execute** cycle repeats continuously: fetch the next instruction from memory (addressed by the program counter), decode it, execute it, repeat. Modern CPUs use pipelining, out-of-order execution, and speculative execution to improve throughput — optimizations that have surprising security consequences (e.g., Spectre/Meltdown, which exploit speculative execution and cache timing).

### Registers

x86-64 general-purpose registers: `rax`, `rbx`, `rcx`, `rdx`, `rsi`, `rdi`, `rbp`, `rsp`, and `r8`--`r15`. Special registers include:

- **RIP (instruction pointer):** address of the next instruction. Attackers who control RIP control execution flow.
- **RSP (stack pointer):** top of the stack.
- **RBP (base pointer):** stable reference frame for a function's local variables.
- **Flags register:** stores condition codes from arithmetic (zero, carry, sign, overflow), used by conditional jumps.

Calling conventions specify how arguments are passed (in registers on x86-64 Linux: `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`) and how return values are passed (`rax`). Understanding this is essential for reverse engineering and exploitation.

### Memory Hierarchy

```
   +--------------------------------+
   | Registers      ~1 ns    <1 KB  |  fastest, most expensive
   +--------------------------------+
   | L1 Cache       ~1 ns    32-64 KB
   +--------------------------------+
   | L2 Cache       ~4 ns    256 KB-1 MB
   +--------------------------------+
   | L3 Cache       ~10 ns   8-64 MB (shared)
   +--------------------------------+
   | Main Memory    ~100 ns  GB     (DRAM)
   +--------------------------------+
   | SSD            ~100 us  GB-TB
   +--------------------------------+
   | HDD / Network  ~ms      TB+    slowest, cheapest
   +--------------------------------+
```

Each level is slower but larger and cheaper. **Locality** (temporal and spatial) makes caches effective. Cache behavior leaks information: cache-timing side channels can reveal memory access patterns, which is the basis of several microarchitectural attacks.

## 2.5 RAM and Virtual Memory

**RAM (Random Access Memory)** is volatile working storage. Programs do not see physical addresses directly; the OS and CPU's Memory Management Unit (MMU) provide **virtual memory**:

- Each process gets its own **virtual address space**, giving the illusion of a private, contiguous memory region.
- The MMU translates virtual addresses to physical addresses via **page tables**.
- Memory is divided into fixed-size **pages** (typically 4 KB).
- **Demand paging:** pages are loaded from disk only when needed; a page fault triggers loading (or an error).
- **Swapping:** pages can be moved to disk to free RAM.

Virtual memory provides **isolation** (one process cannot read another's memory by default) and **protection** (pages have permissions: read, write, execute, user/supervisor). Security boundaries in operating systems are implemented largely through these mechanisms.

## 2.6 Processes and Threads

A **process** is an instance of a running program with its own address space, file descriptors, and security context. A **thread** is a unit of execution within a process; threads share the address space and resources but have their own stack, registers, and program counter.

- Multiprocessing gives isolation; a crash in one process usually does not kill others.
- Multithreading gives efficiency and shared state — and introduces **race conditions** when shared data is accessed without synchronization.

The OS scheduler decides which thread runs on which CPU core. **Context switches** save and restore state. The classic race condition:

```c
// Two threads execute this concurrently on the same balance
balance = balance + 100;
```

This is three machine operations (load, add, store). An interleaving can lose an update. Security-relevant races appear in TOCTOU (time-of-check to time-of-use) bugs, token reuse, and double-spend patterns.

## 2.7 System Calls and Mode Switching

**System calls** are the controlled interface between user programs and the kernel. When a program needs to open a file, send network data, or allocate memory, it invokes a syscall (e.g., `open`, `sendto`, `mmap` on Linux).

**User mode** (ring 3) restricts what code can do: no direct hardware access, no arbitrary memory access. **Kernel mode** (ring 0) has full privileges. A syscall triggers a controlled transition (via `syscall` instruction or interrupt) from user to kernel mode. Drivers and kernel code run in ring 0; a bug there can compromise the whole system.

Security depends on this boundary. Exploitation often aims to escalate from user mode to kernel mode by abusing a kernel bug. Sandboxes (e.g., browser renderers) use the same idea at a finer granularity.

## 2.8 File Systems and Permissions

A **file system** organizes persistent data into files and directories. Linux uses inodes, a directory tree rooted at `/`, and mounts to attach storage. Common Linux file systems: ext4, XFS, Btrfs.

Unix permissions are a foundational access-control model. Each file has an owner and group, and three permission sets:

```
-rwxr-xr--  1 alice staff  4096 file
 ||||||  |
 ||| |  +--- others: read only
 ||  +------ group: read + execute
 | +-------- owner: read + write + execute
 +---------- regular file (d = directory, l = symlink)
```

- **Read (r=4):** view contents; on a directory, list names.
- **Write (w=2):** modify contents; on a directory, create/delete entries.
- **Execute (x=1):** run a file; on a directory, traverse into it.

Special bits: **setuid (s)** runs a program with the owner's privileges — a powerful mechanism and a classic source of privilege-escalation vulnerabilities. **setgid** and the **sticky bit** have analogous roles.

## 2.9 Memory Allocation: Stack and Heap

A process's memory layout (simplified, typical Linux):

```
   High address
   +---------------------------+
   | Stack   (grows downward)  |  local vars, return addresses
   +---------------------------+
   |            |              |
   |     free space            |
   |            |              |
   +---------------------------+
   | Heap    (grows upward)    |  malloc/new allocations
   +---------------------------+
   | BSS                       |  uninitialized globals
   +---------------------------+
   | Data                      |  initialized globals
   +---------------------------+
   | Text (code)  r-x          |  program instructions
   +---------------------------+
   Low address
```

**Stack:** LIFO region used for function call frames. Each frame holds local variables, saved registers, and the return address. Pushing/popping is fast. Overflowing a stack buffer can overwrite the return address — the classic **stack buffer overflow** (Chapter 21).

**Heap:** region for dynamically allocated memory (`malloc`/`free` in C, `new` in C++). Managing the heap is complex; errors produce **use-after-free**, **double free**, and **heap overflow** vulnerabilities. Modern allocators add checks, but the underlying risk remains.

**Pointers:** variables that hold memory addresses. In C, pointer arithmetic has no bounds checking. `*(p + i)` reads whatever is at that address. Pointer bugs are the root of most memory-corruption vulnerabilities.

## 2.10 Compilers, Interpreters, and Assembly

A **compiler** translates source code into machine code (or an intermediate representation) ahead of time (e.g., C → x86-64). An **interpreter** executes source code directly, statement by statement (e.g., Python). **Bytecode VMs** (Java, .NET, Python) compile to a portable intermediate form executed by a runtime.

**Assembly language** is a human-readable representation of machine instructions. Example x86-64:

```asm
mov rax, 1        ; put 1 in rax
add rax, 2        ; rax = 3
cmp rax, 3        ; compare
je  equal         ; jump if equal
```

Compilers optimize aggressively, which can introduce subtle behavior (e.g., optimizations assuming no undefined behavior). Security researchers read assembly to understand what code *actually* does, especially in binaries without source.

**Undefined behavior (UB):** operations the language specification does not define (e.g., signed integer overflow, out-of-bounds access in C). compilers may assume UB never happens and optimize accordingly; this can turn a benign-looking bug into an exploitable condition. Safe languages (Rust, Go) eliminate entire classes of memory UB.

## 2.11 Data Structures, Algorithms, and Complexity

Security researchers need algorithmic literacy:

- **Arrays/lists:** contiguous vs. linked; indexing vs. traversal.
- **Hash tables:** key→value mapping; collisions and hash-flooding DoS (attacker sends many colliding keys).
- **Trees/graphs:** hierarchies and relationships; used in DOM, DNS, dependency graphs.
- **Strings:** representation (length-prefixed vs. null-terminated) matters for off-by-one bugs.
- **Regular expressions:** powerful but can exhibit catastrophic backtracking (ReDoS), a classic DoS vector.

**Big-O notation** describes growth of resource use with input size n: O(1) constant, O(\log n) logarithmic, O(n) linear, O(n\log n) linearithmic, O(n^2) quadratic, 2^n exponential. A parser that is O(n^2) on attacker-controlled input can be a denial-of-service vector. Complexity analysis is therefore a security skill.

## 2.12 Operating System Architecture

An OS manages hardware and provides services:

- **Kernel:** core — process scheduling, memory management, file systems, device drivers, networking.
- **Monolithic kernel** (Linux): most services run in kernel mode; fast but large attack surface.
- **Microkernel:** minimal kernel; services run in user mode; smaller trusted computing base.
- **User space:** applications and system daemons; isolated via processes and permissions.
- **System call interface, device drivers, and kernel modules** are the boundary between trusted and untrusted code.

Key protection mechanisms:

- Privilege rings (user vs. kernel).
- Virtual memory and page permissions.
- Access control (Unix permissions, capabilities, SELinux/AppArmor MAC).
- Address space layout randomization (ASLR), NX/DEP, stack canaries (Chapter 21).

## 2.13 How These Concepts Influence Security

| Concept | Security consequence |
|---------|----------------------|
| Two's complement / fixed-width integers | Integer overflow → wrong bounds, allocations, or checks |
| Pointers + no bounds checking | Buffer overflows, use-after-free, arbitrary read/write |
| Virtual memory isolation | Process sandboxes; kernel bugs break isolation |
| Shared threads + scheduling | Race conditions, TOCTOU, double-spend |
| System call boundary | Privilege escalation via kernel/driver bugs |
| File permissions / setuid | Local privilege escalation |
| Compilers + UB | "Impossible" bugs become exploitable under optimization |
| Big-O complexity | Algorithmic DoS (ReDoS, hash flooding, parser bombs) |
| Cache hierarchy | Side-channel leakage (timing attacks) |

The recurring theme: **abstractions hide details, and attackers exploit the gap between the abstraction and the implementation.** Your job as a researcher is to look behind the abstraction.

## 2.17 Mastery Deep Dive: Number Systems and Bit-Level Reasoning

Chapter 2 introduced number systems at a definition level. Mastery means being able to *operate* in them without a calculator: to look at a hexdump and know what you are seeing, to predict when an arithmetic result will wrap, and to explain why two machines disagree about the bytes on the wire. Every memory-corruption and parsing bug you will ever study is, at bottom, a disagreement about representation.

> **Scope note.** All lab steps below are for systems you own or an explicitly authorized engagement. They teach mechanics and detection, not unauthorized access.

### 2.17.1 Positional Notation and Worked Conversions

A numeral in base b is a polynomial evaluated at b: value = \sum_i d_i b^i, where each digit d_i \in [0, b-1]. Binary is base 2, decimal base 10, hex base 16. The three systems differ only in the *radix*, not in the underlying mathematics.

**Worked conversion: decimal 2026 to binary and hex.** Repeatedly divide by 2 and record remainders (least significant first): 2026/2=1013 r0, 1013/2=506 r1, 506/2=253 r0, 253/2=126 r1, 126/2=63 r0, 63/2=31 r1, 31/2=15 r1, 15/2=7 r1, 7/2=3 r1, 3/2=1 r1, 1/2=0 r1. Reading the remainders back gives `11111101010`. Check by summing powers: 2^10+2^9+2^8+2^7+2^6+2^5+2^3+2^1 = 1024+512+256+128+64+32+8+2 = 2026. Group from the right into fours, padding the left with zeros: `0111 1110 1010` = `0x7EA`. Verify in hex: 7×256 + 14×16 + 10 = 1792+224+10 = 2026.

**Worked conversion: `0xC0FFEE` to decimal.** Expand by place value: 12×16^5 + 0×16^4 + 15×16^3 + 15×16^2 + 14×16 + 14 = 12{,}582{,}912 + 0 + 61{,}440 + 3{,}840 + 224 + 14 = 12{,}648{,}430. The trick that makes hex useful: each digit is exactly one nibble, so binary-to-hex needs no arithmetic at all — just regrouping. A 64-bit address becomes 16 digits, which a human can scan and compare.

**Fractional binary and why floating point surprises you.** After the radix point, place values are 2^-1, 2^-2, 2^-3\dots So `0.101₂ = 0.5 + 0.125 = 0.625` exactly. But 0.1 decimal has no finite binary representation: 0.1_{10} = 0.0001100110011\ldots_2 repeating. IEEE 754 single precision stores it approximated, which is why `0.1 + 0.2` does not equal `0.3` bit-for-bit. Worked encoding: 0.5 is 1.0 × 2^-1; sign 0, biased exponent 127-1 = 126 = \texttt{01111110}_2, all-zero mantissa → bits `0011 1111 0000 0000 0000 0000 0000 0000` = `0x3F000000`. For 1.0 the exponent is 127 → `0x3F800000`. Recognize these constants when reading a disassembly that loads a float literal.

| Base | Digits | One digit equals | Typical use in security work |
|------|--------|------------------|------------------------------|
| 2 | 0--1 | 1 bit | Bit flags, masks, subnet math |
| 10 | 0--9 | \log_2 10 \approx 3.32 bits | Counts, ports, human input |
| 16 | 0--F | 4 bits (nibble) | Addresses, hexdumps, hashes, opcodes |

### 2.17.2 Signed Numbers, Sign Extension, and Overflow Detection

Two's complement is elegant because addition needs no special case for negatives: the same adder handles both. To negate, invert every bit and add one. Worked: +5 = \texttt{00000101}; invert → `11111010`; add 1 → `11111011` = -5. Verify by unsigned reinterpretation: `11111011₂ = 251`, and 256 - 251 = 5.

**The sign-extension trap.** -5 widened to 16 bits is `1111111111111011` (`0xFFFB`), not `0000000000001011`. A compiler sign-extends a `signed char`; a careless cast through `unsigned char` zero-extends instead and turns -1 into 255. This single distinction produces a whole family of "negative length becomes huge allocation" bugs.

| Width | Unsigned max | Signed range |
|-------|--------------|--------------|
| 8-bit | 255 | -128 \ldots 127 |
| 16-bit | 65,535 | -32{,}768 \ldots 32{,}767 |
| 32-bit | 4,294,967,295 | -2{,}147{,}483{,}648 \ldots 2{,}147{,}483{,}647 |
| 64-bit | 2^64-1 | -2^63 \ldots 2^63-1 |

**Detecting overflow like the CPU does.** Add 127 and 1 in 8 bits: `01111111 + 00000001 = 10000000`, which as a signed byte is -128. The carry *into* the sign bit is 1, the carry *out* of the sign bit is 0; their inequality sets the overflow flag (OF). The carry-out itself sets the carry flag (CF), which matters for unsigned arithmetic. Rule of thumb: **CF for unsigned overflow, OF for signed overflow** — confusing the two is a classic bug in hand-written bounds checks. A 64-bit `size_t` allocation `n * 8` wraps once n > 2^61-1, so a parser can pass a "safe" check on `n` and then allocate a tiny buffer for a huge count.

### 2.17.3 Endianness: Reading Bytes the Way the Machine Does

Endianness is the order in which the bytes of a multi-byte value are stored. **Little-endian** (x86, most ARM in little mode) puts the least significant byte at the lowest address. **Big-endian** puts the most significant byte first; this is *network byte order*.

Worked example: store `0xDEADBEEF` at address `0x1000`.

| Address | Little-endian byte | Big-endian byte |
|---------|--------------------|-----------------|
| `0x1000` | `EF` | `DE` |
| `0x1001` | `BE` | `AD` |
| `0x1002` | `AD` | `BE` |
| `0x1003` | `DE` | `EF` |

So a little-endian hexdump of that word reads `ef be ad de`. Learning to "see" the reversal is what lets you recognize a pointer (`0x7f...` appears as `... 7f 00 00`) or a length field inside a packet.

Port numbers reinforce the point. Port 443 is `0x01BB`. On the wire (big-endian) the bytes are `01 BB`; in little-endian host memory they are `BB 01`. Hence `htons(443)` and `ntohs()` — forgetting them does not corrupt the value conceptually, but it produces the wrong numeric field on the wire. The host functions `htonl`/`ntohl` do the same for 32-bit values.

**Common mistakes:** reading a packet's 32-bit field as a native integer without `ntohl`; writing a magic constant into a serialized buffer without byte-swapping; assuming a `struct`'s in-memory layout matches its on-disk or on-wire layout (padding and endianness both differ). Network protocols define wire order explicitly; host structs do not.

### 2.17.4 Bitwise Operations as a Security Primitive

| Operation | Use | Worked example |
|-----------|-----|----------------|
| AND (`&`) | Mask / extract bits | `0b10110110 & 0b00001111 = 0b00000110` (low nibble) |
| OR (`\|`) | Set bits | `0b1000 | 0b0010 = 0b1010` (set bit 1) |
| XOR (`^`) | Toggle / compare | `0b1100 ^ 0b1010 = 0b0110` |
| Shift (`<<`, `>>`) | Multiply/divide by 2^k | `5 << 3 = 40`, `40 >> 3 = 5` |
| NOT (`~`) | Complement | `~0x0F = 0xFFFFFFF0` (32-bit) |

Applying a subnet mask to an IP address is nothing more than a bitwise AND — the entire subnetting topic in Chapter 4 is applied bit math. Flag fields work the same way: permission bits `rwx` are a 3-bit mask; a Unix mode `0755` packs four octal (3-bit) groups into 12 bits.

XOR deserves special attention because a ⊕ a = 0, a ⊕ 0 = a, and the operation is its own inverse. If C = P ⊕ K then P = C ⊕ K. Worked with a two-byte repeating key: `H`=`0x48`, `I`=`0x49`; key `0x2A`, `0x7F` → ciphertext `0x6B`, `0x36`. XOR with a *repeating* key leaks structure (equal plaintext bytes a key-length apart produce equal ciphertext bytes), which is why it is a teaching tool, not a cipher. a ⊕ b also computes "bits that differ," the basis of many diff and parity checks.

## 2.18 Mastery Deep Dive: CPU Architecture, Caches, and Virtual Memory

### 2.18.1 The Instruction Cycle, Pipelining, and Speculation

The fetch--decode--execute cycle is performed by the **program counter (PC)**, instruction register, and ALU in concert: (1) fetch the instruction at the address in RIP from the instruction cache; (2) decode it into control signals and register operands; (3) execute (ALU result, memory address, or branch target); (4) access memory if needed; (5) write the result back. RIP advances to the next instruction unless a branch changes it.

Modern CPUs overlap these stages in a pipeline: `IF → ID → EX → MEM → WB`. With five stages and one instruction entering per cycle, throughput approaches one instruction per cycle after the pipeline fills — even though any single instruction still takes about five cycles. Three **hazards** interrupt this:

- **Data hazard:** an instruction needs a result not yet written back. Solved by forwarding (bypassing the register file) or stalling.
- **Control hazard:** a branch's outcome is unknown. Solved by *speculation* — guess the direction using a branch predictor, execute ahead, and squash the wrong path.
- **Structural hazard:** two instructions need the same hardware unit.

Security consequence: speculative instructions execute with observable side effects (cache fills) even when architecturally discarded. Meltdown and Spectre are not software bugs in the usual sense; they are the gap between the programmer's sequential model and the processor's speculative implementation. The defensive lesson is that **secret-dependent memory access patterns can leak through microarchitectural state**, so cryptographic code aims for constant-time behavior (no secret-indexed table lookups, no secret-dependent branches).

### 2.18.2 Registers, the ABI, and a Worked Stack Frame

Under the x86-64 System V ABI (Linux/macOS), the first six integer/pointer arguments go in `rdi, rsi, rdx, rcx, r8, r9`; the return value goes in `rax`. Callee-saved registers (`rbx`, `rbp`, `r12`--`r15`) must be preserved across a call; caller-saved registers may be clobbered. `rsp` points to the top of the stack, which grows **downward** toward lower addresses.

A call does two things: `call func` pushes the return address (the instruction after the call) onto the stack and jumps. A typical prologue and epilogue:

```asm
push rbp            ; save caller's frame pointer   [rsp] = old rbp
mov  rbp, rsp       ; new stable frame base
sub  rsp, 32        ; reserve 32 bytes for locals
...
leave               ; rsp = rbp; pop rbp
ret                 ; pop return address into RIP
```

Worked layout just after `sub rsp,32` (addresses illustrative, in a lab binary):

| Address | Contents |
|---------|----------|
| `0x7fff...ff28` | local buffer (32 reserved bytes) |
| `0x7fff...ff48` | saved `rbp` (old frame pointer) |
| `0x7fff...ff50` | **return address** → RIP after `ret` |
| `0x7fff...ff58` | caller's stack frame |

A stack buffer overflow that writes past the 32-byte local region first corrupts the saved frame pointer and then the return address. Control of that address is control of RIP. This is why a **stack canary** (a random value placed between locals and saved state, checked before `ret`) converts a silent overwrite into a detected crash, and why **ASLR** changes these addresses between runs so a hard-coded return address fails.

**Verify in your lab:**

```bash
gcc -O0 -g -fno-stack-protector -o lab_fn lab_fn.c
objdump -d -M intel lab_fn | less
```
Interpretation: find `<main>`; the first instructions should be the prologue; a `call` to `printf@plt` appears as `call 1040 <printf@plt>` with the argument already in `rdi` (e.g., `lea rax,[rip+...]` then `mov rdi,rax`). Seeing arguments in registers rather than pushed on the stack confirms the ABI. Disassemble again with `-O2` and note how optimization can eliminate the frame entirely — the source and the machine code are different programs.

### 2.18.3 Cache Behavior and the Memory Hierarchy

| Level | Typical size | Latency | Analogy if 1 CPU cycle = 1 second |
|-------|--------------|---------|-----------------------------------|
| Register | < 1 KB | ~0.3 ns | 0.3 s |
| L1 cache | 32--64 KB | ~1 ns | ~3 s |
| L2 cache | 256 KB--1 MB | ~4 ns | ~12 s |
| L3 cache (shared) | 8--64 MB | ~10--40 ns | ~1 minute |
| DRAM | GB | ~100 ns | ~5 minutes |
| SSD | GB--TB | ~100 µs | ~3.5 days |
| Disk / network | TB+ | ms | Months |

Caches exploit **temporal locality** (recently used data is likely reused) and **spatial locality** (nearby addresses are likely needed). Data moves in **cache lines**, typically 64 bytes — which is why iterating an array in order is dramatically faster than hopping randomly, and why a one-byte write can invalidate a whole line shared with another core (false sharing). Coherence protocols such as MESI keep multiple cores' caches consistent.

Security relevance: an attacker who can time access to a shared cache line can infer whether a victim touched that line. Flush+Reload and Prime+Probe are the canonical techniques, studied only in controlled labs on hardware you own. Defenses include constant-time libraries, cache partitioning, and avoiding shared physical cores across trust boundaries. The defensive checklist: **assume memory access patterns are observable, not just memory contents.**

### 2.18.4 Virtual Memory and Address Translation — Worked Walkthrough

The MMU maps a **virtual address (VA)** to a **physical address (PA)** in fixed-size **pages** (4 KB typical). Each process has its own page tables, so the same VA in two processes maps to different physical frames — that is isolation.

On x86-64 with 4 KB pages and 48-bit virtual addresses, the VA splits into five chunks: 9 bits indexing each of four table levels, plus a 12-bit page offset (4 × 9 + 12 = 48). Translation walks: **PML4 → PDPT → Page Directory → Page Table → offset**.

Worked walkthrough for VA `0x00007f12abcd1234`:

| Field | Bits | Value (decimal / hex) |
|-------|------|-----------------------|
| PML4 index | 47:39 | 254 / `0xFE` |
| PDPT index | 38:30 | 74 / `0x4A` |
| PD index | 29:21 | 350 / `0x15E` |
| PT index | 20:12 | 209 / `0xD1` |
| Page offset | 11:0 | 564 / `0x234` |

The CPU reads the entry at `PML4_base + 8*254`, uses the physical address found there to index the PDPT at `+8*74`, and so on. Each **PTE** carries more than an address: present (P), read/write (RW), user/supervisor (US), accessed (A), dirty (D), page size (PS), and the no-execute bit (NX, bit 63). A missing PTE causes a **page fault**: the kernel either maps a page (minor fault, or major fault if disk I/O is needed) or delivers SIGSEGV. The US bit is what stops user code from touching kernel pages; NX is what makes a stack non-executable.

Two consequences worth internalizing: **copy-on-write** makes `fork()` cheap by mapping both processes to the same physical pages read-only until one writes; and **kernel page-table isolation (KPTI)** maps a reduced kernel set in user mode to close the Meltdown-style leak. `/proc/self/maps` shows the process's virtual regions and their permissions; `/proc/self/pagemap` exposes the VA→PA mapping to privileged processes.

**Verify in your lab:**

```bash
cat /proc/self/maps | head -20
pmap -x $$
strace -e trace=mmap,brk,munmap /bin/true 2>&1 | head -20
```
Interpretation: look for the `[stack]`, `[heap]`, and `r--p`/`rw-p`/`r-xp` library mappings; the `r-xp` text mapping is executable-but-not-writable, and the `rw-p` data mapping is writable-but-not-executable. That split *is* W⊕X enforced by page permissions.

## 2.19 Mastery Deep Dive: Processes, Threads, and Concurrency Mechanics

### 2.19.1 Process Lifecycle and fork/exec

A process moves through states: **new → ready → running → blocked → ready → terminated**. A child created by `fork()` is a near-copy of the parent (copy-on-write pages, duplicated file descriptors); `fork()` returns 0 in the child and the child's PID in the parent. `execve()` replaces the address space with a new program image while keeping the PID. When a process exits, it becomes a **zombie** until its parent calls `wait()` to reap it; if the parent dies first, the child is reparented to `init`/`systemd`.

Why this matters operationally: a service that never reaps children accumulates zombies; `ps -ef` shows them as `[defunct]`. A daemon that calls `fork()` and does not close inherited file descriptors leaks access to sockets and files — a common source of unintended capability carrying.

**Verify in your lab:**

```bash
ps -eo pid,ppid,stat,comm | head -20
# STAT: R running, S sleeping, D uninterruptible, Z zombie, T stopped
```
Interpretation: a `Z` process consumes no memory but holds a PID and an entry in the process table; the fix is reaping, not `kill -9`.

### 2.19.2 Threads, Context Switching, and What Is Shared

Linux implements threads with `clone()` and flags such as `CLONE_VM` (shared address space), `CLONE_FS`, and `CLONE_FILES`. The distinction is precise and worth memorizing:

| Shared by threads in one process | Private to each thread |
|----------------------------------|------------------------|
| Address space (code, heap, globals) | Stack |
| File descriptors | Registers / program counter |
| Current working directory | Thread-local storage (TLS) |
| Signal handlers | Signal mask |
| User/group credentials | Scheduling priority |

A **context switch** saves the outgoing thread's registers, updates its task structure, loads the incoming thread's registers, and may switch page tables (writing CR3) and flush or tag the TLB. That cost is why thread pools exist and why excessive thread counts hurt throughput. A **mode switch** (syscall) is cheaper: it stays in the same process and usually does not change page tables.

**Verify in your lab:**

```bash
ps -L -f -p <LAB_PID>          # list threads of a process
ls /proc/<LAB_PID>/task        # one directory per thread
```
Interpretation: every thread ID has its own `task/<tid>` directory with `regs`, `stack`, and `status`, while `/proc/<PID>/maps` is shared — exactly the table above made visible.

### 2.19.3 Race Conditions and TOCTOU, Worked

Consider `balance = balance + 100` compiled to load/add/store. Two threads start from 0:

| Step | Thread A | Thread B | Memory |
|------|----------|----------|--------|
| 1 | load 0 into regA | -- | 0 |
| 2 | -- | load 0 into regB | 0 |
| 3 | regA = 100 | -- | 0 |
| 4 | -- | regB = 100 | 0 |
| 5 | store 100 | -- | 100 |
| 6 | -- | store 100 | **100** (expected 200) |

One update is lost. The fix is atomicity: a lock (`pthread_mutex_lock`), an atomic instruction (`lock xadd`, compare-and-swap), or designing the data to be immutable.

**TOCTOU (time-of-check to time-of-use)** is the same gap stretched across a syscall pair. In an authorized lab directory:

```c
if (access("/lab/tmp/file", W_OK) == 0) {   // CHECK
    fd = open("/lab/tmp/file", O_WRONLY);   // USE
}
```
Between CHECK and USE, the path can be replaced with a symlink to a privileged target. The correct pattern removes the gap: open the file first, then call `fstat(fd, ...)` on the *opened descriptor* and validate that; use `openat()` with `O_NOFOLLOW`/`O_DIRECTORY` and `O_CLOEXEC`. The general rule: **check the object you actually use, not a name that can be rebound.**

### 2.19.4 Scheduler, Resource Limits, and Denial of Service

Linux's CFS scheduler aims for fair CPU share using virtual runtime; `nice` values bias the weighting, and real-time policies (`SCHED_FIFO`, `SCHED_RR`) can starve ordinary tasks. From a defensive standpoint, an untrusted process that can spawn unlimited threads or consume unbounded memory is a local DoS. Use `ulimit -u` (max processes), `ulimit -v` (virtual memory), and cgroup v2 `pids.max` / `memory.max` in services. A fork bomb is studied only inside a disposable VM with these limits applied first.

**Verify in your lab:**

```bash
ulimit -a
cat /sys/fs/cgroup/pids.max 2>/dev/null
```
Interpretation: record the baseline limits before running any stress test so you can restore the VM cleanly.

## 2.20 Mastery Deep Dive: Representation, Algorithms, and Discrete Math

### 2.20.1 Strings, Encoding, and Off-by-One Errors

A null-terminated C string costs O(n) to measure and has no stored capacity. A length-prefixed string (Pascal-style, or Go slices) carries its length explicitly. Most string vulnerabilities come from forgetting the terminator: a 16-byte buffer holding the 16-character string `"AAAAAAAAAAAAAAAA"` needs 17 bytes for the trailing `0x00`. `strcpy` writes it blindly; `strncpy` may omit it; `snprintf` truncates but reports the would-be length. Worked: `snprintf(buf, 16, "%s", src)` writes at most 15 characters plus NUL — the "off-by-one" is intentional and must be understood when auditing.

Unicode adds a second representation layer. UTF-8 encodes U+00E9 (`é`) as bytes `C3 A9`; overlong encodings (e.g., encoding ASCII in two bytes) are invalid but historically accepted by lenient decoders, enabling filter bypasses. Normalization (NFC vs NFD) means two visually identical strings can have different byte sequences; homoglyphs use different code points entirely. Security rule: **validate after canonicalization, and compare bytes, not glyphs.** Embedded NULs in paths were a classic bypass where a C API stopped at `0x00` but a higher-level API kept reading.

### 2.20.2 Inodes and Filesystem Representation

A Unix filesystem separates a **name** (a directory entry) from the **object** (an inode). The inode holds mode, owner, size, timestamps, block pointers, and link count; the directory is just a name→inode-number table. This explains hard links (two names, one inode), symlinks (a name whose *content* is a path), and why `rm` removes a name, not necessarily data.

```bash
ls -li labfile                     # first column = inode number
stat labfile                       # show all inode metadata
ln labfile hardlink; ln -s labfile symlink
readlink -f symlink                # resolve to canonical path
```
Interpretation of `stat`: `Links:` counts hard links; `Inode:` is the object identity; `Access:` (atime), `Modify:` (mtime), and `Change:` (ctime) differ — ctime changes on metadata changes even if content is untouched, which matters in forensics. Timestamps are attacker-influenceable in some contexts, so never treat mtime alone as evidence of when a file was written.

### 2.20.3 Complexity as a Security Property

| Complexity | n=100 | n=1,000 | n=1,000,000 |
|------------|-------|---------|-------------|
| O(1) | 1 | 1 | 1 |
| O(\log n) | ~7 | ~10 | ~20 |
| O(n) | 100 | 1,000 | 1,000,000 |
| O(n\log n) | ~700 | ~10,000 | ~20,000,000 |
| O(n^2) | 10,000 | 1,000,000 | 10^12 |

An algorithm that is fine on trusted input can be a remote DoS on attacker-controlled input. Three concrete families:

- **ReDoS:** a regex like `^(a+)+$` against `"aaaa…aaaa!"` forces exponential backtracking because nested quantifiers offer exponentially many ways to split the `a`s. Mitigate with linear-time engines, atomic groups/possessive quantifiers, input length caps, and timeouts.
- **Hash flooding:** if an attacker can choose keys that collide in a hash table, lookups degrade to O(n^2). Languages defend with randomized, keyed hashes (e.g., Python's `PYTHONHASHSEED`) and mixed bucket types.
- **Parser bombs / amplification:** deeply nested or recursive structures (XML "billion laughs," JSON depth attacks, compressed data that expands) turn a small request into huge CPU/memory use. Bound depth, entity expansion, and decompression ratio.

**Verify in your lab (own host):**

```bash
python3 - <<'PY'
import re, time
for n in (20, 22, 24, 26):
    s = 'a'*n + '!'
    t = time.perf_counter()
    re.match(r'^(a+)+$', s)
    print(n, round(time.perf_counter()-t, 4))
PY
```
Interpretation: runtime roughly doubles for each two extra characters — the signature of exponential backtracking. A linear regex would stay flat.

### 2.20.4 Discrete Math You Will Actually Use

**Modular arithmetic** is "clock math": 17 \bmod 5 = 2 because 17 = 3×5+2. Addition and multiplication are valid modulo m, and a **multiplicative inverse** a^-1 satisfies a× a^-1 \equiv 1 \pmod m (it exists only when \gcd(a,m)=1). Worked extended Euclid: find 7^-1 \bmod 26. 26 = 3×7+5; 7 = 1×5+2; 5 = 2×2+1. Back-substitute: 1 = 5 - 2×2 = 5 - 2(7-5) = 3×5 - 2×7 = 3(26-3×7) - 2×7 = 3×26 - 11×7. So the inverse is -11 \equiv 15 \pmod{26}; check 7×15 = 105 = 4×26+1. This is the arithmetic underneath RSA and affine ciphers.

**Primes and Fermat's little theorem.** Test primality of 97 by trial division up to \sqrt{97} \approx 9.8: check 2, 3, 5, 7 — none divide, so 97 is prime. Fermat: for prime p and \gcd(a,p)=1, a^p-1 \equiv 1 \pmod p. Worked: 3^6 \bmod 7; 3^2 = 9 \equiv 2, 3^4 \equiv 4, 3^6 = 3^4×3^2 \equiv 4×2 = 8 \equiv 1. This underlies primality tests and key generation.

**A tiny RSA walkthrough (illustrative only, never use small keys):** p=61, q=53, n=3233, \varphi(n)=(60)(52)=3120, choose e=17, and d=2753 because 17×2753 = 46{,}801 = 15×3120+1. Encrypt m=65: c = 65^17 \bmod 3233 = 2790. Decrypt: 2790^2753 \bmod 3233 = 65. Modular exponentiation is efficient via square-and-multiply; the security rests on the hardness of factoring n, not on the arithmetic being obscure.

**Hashes.** A cryptographic hash is deterministic, fast, avalanche-prone, and offers preimage, second-preimage, and collision resistance. A toy sum hash illustrates the *weak* kind: define h = (\sum bytes) \bmod 256. Then `"abc"` → (97+98+99) \bmod 256 = 38, and byte sequences `[0x01,0x02]` and `[0x02,0x01]` both hash to 3 — a trivial collision. Real hashes avoid this, but the lesson stands: **a checksum is not a cryptographic hash**, and collision resistance is what makes signatures and integrity checks meaningful. Length-extension attacks on Merkle--Damgård constructions (MD5, SHA-1) are why HMAC exists.

**Randomness.** A linear congruential generator X_{n+1} = (aX_n + c) \bmod m is predictable once you observe enough outputs — never use it for tokens, nonces, or keys. Use `/dev/urandom` or `getrandom(2)`.

```bash
head -c 16 /dev/urandom | xxd          # 128 bits of entropy, displayed as hex
```
Interpretation: 16 random bytes = 32 hex digits = 128 bits of uncertainty. A session token with 128 bits of CSPRNG entropy is not guessable; a token derived from a timestamp or LCG is.

### 2.21.3 Common Mistakes and Their Fixes

| Mistake | Why it fails | Fix |
|---------|--------------|-----|
| Checking `len > 0` on a signed int then casting to `size_t` | Negative becomes huge | Check the signed value before casting, or use unsigned throughout |
| Assuming struct layout matches wire format | Padding + endianness differ | Serialize field by field with explicit byte order |
| Using `strcpy` on user input | No capacity check, NUL overflow | `snprintf` with explicit size or length-aware APIs |
| Treating hash output as "unique" | Collisions exist by pigeonhole | Compare the underlying object when correctness matters |
| Using `rand()` for a session token | Predictable LCG | `getrandom(2)` / `/dev/urandom` |

### 2.21.4 Knowledge Checks (Answers Included)

1. **Why does `0xDEADBEEF` appear as `ef be ad de` in a little-endian hexdump?** Because the least significant byte (`EF`) is stored at the lowest address; hexdumps display addresses ascending.
2. **In 8-bit two's complement, what is `0x7F + 0x01`?** `0x80` = -128. Signed overflow; OF is set, CF is clear.
3. **What is 7^-1 \bmod 26?** 15, since 7×15 = 105 = 4×26+1.
4. **Why can speculation leak secrets if the wrong path is discarded?** Because speculative execution still touches caches, leaving timing-observable state.
5. **Name the PTE bit that prevents execution of stack pages.** NX (bit 63 on x86-64).
6. **What is the difference between a mode switch and a context switch?** A mode switch crosses user/kernel within one process; a context switch changes the running thread and may switch address spaces.
7. **Why is `access()` + `open()` a TOCTOU pattern?** The path can be rebound between the check and the use; validate the opened fd with `fstat` instead.
8. **What complexity does a hash table degrade to under mass collisions?** O(n^2); mitigated by randomized hashing.
9. **Why is a repeating-key XOR cipher breakable?** Equal plaintext bytes at key-distance positions produce equal ciphertext bytes, leaking structure.
10. **What does 128 bits of CSPRNG entropy mean for a token?** Roughly 2^128 possible values, making brute force infeasible — assuming the generator is cryptographically secure.

## 2.15 Key Takeaways

- Data is bits; hex is a compact representation of binary; fixed-width arithmetic can overflow.
- The CPU executes a fetch--decode--execute cycle; caches and registers sit atop a memory hierarchy.
- Virtual memory gives isolation; syscalls and privilege rings enforce the user/kernel boundary.
- Processes are isolated; threads share state and create races.
- Stack and heap have distinct lifetime and failure modes; pointer bugs undermine memory safety.
- Security flaws arise where abstractions meet implementation reality.
