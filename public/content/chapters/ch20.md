# Chapter 20: Source Code and Software Supply Chain Security

> **Learning objectives.** Perform secure code review; apply static/dynamic analysis; identify dependency, typosquatting, dependency-confusion, secret-exposure, and CI/CD risks; use SBOMs; and practice responsible open-source research.

## 20.1 Secure Code Review

Code review is the systematic reading of source to find security defects. Focus on:

- **Trust boundaries:** where does untrusted data enter?
- **Validation/encoding:** is it context-appropriate?
- **Authorization:** is it checked per object and function?
- **Crypto:** algorithms, key management, RNG.
- **Error handling:** fail-open vs. fail-closed; information leakage.
- **Dangerous APIs:** `eval`, `exec`, `system`, deserialization, file paths, redirects.
- **Concurrency:** shared state, TOCTOU.

A productive technique is **taint tracking by hand**: trace data from source (input) to sink (dangerous operation) and check whether sanitization occurs on every path.

```
source (HTTP param) -> ... transformations ... -> sink (SQL query)
        [is there validation on ALL paths?]
```

## 20.2 Static and Dynamic Analysis

- **SAST (Static Application Security Testing):** analyzes source/bytecode without running (Semgrep, CodeQL, SonarQube). Finds taint flows and patterns; produces false positives needing triage.
- **DAST (Dynamic Application Security Testing):** tests a running app from outside (ZAP, Burp, Nuclei). Finds exploitable issues but needs a deployed environment.
- **IAST (Interactive AST):** instruments the app at runtime for higher precision.
- **SCA (Software Composition Analysis):** finds vulnerable dependencies (Trivy, Grype, Dependency-Check).

Use them together; none replaces human reasoning.

## 20.3 Dependency Vulnerabilities

Modern apps depend on hundreds of packages. A vulnerability in any of them affects the app. Track dependencies with lockfiles, scan them continuously (Dependabot, Renovate, Trivy), and patch promptly. Note that a CVE's presence does not mean exploitability in your context — triage reachability.

## 20.4 Typosquatting and Dependency Confusion

- **Typosquatting:** publishing malicious packages with names similar to popular ones (`reqeusts` vs `requests`). Defend by verifying package names, using lockfiles with hashes, and internal mirrors.
- **Dependency confusion:** an attacker publishes a package with the same name as an internal package to a public registry, with a higher version, hoping the build fetches the public one. Defend with scoped namespaces, registry pinning, and `--ignore-scripts`.

## 20.5 Secret Exposure

Secrets (API keys, tokens, passwords) leak via:

- Source code and git history (scan with Gitleaks/truffleHog).
- Logs and error messages.
- CI/CD variables and build artifacts.
- Container images and mobile apps.
- Public paste sites and documentation.

If a secret leaks, **rotate it first**, then investigate. Rotation is more important than deletion.

## 20.6 Git History Analysis

Deleted secrets often remain in git history. Use `git log -p`, `git grep` across history, or Gitleaks full-history scans. Rewriting history (e.g., with `git filter-repo`) is possible but coordination is required; rotation remains essential.

## 20.7 CI/CD Pipeline Security

- Protect default branches; require reviews and status checks.
- Restrict secrets to needed jobs; avoid exposing them to PRs from forks.
- Pin actions to commit SHAs.
- Use OIDC for cloud access instead of static keys.
- Sign artifacts (Sigstore/cosign) and verify at deployment.
- Isolate runners; never run untrusted code with privileged credentials.

## 20.8 Build System Security

Compromised build systems can inject malicious code into signed products (SolarWinds). Defenses: reproducible builds, hermetic builders, separated signing keys, monitored build environments, and provenance attestation (SLSA framework).

## 20.9 Software Bill of Materials (SBOM)

An SBOM is a machine-readable inventory of components (formats: SPDX, CycloneDX). It enables rapid response when a new vulnerability appears: query the SBOM to see which products are affected. Generate SBOMs in CI and store them with releases.

## 20.10 Open-Source Vulnerability Research

Finding vulnerabilities in open-source software is a valuable, legitimate path:

1. Choose a project and understand its threat model.
2. Review recent changes and complex parsers/deserializers.
3. Build the project and run its tests; set up a lab harness.
4. Use SAST and fuzzing to generate leads.
5. Manually validate and minimize a reproducer.
6. Report privately to maintainers with a clear advisory.
7. Coordinate disclosure and, if assigned, a CVE via a CNA.

Respect maintainers' time: provide a minimal reproducer and a proposed fix when possible.

## 20.11 Secure Development Lifecycle (SDL)

Security must be integrated throughout: requirements (abuse cases), design (threat modeling), implementation (secure coding, SAST), verification (DAST, pentest), and release/maintenance (patching, monitoring). Security gates and training make this repeatable.

## 20.12 Practical Code Review Exercises

1. Review a small lab Python web app; list every input source and sink and identify missing validation.
2. Run Semgrep with an OWASP ruleset and triage each finding as true/false positive with reasoning.
3. Scan a lab repo with Gitleaks; rotate a deliberately committed fake key and document the process.
4. Create a CycloneDX SBOM for a lab project with Trivy or Syft and inspect the component list.
5. Analyze a lab GitHub Actions workflow for secret exposure and pin an action to a SHA.

## 20.13 Key Takeaways

- Code review is taint tracking, authorization checking, and dangerous-API identification across all paths.
- SAST, DAST, SCA, and manual review are complementary.
- Dependencies, secrets, and CI/CD are high-leverage supply-chain targets.
- SBOMs and integrity controls enable rapid, trustworthy response.
