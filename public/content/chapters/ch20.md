# Chapter 20: Source Code and Software Supply Chain Security

> **Learning objectives.** Perform secure code review; apply static/dynamic analysis; identify dependency, typosquatting, dependency-confusion, secret-exposure, and CI/CD risks; use SBOMs; and practice responsible open-source research.

## 20.1 Secure Code Review

Code review is the systematic reading of source to find security defects. Focus on:

- **Trust boundaries:** where does untrusted data enter?
- **Validation/encoding:** is it context-appropriate?
- **Authorization:** is it checked per object and function?
- **Crypto:** algorithms, key management, RNG.
- **Error handling:** fail-open vs. fail-closed; information leakage.
- **Dangerous APIs:** `eval`, `exec`, `system`, deserialization, file paths, redirects.
- **Concurrency:** shared state, TOCTOU.

A productive technique is **taint tracking by hand**: trace data from source (input) to sink (dangerous operation) and check whether sanitization occurs on every path.

```
source (HTTP param) -> ... transformations ... -> sink (SQL query)
        [is there validation on ALL paths?]
```

## 20.2 Static and Dynamic Analysis

- **SAST (Static Application Security Testing):** analyzes source/bytecode without running (Semgrep, CodeQL, SonarQube). Finds taint flows and patterns; produces false positives needing triage.
- **DAST (Dynamic Application Security Testing):** tests a running app from outside (ZAP, Burp, Nuclei). Finds exploitable issues but needs a deployed environment.
- **IAST (Interactive AST):** instruments the app at runtime for higher precision.
- **SCA (Software Composition Analysis):** finds vulnerable dependencies (Trivy, Grype, Dependency-Check).

Use them together; none replaces human reasoning.

## 20.3 Dependency Vulnerabilities

Modern apps depend on hundreds of packages. A vulnerability in any of them affects the app. Track dependencies with lockfiles, scan them continuously (Dependabot, Renovate, Trivy), and patch promptly. Note that a CVE's presence does not mean exploitability in your context — triage reachability.

## 20.4 Typosquatting and Dependency Confusion

- **Typosquatting:** publishing malicious packages with names similar to popular ones (`reqeusts` vs `requests`). Defend by verifying package names, using lockfiles with hashes, and internal mirrors.
- **Dependency confusion:** an attacker publishes a package with the same name as an internal package to a public registry, with a higher version, hoping the build fetches the public one. Defend with scoped namespaces, registry pinning, and `--ignore-scripts`.

## 20.5 Secret Exposure

Secrets (API keys, tokens, passwords) leak via:

- Source code and git history (scan with Gitleaks/truffleHog).
- Logs and error messages.
- CI/CD variables and build artifacts.
- Container images and mobile apps.
- Public paste sites and documentation.

If a secret leaks, **rotate it first**, then investigate. Rotation is more important than deletion.

## 20.6 Git History Analysis

Deleted secrets often remain in git history. Use `git log -p`, `git grep` across history, or Gitleaks full-history scans. Rewriting history (e.g., with `git filter-repo`) is possible but coordination is required; rotation remains essential.

## 20.7 CI/CD Pipeline Security

- Protect default branches; require reviews and status checks.
- Restrict secrets to needed jobs; avoid exposing them to PRs from forks.
- Pin actions to commit SHAs.
- Use OIDC for cloud access instead of static keys.
- Sign artifacts (Sigstore/cosign) and verify at deployment.
- Isolate runners; never run untrusted code with privileged credentials.

## 20.8 Build System Security

Compromised build systems can inject malicious code into signed products (SolarWinds). Defenses: reproducible builds, hermetic builders, separated signing keys, monitored build environments, and provenance attestation (SLSA framework).

## 20.9 Software Bill of Materials (SBOM)

An SBOM is a machine-readable inventory of components (formats: SPDX, CycloneDX). It enables rapid response when a new vulnerability appears: query the SBOM to see which products are affected. Generate SBOMs in CI and store them with releases.

## 20.10 Open-Source Vulnerability Research

Finding vulnerabilities in open-source software is a valuable, legitimate path:

1. Choose a project and understand its threat model.
2. Review recent changes and complex parsers/deserializers.
3. Build the project and run its tests; set up a lab harness.
4. Use SAST and fuzzing to generate leads.
5. Manually validate and minimize a reproducer.
6. Report privately to maintainers with a clear advisory.
7. Coordinate disclosure and, if assigned, a CVE via a CNA.

Respect maintainers' time: provide a minimal reproducer and a proposed fix when possible.

## 20.11 Secure Development Lifecycle (SDL)

Security must be integrated throughout: requirements (abuse cases), design (threat modeling), implementation (secure coding, SAST), verification (DAST, pentest), and release/maintenance (patching, monitoring). Security gates and training make this repeatable.

## 20.12 Practical Code Review Exercises

1. Review a small lab Python web app; list every input source and sink and identify missing validation.
2. Run Semgrep with an OWASP ruleset and triage each finding as true/false positive with reasoning.
3. Scan a lab repo with Gitleaks; rotate a deliberately committed fake key and document the process.
4. Create a CycloneDX SBOM for a lab project with Trivy or Syft and inspect the component list.
5. Analyze a lab GitHub Actions workflow for secret exposure and pin an action to a SHA.

## 20.15 Mastery Deep Dive: SAST, DAST, IAST, and SCA Compared

Modern AppSec uses four complementary analysis families. Mastery means knowing what each one can and cannot see, so you can choose the right tool and triage its output instead of trusting a dashboard.

### 20.15.1 What Each Technique Sees

| Technique | Analyzes | Needs running app? | Finds | Blind to |
|-----------|----------|--------------------|-------|----------|
| SAST | Source/bytecode, no execution | No | Taint flows, dangerous patterns, config issues | Runtime-only behavior, environment-dependent flows |
| DAST | Running app from outside | Yes | Exploitable HTTP-level issues (XSS, SQLi, auth flaws) | Source-level root cause, buried code paths |
| IAST | Running app with in-process agent | Yes | Precise taint with runtime context | Languages without agents; production overhead |
| SCA | Dependency manifests / lockfiles | No | Known CVEs, license issues in third-party code | Custom code; whether a CVE is actually reachable |

The key mental model: **SAST sees code you wrote; SCA sees code you imported; DAST/IAST see the assembled running system.** No single family covers the whole picture, which is why all four belong in a mature pipeline.

### 20.15.2 SAST Mechanics: Sources, Sinks, and Sanitizers

SAST engines model **taint flow**: data originates at a **source** (HTTP parameter, file, env var) and is dangerous at a **sink** (SQL query, `eval`, shell command, HTML response). A finding is valid only if an untrusted path from source to sink lacks effective sanitization.

```python
# Lab: a tainted flow a SAST tool should flag
from flask import request
import subprocess

@app.route("/ping")
def ping():
    host = request.args["host"]          # SOURCE
    return subprocess.check_output(
        "ping -c 1 " + host, shell=True  # SINK (command injection)
    ).decode()
```

To reason like a SAST engine, annotate three things:

- **Source:** `request.args["host"]` — attacker-controlled.
- **Sink:** `subprocess(..., shell=True)` — executes a string.
- **Sanitizer:** none — concatenation passes taint unchanged.

A semgrep rule expresses this generically:

```yaml
rules:
  - id: lab-shell-injection
    pattern: subprocess.check_output($CMD, shell=True)
    message: "Shell=True with dynamic command: validate/allow-list input"
    severity: ERROR
    languages: [python]
```

**False positives** occur when a sanitizer exists but the tool cannot model it (e.g., a custom `allow_list()` helper). **False negatives** occur when taint flows through an unmodeled framework feature (reflection, ORM magic). Both are why human triage is mandatory.

### 20.15.3 DAST and IAST Mechanics

DAST tools (ZAP, Burp, Nuclei) crawl the app, inject payloads into every parameter, and classify responses. Authenticated scans are essential — unauthenticated crawls miss the majority of an application's attack surface. Limitations: they cannot see logic flaws requiring business context, and a scanning agent can damage stateful workflows.

IAST instruments the app (via an agent) so it observes taint as data flows through real code paths at runtime. It is far more precise than SAST but requires a supported runtime and adds overhead, so it belongs in test/staging, not production.

### 20.15.4 SCA and Reachability

SCA maps your dependencies to known vulnerabilities (CVEs). A critical skill is **reachability triage**: a vulnerable function in a dependency you never call is lower risk than one on a request path. Modern tools combine SBOM data with call-graph analysis to compute this.

```bash
# Lab: generate an SBOM and scan it
syft <YOUR_LAB_IMAGE> -o cyclonedx-json > sbom.json
grype sbom:sbom.json
```

**Knowledge check.** A SCA tool flags a critical CVE in a dependency; SAST shows your code never imports the affected module. What do you do? **Answer:** Record it as "not reachable / low priority" with evidence (the import graph), monitor for changes, but do not ignore it entirely — reachability can change with a future code change or a transitive import.

## 20.16 Mastery Deep Dive: Dependency Attacks — Typosquatting, Confusion, and Lockfile Poisoning

Package registries are a supply-chain frontier because a single `install` command executes code on developer machines and build servers. Understanding the poisoning mechanics lets you build effective defenses.

### 20.16.1 Dependency Confusion (Lab Only)

**Mechanic:** enterprises often host *private* packages (e.g., `acme-internal-utils`) on an internal registry. If the build tool is misconfigured to also query the public registry, an attacker can publish a **public** package with the same name and a **higher version number**. Many resolvers prefer the highest version, so the build fetches the malicious public package instead of the private one.

A safe lab reproduction uses names you invent, never real internal package names:

```bash
# Lab: demonstrate resolution order with a fictional name
npm view <YOUR_LAB_SCOPE>/<YOUR_LAB_FICTIONAL_PKG> versions --json
```

The malicious payload typically lives in an **install script** (`preinstall`/`postinstall` in npm, `setup.py` in pip) that runs automatically:

```json
{
  "name": "<YOUR_LAB_FICTIONAL_PKG>",
  "version": "99.0.0",
  "scripts": { "postinstall": "node lab-marker.js" }
}
```

Why this is dangerous: install scripts run with the privileges of the build agent, which often holds cloud credentials and source access.

### 20.16.2 Typosquatting and Combosquatting

- **Typosquatting:** near-identical names (`reqeusts` vs `requests`, `lodahs` vs `lodash`).
- **Combosquatting:** plausible combinations (`python-dateutil-installer`).
- **Homoglyph attacks:** Unicode look-alikes (Cyrillic `о` vs Latin `o`).

Defenses: verify exact names, rely on lockfiles with integrity hashes, use scoped namespaces you control (`@yourorg/*`), and pin an internal mirror as the sole source.

### 20.16.3 Lockfile Poisoning

A lockfile (`package-lock.json`, `poetry.lock`, `Cargo.lock`) records exact versions and integrity hashes. If an attacker can land a change to both the manifest and lockfile in a PR — or exploit a resolver that updates the lockfile — the build pulls attacker-chosen code. Watch for PRs that modify dependency files without a clear explanation.

### 20.16.4 Defense Decision Table

| Attack | Primary defense | Secondary defense |
|--------|-----------------|-------------------|
| Dependency confusion | Scoped names + registry pinning (internal-only) | `--ignore-scripts`, network egress controls |
| Typosquatting | Exact-name verification, curated allow-list | Lockfile hashes, internal mirror |
| Lockfile poisoning | Review dependency diffs, signed commits | CI that verifies lockfile reproducibility |
| Malicious install scripts | `--ignore-scripts`, disable lifecycle scripts | Run installs in sandboxed, credential-less builders |

### 20.16.5 Verify It in Your Lab

1. Create a local registry (e.g., Verdaccio) with a fictional private package.
2. Publish a higher-version public-looking package with the same fictional name to a **separate** test registry.
3. Show that a misconfigured resolver picks the higher version, then fix the config (scope + pinned registry) and show it picks the private one.
4. Inspect the installed package's `package.json` scripts to see what would have executed.

> **Rule:** only publish fictional packages to registries you own. Never publish to a real public registry, and never use a real organization's package name.

## 20.17 Mastery Deep Dive: CI/CD and GitHub Actions Security

The pipeline is a high-value target because it holds secrets and produces trusted artifacts. A single workflow misconfiguration can leak credentials or poison every release.

### 20.17.1 The GitHub Actions Permission Model

`GITHUB_TOKEN` is an automatic token whose scope is controlled by a `permissions:` block. The default can be read/write, which is too broad. Set a top-level default of `read-all` or `contents: read` and grant additional scopes only where needed.

```yaml
# Lab: least-privilege workflow
name: lab-ci
on: [push, pull_request]
permissions:
  contents: read        # default: read-only
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<PINNED_SHA>   # pin to immutable SHA
      - run: npm test
```

Pinned actions: `@v4` is a mutable tag; an attacker who compromises the upstream repo can retag it. Pin to a full commit SHA.

### 20.17.2 Pwn Requests and `pull_request_target`

The classic CI secret leak is the **pwn request**: a workflow using `pull_request_target` runs in the *base* repository context, so it has access to secrets and a write-scoped token. If that workflow checks out and executes code from the contributor's PR branch, the contributor's code runs with privileged secrets.

```yaml
# DANGEROUS pattern — do not use
on: pull_request_target
jobs:
  build:
    steps:
      - uses: actions/checkout@<PINNED_SHA>
        with:
          ref: ${{ github.event.pull_request.head.sha }}  # untrusted code!
      - run: npm install && npm test                      # with secrets available
```

Defenses: never execute untrusted PR code in a privileged context; use `pull_request` (no secrets) for untrusted code; explicitly gate approval before privileged workflows run; keep `permissions` minimal.

### 20.17.3 OIDC Short-Lived Credentials

Instead of storing a cloud access key as a secret, workflows can request an OIDC token and exchange it for short-lived cloud credentials. (See Chapter 19 for the trust-policy side.) This removes long-lived keys from the pipeline entirely.

```yaml
jobs:
  deploy:
    permissions:
      id-token: write   # required for OIDC
      contents: read
    steps:
      - uses: aws-actions/configure-aws-credentials@<PINNED_SHA>
        with:
          role-to-assume: arn:aws:iam::<YOUR_LAB_ACCOUNT>:role/<YOUR_LAB_ROLE>
          aws-region: <YOUR_LAB_REGION>
```

### 20.17.4 Artifact and Cache Poisoning

Build artifacts and caches are trusted inputs to later jobs. If an attacker can poison a cached dependency or an uploaded artifact, downstream jobs — and eventually releases — consume malicious content. Defenses: scope caches to trusted refs, do not restore caches in privileged jobs from untrusted PRs, and sign/verify artifacts.

### 20.17.5 Assessment Checklist

- [ ] All workflows have explicit, minimal `permissions`.
- [ ] No `pull_request_target` workflow executes untrusted PR code with secrets.
- [ ] Actions pinned to SHAs, not tags.
- [ ] OIDC used instead of static cloud keys.
- [ ] Secrets restricted to the jobs that need them; fork PRs get none.
- [ ] Artifacts signed (Sigstore/cosign) and verified at deployment.

**Knowledge check.** Why is pinning `@v4` insufficient? **Answer:** Tags are mutable; a compromised upstream can move the tag to malicious code. A commit SHA is immutable and therefore verifiable.

## 20.18 Mastery Deep Dive: Secrets Discovery and Rotation

A leaked secret is a live incident. The correct response order is **rotate first, investigate second** — deleting the secret without revoking it leaves it usable.

### 20.18.1 Where Secrets Leak

- Source code and **git history** (deleted secrets persist in objects).
- Logs, error messages, stack traces, and debug endpoints.
- CI/CD variables, build artifacts, and container image layers.
- Mobile apps and client-side JavaScript (anything shipped to a client is public).
- Paste sites, documentation, screenshots, and support tickets.

### 20.18.2 Detection Techniques

Secret scanners (Gitleaks, truffleHog) use regex patterns and **entropy analysis** (random-looking strings) to find candidates. Tune them to reduce noise:

```bash
# Lab: scan current tree and full history
gitleaks detect --source . --redact
gitleaks detect --source . --log-opts="--all" --redact
```

Entropy produces false positives (hashes, base64 assets). Triage by checking the surrounding context and validating whether the string matches a real credential format.

### 20.18.3 Git History and Rotation

Even after removing a secret from the working tree, old commits retain it. `git filter-repo` can rewrite history, but that requires coordination with every clone and is **not** a substitute for rotation.

**Rotation runbook (lab):**

1. **Revoke/invalidate** the exposed credential at the issuer immediately.
2. **Issue a replacement** with narrower scope and store it in a secret manager.
3. **Update consumers** and deploy.
4. **Remove** the secret from code/history and purge from caches/artifacts.
5. **Audit usage** — did the old secret get used by anyone other than your systems?
6. **Add a detection** (scanner rule / alert) so the pattern is caught earlier next time.

**Detection + fix checklist:**

- [ ] Pre-commit hooks and CI secret scanning enabled.
- [ ] Secrets stored in a manager, referenced at runtime.
- [ ] No secrets in client-side code or images.
- [ ] Documented rotation runbook with a short mean-time-to-rotate.
- [ ] Audit logs reviewed for use of any leaked credential.

## 20.19 Mastery Deep Dive: Secure Code Review by Language

Generic review principles become concrete at the language level. Use this table as a per-language "dangerous API" checklist and adapt your taint tracking to each ecosystem.

### 20.19.1 Cross-Language Dangerous API Map

| Language | Dangerous constructs | Typical flaw |
|----------|----------------------|--------------|
| C/C++ | `strcpy`, `sprintf`, pointer arithmetic | Buffer overflow, UAF |
| Java | `ObjectInputStream`, `Runtime.exec`, XXE parsers | Deserialization RCE, command injection, XXE |
| Python | `eval`, `exec`, `pickle.loads`, `yaml.load`, f-strings in SQL | RCE, deserialization, SQLi/SSTI |
| JavaScript/Node | `eval`, `child_process.exec`, `Object.assign` on user keys | RCE, command injection, prototype pollution |
| PHP | `unserialize`, `include` with user input, `eval` | RCE, LFI/RFI |
| Go | `template.HTML` with user data, `exec.Command` with user args | XSS, command injection |
| Ruby | `eval`, `Marshal.load`, `system` with user input | RCE, command injection |

### 20.19.2 Language-Specific Review Notes

**Python:** `pickle` and `yaml.load` (unsafe loader) deserialize arbitrary objects — treat any use on untrusted data as RCE. Template engines (Jinja2) with user-controlled templates yield SSTI. Always use parameterized queries (`cursor.execute("... %s", (val,))`).

**JavaScript/Node:** prototype pollution happens when user-controlled keys are merged into objects (`Object.assign({}, userInput)`), affecting all objects via `__proto__`. Use `Object.create(null)` and validate keys. `child_process.exec` invokes a shell; prefer `execFile`/`spawn` with argument arrays.

**Java:** `ObjectInputStream` on untrusted bytes is deserialization RCE. Disable external entity resolution in XML parsers to prevent XXE. Use `PreparedStatement` for SQL.

**C/C++:** prefer bounded functions (`snprintf`, `strncpy_s`), use sanitizers (ASan/UBSan) in CI, and review all allocation/free pairs for use-after-free.

### 20.19.3 A Repeatable Review Checklist

For every function that handles untrusted data:

- [ ] Identify the source and mark data as tainted.
- [ ] Trace every path to a sink; confirm sanitization on each path.
- [ ] Check authorization at the object/function level, not just the route.
- [ ] Verify crypto: modern algorithms, secure RNG, proper key storage.
- [ ] Confirm errors fail closed and do not leak internals.
- [ ] Check concurrency/shared state for TOCTOU and races.

**Knowledge check.** A Node.js handler does `Object.assign(config, req.body)`. What flaw class? **Answer:** Prototype pollution — a body containing `__proto__` keys can mutate `Object.prototype`, affecting unrelated objects across the app.

## 20.20 Mastery Deep Dive: Build Integrity, SLSA, SBOM, and Provenance

Knowing your code is secure is not enough if the artifact shipped is not the artifact you reviewed. Build integrity closes that gap.

### 20.20.1 The SLSA Model

SLSA (Supply-chain Levels for Software Artifacts) is a maturity ladder:

| Level | Meaning |
|-------|---------|
| 1 | Build and provenance documentation exist |
| 2 | Hosted build service; signed provenance |
| 3 | Hardened, isolated, hermetic builds; tamper-resistant provenance |
| 4 | Two-party review + fully reproducible builds (highest assurance) |

The goal is that a consumer can verify **where, how, and from what source** an artifact was built.

### 20.20.2 SBOMs and Provenance

An **SBOM** (SPDX or CycloneDX) inventories components. **Provenance** is signed metadata describing the build (source repo, commit, builder, inputs). Together they let you answer, "Are we affected by this new CVE?" and "Is this binary genuinely from our source?"

```bash
# Lab: generate an SBOM and sign an artifact with Sigstore/cosign
syft . -o spdx-json > sbom.spdx.json
cosign sign --key <YOUR_LAB_KEY_REF> <YOUR_LAB_REGISTRY>/<YOUR_LAB_IMAGE>:<TAG>
cosign verify --key <YOUR_LAB_KEY_REF> <YOUR_LAB_REGISTRY>/<YOUR_LAB_IMAGE>:<TAG>
```

### 20.20.3 Reproducible and Hermetic Builds

- **Hermetic:** the build does not reach the network; all inputs are pinned. This prevents a compromised dependency server from changing inputs mid-build.
- **Reproducible:** the same source and inputs always produce byte-identical output. This lets independent parties verify the artifact.

The SolarWinds-style lesson: a compromised build system can inject code into a correctly signed product. Therefore signing alone is insufficient — you also need isolated builders, separated signing keys, monitored build environments, and provenance attestation.

### 20.20.4 Incident Response for a Supply-Chain Compromise

1. Identify affected artifacts via SBOM/provenance queries.
2. Revoke signing keys and invalidate tokens used by the build system.
3. Rebuild from a known-good, reviewed source state in a clean environment.
4. Notify consumers with exact affected version ranges.
5. Add detection for the malicious artifact's indicators.

**Knowledge check.** Why doesn't a valid signature prove an artifact is safe? **Answer:** It proves the artifact came from a key holder — if the build system or signing key is compromised, a malicious artifact can still be validly signed. Provenance and hermetic/reproducible builds add the missing assurance.

## 20.21 Mastery Deep Dive: Vulnerability Management and Triage

Finding vulnerabilities is only useful if they are fixed in a risk-based order. Triage is the skill that separates a security engineer from a scanner operator.

### 20.21.1 The Triage Dimensions

For each finding, score:

- **Exploitability:** is there a public exploit? Is it reachable from an untrusted input?
- **Reachability:** is the vulnerable code actually called (for dependencies)?
- **Impact:** confidentiality, integrity, availability, scope change.
- **Exposure:** internet-facing vs. internal; authenticated vs. anonymous.
- **Exploit Maturity / EPSS:** likelihood of exploitation in the wild.
- **Asset criticality:** does it hold sensitive data or a privileged role?

A critical CVE in a non-reachable, internal-only dependency is lower priority than a medium flaw on an internet-facing auth endpoint.

### 20.21.2 The Management Lifecycle

1. **Discover** (SAST/SCA/DAST/pentest/bug bounty).
2. **Deduplicate and validate** (eliminate false positives).
3. **Prioritize** using the dimensions above and agreed SLAs.
4. **Remediate** (patch, config change, or compensating control).
5. **Verify** (rescan; confirm the fix actually removes the finding).
6. **Track metrics:** mean time to remediate, recurrence rate, false-positive rate.

### 20.21.3 False-Positive Triage Discipline

Never close a finding as "false positive" without a reason code and evidence. Common legitimate dispositions: **not reachable**, **compensating control exists**, **accepted risk (with owner and expiry)**, or **false positive (tool error, with explanation)**. Recording the rationale prevents the same debate next quarter.

### 20.22.3 Knowledge Checks (With Answers)

**Q1.** A tool flags a critical CVE in a transitive dependency never imported by your code. How do you triage? **A:** Mark "not reachable" with evidence (import/call graph), keep monitoring, and revisit if code changes — not a blanket ignore.

**Q2.** What makes `pull_request_target` dangerous with untrusted code? **A:** It runs in the base context with secrets/write token; executing contributor code there leaks credentials.

**Q3.** Why pin actions to a SHA rather than a tag? **A:** Tags are mutable; a compromised upstream can move them. SHAs are immutable.

**Q4.** You find a secret in git history. What is step one? **A:** Rotate/revoke it at the issuer immediately; history rewriting is secondary and does not invalidate the credential.

**Q5.** Does a valid artifact signature prove the code is safe? **A:** No — it proves the signing key produced it. If the build/key is compromised, malicious code can be validly signed; provenance and hermetic/reproducible builds add assurance.

## 20.23 Mastery Deep Dive: Threat Modeling Source and Supply Chain

Threat modeling turns a vague "we should secure the pipeline" into a prioritized list of concrete risks. Apply STRIDE to the development lifecycle and you will find that most supply-chain incidents are failures at identifiable trust boundaries.

### 20.23.1 Assets, Trust Boundaries, and Actors

Start by listing **assets**: source code, build secrets, signing keys, registry credentials, artifact repositories, and the produced binaries. Then draw **trust boundaries**:

- Developer workstation → source control (commit boundary).
- Source control → CI runner (checkout boundary).
- CI runner → package registry (dependency fetch boundary).
- Build → artifact store (publish boundary).
- Artifact store → production (deploy/verify boundary).

**Actors** include the developer, an external contributor (fork PR), a compromised dependency, a compromised runner, and a malicious insider. Most real incidents involve one of the last four crossing a boundary that was assumed trusted.

### 20.23.2 STRIDE Applied to the Pipeline

| STRIDE | Pipeline example | Control |
|--------|------------------|---------|
| Spoofing | Fork PR impersonating trusted contributor | Signed commits, verified identity, approval gates |
| Tampering | Poisoned artifact in registry | Signing + verification, immutable tags |
| Repudiation | Unknown change to build config | Audit logs, protected branches, signed provenance |
| Information disclosure | Secrets in CI logs/artifacts | Secret masking, minimal permissions, no secrets on forks |
| Denial of service | Dependency confusion breaking builds | Registry pinning, lockfiles, vendoring |
| Elevation of privilege | Workflow token with write scope executing untrusted code | Minimal permissions, no `pull_request_target` with PR code |

### 20.23.3 A Repeatable Threat-Model Exercise (Lab)

1. Draw the five boundaries for a lab repo and its CI.
2. For each boundary, ask "what asset crosses here, and who controls it?"
3. List one STRIDE threat per boundary and one control.
4. Mark which controls are deterministic (enforced by tooling) vs. procedural (relying on humans). Favor deterministic ones.

**Knowledge check.** Which boundary does dependency confusion cross? **A:** CI runner → package registry. The control is registry pinning/scoped names and lockfiles, not code review of application source.

## 20.24 Mastery Deep Dive: Secure Dependency Management in Practice

Theory about dependency attacks becomes useful when you can configure a registry and verify a build end to end. This section covers the operational controls that make poisoning hard.

### 20.24.1 Lockfiles, Hashes, and Reproducibility

A lockfile is a security control only if it records **integrity hashes** and the build **verifies** them. Generate lockfiles in a clean environment, commit them, and configure CI to install from the lockfile rather than resolving fresh.

```bash
# Lab: npm install with lockfile integrity enforcement
npm ci                     # uses package-lock.json, fails if it is out of sync
# pip:
pip install --require-hashes -r requirements.lock
```

A build that runs `npm install` (which may update the lockfile) instead of `npm ci` is a common finding — it lets a PR silently change resolved versions.

### 20.24.2 Registry Hardening Steps

- Use a single internal mirror; block direct internet registry access from builders.
- Reserve scoped namespaces (`@yourorg/*`) that only your organization can publish to.
- Enable two-factor authentication and restrict publish tokens.
- Quarantine new packages for a review period before they are consumable.

### 20.24.3 Vendoring and Hermetic Builds

For high-assurance builds, **vendor** dependencies into your repository or an internal artifact store and build without network access (hermetic). This prevents a compromised upstream registry from changing inputs between your review and your build. Pair this with reproducible builds so an independent party can verify the published artifact matches the source.

### 20.24.4 Verifying Provenance at Deploy Time

Signing is only useful if someone verifies. Deploy systems should reject artifacts that lack valid provenance:

```bash
# Lab: verify a signed image before deployment
cosign verify --key <YOUR_LAB_KEY_REF> <YOUR_LAB_REGISTRY>/<YOUR_LAB_IMAGE>:<TAG>
# Then check that the provenance attestation matches the expected source repo/build
```

### 20.24.5 Responsible Open-Source Research Deep Dive

When you move from consumer to researcher, quality of reporting matters:

1. **Choose a target with a clear threat model** — parsers, deserializers, and auth code are fertile ground.
2. **Set up a reproducible harness** with pinned versions and a minimal input generator (fuzzing with AFL++/libFuzzer or structural fuzzers).
3. **Triage crashes** by root cause; discard nondeterministic ones; minimize the reproducer to a tiny input.
4. **Assess impact** in the project's threat model — a bug in a function never exposed to untrusted input may be informational.
5. **Draft an advisory** with affected versions, impact, steps to reproduce, and a suggested fix.
6. **Report privately** via the project's security policy; coordinate disclosure; request a CVE via a CNA if appropriate.

Respect maintainers: a minimal reproducer and a proposed patch dramatically increase the chance of a fast fix.

**Knowledge check.** Why is `npm ci` safer than `npm install` in CI? **A:** `npm ci` installs exactly from the lockfile and fails if it is out of sync, preventing silent version changes; `npm install` can rewrite the lockfile and pull new versions.

## 20.25 Mastery Deep Dive: Twelve Realistic Supply-Chain Case Patterns

Recognizing a pattern at a glance is a mastery skill. Each row below is a scenario you should be able to diagnose, explain, and fix without hesitation.

| # | Pattern | Root cause | Impact | Fix |
|---|---------|-----------|--------|-----|
| 1 | PR adds a new dependency with a suspicious name | Typosquatting | Malicious code on dev/build machines | Verify names, lockfile hashes, allow-list |
| 2 | Build pulls public `acme-lib` v99 over internal v1 | Dependency confusion | Build-server code execution | Scoped names + pinned internal registry |
| 3 | Lockfile silently updated in CI | `npm install` vs `npm ci` | Unreviewed code enters build | Use `npm ci` / `--require-hashes`; verify lockfile in CI |
| 4 | Workflow uses `pull_request_target` + untrusted checkout | Pwn request | Fork PR steals secrets | Use `pull_request`; never run PR code with secrets |
| 5 | Action referenced as `@v4` | Mutable tag | Upstream compromise hijacks CI | Pin to full commit SHA |
| 6 | Cloud access key stored as Actions secret | Long-lived credential | Leak → cloud account compromise | OIDC short-lived credentials |
| 7 | Fake key committed then deleted | Git history persistence | Credential still valid | Rotate first, then purge history |
| 8 | Secret appears in CI log | Missing masking | Credential disclosure | Mask secrets, minimize scope, restrict forks |
| 9 | Image built on outdated base | Vulnerable dependency | Known CVEs in production | Scan base images (Trivy); patch on schedule |
| 10 | Artifact published unsigned | No integrity check | Tampered binary reaches users | Sign with cosign; verify at deploy |
| 11 | No SBOM for a release | Poor vulnerability response | Slow, incomplete incident response | Generate SPDX/CycloneDX in CI; store with release |
| 12 | Critical CVE in unreachable code marked "ignore" | Poor triage discipline | Real risk hidden / noise overload | Use reason codes + evidence; monitor reachability |

**Knowledge check.** A PR changes only `package-lock.json` with a new high-version package from an unfamiliar registry. What do you check first? **A:** Treat it as a potential dependency-confusion/poisoning attempt: verify the package name/scope, the registry source, the integrity hash, and whether CI uses `npm ci`; require explicit review.

## 20.13 Key Takeaways

- Code review is taint tracking, authorization checking, and dangerous-API identification across all paths.
- SAST, DAST, SCA, and manual review are complementary.
- Dependencies, secrets, and CI/CD are high-leverage supply-chain targets.
- SBOMs and integrity controls enable rapid, trustworthy response.
