# Chapter 17: API Security Mastery

> **Learning objectives.** Apply the OWASP API Security Top 10; test REST, GraphQL, and API authentication/authorization; identify BOLA, BFLA, mass assignment, excessive exposure, and JWT/OAuth flaws; and test APIs safely in authorized labs.

## 17.1 The API Security Top 10

OWASP publishes a separate **API Security Top 10** (current edition: 2023; verify at https://owasp.org/API-Security/). Key categories:

- **API1 Broken Object Level Authorization (BOLA)** — object IDs not ownership-checked.
- **API2 Broken Authentication** — flawed token/session handling.
- **API3 Broken Object Property Level Authorization** — excessive exposure and mass assignment.
- **API4 Unrestricted Resource Consumption** — missing rate/size limits.
- **API5 Broken Function Level Authorization (BFLA)** — privileged functions callable by low-privilege users.
- **API6 Unrestricted Access to Sensitive Business Flows** — automation of legitimate flows (scalping, spam).
- **API7 Server Side Request Forgery** — server fetches attacker-chosen URLs.
- **API8 Security Misconfiguration** — verbose errors, exposed docs, permissive CORS.
- **API9 Improper Inventory Management** — old/unknown API versions exposed.
- **API10 Unsafe Consumption of APIs** — trusting third-party API data.

## 17.2 REST API Vulnerabilities

REST APIs are especially prone to authorization and inventory issues because endpoints are numerous and often auto-generated. Test:

- Every object ID (BOLA) with a second test account.
- Every admin/function endpoint (BFLA) with a low-privilege token.
- HTTP method mismatches: an endpoint may block GET but allow PUT/DELETE.
- Content-type variations: JSON vs. form vs. XML parsers may have different validation.
- Duplicate JSON keys: `{"role":"user","role":"admin"}` — parsers differ on which wins.
- Parameter pollution and array/type confusion: `{"id":["1","2"]}`.

## 17.3 GraphQL Vulnerabilities

- **Introspection:** `query { __schema { types { name } } }` may reveal the full schema (disable in production or restrict).
- **Depth/complexity:** deeply nested queries can exhaust resources; enforce limits.
- **Resolver authorization:** each field/mutation must authorize; a list query may leak objects a detail query protects.
- **Batching:** multiple operations in one request can evade naive rate limits.
- **Field suggestions:** can reveal field names.
- **Aliases:** can duplicate expensive fields.

Test every query and mutation with two accounts; inspect responses for fields the UI never displays.

## 17.4 API Authentication and Authorization

- Validate JWTs fully (signature, `exp`, `nbf`, `iss`, `aud`, algorithm) — never trust decoded claims without verification (Chapters 7 and 10).
- Opaque tokens should be high-entropy, short-lived, and revocable.
- API keys must be scoped and rotated; they are not user authentication.
- Authorization must be per object and per function, server-side.
- Service-to-service calls need mTLS or signed tokens and least privilege.

## 17.5 Excessive Data Exposure and Mass Assignment

**Excessive exposure:** the API returns full objects (including password hashes, internal IDs) and the frontend filters them. Fix with response schemas/DTOs.

**Mass assignment (auto-binding):** binding request fields directly to model properties lets an attacker set fields like `isAdmin`, `role`, or `balance`. In labs, add unexpected fields to JSON bodies and observe whether they are honored. Fix with explicit allow-lists of writable fields.

## 17.6 Rate Limiting and Resource Consumption

APIs need limits on: requests per time window, payload size, query depth, batch size, and expensive operations. Test in labs for:

- Missing limits on login, OTP, password reset (brute force).
- Bypass via header spoofing (`X-Forwarded-For`), IP rotation, or token variation.
- GraphQL complexity abuse.
- Large file uploads or huge query strings.

## 17.7 API Inventory and Improper Asset Management

Old API versions (`/api/v1`, `/api/v2-beta`) often lack newer security controls. Discover them via docs, JS bundles, and historical URLs (Chapter 14). Maintain an inventory and retire old versions.

## 17.8 Webhook Security

Webhooks deliver data to a URL you control. Security concerns:

- **SSRF** if the URL is user-controlled.
- Missing signature verification (attacker can forge events).
- Replay attacks (no timestamp/nonce).
- Leaking secrets in URLs.

Fix: allow-list destinations, sign payloads (HMAC), verify signatures and timestamps, and avoid sensitive data in callbacks.

## 17.9 API Fuzzing and Schema Analysis

- Generate requests from OpenAPI/Swagger schemas; fuzz parameters with type/null/length variations.
- Use schema-aware fuzzers (e.g., Schemathesis) in labs.
- Compare behavior across versions and representations (JSON vs. XML).
- Look for 500s, timing anomalies, and authorization differences.

## 17.10 Multi-Tenant API Security

Every data access must include a tenant scope derived from the authenticated context — never from client input. Cache keys, search indices, and background jobs must also include tenant identity. Test with two of your own tenants in an authorized program.

## 17.11 API Security Testing Exercises

1. In crAPI (OWASP), use two accounts to find BOLA on a vehicle/order endpoint.
2. On a lab GraphQL API, run introspection and identify unprotected mutations.
3. Send a JSON body with an extra `role=admin` field to a lab endpoint; observe mass assignment.
4. Test login rate limits in a lab and identify a bypass via a forwarded header.
5. Write a Schemathesis test for a lab OpenAPI spec and triage the findings.

## 17.14 Mastery Deep Dive: BOLA and BFLA in Depth

### 17.14.1 Root cause and mechanism

APIs expose object identifiers by design, so Broken Object Level Authorization (BOLA/API1) is the most prevalent API flaw. The server retrieves an object by ID from the request and fails to verify ownership or tenancy. Broken Function Level Authorization (BFLA/API5) is the function-level twin: a low-privilege token can invoke an admin operation because the endpoint checks only "authenticated," not "authorized for this action." Both share a root cause: authorization derived from client input or assumed from network position rather than from the verified principal on every request.

```http
GET /api/v3/users/8421/profile HTTP/1.1
Host: <LAB_HOST>
Authorization: Bearer <lab-token-user-A>

HTTP/1.1 200 OK
{"id":8421,"email":"userB@lab","role":"user"}   <-- BOLA in a lab
```

### 17.14.2 Lab-safe testing methodology

1. Create two accounts and, where relevant, two tenants. Capture a full request inventory from account A (crawl the app, record every REST and GraphQL call).
2. For every request with an identifier in the path, query, body, or header, replace it with B's identifier (from B's own responses). Record status, body length, and data returned.
3. Try alternate identifier forms and encodings; test plural/bulk endpoints (`/users?id[]=A&id[]=B`) where one unauthorized ID can hide in a batch.
4. For BFLA, replay admin endpoints with A's token; vary HTTP methods and content types; test deprecated versions (`/api/v1/admin/...`).
5. Demonstrate impact only with your own accounts: show A reading or modifying B's object. Never touch real customers.

### 17.14.3 Detection and defense

Detection signals: sequential or guessable IDs, different bodies/lengths for swapped IDs, endpoints absent from the UI but present in the bundle or docs, and 403/404 inconsistencies. Automate with a multi-token replay harness that diffs responses. Defense: centralize authorization and derive the principal from the verified token; scope every query by owner and tenant (`WHERE id=? AND tenant_id=? AND owner_id=?`); deny by default; test the role × action × object matrix in CI. Verify by replaying the exact cross-account requests after the fix and confirming uniform denial.

## 17.15 Mastery Deep Dive: Mass Assignment and Excessive Data Exposure

### 17.15.1 Mass assignment (auto-binding)

When a framework binds request fields directly to a persistence model, an attacker can set fields the developer never exposed in the UI. In labs, add unexpected fields to JSON bodies: `{"email":"a@lab","role":"admin","isAdmin":true,"balance":999999,"verified":true}`, including nested and array variants. If the stored object reflects them, you have a privilege or integrity flaw. Defense: use Data Transfer Objects with explicit writable-field allow-lists; ignore or reject unknown fields; never bind to ORM entities directly. Verify that extra fields are ignored and no state changes.

### 17.15.2 Excessive data exposure

APIs often serialize full internal objects and let the frontend filter them. The fix is not client-side filtering — it is response schemas/DTOs that emit only the fields the client needs. Detect by inspecting raw API responses for fields the UI never displays: password hashes, internal IDs, `mfaSecret`, `resetToken`, `salary`, and other tenants' data. Defense: allow-list output fields, enforce schema validation on responses, and remove secrets from models entirely. Verify that raw responses contain only allow-listed fields. Common mistake: relying on GraphQL/REST field selection to hide data — if the resolver can return it, an attacker can request it.

## 17.16 Mastery Deep Dive: GraphQL Security

### 17.16.1 Introspection and schema recon

GraphQL exposes a typed schema. Introspection can reveal it wholesale:

```graphql
query { __schema { queryType { name } mutationType { name }
  types { name fields { name args { name type { name kind } } } } } }
```

Labs often leave introspection enabled; production should disable it or gate it to authenticated developers. Field suggestions ("Did you mean `resetPassword`?") also leak names. Even without introspection, error messages and batching behavior reveal the schema.

### 17.16.2 Query abuse patterns (labs only)

- **Depth/complexity:** deeply nested queries expand exponentially (`user { friends { friends { ... } } }`), exhausting CPU/memory. Defense: depth and complexity limits, query cost analysis, and timeouts.
- **Aliases and batching:** alias the same expensive field many times, or send an array of operations in one request, to multiply work and evade naive per-request rate limits. Defense: limit alias count, batch size, and total cost per request.
- **Resolver authorization:** a list query may return objects a detail query protects, or a field may expose sensitive data for another user. Test every query *and* mutation with two accounts and inspect all returned fields. Defense: authorize at the resolver/field level; never rely on the transport layer.
- **Mutation bypasses:** a mutation may reach data through a path the REST controller protects. Defense: unify authorization logic across REST and GraphQL.

Verify defenses by replaying each abusive query and confirming rejection (or a 400 with a cost-limit message) and no cross-account data.

## 17.17 Mastery Deep Dive: API Keys, JWT, OAuth, and Mobile Backends

### 17.17.1 API key handling

API keys identify a *client/project*, not a user; they are not authentication for user data. Common flaws: keys shipped in mobile apps or JS bundles, keys with excessive scope, no rotation, keys in URLs (leak via logs/referrers), and accepting keys in more places than necessary (query param, body, header). Detection: search authorized bundles/binaries for key-shaped strings; check whether a key grants more than its intended scope. Defense: treat keys as secrets, scope them minimally, rotate them, send them only in headers, and pair them with user auth for user data. Verify by confirming a leaked lab key cannot access another user's objects.

### 17.17.2 JWT and OAuth for APIs

APIs commonly use JWTs as bearer tokens. Apply the full validation checklist (signature, algorithm pinning, `exp`, `nbf`, `iss`, `aud`, and app claims); prefer short-lived access tokens plus revocable refresh tokens, because a signed JWT cannot be individually revoked without a denylist. For OAuth, validate scopes strictly — a token with `scope=read:profile` must not access `write:orders`; verify `iss`/`aud`; and use PKCE for public/mobile clients. Detect scope confusion by using a lab token with fewer scopes against a privileged endpoint. Defense: enforce scopes/permissions at each endpoint and validate tokens centrally.

### 17.17.3 Mobile backends

Mobile apps concentrate secrets in the client: hardcoded keys, pinned certs, embedded credentials, and local storage tokens. Reverse the app you own (or are authorized to test) to find API endpoints, hardcoded secrets, and weak certificate validation that enable MITM. The backend must not trust the client: device identity, app integrity attestation, and user authorization must be verified server-side. Test API endpoints directly (not through the UI) with a second account. Defense: move secrets server-side, use certificate pinning *plus* proper server validation, and enforce per-user authorization on every endpoint.

## 17.18 Mastery Deep Dive: Rate Limiting and Resource Consumption

### 17.18.1 What to limit

APIs need limits on requests per window, payload size, upload size, GraphQL depth/complexity, batch size, and expensive operations (search, export, OTP generation). Missing limits on login, OTP, and password reset enable brute force and OTP bypass (API4 and API2).

### 17.18.2 Bypass patterns (labs only)

- **Header spoofing:** `X-Forwarded-For`, `X-Real-IP`, `X-Client-IP` when the app trusts a client-supplied value for the rate-limit key.
- **Rotation:** varying API keys, tokens, or session IDs to get a fresh bucket; distributing across IPs.
- **Boundary games:** requests just under the limit, split across windows; HTTP/2 multiplexing to burst; changing case/encoding of the endpoint path to create a "new" bucket.
- **GraphQL:** batching and aliases to multiply operations inside one counted request.

Detection: script N+1 requests and confirm whether the (N+1)th is blocked; then try each bypass and see if the block disappears. Defense: key limits on authenticated principal where possible, trust only sanitized proxy headers, apply limits at the gateway and the app, cap payload/depth/batch sizes, and use exponential backoff. Verify by replaying every bypass and confirming a consistent 429.

## 17.19 Mastery Deep Dive: Inventory, Recon, and Fuzzing Workflow

### 17.19.1 Improper asset management (API9)

Old versions (`/api/v1`, `/beta`, `/internal`) often lack newer controls. Discover them through documentation, JS bundles, OpenAPI specs (`/openapi.json`, `/swagger.json`), Certificate Transparency logs, and historical URLs — for assets you are authorized to test. Maintain a canonical inventory and retire stale versions; a single forgotten v1 endpoint can undermine every modern control.

### 17.19.2 A disciplined recon-and-fuzz workflow

1. **Inventory:** enumerate hosts, subdomains, and API versions from docs, bundles, and CT logs (in scope only).
2. **Schema:** obtain OpenAPI/GraphQL schemas; note all paths, methods, parameters, and auth requirements.
3. **Auth model:** map which endpoints need which token/scope; create two accounts and two tenants.
4. **Fuzz from schema:** generate requests with type/null/length/boundary variations ( Schemathesis, ffuf, Burp Intruder ) against your lab. Test duplicate keys, arrays where scalars are expected, and extra fields.
5. **Triage:** look for 500s, timing anomalies, response-length differences, and authz differences between accounts. Refute false positives before reporting.
6. **Verify fixes:** replay the exact request after remediation.

Example lab-safe fuzz case: take `POST /api/orders` with schema `{itemId:int, qty:int}` and try `qty = -1`, `qty = 1e309`, `qty = []`, `qty = "1 OR 1=1"`, and an extra `"price":0` field; observe which the server honors. Defense is strict schema validation with allow-lists and authoritative server-side pricing.

### 17.19.3 OWASP API Top 10 coverage map

| Category | Core test | Primary defense |
|----------|-----------|-----------------|
| API1 BOLA | Swap object IDs with second account | Per-object ownership checks |
| API2 Broken Auth | Weak tokens, no rate limits, reset flaws | Secure sessions, MFA, rate limits |
| API3 Property Auth | Extra fields, full-object responses | DTO allow-lists for input and output |
| API4 Resource Consumption | Payload/depth/batch abuse | Limits at gateway and app |
| API5 BFLA | Admin endpoints with low-priv token | Function-level authorization |
| API6 Business Flows | Automate legitimate flows | Abuse detection, flow limits |
| API7 SSRF | User-controlled URLs to lab listener | Allow-lists, egress controls |
| API8 Misconfiguration | Verbose errors, exposed docs, CORS | Hardened baselines |
| API9 Inventory | Old versions | Asset inventory, retirement |
| API10 Unsafe Consumption | Trusting third-party API data | Validate and sanitize external data |

## 17.20 Mastery Deep Dive: Verification and Practice

### 17.20.1 What mastery looks like — checklist

- [ ] I can run a two-account BOLA/BFLA sweep across every endpoint and method.
- [ ] I can demonstrate mass assignment and excessive exposure with raw responses and DTO fixes.
- [ ] I can run introspection, depth, alias, and resolver-auth tests on a lab GraphQL API.
- [ ] I can explain why API keys are not user authentication and how to scope them.
- [ ] I can bypass and then fix rate limits in a lab using header, rotation, and batching techniques.
- [ ] I can perform a schema-driven fuzzing workflow and triage results rigorously.
- [ ] I can map any finding to the OWASP API Top 10 and verify remediation by replay.

### 17.20.2 Common mistakes

- Treating CORS or client-side filtering as authorization for API data.
- Reporting excessive exposure based on a UI that hides fields, rather than the raw response.
- Forgetting non-REST paths (GraphQL, mobile, old versions) when testing authorization.
- Using a rate limit keyed only on an IP that the client can spoof with a forwarded header.
- Testing APIs on systems outside authorized scope — always use labs, your own apps, or in-scope programs.

### 17.20.3 Knowledge checks (answers below)

1. Why is an API key insufficient to authorize access to a specific user's order?
2. A GraphQL list query returns another user's email while the detail query blocks it. What is the flaw?
3. Adding `"role":"admin"` to a JSON body changes the stored user's role. Name the flaw and the fix.
4. A rate limit uses `X-Forwarded-For` directly from the request. What is the bypass and the fix?
5. Why should introspection be disabled (or gated) in production?

**Answers.** (1) A key identifies the client/project, not the user; object-level authorization must derive from verified user identity. (2) Resolver-level authorization gap (API1/API3) — authorize every field/path, not just the detail endpoint. (3) Mass assignment (API3); fix with DTO allow-lists and rejection of unknown fields. (4) Spoof the header to get a fresh bucket; fix by trusting only sanitized proxy headers (or the socket peer) and keying on the authenticated principal. (5) It discloses the full schema, accelerating attacker recon; gate it to authenticated developers or disable it.

### 17.20.4 Lab exercises

1. In OWASP crAPI, use two accounts to find BOLA on a vehicle/order endpoint and verify the fix by replaying the cross-account request.
2. On a lab GraphQL API, run introspection, then craft a deep/aliased query and confirm complexity limits reject it.
3. Send a JSON body with extra `role=admin` and `balance` fields to a lab endpoint; observe mass assignment, then add DTOs and re-test.
4. Implement per-account and per-IP rate limits on a lab login; demonstrate the forwarded-header bypass, then fix and confirm 429.
5. Write a schema-aware fuzz test for a lab OpenAPI spec, triage three findings, and map each to the API Top 10.

## 17.21 Mastery Deep Dive: Advanced BFLA and Function-Level Testing

### 17.21.1 Building the method × content-type matrix

A function-level check may protect the documented verb while leaving alternates open. For each privileged endpoint in your lab, test every method (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS`) combined with content types (`application/json`, `application/x-www-form-urlencoded`, `multipart/form-data`, `application/xml`) and an alternate verb via `X-HTTP-Method-Override` or `X-Original-URL`. A 200/201 for a low-privilege token on any combination is a BFLA. Also test "internal" endpoints discovered in JS bundles or API docs — those protected only by network position or an assumed header. Defense: enforce function-level authorization in one central policy layer that every route must call, independent of method and content type; deny by default. Verify by replaying the full matrix and confirming uniform denial.

### 17.21.2 Microservice and internal-API trust

In microservices, an API gateway may authenticate a request and forward it with an assertion (a signed JWT or header) naming the user/role. If an internal service trusts client-supplied copies of that header rather than the gateway-signed assertion, an attacker can forge identity. Test in a lab by calling internal endpoints directly with a forged role/tenant header. Defense: use mTLS between services and validate gateway-issued signed tokens; never trust identity headers that a client can set. Verify that direct access to internal endpoints without the signed assertion is denied.

## 17.22 Mastery Deep Dive: Schema-Driven Fuzzing and Differential Testing

### 17.22.1 Schema-aware fuzzing workflow

Given an OpenAPI spec for a lab API, a thorough fuzz campaign varies each parameter across: valid boundary values, type mismatches (string for integer), null, empty, oversized values, special characters, duplicate keys, and extra undeclared fields. For GraphQL, vary aliases, batch sizes, and field nesting. Tools like Schemathesis, ffuf, or Burp Intruder automate generation, but interpretation is human: look for 500s with stack traces, timing anomalies, response-length differences, and authorization differences between accounts. Triage each candidate by replaying it in isolation and checking whether it is a real behavior change or a generic error.

### 17.22.2 Authorization differential testing

The highest-signal fuzz is a **differential** test: replay the *same* request with token A and token B and compare. Differences in status, body length, or returned fields reveal authorization gaps that no single-request fuzzer will find. Extend this across REST and GraphQL representations of the same data, across API versions, and across content types — the same object may be protected on one path and exposed on another. Automate the diff and review every discrepancy. Defense: unify authorization logic and enforce it on every path; verify by confirming zero unauthorized differences after remediation.

## 17.23 Mastery Deep Dive: API Threat Modeling and Defense Architecture

### 17.23.1 Defense at the gateway and in the app

A robust API security architecture layers controls:

| Layer | Controls |
|-------|----------|
| Edge/CDN | TLS, rate limits, WAF, bot detection, Geo/IP rules |
| Gateway | AuthN enforcement, token validation, schema validation, quotas |
| Service | Object/function authorization, business logic, output DTOs |
| Data | Row/tenant scoping, least privilege, encryption |
| Observability | Structured logs, anomaly alerts, audit trails |

No single layer is sufficient: the gateway can be bypassed by internal traffic, and the service must not assume the gateway validated everything. Test each layer in a lab by disabling it and confirming the others still hold.

### 17.23.2 Secure development lifecycle for APIs

Prevent the classes in this chapter structurally: generate API docs/schemas from code and keep them current; add authorization tests (two-account replay) to CI; add schema-validation middleware that rejects undeclared fields and wrong types; enable rate limits by default at the gateway; and retire old versions on a schedule (API9). Use contract testing so clients and servers agree on shapes. Verify the program by re-running the full test suite against each release and confirming no regressions in authorization, exposure, or rate limiting.

### 17.23.3 Putting it all together

Mastery is the ability to take an unfamiliar API and, using only authorized targets, produce a prioritized list of findings with reproducible evidence: a BOLA demonstrated with two accounts, a BFLA via the method matrix, an excessive-exposure field shown in the raw response, a rate-limit bypass scripted, and a GraphQL complexity abuse captured — each mapped to the API Top 10, each with a concrete defense, and each re-verified after a fix. Keep the scope discipline absolute: labs, your own apps, or explicitly in-scope programs only.

## 17.24 Mastery Deep Dive: Webhooks, Mobile Keys, and Inventory

### 17.24.1 Webhook security in depth

Webhooks are outbound callbacks: an API posts an event to a URL. Two directions of risk exist. **Inbound webhooks** your API receives must be authenticated: verify an HMAC signature over the raw body with a shared secret, check a timestamp/nonce to prevent replay, and reject unrecognized event types. Test in a lab by sending a tampered body and an old timestamp and confirming rejection. **Outbound webhook URLs**, if user-controlled, are an SSRF vector: allow-list destinations, disallow private/link-local ranges, and re-validate on redirects. Avoid placing secrets in callback URLs (they leak via logs and referrers). Defense summary: signature + timestamp verification, destination allow-lists, and minimal payload data.

### 17.24.2 Keys and secrets in mobile clients

A mobile app is a hostile distribution channel: anything shipped in the binary can be extracted. Hardcoded API keys, embedded credentials, pinned certificates, and local token storage are recurring findings. In an app you own or are authorized to test, inspect strings and local storage for key-shaped secrets, and intercept traffic to see which headers are sent. Defense: keep secrets server-side, scope keys to the minimum, use short-lived tokens obtained via secure login, enforce certificate validation on the client *and* server-side authorization, and treat device attestation as a signal rather than a trust boundary. Verify that an extracted lab key cannot access another user's data.

### 17.24.3 Inventory as a security control

Improper inventory management (API9) is a force multiplier for every other flaw. Maintain a living registry of every host, environment, version, and schema, with owners and deprecation dates. Reconcile it against Certificate Transparency logs, DNS, JS bundles, and gateway routes for assets you are authorized to test. In labs, demonstrate that a forgotten `/api/v1` or `/beta` endpoint retains a flaw fixed in `/v3`; then retire the old version and confirm the flaw is gone everywhere. Defense: automated discovery, mandatory ownership metadata, scheduled retirement, and gateway rules that block unregistered paths by default.

## 17.12 Key Takeaways

- API security is dominated by authorization failures (BOLA/BFLA) and excessive exposure.
- GraphQL, REST, and mobile-facing APIs can have different controls over the same data.
- JWT/OAuth flaws and missing rate limits are common and high-impact.
- Test with two accounts and explicit allow-list thinking, on authorized targets only.
