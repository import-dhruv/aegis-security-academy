# Chapter 17: API Security Mastery

> **Learning objectives.** Apply the OWASP API Security Top 10; test REST, GraphQL, and API authentication/authorization; identify BOLA, BFLA, mass assignment, excessive exposure, and JWT/OAuth flaws; and test APIs safely in authorized labs.

## 17.1 The API Security Top 10

OWASP publishes a separate **API Security Top 10** (current edition: 2023; verify at https://owasp.org/API-Security/). Key categories:

- **API1 Broken Object Level Authorization (BOLA)** — object IDs not ownership-checked.
- **API2 Broken Authentication** — flawed token/session handling.
- **API3 Broken Object Property Level Authorization** — excessive exposure and mass assignment.
- **API4 Unrestricted Resource Consumption** — missing rate/size limits.
- **API5 Broken Function Level Authorization (BFLA)** — privileged functions callable by low-privilege users.
- **API6 Unrestricted Access to Sensitive Business Flows** — automation of legitimate flows (scalping, spam).
- **API7 Server Side Request Forgery** — server fetches attacker-chosen URLs.
- **API8 Security Misconfiguration** — verbose errors, exposed docs, permissive CORS.
- **API9 Improper Inventory Management** — old/unknown API versions exposed.
- **API10 Unsafe Consumption of APIs** — trusting third-party API data.

## 17.2 REST API Vulnerabilities

REST APIs are especially prone to authorization and inventory issues because endpoints are numerous and often auto-generated. Test:

- Every object ID (BOLA) with a second test account.
- Every admin/function endpoint (BFLA) with a low-privilege token.
- HTTP method mismatches: an endpoint may block GET but allow PUT/DELETE.
- Content-type variations: JSON vs. form vs. XML parsers may have different validation.
- Duplicate JSON keys: `{"role":"user","role":"admin"}` — parsers differ on which wins.
- Parameter pollution and array/type confusion: `{"id":["1","2"]}`.

## 17.3 GraphQL Vulnerabilities

- **Introspection:** `query { __schema { types { name } } }` may reveal the full schema (disable in production or restrict).
- **Depth/complexity:** deeply nested queries can exhaust resources; enforce limits.
- **Resolver authorization:** each field/mutation must authorize; a list query may leak objects a detail query protects.
- **Batching:** multiple operations in one request can evade naive rate limits.
- **Field suggestions:** can reveal field names.
- **Aliases:** can duplicate expensive fields.

Test every query and mutation with two accounts; inspect responses for fields the UI never displays.

## 17.4 API Authentication and Authorization

- Validate JWTs fully (signature, `exp`, `nbf`, `iss`, `aud`, algorithm) — never trust decoded claims without verification (Chapters 7 and 10).
- Opaque tokens should be high-entropy, short-lived, and revocable.
- API keys must be scoped and rotated; they are not user authentication.
- Authorization must be per object and per function, server-side.
- Service-to-service calls need mTLS or signed tokens and least privilege.

## 17.5 Excessive Data Exposure and Mass Assignment

**Excessive exposure:** the API returns full objects (including password hashes, internal IDs) and the frontend filters them. Fix with response schemas/DTOs.

**Mass assignment (auto-binding):** binding request fields directly to model properties lets an attacker set fields like `isAdmin`, `role`, or `balance`. In labs, add unexpected fields to JSON bodies and observe whether they are honored. Fix with explicit allow-lists of writable fields.

## 17.6 Rate Limiting and Resource Consumption

APIs need limits on: requests per time window, payload size, query depth, batch size, and expensive operations. Test in labs for:

- Missing limits on login, OTP, password reset (brute force).
- Bypass via header spoofing (`X-Forwarded-For`), IP rotation, or token variation.
- GraphQL complexity abuse.
- Large file uploads or huge query strings.

## 17.7 API Inventory and Improper Asset Management

Old API versions (`/api/v1`, `/api/v2-beta`) often lack newer security controls. Discover them via docs, JS bundles, and historical URLs (Chapter 14). Maintain an inventory and retire old versions.

## 17.8 Webhook Security

Webhooks deliver data to a URL you control. Security concerns:

- **SSRF** if the URL is user-controlled.
- Missing signature verification (attacker can forge events).
- Replay attacks (no timestamp/nonce).
- Leaking secrets in URLs.

Fix: allow-list destinations, sign payloads (HMAC), verify signatures and timestamps, and avoid sensitive data in callbacks.

## 17.9 API Fuzzing and Schema Analysis

- Generate requests from OpenAPI/Swagger schemas; fuzz parameters with type/null/length variations.
- Use schema-aware fuzzers (e.g., Schemathesis) in labs.
- Compare behavior across versions and representations (JSON vs. XML).
- Look for 500s, timing anomalies, and authorization differences.

## 17.10 Multi-Tenant API Security

Every data access must include a tenant scope derived from the authenticated context — never from client input. Cache keys, search indices, and background jobs must also include tenant identity. Test with two of your own tenants in an authorized program.

## 17.11 API Security Testing Exercises

1. In crAPI (OWASP), use two accounts to find BOLA on a vehicle/order endpoint.
2. On a lab GraphQL API, run introspection and identify unprotected mutations.
3. Send a JSON body with an extra `role=admin` field to a lab endpoint; observe mass assignment.
4. Test login rate limits in a lab and identify a bypass via a forwarded header.
5. Write a Schemathesis test for a lab OpenAPI spec and triage the findings.

## 17.12 Key Takeaways

- API security is dominated by authorization failures (BOLA/BFLA) and excessive exposure.
- GraphQL, REST, and mobile-facing APIs can have different controls over the same data.
- JWT/OAuth flaws and missing rate limits are common and high-impact.
- Test with two accounts and explicit allow-list thinking, on authorized targets only.
