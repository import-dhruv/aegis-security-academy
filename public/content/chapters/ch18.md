# Chapter 18: Android and iOS Security

> **Learning objectives.** Explain Android and iOS architecture and app sandboxes; analyze APK/IPA structure, permissions, deep links, intents, storage, and communication; and perform static/dynamic analysis with MobSF, Frida, JADX, APKTool, and Burp in a lab.

## 18.1 Mobile Platform Architecture

### Android

Android is Linux-based. Each app runs as a distinct Linux user in a sandbox. Key components:

- **Linux kernel:** process isolation, permissions, Binder IPC.
- **Hardware Abstraction Layer (HAL).**
- **Android Runtime (ART):** runs DEX bytecode; earlier versions used Dalvik.
- **Application Framework:** services (Activity Manager, Package Manager, etc.).
- **Apps:** installed as APKs, composed of components: Activities, Services, Broadcast Receivers, Content Providers.
- **Permissions:** declared in `AndroidManifest.xml`; dangerous permissions require runtime grant.
- **Binder:** inter-process communication mechanism; **Intents** are messages between components.

### iOS

iOS is based on macOS/XNU with:

- **App sandbox:** strict filesystem and capability restrictions.
- **Codesigning:** all apps must be signed by Apple-issued certificates.
- **Entitlements/capabilities:** declared permissions (e.g., keychain groups, push notifications).
- **UIKit/SwiftUI:** UI frameworks.
- **Security enclave:** hardware-backed key storage.

## 18.2 APK and IPA Structure

**APK** (Android Package) is a ZIP containing:

```
AndroidManifest.xml   (binary XML: permissions, components)
classes.dex           (compiled app code)
resources.arsc        (compiled resources)
res/                  (layouts, strings, images)
META-INF/             (signatures)
lib/                  (native libraries)
assets/               (arbitrary files)
```

**IPA** (iOS App Store Package) is a ZIP containing `Payload/<App>.app/` with the Mach-O binary, `Info.plist`, resources, and a `CodeResources` signature file.

## 18.3 Common Mobile Vulnerabilities

- **Insecure data storage:** plaintext credentials/tokens in shared preferences, SQLite, files, or logs.
- **Insecure communication:** HTTP or poorly validated TLS; missing certificate pinning.
- **Weak authentication/session handling:** tokens in predictable locations, no expiry, biometric bypass.
- **Client-side injection:** WebView JavaScript injection, local file inclusion.
- **Deep link/intent abuse:** unvalidated URL schemes or intent filters allow phishing or data theft.
- **Exported components:** activities/services/providers accessible by other apps without permission.
- **Content provider SQL injection.**
- **Certificate pinning bypass** (relevant to analysis, not a vulnerability by itself).
- **Root/jailbreak detection weaknesses.**
- **Hardcoded secrets** in code or resources.

## 18.4 Deep Links and Intents

Android deep links (`myapp://open?url=...`) and iOS universal links can be abused if the app trusts unvalidated input. Test in your own lab app:

- Can a crafted link open an arbitrary internal activity?
- Can a `url` parameter load an attacker-controlled page in a WebView?
- Are intent filters too broad (exported components)?

Check `AndroidManifest.xml` for `android:exported="true"` and intent filters. Remediate with explicit allow-lists and validation.

## 18.5 Certificate Pinning

Pinning restricts trusted certificates to a known set, defending against MITM. For authorized analysis, pinning must be bypassed (e.g., with Frida/Objection scripts) to route traffic through Burp in a lab. Pinning is a defense for apps; bypass is a lab technique, not an attack on real users.

## 18.6 Secure Storage

- Android: use `Keystore` system and `EncryptedSharedPreferences`; avoid plaintext `SharedPreferences` for secrets.
- iOS: use Keychain with appropriate accessibility classes; avoid `NSUserDefaults` for secrets.
- Never store secrets in app resources, logs, or screenshots.

## 18.7 Root/Jailbreak Detection

Apps may detect rooted/jailbroken devices to enforce policy. Detection is bypassable in labs; it is a defense-in-depth measure, not a security boundary. Do not rely on it alone.

## 18.8 Static Analysis

1. Download an APK/IPA you own or a deliberately vulnerable lab app.
2. Unpack with APKTool (`apktool d app.apk`) to get the manifest and resources.
3. Decompile with JADX (`jadx -d out app.apk`) to read Java source.
4. Run MobSF for automated findings (permissions, hardcoded secrets, insecure config).
5. Review manifest for exported components, permissions, and cleartext traffic.
6. Search decompiled code for hardcoded keys, URLs, and crypto misuse.

## 18.9 Dynamic Analysis

1. Install the app on a lab emulator/device.
2. Configure a proxy (Burp) and install its CA cert; bypass pinning if needed with Frida/Objection.
3. Exercise app flows and inspect traffic in Burp.
4. Use Frida to hook security-relevant functions (e.g., crypto, PIN checks).
5. Inspect local storage and logs after use.

## 18.10 Tool Integration

- **MobSF:** automated static/dynamic reports and a web UI.
- **JADX / APKTool:** decompilation and resource decoding.
- **Frida / Objection:** runtime instrumentation and pinning bypass (lab only).
- **Burp Suite:** HTTP(S) interception for mobile traffic via proxy configuration.

## 18.11 Legal and Ethical Scope

Only analyze apps you own or have explicit written permission to test. Reverse engineering may be restricted by licenses and laws; respect them. Do not distribute modified apps or extracted proprietary data.

## 18.12 Exercises

1. Analyze a deliberately vulnerable lab APK with MobSF; list findings by severity.
2. Decompile the same APK with JADX and manually confirm one automated finding.
3. Configure an emulator to proxy through Burp and capture an HTTPS request from a lab app.
4. Inspect a lab app's manifest and identify exported components.
5. Use Frida to log the arguments of a chosen method in a lab app.

## 18.15 Mastery Deep Dive: Android Internals and Attack Surface

### 18.15.1 Verified Boot, the Sandbox, and the Real Privilege Model

Mastery begins with the trust chain, not the app. On a modern Android device the boot ROM verifies the bootloader signature, the bootloader verifies the `boot`/`system` partitions via **dm-verity** (a read-only hash tree), and only then does `init` start the runtime. Understanding this matters because it explains why "rooting" and "hooking" are meaningful only in a lab image you control: in a locked, verified device the kernel and framework are immutable, so the app sandbox is enforced by the Linux kernel, not by the app.

Each installed app is assigned a unique Linux UID (e.g., `u0_a142`). Its process runs as that UID, so files it creates are owned by that UID and are unreadable by other apps unless explicitly shared via a `content provider` or world-readable mode. The sandbox therefore rests on standard Linux discretionary access control plus **SELinux** (enforcing, type `untrusted_app`), which blocks even same-UID tricks like reading `/proc` of another process or opening raw block devices. Practical consequence: an "insecure file permission" finding (mode `0666`, `MODE_WORLD_READABLE`) is serious only because it defeats this kernel boundary, letting a *different* UID read the file.

> **Lab-only framing:** Everything in this chapter is performed on an emulator/device image you own, a deliberately vulnerable app you built, or an explicitly in-scope program. Never analyze or modify a third party's app or device.

### 18.15.2 APK Binary Format Walkthrough

An APK is a ZIP, but three members deserve a byte-level mental model:

- **`AndroidManifest.xml`** is *binary XML*, not text. Aapt compiles strings into a string pool and encodes tags/attributes as integer IDs. Tools like `apktool`/`jadx` decode it back to text. When you read a decoded manifest, remember the original is compact binary — that is why raw `strings` finds little there.
- **`classes.dex`** (and `classes2.dex`, ...) holds the app's Java/Kotlin code compiled to Dalvik EXecutable bytecode. DEX uses register-based instructions and a shared string/type pool, making it more compact than JVM class files. Multidex apps split code across several DEX files.
- **`resources.arsc`** is the compiled resource table mapping resource IDs (`0x7f0e0001`) to names/values; it is how `getString(R.string.api_key)` resolves at runtime.
- **`META-INF/`** holds signatures. **v1 (JAR)** signs individual files; **v2/v3** sign the entire APK via an **APK Signing Block** inserted before the central directory. v2/v3 protect more of the file, so "repack and re-sign" changes are detectable by the platform. Understanding this explains why a repackaged lab APK must be re-signed with your own debug key and why signature checks (`GET_SIGNING_CERTIFICATES`) can be a defense.
- **`lib/<abi>/`** contains native `.so` libraries (armeabi-v7a, arm64-v8a, x86_64); these are where JNI crypto and pinning often live.

A representative decode workflow you would run in your lab:

```bash
<LAB> apktool d -s lab.apk -o apktool_out   # -s keeps dex (no decompile) for speed
<LAB> jadx -d jadx_out lab.apk              # decompile dex to Java-like source
<LAB> unzip -l lab.apk | grep -E 'dex|arsc|META-INF|lib/'
<LAB> aapt2 dump badging lab.apk | head -40 # readable manifest summary
```

Interpreting `aapt2 dump badging`: look for `sdkVersion`, `targetSdkVersion`, `uses-permission`, `launchable-activity`, and `application-label`. A `targetSdkVersion` far below the current OS often signals legacy behavior (e.g., implicit intents still working, cleartext traffic allowed) — a rich source of lab findings.

### 18.15.3 Permission Model and Runtime Grants

Permissions are declared with `<uses-permission>` and guarded by **protection levels**:

| Level | Meaning | Example |
|-------|---------|---------|
| normal | Granted at install, low risk | `INTERNET` |
| dangerous | Requires runtime user grant | `CAMERA`, `READ_SMS` |
| signature | Only apps signed with the same platform key | `BIND_DEVICE_ADMIN` |
| signatureOrSystem | Signature or system apps | legacy privileged perms |

Since Android 6 (API 23), dangerous permissions are requested at runtime with `requestPermissions()`. Mastery means checking three things: (1) is the permission actually needed, (2) is the app enforcing the check itself or relying on the OS (the OS enforces at the framework/Binder layer, so a missing check in your own exported component is a real bug), and (3) are **pending intents** used with an explicit component — an implicit pending intent can be hijacked.

**Common mistake:** assuming `uses-permission` implies enforcement. Declaring `READ_CONTACTS` does not stop your own exported activity from returning contact data to any caller that can reach it; the OS never gates *your* component by *your* declared permission unless you add `android:permission`.

### 18.15.4 Intent and Deep-Link Routing Deep Dive

Intents are typed messages: **explicit** (component name set) vs **implicit** (an action/category/data that the framework resolves). An `<intent-filter>` with `android:exported="true"` makes a component reachable from outside. Deep links use a `<data android:scheme="myapp" android:host="open">` filter; **Android App Links** add `android:autoVerify="true"` plus a `/.well-known/assetlinks.json` file to bind a domain to the app.

Lab test sequence for an app you own:

```bash
<LAB> adb shell am start -a android.intent.VIEW \
        -d "myapp://open?url=https://<LAB>/page" -n <LAB_PACKAGE>/.DeepLinkActivity
<LAB> adb shell am start -a android.intent.VIEW \
        -d "myapp://open?next=<LAB_PACKAGE>/.SecretActivity"
```

Interpretation: if the second command navigates to an internal activity the developer never intended to be externally reachable, the app is treating a URL parameter as an internal route — a classic **intent/depth-link routing** flaw. If the first loads the supplied `url` into a WebView without allow-listing the host, you have a WebView URL-loading issue. Both are *lab findings in your own app*; the fix is an explicit allow-list of hosts and an allow-list map of route names to activities, never a free-form class name.

Also test **intent hijacking**: fire an implicit intent your app emits and see whether a malicious-looking lab app with a matching filter can receive it. The defense is explicit intents and `Intent.createChooser()` for user-disambiguated sharing.

### 18.15.5 Activity Lifecycle and Task Hijacking

The lifecycle (`onCreate → onStart → onResume → onPause → onStop → onDestroy`) is a state machine; mishandling it causes both functional bugs and security ones. `onSaveInstanceState` stores a `Bundle` — if secrets are placed there they can be read from a backup or another app in the same task. Task and back-stack manipulation (`taskAffinity`, `launchMode`) was the basis of **strandhogg**-style attacks where a malicious activity with the same affinity sits on top of a legitimate one to phish credentials.

In your lab, set `android:taskAffinity` on a test activity and observe with:

```bash
<LAB> adb shell dumpsys activity activities | grep -A6 'mResumedActivity'
```

Mastery defense: set `android:exported` explicitly, avoid `singleTask`/affinity tricks you don't need, and set `android:filterTouchesWhenObscured="true"` on sensitive screens so touches over overlays are blocked.

### 18.15.6 Content Providers and SQL Injection

A `ContentProvider` exposes structured data via a `content://` URI. If `android:exported="true"` and no `android:permission`, any app on the device can `query()`/`insert()`/`update()`/`delete()` it. Two bug classes dominate:

1. **SQL injection** if the provider concatenates a selection string: `db.rawQuery("SELECT * FROM notes WHERE id=" + id, null)`. A crafted selection like `1=1 UNION SELECT ...` can dump other tables.
2. **Path traversal** if a file provider opens paths built from user input (`openFile()` with `../`).

A lab probe (your own provider) looks like:

```bash
<LAB> adb shell content query --uri content://<LAB_PACKAGE>.provider/notes \
        --where "id=1 OR 1=1"
```

If the result set includes rows beyond `id=1`, the `where` clause is being concatenated into SQL. The defense is parameterized selection (`selectionArgs`) and a strict projection allow-list.

### 18.15.7 Keystore and Secure Storage Internals

The Android **Keystore** system stores keys in a hardware-backed TEE (StrongBox where available) so key material never enters app process memory. Keys are created with a `KeyGenParameterSpec` that pins authorized uses (purposes, padding, authentication requirements). `EncryptedSharedPreferences` and `EncryptedFile` (from `security-crypto`) build on this: a master key in Keystore encrypts a data key that encrypts values.

What mastery checks:

- Is the master key hardware-backed? `KeyInfo.isInsideSecureHardware()` should be true for sensitive keys.
- Is the key invalidated on new biometric enrollment (`setInvalidatedByBiometricEnrollment`)?
- Are secrets accidentally in `SharedPreferences` plaintext, `build.gradle`, logs (`Log.d`), or `onSaveInstanceState`?
- Is `allowBackup="true"` leaking the credential store via `adb backup` / Auto Backup? Set `android:allowBackup="false"` or use a backup rules file with `<exclude>` for secrets.

```java
// <LAB> — hardware-backed key with authentication requirement
KeyGenParameterSpec spec = new KeyGenParameterSpec.Builder(
        "lab_key", KeyProperties.PURPOSE_ENCRYPT | KeyProperties.PURPOSE_DECRYPT)
    .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
    .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
    .setUserAuthenticationRequired(true)
    .setInvalidatedByBiometricEnrollment(true)
    .build();
```

### 18.15.8 WebView Attack Surface

A WebView embeds a browser; misconfiguration turns it into a bridge into the app. The dangerous knobs:

| API | Risk | Safer alternative |
|-----|------|-------------------|
| `addJavascriptInterface(obj,"JS")` | Exposes Java methods to page JS (pre-4.2 RCE; later still dangerous) | Avoid; use `evaluateJavascript` with allow-listed messages |
| `setAllowFileAccess(true)` | `file://` pages can read local files / JS from file origin | Disable by default |
| `setJavaScriptEnabled(true)` on untrusted content | Enables XSS → bridge abuse | Only for trusted, allow-listed origins |
| `shouldOverrideUrlLoading` returning false | Lets arbitrary URLs navigate in WebView | Validate scheme + host against allow-list |
| `setAllowUniversalAccessFromFileURLs(true)` | file origin reads any origin | Never enable |

A lab check: load a page you host containing `<script>JSBridge.someMethod()</script>` into the WebView and see whether the annotated method executes. If it does, and the interface exposes file/network primitives, you have a concrete finding. The modern fix is `WebViewAssetLoader` plus origin allow-listing and `@JavascriptInterface` only on narrowly scoped, non-privileged methods.

## 18.16 Mastery Deep Dive: iOS Internals and Analysis

### 18.16.1 Codesigning, Sandbox, and Entitlements

iOS security is anchored in **codesigning**: every executable must be signed by Apple-issued material, and the kernel enforces that signatures are valid before allowing execution (with limited JIT exceptions). The **app sandbox** is enforced by the `Seatbelt`/Sandbox profile in the kernel, restricting filesystem paths, network, and IPC. **Entitlements** are signed key-value pairs granting specific capabilities (keychain-access-groups, push-notifications, associated-domains, inter-app-audio). Because entitlements are inside the signature, you cannot add them at runtime without breaking the signature — this is why lab instrumentation requires a re-signed, developer-provisioned build.

Mastery distinction: the sandbox is a *kernel* boundary and a strong one; jailbreak detection is merely an app-level policy check and is bypassable. Do not conflate them.

### 18.16.2 IPA Bundle and Mach-O Walkthrough

An IPA is a ZIP containing `Payload/<App>.app/`. Inside:

- **Mach-O executable** — the main binary; header + load commands + segments/sections.
- **`Info.plist`** — manifest: bundle ID, `CFBundleURLTypes` (URL schemes), `NSAppTransportSecurity`, `NSAppleMusicUsageDescription`-style usage strings, `UIRequiredDeviceCapabilities`.
- **`embedded.mobileprovision`** — provisioning profile (entitlements, team ID, app ID).
- **`CodeResources`** — signature seal listing file hashes (`_CodeSignature/`).
- Resources: `.nib`/`.storyboardc`, images, localized `.strings`, and often bundled frameworks/`PlugIns`.

Parse the binary in your lab:

```bash
<LAB> otool -hv Payload/App.app/App        # Mach-O header (filetype, flags)
<LAB> otool -l Payload/App.app/App | grep -A4 LC_ENCRYPTION_INFO  # is it FairPlay-encrypted?
<LAB> class-dump -H Payload/App.app/App -o headers/               # Obj-C class interfaces
<LAB> plutil -p Payload/App.app/Info.plist
```

Interpretation: `LC_ENCRYPTION_INFO` with `cryptid != 0` means App Store FairPlay encryption; you must work with your own developer build (unencrypted) for analysis. `class-dump` output reveals Objective-C selectors and properties — an enormous head start because selector names like `verifyPin:`, `decryptData:` reveal intent. Swift binaries carry mangled symbols instead; use `swift-demangle` or `nm -g` to read them.

### 18.16.3 Keychain, Data Protection, and Secure Enclave

The iOS **Keychain** is an encrypted SQLite database per device, with items partitioned by **access groups** (from entitlements). Each item has an accessibility class (e.g., `kSecAttrAccessibleWhenUnlocked`, `...WhenUnlockedThisDeviceOnly`) that ties decryption to device state and, for `ThisDeviceOnly`, prevents migration to another device via backup. The **Secure Enclave** is a separate processor performing key operations so private keys never leave it; biometric (`kSecAccessControlBiometryCurrentSet`) gates use of those keys.

Mastery checks on your own app:

- Are tokens in Keychain with `WhenUnlocked` rather than `NSUserDefaults`/plist?
- Are items in the correct access group so they are not shared more widely than needed?
- Is `kSecAttrAccessibleAlways` avoided (deprecated and insecure)?
- Does the app use `ThisDeviceOnly` where backup leakage matters?

### 18.16.4 ATS, URL Schemes, and Universal Links

**App Transport Security (ATS)** requires HTTPS with TLS 1.2+, forward secrecy, and strong ciphers by default; exceptions in `NSAppTransportSecurity` (`NSAllowsArbitraryLoads`) weaken it. In a lab, check whether the app has a blanket exception that permits cleartext — that is a concrete finding.

**Custom URL schemes** (`myapp://`) are globally registrable; any app can claim a scheme, so they must never carry sensitive data. **Universal Links** (`https://<LAB>/...` with an `apple-app-site-association` file hosted at the domain) are cryptographically bound to your app via entitlements and are the safe choice. Test in your own app:

```bash
<LAB> xcrun simctl openurl booted "myapp://callback?token=<LAB>"
```

If the token lands in a place an attacker-supplied URL could also reach, and the scheme is not reserved, you have an authorization/routing issue to fix by moving to Universal Links and validating the `apple-app-site-association`.

### 18.16.5 iOS Static and Dynamic Analysis Tools

Static toolkit workflow (your own build):

```bash
<LAB> mobsf --upload Payload/App.app           # automated report
<LAB> otool -L Payload/App.app/App             # linked dylibs/frameworks
<LAB> nm -gU Payload/App.app/App | head -50    # external symbols
<LAB> strings -a Payload/App.app/App | grep -Ei 'http|key|secret'
```

Dynamic toolkit: run on a jailbroken *lab* device (or emulator you control), attach Frida, and use objection:

```bash
<LAB> objection -g <LAB_BUNDLE_ID> explore
...> ios sslpinning disable
...> ios nsuserdefaults get
...> environment
```

Interpretation: `ios sslpinning disable` patches common pinning calls so Burp can see traffic — only on your own app. `ios nsuserdefaults get` dumps `NSUserDefaults`; secrets found there are a finding. Always restore the device snapshot afterward.

## 18.17 Mastery Deep Dive: Analysis Workflows and Tool Mastery

### 18.17.1 Static Analysis Workflow with Output Interpretation

A disciplined static pass on a lab APK/IPA follows layers, each answering a different question:

1. **Inventory** — `unzip -l lab.apk`, `file`, hash (`sha256sum`). Establishes what you are looking at and gives a baseline to detect tampering.
2. **Manifest/config** — `aapt2 dump badging`, decoded manifest, `Info.plist`. Look for `exported`, `allowBackup`, `usesCleartextTraffic`, ATS exceptions, min/target SDK.
3. **Decompile** — `jadx`/`class-dump`. Search for `http://`, `AKIA`, `BEGIN PRIVATE KEY`, `setJavaScriptEnabled`, `addJavascriptInterface`, `TrustManager`, `HostnameVerifier`, `ALLOW_ALL`.
4. **Automated** — MobSF report. Triage by severity but *manually confirm every finding*; tools over-report.
5. **Native** — `readelf`/`otool`, `strings` on `.so`/Mach-O, check `checksec`-style flags.

A common trap: trusting the MobSF "high severity" count. Mastery means opening the exact decompiled line, confirming data flow from source (user input, network) to sink (file, SQL, WebView), and discarding false positives with a documented reason.

### 18.17.2 Dynamic Analysis Workflow with Output Interpretation

Dynamic analysis confirms behavior that static analysis can only suggest. Lab sequence:

```bash
<LAB> adb connect <LAB_EMULATOR>:5555
<LAB> adb root && adb remount                       # lab image only
<LAB> adb shell settings put global http_proxy <LAB_PROXY>:8080
# install Burp/CA cert into the lab device trust store (Android 7+ needs user CA or system push)
<LAB> frida-ps -U                                   # list processes
<LAB> frida -U -f <LAB_PACKAGE> -l hook.js --no-pause
```

Interpreting Frida output: a hook that prints `Hooked verifyPin(pin="1234")` shows the PIN comparison argument — in *your own* app this confirms client-side-only validation and motivates moving the check server-side. Watch logcat during the run:

```bash
<LAB> adb logcat | grep -iE '<LAB_PACKAGE>|E/|Webview'
```

Unexpected `E/` lines with stack traces often reveal internal class names and error messages that guide the next static pass.

### 18.17.3 Certificate Pinning: Concepts and Lab Bypass

Pinning restricts the app's trusted certificates to a known set (public-key or cert hash). It defends against MITM by an attacker with a rogue CA. Concepts to master: **trust manager** (Android `X509TrustManager`), **hostname verifier**, network-security-config `<pin-set>` with a `digest` of the SubjectPublicKeyInfo, and iOS `TrustKit`/`AFNetworking` pinning or `URLSession` `urlSession:didReceiveChallenge:`.

In an authorized lab, bypass is a *technique for observing your own traffic*, not an end in itself. Approaches, strongest-first:

1. **Patch config** — remove `<pin-set>` in a rebuilt lab APK; set `NSAllowsArbitraryLoads` in a lab build.
2. **Frida/objection** — `android sslpinning disable` / `ios sslpinning disable` hook common validation methods.
3. **Hook at the connection layer** — intercept `TrustManager.checkServerTrusted` or `SecTrustEvaluate` and make them no-ops.

Verification of a correct bypass: Burp shows the app's requests with `HTTP/2 200` and no TLS error; the app does not crash with a certificate failure. Document this as "pinning bypassed in lab to enable authorized traffic inspection" — never as an attack on a real service.

### 18.17.4 Mobile API Testing

The mobile app is often just a client; the real asset is its API. Lab workflow:

1. Proxy the app through Burp, capture request/response pairs.
2. Test authentication: replay a captured token after logout, test token expiry and refresh, check for IDOR by changing an ID parameter within your own test accounts.
3. Test authorization: call an admin endpoint with a low-privilege token.
4. Test client-side assumptions: if the app computes a price or a "isPremium" flag, try modifying it in transit — the server must not trust it.
5. Rate limiting and certificate pinning as relevant.

Mastery insight: vulnerabilities in the API are usually higher impact than client bugs because they affect all users. Always map the client's endpoints with a tool like `gospider`/Burp sitemap from captured traffic, then test systematically.

### 18.17.5 Mapping Findings to OWASP MASVS/MSTG

**MASVS** (Mobile Application Security Verification Standard) is the *requirement* catalog; **MSTG** (Mobile Security Testing Guide) is the *how-to*. Map each lab finding to a control ID so reports are consistent:

| Area | MASVS category | Typical MSTG test |
|------|----------------|-------------------|
| Storage | MASVS-STORAGE | ` MSTG-STORAGE-*` encrypted storage checks |
| Crypto | MASVS-CRYPTO | key management, RNG |
| Auth | MASVS-AUTH | session, biometric |
| Network | MASVS-NETWORK | TLS, pinning |
| Platform | MASVS-PLATFORM | intents, WebView, providers |
| Code | MASVS-CODE | obfuscation, anti-tamper (defense in depth) |
| Resilience | MASVS-RESILIENCE | root/jailbreak, anti-debug |

The value of this mapping: it forces complete coverage. A "mobile pentest" that only checks storage and network but ignores MASVS-PLATFORM has missed WebView, intent, and provider issues.

## 18.18 Mastery Deep Dive: Hardening, Verification, and Practice

### 18.18.1 Building a Hardened Mobile Lab

A safe lab is a set of *containment boundaries*, not a single tool:

- **Dedicated device/emulator** with no real accounts, no synced contacts, no payments.
- **Host-only network** or NAT with internet disabled when analyzing unknown samples; route traffic through a local proxy you control.
- **Snapshots** taken before each experiment; restore after.
- **Separate CA** installed only in the lab, never in your daily driver.
- **No personal data** on the lab device; factory reset between unrelated projects.
- **Legal hygiene:** only your own apps or in-scope targets; keep a scope document.

### 18.18.2 Detection and Defense Checklists

Defensive checklist for an Android/iOS app you are hardening:

- [ ] `android:exported` explicit on every component; exported components protected with `android:permission`
- [ ] `allowBackup=false` or backup rules excluding secrets
- [ ] No cleartext traffic; `usesCleartextTraffic=false`, ATS enforced
- [ ] Secrets in Keystore/Keychain, not plaintext or resources
- [ ] Deep links and Universal Links validate host against an allow-list; no dynamic class loading from URL params
- [ ] WebView: JS disabled unless required, no dangerous JS bridges, file access off
- [ ] Content providers use parameterized queries and path allow-lists
- [ ] Tokens stored server-validated; client-side flags never trusted
- [ ] Certificate pinning implemented (with a backup pin and rotation plan)
- [ ] Logs contain no sensitive data
- [ ] Root/jailbreak detection present but treated only as defense in depth

Detection checklist for a defender **monitoring** mobile threats (MAM/MDM signals):

- [ ] Device integrity/Play Integrity (or App Attest on iOS) attestation enforced server-side
- [ ] Anomalous API call patterns, unusual geolocation or device fingerprint changes
- [ ] Repackaged-app detection via signature hash checks
- [ ] Certificate/pinning failure telemetry

### 18.18.3 Common Mistakes to Avoid

1. **Testing only the debug build.** Release builds differ (minification, pinning, different configs). Always test a release-equivalent build.
2. **Trusting decompiler output literally.** Kotlin coroutines and obfuscation produce misleading pseudocode; verify dynamically.
3. **Ignoring the server.** A "secure" client with an insecure API is insecure.
4. **Assuming pinning = untestable.** In a lab you control the device and build; pinning is a config, not magic.
5. **Forgetting `android:exported` default changes.** On Android 12+, components with intent filters must declare it explicitly or the app fails to install — a common source of confusion.
6. **Skipping scope documentation.** Without written authorization, even lab-grade curiosity can become a legal problem if the target is not yours.

### 18.18.4 Verify in Your Lab

A concrete verification path:

1. Build a small lab app with one exported activity, one deep link, a WebView, and a token in `SharedPreferences`.
2. Confirm with `adb shell am start` that an external intent reaches the exported activity.
3. Decompile with `jadx` and locate where the deep-link `url` is passed to `WebView.loadUrl`.
4. Proxy through Burp and capture one HTTPS request; install the lab CA.
5. Add pinning to the lab app; confirm Burp now fails; use objection to bypass; confirm Burp succeeds again.
6. Move the token to `EncryptedSharedPreferences`; confirm it is no longer readable as plaintext in the app data directory (`adb shell run-as <LAB_PACKAGE> ls files`).
7. Write a one-page report mapping each finding to a MASVS category.

### 18.18.5 What Mastery Looks Like

You have mastered this material when you can:

- Explain *why* a finding matters at the kernel/framework level, not just that a tool flagged it.
- Decode an APK/IPA by hand and describe the role of each member.
- Build a reproducible static + dynamic workflow and interpret tool output rather than copy-pasting it.
- Distinguish a genuine client-side flaw from a server-side trust problem and prioritize the latter.
- Configure a contained lab, document scope, and restore it cleanly.
- Map findings to MASVS/MSTG and write a defensible, severity-rated report.

### 18.18.6 Knowledge Check (Answers Included)

**Q1.** An APK declares `READ_CONTACTS` but its exported content provider has no `android:permission`. Is the contact data safe?
**A1.** No. The declared permission does not gate your own component. Any app that can reach the exported provider can query it; add `android:permission` and enforce it.

**Q2.** `LC_ENCRYPTION_INFO` shows `cryptid = 1`. What does this imply for analysis?
**A2.** The binary is FairPlay-encrypted (App Store build). Analyze your own unencrypted developer build instead; do not attempt to decrypt third-party apps.

**Q3.** Why is a custom URL scheme riskier than a Universal Link for carrying a token?
**A3.** Any app can register a custom scheme, so a token sent via `myapp://` can be intercepted by a different app. Universal Links are bound to your signed app via `apple-app-site-association` and HTTPS.

**Q4.** You enable `addJavascriptInterface` and load a remote page. What is the core risk?
**A4.** JavaScript in that page can invoke the exposed Java methods; if those methods touch files, network, or credentials, a malicious/compromised page gains app-level capabilities. Remove the bridge or strictly allow-list origins and methods.

**Q5.** Pinning makes Burp show TLS errors. Name two authorized lab ways to proceed.
**A5.** Rebuild the app without the pin-set (lab build), or use Frida/objection to disable pinning at runtime — both only on a device/app you control for authorized traffic inspection.

## 18.13 Key Takeaways

- Mobile apps are constrained by sandboxing and permissions but still suffer storage, communication, and logic flaws.
- APK/IPA structure reveals configuration and code; static analysis finds many issues quickly.
- Dynamic analysis with a proxy and instrumentation confirms behavior.
- Only test apps and devices you own or are authorized to assess.
