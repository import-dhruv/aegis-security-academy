# Chapter 3: Linux Mastery for Security Researchers

> **Learning objectives.** Navigate and script the Linux shell fluently; manage users, permissions, processes, services, and packages; configure SSH and cron; use networking and logging commands; and explain Linux security mechanisms including capabilities, namespaces, and containers.

## 3.1 Why Linux Matters

Linux dominates security practice. It powers servers, cloud infrastructure, Android, and most security tooling. Kali Linux is a purpose-built penetration-testing distribution; Ubuntu is a common general-purpose and lab platform. A researcher who is fluent in Linux can work efficiently, understand the systems they test, and build reproducible labs.

Two distribution families matter here:

- **Debian-based:** Ubuntu, Kali, Linux Mint. Use `apt`/`dpkg`.
- **Red Hat-based:** RHEL, Fedora, CentOS Stream. Use `dnf`/`yum`/`rpm`.

Kali Linux is Debian-based and preloaded with hundreds of security tools. It is a good *toolbox*, not a daily-driver general OS, and should be used in labs and authorized engagements.

## 3.2 Linux Architecture

```
   +-----------------------------------------------------+
   | User applications (shell, tools, browsers, servers) |
   +-----------------------------------------------------+
   | Libraries (glibc, libssl, ...)                       |
   +-----------------------------------------------------+
   | System call interface                                |
   +=====================================================+
   | Kernel: process mgmt, memory, VFS, network, drivers  |
   +-----------------------------------------------------+
   | Hardware: CPU, RAM, disk, NIC                        |
   +-----------------------------------------------------+
```

The kernel exposes everything through system calls; user programs interact via libraries. The **Virtual File System (VFS)** layer abstracts file systems, and the **/proc** and **/sys** pseudo-filesystems expose kernel and process information as files. This "everything is a file" philosophy makes Linux introspection powerful: `cat /proc/cpuinfo`, `cat /proc/<pid>/maps`, etc.

## 3.3 Terminal Mastery

The shell is a command interpreter. Bash is the default on most distributions. Essential commands:

```
pwd                 print working directory
ls -la              list all files with details
cd /path            change directory
cp /a /b            copy; -r for directories
mv /a /b            move/rename
rm file             remove; -r recursive, -f force (dangerous)
mkdir -p a/b        create dirs including parents
cat file            print file
less file           page through file
head -n 10 file     first 10 lines
tail -f log         follow appended lines (great for logs)
grep -i "err" file  search case-insensitively
find . -name '*.py' search by name
locate file         fast search via updated database
wc -l file          count lines
sort / uniq         sort / deduplicate
cut -d: -f1 /etc/passwd   extract fields
sed 's/old/new/g'   stream editing
awk '{print $1}'    field extraction and processing
```

**Pipes and redirection** are the core of Unix power:

```
cmd1 | cmd2          pipe stdout of cmd1 into stdin of cmd2
cmd > file           redirect stdout to file (overwrite)
cmd >> file          append stdout
cmd 2> errors.log    redirect stderr
cmd &> all.log       redirect stdout and stderr
cmd < file           stdin from file
```

Combining tools is how real analysis happens:

```
cat access.log | grep " 404 " | awk '{print $1}' | sort | uniq -c | sort -rn | head
```

**Quoting:** single quotes preserve literally; double quotes allow variable expansion. Always quote variables in scripts to avoid word splitting and globbing bugs: `"$var"`.

## 3.4 Bash Scripting Fundamentals

```bash
#!/usr/bin/env bash
set -euo pipefail          # exit on error, unset var is error, pipe failures matter

target="${1:-localhost}"   # first arg or default
count=0

for port in 80 443 8080; do
  if timeout 1 bash -c "echo >/dev/tcp/target/port" 2>/dev/null; then
    echo "open: $port"
    ((count++))
  fi
done

echo "Checked 3 ports on target;count open."
```

Key constructs: variables (`x=1`, no spaces around `=`), conditionals (`if [ ... ]; then`, `[[ ]]` is more capable), loops (`for`, `while`), functions, arrays, and parameter expansion. Use `shellcheck` to find script bugs. Scripts are a superpower for repetitive security tasks — but always test them in a lab first.

## 3.5 Users, Groups, and Permissions

Linux is multi-user. Identity is defined by numeric UIDs/GIDs.

```
whoami                 current user
id                     uid, gid, groups
useradd -m alice       create user with home dir
passwd alice           set password
usermod -aG sudo alice add to sudo group
groupadd researchers   create group
su - alice             switch user
sudo command           run as root (or another user)
```

Important files:

- `/etc/passwd`: user accounts (name, UID, GID, home, shell). The password field is usually `x`, with hashes in `/etc/shadow`.
- `/etc/shadow`: password hashes (root-only readable). Offline password cracking targets this file.
- `/etc/group`: group definitions.
- `/etc/sudoers`: sudo policy (edit with `visudo`).

Permissions: `chmod 755 file` (rwxr-xr-x), `chown alice:staff file`, `umask 022` sets default permissions. Special bits: setuid (`chmod u+s`), setgid, sticky bit (`chmod +t` on `/tmp`). Setuid root binaries are a classic local privilege-escalation target.

**Capabilities** split root's privileges into fine-grained units (e.g., `CAP_NET_RAW` to craft packets, `CAP_NET_ADMIN` to configure interfaces). Inspect with `getcap -r / 2>/dev/null`. Misconfigured capabilities can be as dangerous as setuid.

## 3.6 Processes and Services

```
ps aux                 snapshot of processes

top / htop             interactive process viewer
jobs                   background jobs in current shell
bg / fg                background/foreground a job
kill -9 PID            force kill
pkill -f pattern       kill by command line
nohup cmd &            run immune to hangup
systemctl status ssh   service status (systemd)
systemctl start/stop/enable NAME

```

Signals: `SIGTERM` (15, graceful), `SIGKILL` (9, uncatchable), `SIGHUP` (1, hangup/reload), `SIGINT` (2, Ctrl-C). A process tree (`pstree`) shows parent/child relationships. Understanding process behavior is essential for debugging and for malware analysis.


## 3.9 SSH

SSH provides encrypted remote login. Key-based authentication is preferred over passwords.

```
ssh-keygen -t ed25519 -C "you@example.com"    generate key pair
ssh-copy-id user@host                          install public key
ssh -i ~/.ssh/key user@host                    connect with specific key
scp file user@host:/path                       copy file
rsync -avz dir/ user@host:/dir/                sync
```

Hardening `/etc/ssh/sshd_config`: disable root login (`PermitRootLogin no`), disable password auth (`PasswordAuthentication no`), use key-based auth, restrict users, change default port (minor), keep software updated. SSH keys must be protected (passphrase, restricted permissions `600`). Compromised private keys are a major attack vector.

## 3.10 Cron and Environment Variables

**Cron** schedules recurring tasks via crontabs:

```
# m h dom mon dow user  command
*/5 * * * *  root  /usr/local/bin/check.sh
0 2 * * *    root  /usr/local/bin/backup.sh
```

- System crontab: `/etc/crontab`; user crontabs via `crontab -e`; `/etc/cron.d/`.
- Security relevance: world-writable cron scripts, PATH hijacking, and insecure permissions can lead to privilege escalation. Cron runs with the privileges of the owner.

**Environment variables** configure process behavior: `PATH`, `HOME`, `SHELL`, `LANG`, `PWD`. `env` and `export` inspect/set them. Insecure `PATH` (including `.` or a writable directory) can cause a privileged script to execute an attacker-controlled binary — a classic escalation path.

## 3.11 Logs and Monitoring

Linux logs are concentrated in `/var/log/`:

- `/var/log/auth.log` (Debian) or `/var/log/secure` (RHEL): authentication events, sudo usage, SSH logins.
- `/var/log/syslog` or `/var/log/messages`: general system messages.
- `/var/log/kern.log`: kernel messages.
- Application logs in `/var/log/<app>/`.

Use `journalctl` for systemd logs, `grep`/`awk`/`tail -f` for analysis, `logrotate` for rotation. Security monitoring looks for patterns: repeated failed logins, unusual privileged commands, new accounts, unexpected cron entries, changes to `/etc/passwd` or `sudoers`.

## 3.12 Linux Security Mechanisms

- **Discretionary Access Control (DAC):** traditional owner/group/other permissions.
- **Mandatory Access Control (MAC):** SELinux (Red Hat) and AppArmor (Ubuntu/Debian) enforce policies regardless of owner. SELinux contexts (e.g., `unconfined_u:object_r:httpd_t:s0`) are a common source of "permission denied" puzzles.
- **Namespaces:** isolate kernel resources — PID, mount, network, user, IPC, UTS, cgroup. Containers are built on namespaces plus cgroups.
- **Control groups (cgroups):** limit and account for resource usage (CPU, memory, I/O).
- **Seccomp:** restricts which syscalls a process may make; used by sandboxes.
- **Capabilities:** fine-grained privilege subdivision (see above).
- **PAM (Pluggable Authentication Modules):** flexible authentication framework.

```
+-------------------------------------------+
| Container (namespaces: pid, net, mnt,...) |
|   +-------------------------------------+  |
|   | Process (seccomp filters syscalls)  |  |
|   +-------------------------------------+  |
|   cgroups limit CPU/memory                |
+-------------------------------------------+
                   |
             Linux kernel
```

Containers are **not** full virtual machines: they share the host kernel. A kernel vulnerability can break container isolation. This matters for cloud and infrastructure security (Chapter 19).

## 3.13 Kernel Fundamentals

The Linux kernel is monolithic but modular. Loadable kernel modules (`.ko`) extend it; they run in ring 0. Device drivers are a large source of kernel bugs. Kernel exploitation requires bypassing KASLR (kernel ASLR), SMEP/SMAP (prevent executing/accessing user memory from kernel), and other mitigations. The kernel's attack surface is exposed through syscalls, /proc, netlink, ioctl, and eBPF. For most web researchers, kernel exploitation is a specialization pursued later (Chapter 21).

## 3.14 Practical Exercises (Do These in a Lab)

1. Create a user, set a password, add to a group, and verify with `id` and `/etc/passwd`.
2. Create a file with mode `600`, then experiment with `chmod` values and observe who can read it.
3. Write a Bash script that takes a domain, resolves it with `dig`, and prints the A records.
4. Use `ss -tulpn` to identify which process listens on port 22 and 80 in your lab VM.
5. Set up an SSH key pair and disable password login in a disposable VM; confirm key-only login works.
6. Schedule a cron job that appends the date to a file every minute; verify with `tail -f`.
7. Inspect a process's maps with `cat /proc/<pid>/maps`; identify stack, heap, and library regions.

## 3.17 Mastery Deep Dive: The Linux Permission Model

Chapter 3 named the permission bits; mastery means being able to predict the *effective* access of a process before you run it, and to explain exactly where the kernel inserts its check. Every local privilege-escalation finding is a story about a privilege boundary that was wider than the author intended.

> **Authorization note.** Every command below is intended for a system you own, a disposable VM, or an explicitly in-scope engagement. The offensive mechanics are described so you can recognize and defend against them — do not apply them to third-party systems.

### 3.17.1 Mode Bits and umask, Worked

A Unix mode is a 12-bit number: three sets of `rwx` (owner, group, other) plus three special bits. Octal is used because each digit packs exactly three bits: `7 = 111`, `6 = 110`, `5 = 101`, `4 = 100`, `0 = 000`.

**Worked `umask` calculation.** `umask` is a *mask of bits to remove*. A program requests a base mode (666 for files, 777 for directories, because the kernel adds no execute bit to a newly created file). Effective mode = `requested & ~umask`.

| umask | File 666 & ~mask | Directory 777 & ~mask | Meaning |
|-------|------------------|-----------------------|---------|
| `022` | `644` (`rw-r--r--`) | `755` (`rwxr-xr-x`) | Public read, owner write |
| `077` | `600` (`rw-------`) | `700` (`rwx------`) | Private |
| `002` | `664` | `775` | Group-shared |
| `027` | `640` | `750` | Group read, no other access |

Check `022` by hand: `~022 = 755` in octal, `666 & 755 = 644`. For the directory: `777 & 755 = 755`. A common mistake is assuming `umask 022` is "secure" — it is the traditional default that makes every new file world-readable. On a host handling secrets, `umask 077` in service units (`UMask=0077` in systemd) is the correct default.

**Directory permissions differ from file permissions:** `r` lists names, `w` creates/deletes/renames entries, and `x` traverses (allows resolving a name inside). To read a file at `/lab/dir/file` you need `x` on `/`, `/lab`, and `/lab/dir`, plus `r` on the file. `w` on a directory gives the ability to unlink a file *regardless of the file's own mode* — the reason sticky bits exist on `/tmp`.

### 3.17.2 Special Bits: setuid, setgid, and Sticky

| Bit | Octal | Effect on a file | Effect on a directory |
|-----|-------|------------------|-----------------------|
| setuid | 4000 | Executes with the **owner's** UID | Ignored on Linux |
| setgid | 2000 | Executes with the file's group | New files inherit the directory's group |
| sticky | 1000 | Ignored | Only the owner (or root) can delete entries |

`setuid` is a privilege *delegation* mechanism: a program owned by root with mode `4755` runs with UID 0 while the invoking user stays the same real UID. This is how `passwd` can write `/etc/shadow`. It is also a classic escalation surface — if such a program can be coerced into executing a shell, loading a library from a writable path, or following a symlink, the delegated privilege becomes full root.

```bash
find / -xdev -perm -4000 -type f 2>/dev/null     # setuid files
find / -xdev -perm -2000 -type f 2>/dev/null     # setgid files
find / -xdev -perm -0002 -type f 2>/dev/null     # world-writable files
find / -xdev -perm -1000 -type d 2>/dev/null     # sticky directories
```
Interpretation: baseline this list on a clean system and re-run after changes. An *unexpected* setuid binary in a writable directory is a high-priority review item. Note `setgid` directories (e.g., `/var/mail`) and that a setgid *binary* can be just as dangerous as setuid.

**Decision tree for reviewing a writable executable:**

1. Is the file in a directory where a non-root user can create or rename entries? If yes → treat as critical.
2. Can the binary be invoked with an argument that becomes a path, command, library, or config file? If yes → check who controls that path.
3. Does it call `system()`/`popen()` or `exec*` with a relative path? Relative paths consult `PATH` — a privileged process with a user-controlled `PATH` will execute the user's binary.
4. Does it load shared libraries via `LD_LIBRARY_PATH`? Setuid binaries ignore this for security, but setgid or capability-bearing binaries have subtleties worth testing in a lab.
5. Is the binary unsigned, from a third-party repo, or recently changed? Compare hashes against a known-good baseline.

### 3.17.3 POSIX Capabilities: Root Without Being Root

Root's privilege is subdivided into roughly 40 capabilities. The ones you will encounter constantly:

| Capability | What it grants | Why it matters |
|------------|----------------|----------------|
| `CAP_NET_RAW` | Raw sockets, packet crafting | Enables sniffing/spoofing in a lab |
| `CAP_NET_ADMIN` | Interface/routing/firewall changes | Can redirect traffic |
| `CAP_SETUID` / `CAP_SETGID` | Change UID/GID | Effectively a path to root |
| `CAP_DAC_OVERRIDE` | Bypass file read/write/execute checks | Reads any file |
| `CAP_SYS_ADMIN` | Mount, namespaces, many admin ops | Near-root power |
| `CAP_SYS_PTRACE` | Trace other processes | Reads another process's memory |

There are three capability sets per thread: **permitted** (what it may use), **effective** (what is currently used), and **inheritable** (what `exec` may pass on). A file capability (`setcap`) grants bits on execution; an ambient set can be inherited across `execve`. A binary with `CAP_SETUID+ep` is functionally as dangerous as a setuid-root binary and is often missed by audits that only check `-perm -4000`.

```bash
getcap -r / 2>/dev/null                       # find file capabilities
capsh --print                                  # current bounding/effective sets
setcap cap_net_raw+ep /lab/bin/labtool         # lab only
getcap /lab/bin/labtool
```
Interpretation: `+ep` means effective and permitted. Any result outside your baseline deserves review. The bounding set limits what a process can ever acquire; dropping unused capabilities from a service unit (`CapabilityBoundingSet=`) is a high-value hardening step.

### 3.17.4 ACLs, Ownership, and the Effective Permission Algorithm

POSIX ACLs extend the three-class model with named users/groups and a **mask** that caps all named entries.

```bash
setfacl -m u:<LAB_USER>:rw /lab/shared/file
setfacl -m g:<LAB_GROUP>:r-x /lab/shared/dir
setfacl -d -m u:<LAB_USER>:rwx /lab/shared/dir   # default ACL for new children
getfacl /lab/shared/file
```
Interpretation of `getfacl`: `user::<LAB_OWNER>` is the owner entry; `mask::` is the maximum effective permission for named users/groups; `effective:` is computed permission after the mask. A `+` at the end of an `ls -l` mode (e.g., `rw-rw-r--+`) signals an ACL. The kernel's check order is deliberately simple: if UID matches owner → use owner class; else if any group entry matches → union of matching entries **intersected with the mask**; else → other class. Note that a user who is *not* the owner but belongs to the owning group gets the **group** bits, not owner bits — a frequent source of surprise.

Ownership rules matter too: only root can `chown` to another user (a non-root user cannot give a file away), and changing group is limited to groups the user belongs to. Sticky-bit directories combined with group-writable files create the classic "I can't delete your file, but I can overwrite it if it's world-writable" scenario.

### 3.17.5 Verification Checklist for Permissions

- [ ] `find / -xdev -perm -4000 -o -perm -2000` output is baselined and reviewed.
- [ ] No setuid/setgid/capability binary resides in a writable directory.
- [ ] Service accounts use `UMask=0077` or equivalent.
- [ ] ACLs on shared directories have explicit masks; default ACLs are intentional.
- [ ] `/tmp` is mounted `nodev,nosuid,noexec` where practical.
- [ ] Capabilities are dropped with `CapabilityBoundingSet=` in service units.

## 3.18 Mastery Deep Dive: Identity, PAM, sudo, and SSH

### 3.18.1 The Account Databases, Field by Field

```
<LAB_USER>:x:1001:1001:Lab User:/home/<LAB_USER>:/bin/bash
```
`/etc/passwd` fields, in order: username, password marker (`x` means the hash lives in `/etc/shadow`), UID, primary GID, GECOS/comment, home directory, login shell. UID 0 is root; UIDs below 1000 are system accounts on Debian-based systems. A shell of `/usr/sbin/nologin` or `/bin/false` prevents interactive login while allowing a service to own files.

`/etc/shadow` fields: username, hash, days since epoch of last change, minimum days between changes, maximum days, warning days, inactivity days, expiry date, reserved. Prefix `6` denotes SHA-512 crypt, `y` denotes yescrypt, `1` is MD5-crypt (obsolete). Because this file is root-readable only, an attacker who reads it can crack hashes offline — its permissions (normally `640 root:shadow`) are a critical control.

```bash
getent passwd <LAB_USER>
getent shadow <LAB_USER>      # root only
getent group <LAB_GROUP>
awk -F: '3==0 {print1}' /etc/passwd    # all UID 0 accounts
awk -F: '(2==""){print1}' /etc/shadow  # accounts with empty passwords
```
Interpretation: the last two commands are what an auditor runs to find *additional root accounts* and *passwordless accounts* — both should normally return nothing. Unexpected UID-0 entries are a persistence indicator.

### 3.18.2 PAM: The Authentication Stack

PAM (Pluggable Authentication Modules) separates "how you authenticate" from "what the application does." A service file such as `/etc/pam.d/<LAB_SERVICE>` contains lines of the form:

```
type   control   module            arguments
auth   required  pam_unix.so       try_first_pass
auth   required  pam_faillock.so   authfail deny=5 unlock_time=900
account required  pam_unix.so
session optional  pam_systemd.so
password [success=1 default=ignore] pam_unix.so obscure sha512
```

The four **types** are `auth` (verify identity), `account` (is the account allowed *now* — expiry, time restrictions), `session` (set up/tear down, e.g., mount home), and `password` (update credentials). Control flags: `required` (failure ultimately fails but other modules still run), `requisite` (failure stops immediately), `sufficient` (success can short-circuit if no prior `required` failed), `optional`. Modules stack in order; the cumulative result decides.

Practical consequences: adding `pam_faillock` implements lockout; `pam_pwquality.so` enforces password policy; `pam_limits.so` sets resource limits. A "permission denied" that survives correct passwords is often an `account`-type module (expired account) or a PAM stack ordering mistake, not the password itself. Debug in a lab with `journalctl -u <LAB_SERVICE>` and `/var/log/auth.log` rather than guessing.

### 3.18.3 sudo Policy and the Privilege Boundary

`sudo` executes a command as another user under a policy in `/etc/sudoers` (always edit with `visudo`, which validates syntax). Useful constructs:

```
Defaults      secure_path="/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
Defaults      !visiblepw, timestamp_timeout=5, logfile="/var/log/sudo.log"
%<LAB_ADMINS> ALL=(ALL:ALL) ALL
<LAB_USER>    ALL=(root) /usr/bin/systemctl status <LAB_UNIT>
```

`secure_path` prevents a user's `PATH` from influencing which binary sudo runs — without it, `sudo <LAB_TOOL>` could resolve to a user-placed file. `timestamp_timeout` controls credential caching; a long timeout means a walked-away session is a privilege window. `NOPASSWD` removes the password prompt entirely and must be used with extreme care; wildcard command arguments are dangerous because the user may control the argument that reaches a shell.

```bash
sudo -l                     # what am I allowed to do?
visudo -c                   # validate the file before applying
sudo -k                     # invalidate cached credentials
grep -R 'NOPASSWD' /etc/sudoers.d/
```
Interpretation: `sudo -l` is the first thing to check on any host you are authorized to assess. An entry like `(root) /usr/bin/vim` grants file-edit-as-root, which is equivalent to root because the editor can spawn a shell — a conceptual escalation path, never to be used outside the lab.

### 3.18.4 SSH Hardening with a Concrete Config

A hardened `/etc/ssh/sshd_config` for a lab host might read:

```sshconfig
Port 22
Protocol 2
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
AuthenticationMethods publickey
AllowUsers <LAB_USER>
MaxAuthTries 3
LoginGraceTime 30
X11Forwarding no
AllowAgentForwarding no
PermitTunnel no
ClientAliveInterval 300
ClientAliveCountMax 2
Subsystem sftp /usr/lib/openssh/sftp-server
```

Each line closes a specific avenue: disabling root login removes the most-targeted account, password auth removes brute-force and credential-stuffing, `AuthenticationMethods publickey` prevents fallback, `AllowUsers` shrinks the valid principal set, `MaxAuthTries` and `LoginGraceTime` limit guessing and unauthenticated resource use, and disabling forwarding prevents the host from becoming a pivot. Changing the port is *not* security — it only reduces log noise.

```bash
sshd -t -f /etc/ssh/sshd_config && echo "config OK"
sudo systemctl reload ssh
ssh -o PreferredAuthentications=publickey -o PasswordAuthentication=no <LAB_USER>@<LAB_HOST>
grep -E 'Failed password|Accepted publickey|Invalid user' /var/log/auth.log
```
Interpretation: `sshd -t` must succeed *before* reload; otherwise you can lock yourself out. The `grep` shows the difference between attack noise (`Failed password`, `Invalid user`) and intended access (`Accepted publickey`) — the foundation of SSH detection.

Key hygiene: generate with `ssh-keygen -t ed25519 -a 100 -f ~/.ssh/<LAB_KEY>`, protect the private key with `600`, use a passphrase, and rotate keys when an administrator leaves. A private key in a backup, CI secret, or a developer's laptop is a credential with the same power as a root password.

## 3.19 Mastery Deep Dive: Processes, systemd, and Logging

### 3.19.1 Signals and Process Control

A signal is a small asynchronous notification. Mastery means knowing which can be caught and which cannot:

| Signal | Number | Default | Can be caught? | Typical use |
|--------|--------|---------|----------------|-------------|
| SIGHUP | 1 | Terminate | Yes | Terminal closed; daemon reload |
| SIGINT | 2 | Terminate | Yes | Ctrl-C |
| SIGQUIT | 3 | Terminate + core | Yes | Ctrl-\ |
| SIGKILL | 9 | Terminate | **No** | Last resort |
| SIGSEGV | 11 | Terminate + core | Yes | Invalid memory access |
| SIGTERM | 15 | Terminate | Yes | Graceful shutdown |
| SIGSTOP | 19 | Stop | **No** | Suspend |
| SIGCONT | 18 | Continue | Yes | Resume |

`kill -TERM <PID>` asks nicely and lets handlers flush state; `kill -9` cannot be handled and may leave locks, temp files, or corrupted state. Always escalate from 15 to 9, never the reverse. `pkill -f <LAB_PATTERN>` matches the full command line — verify with `pgrep -a -f` first so you do not signal the wrong process.

### 3.19.2 systemd Units and Timers

A unit file declares desired state. A minimal hardened service:

```ini
[Unit]
Description=Lab collector
After=network-online.target

[Service]
Type=simple
User=<LAB_USER>
Group=<LAB_GROUP>
ExecStart=/usr/local/bin/<LAB_TOOL> --config /etc/<LAB_TOOL>/config.yml
WorkingDirectory=/var/lib/<LAB_TOOL>
UMask=0077
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
CapabilityBoundingSet=
ReadOnlyPaths=/
ReadWritePaths=/var/lib/<LAB_TOOL>
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

`NoNewPrivileges=true` blocks setuid/file-capability escalation by the service and its children. `ProtectSystem=strict` mounts most of the filesystem read-only for the unit; `PrivateTmp=true` gives it an isolated `/tmp`; an empty `CapabilityBoundingSet` drops all capabilities. These options are the practical payoff of understanding the permission model in 3.17.

```bash
systemctl daemon-reload
systemctl enable --now <LAB_UNIT>.service
systemctl status <LAB_UNIT>
systemd-analyze security <LAB_UNIT>     # exposure score and suggested directives
journalctl -u <LAB_UNIT> --since "10 min ago" --no-pager
```
Interpretation: `systemd-analyze security` returns an exposure level; each "unsafe" line points at a directive you can add. A service that writes outside its declared `ReadWritePaths` will fail — that is the intended signal that your isolation is working.

Timers replace cron for systemd-native scheduling:

```ini
[Timer]
OnCalendar=*-*-* 02:00:00
Persistent=true
Unit=<LAB_JOB>.service
```
`Persistent=true` runs a missed job at boot; `systemctl list-timers --all` shows next and last run times. Audit timers as rigorously as crontabs: the unit runs with whatever `User=` states, and a writable `ExecStart` path is an escalation surface.

### 3.19.3 journald and auditd: Two Complementary Logs

`journald` collects structured logs from services, the kernel, and the boot process; `auditd` records *specific kernel-observed events* with fine-grained rules.

```bash
journalctl -u ssh --since "1 hour ago" --no-pager
journalctl -k | grep -i 'denied\|segfault'
journalctl _UID=1001 -o json | head -5
journalctl -f -o short-iso
```

Audit rules live in `/etc/audit/rules.d/audit.rules`:

```audit
-w /etc/passwd -p wa -k identity
-w /etc/shadow -p wa -k identity
-w /etc/sudoers -p wa -k scope
-a always,exit -F arch=b64 -S execve -k process_exec
-a always,exit -F path=/usr/bin/sudo -F perm=x -k sudo_use
-e 2
```
`-w` watches a path with permissions `w`rite/`a`ttribute change; `-S execve` records process execution with arguments; `-e 2` locks the rules until reboot. Query with:

```bash
ausearch -k identity --start today
ausearch -m USER_LOGIN -ts recent
aureport -au --summary
```
Interpretation: an `auditd` event carries `uid`, `auid` (the *original* login UID, preserved across `su`/`sudo`), `exe`, and `tty`. `auid` is the field that lets you attribute a root action to the human who logged in — without it, "root did it" is the end of the investigation. Note that audit rules impose overhead; scope them to security-relevant paths.

## 3.20 Mastery Deep Dive: Linux Hardening and Mandatory Access Control

### 3.20.1 AppArmor and SELinux Basics

DAC (owner/group/other) lets a user grant away their own files. **MAC** adds a system policy the owner cannot override. Two dominant implementations:

| | AppArmor | SELinux |
|---|----------|---------|
| Default on | Ubuntu, Debian, SUSE | RHEL, Fedora, CentOS |
| Model | Path-based profiles | Type enforcement with labels |
| Context | `/etc/apparmor.d/<LAB_PROFILE>` | `user:role:type:level` |
| Inspect | `aa-status`, `apparmor_parser` | `sestatus`, `getenforce`, `ls -Z` |
| Debug | `/var/log/syslog` (DENIED) | `ausearch -m AVC`, `/var/log/audit/audit.log` |

AppArmor profiles list path rules with modes such as `r`, `w`, `x`, and owner-qualified `own`. Use `aa-status` to see which profiles are in `enforce` versus `complain` mode; `aa-genprof <LAB_TOOL>` generates a profile by observing behavior in a lab. SELinux labels every process and object; a denial means the *type* of the process is not allowed to access the *type* of the object, even if Unix permissions permit it. `ps -eZ` and `ls -Z` expose labels; `setenforce 0` switches to permissive **temporarily** for diagnosis and should never be left in place on a production host.

> **Common puzzle:** `ls -l` shows mode 644 and the file is owned by you, yet `cat` says "Permission denied." On an SELinux system check `ls -Z` and `ausearch -m AVC`; on AppArmor check `aa-status` and the denial log. DAC passed, MAC refused.

### 3.20.2 Namespaces, cgroups, and seccomp

Namespaces virtualize kernel resources: PID, mount, network, user, IPC, UTS, and cgroup. A container is a process with a restricted set of namespaces plus cgroup limits and often a seccomp filter — **not** a virtual machine, because the host kernel is shared. `unshare --pid --mount-proc --fork bash` in a lab demonstrates a new PID namespace; `lsns` lists existing ones.

cgroups v2 limit resources: `pids.max`, `memory.max`, `cpu.max`. A runaway process in a container can otherwise exhaust the host. Seccomp filters restrict syscalls: `/proc/<PID>/status` shows the `Seccomp` field; `seccomp-tools dump <LAB_BINARY>` displays a BPF filter. Dropping `ptrace`, `keyctl`, `bpf`, and `mount` from an untrusted workload removes entire exploitation paths.

### 3.20.3 Hardening Checklist with Verification Commands

| Control | Apply | Verify |
|---------|-------|--------|
| No root SSH | `PermitRootLogin no` | `sshd -T \| grep permitrootlogin` |
| Key-only auth | `PasswordAuthentication no` | `sshd -T \| grep passwordauthentication` |
| Locked sudo timeout | `Defaults timestamp_timeout=5` | `sudo -l` and review |
| Filesystem mount flags | `nodev,nosuid,noexec` on `/tmp`, `/home` where feasible | `findmnt -no OPTIONS /tmp` |
| Capability drop | `CapabilityBoundingSet=` in units | `systemctl show <LAB_UNIT> -p CapabilityBoundingSet` |
| No new privileges | `NoNewPrivileges=true` | `cat /proc/<PID>/status \| grep NoNewPrivs` |
| Audit identity files | `-w /etc/passwd -p wa` | `ausearch -k identity` |
| MAC enabled | `aa-status` / `getenforce` | `aa-status`, `sestatus` |
| Automatic updates | `unattended-upgrades` / `dnf-automatic` | `systemctl status unattended-upgrades` |
| Resource limits | cgroup `pids.max`, `memory.max` | `cat /sys/fs/cgroup/<LAB_UNIT>/pids.max` |

**Detection mindset on Linux:** alert on new UID-0 accounts, changes to `/etc/passwd`, `/etc/shadow`, `/etc/sudoers*`, and SSH `authorized_keys`; new setuid/setgid or capability-bearing files; unexpected cron entries and systemd units; `auid=0` processes that were not spawned by an administrator; and outbound connections from a process that never made them before. Each of these is a *state transition*, which is why file-integrity baselines and audit rules pair well.

## 3.21 Mastery Deep Dive: Windows Security Architecture for Researchers

### 3.21.1 SIDs, Access Tokens, and Integrity Levels

Windows identity is numeric: a **SID** such as `S-1-5-21-<LAB_DOMAIN>-<LAB_RID>`. Well-known SIDs include `S-1-1-0` (Everyone), `S-1-5-18` (Local System), `S-1-5-32-544` (Administrators), and `S-1-5-32-545` (Users). Rights are granted to SIDs, not names, which is why renaming an account preserves its access.

When a user logs on, LSA creates an **access token** containing the user SID, group SIDs, privileges (e.g., `SeDebugPrivilege`, `SeLoadDriverPrivilege`), and an **integrity level**. Primary tokens are attached to processes; impersonation tokens are attached to threads. The kernel performs an access check by comparing the token's SIDs against a resource's DACL and checking the mandatory integrity policy.

**Integrity levels** (Low, Medium, High, System) implement Mandatory Integrity Control: a lower-integrity process cannot write to a higher-integrity object even if the DACL would allow it. This is the mechanism behind Protected Mode IE/Edge and low-integrity browser renderers. View your own token:

```powershell
whoami /user
whoami /groups
whoami /priv
Get-Process -Id $PID | Select-Object Id,ProcessName,Path
```
Interpretation: `whoami /priv` shows privileges and whether they are *Enabled* or *Disabled*. A disabled privilege cannot be used until a process explicitly enables it — a detail that matters when interpreting why an action failed.

### 3.21.2 UAC and the Split Token

User Account Control is a *privilege boundary*, not merely a prompt. An administrator logging on with Admin Approval Mode receives two tokens: a **filtered** (medium integrity) token for normal use and a **full** (high integrity) token used only after consent. A process started from Explorer is medium integrity even though the user is an Administrator; when it performs an administrative action, the Application Information service prompts and launches the process with the full token.

Why this matters for assessment: a medium-integrity process cannot silently write to high-integrity locations (e.g., `System32`), so persistence requires either consent, a high-integrity host process, or an auto-elevating component. Auto-elevation exists for certain signed Windows binaries and COM objects; discovering one in an authorized lab is a legitimate privilege-boundary finding, but it must never be exercised against a system you do not own. Defensively: enable `ConsentPromptBehaviorAdmin` at the default, keep UAC at the highest level, and treat any medium→high transition without a prompt as suspicious.

### 3.21.3 NTFS ACLs, the Registry, Services, and Tasks

An NTFS security descriptor contains a **DACL** (who is allowed/denied), a **SACL** (what to audit), owner, and group. DACL evaluation walks ACEs in order: explicit deny, explicit allow, inherited deny, inherited allow — placing a deny incorrectly can lock out administrators.

```cmd
icacls <LAB_DIR> /grant <LAB_USER>:(OI)(CI)F
icacls <LAB_DIR> /inheritance:e
icacls <LAB_DIR> /verify /save <LAB_ACL_BACKUP>
```
`(OI)` object inherit, `(CI)` container inherit, `F` full control. Back up ACLs before changing them — a bad `icacls` command can deny the administrators group.

Registry hives: `HKLM` (machine-wide), `HKCU` (per user), `HKU` (loaded hives), `HKCR` (class registration). Persistence-relevant keys include `...\CurrentVersion\Run`, `RunOnce`, `Winlogon`, and service keys under `HKLM\SYSTEM\CurrentControlSet\Services`.

```cmd
reg query "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run"
reg query "HKLM\SYSTEM\CurrentControlSet\Services\<LAB_SERVICE>"
schtasks /query /fo LIST /v | findstr /i "TaskName Author RunAsUser"
```
Services run as a configured account (LocalSystem, NetworkService, LocalService, or a domain account). Two classic lab-only findings: an **unquoted service path** (e.g., `C:\Program Files\Lab Tools\svc.exe` — Windows may try `C:\Program.exe` first) and a service binary in a directory where a low-privilege user can write. Both hinge on the same principle as Linux setuid: a privileged process loads something a lesser user can influence. Fix with quoted paths and restrictive ACLs.

Scheduled tasks are an equally legitimate administrative mechanism and an equally important audit target. Task Scheduler 2.0 stores definitions as XML; inspect with `Get-ScheduledTask | Select TaskName,State` and `Export-ScheduledTask -TaskName <LAB_TASK>`.

### 3.21.4 PowerShell, Event Logs, and Sysmon

PowerShell is a shell, scripting engine, and .NET host — which makes it both an admin tool and a rich source of telemetry. `Get-ExecutionPolicy` is **not** a security boundary; it is a configuration guardrail. Real controls are: Script Block Logging (Event ID **4104**, full deobfuscated script content), Module Logging (**4103**), Protected Event Logging, transcription, AMSI (Antimalware Scan Interface) inspection, and ConstrainedLanguage mode on high-risk hosts.

Security log IDs to know:

| ID | Meaning |
|----|---------|
| 4624 | Successful logon (check LogonType: 2 interactive, 3 network, 10 RDP) |
| 4625 | Failed logon |
| 4672 | Special privileges assigned to a new logon |
| 4688 | Process creation (enable command-line capture via policy) |
| 4720 | User account created |
| 4732 | Member added to a privileged local group |
| 7045 | Service installed (System log) |

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4625; StartTime=(Get-Date).AddHours(-1)} |
  Select-Object TimeCreated,Id,ProviderName -First 20
Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-PowerShell/Operational'; Id=4104} |
  Select-Object TimeCreated,Message -First 5
```
Sysmon extends this with high-fidelity events: **1** process creation (with hashes and parent PID), **3** network connection, **7** image load, **11** file creation, **12/13/14** registry events, **22** DNS query. Deploy with a vetted configuration (`<LAB_SYSMON_CONFIG>`), and forward logs off-host so a local administrator cannot erase evidence. Correlate by `ProcessGuid`: a chain like "Office child process → PowerShell with encoded command → outbound connection → registry Run key write" is a detection signature built from events 1, 1, 3, and 12/13/14.

### 3.21.5 Defender and ASR Hardening

Microsoft Defender for Endpoint includes Attack Surface Reduction rules, Controlled Folder Access, SmartScreen, and tamper protection. ASR rules are GUID-addressed; for example `9E6C4E1F-7D6D-4E41-87F3-35213B8AC2D8` blocks credential theft from LSASS.

```powershell
Get-MpPreference | Select-Object AttackSurfaceReductionRules_Ids,AttackSurfaceReductionRules_Actions
Set-MpPreference -AttackSurfaceReductionRules_Ids <ASR_RULE_GUID> -AttackSurfaceReductionRules_Actions Enabled
Set-MpPreference -EnableControlledFolderAccess Enabled
Get-MpComputerStatus | Select-Object RealTimeProtectionEnabled,TamperProtectionEnabled
```
Interpretation: always deploy ASR in **Audit** mode first, review the events (Event ID 1121 in `Microsoft-Windows-Windows Defender/Operational`), then move to Enabled. Blocking LSASS access breaks credential dumping but can also break legitimate dump collection — understand your tooling before enforcing. Keep tamper protection on, keep cloud-delivered protection on, and verify that EDR sensors report `Healthy` rather than assuming the agent is running.

## 3.22 Mastery Deep Dive: Cross-OS Comparison, Practice, and Knowledge Checks

### 3.22.1 Linux vs Windows: Same Idea, Different Mechanism

| Concept | Linux | Windows |
|---------|-------|---------|
| Identity | UID/GID (numeric) | SID |
| Privileged account | UID 0 (root) | Local System, Administrators |
| Privilege splitting | POSIX capabilities | Privileges in access token (`Se*`) |
| Discretionary ACL | Mode bits + POSIX ACLs | DACL with ACEs on securable objects |
| Mandatory control | SELinux/AppArmor types, integrity via LSM | Integrity levels + MIC |
| Elevated-by-default | `sudo`/setuid delegation | UAC filtered/full split token |
| Logs | journald, auditd, `/var/log` | Event Log, Sysmon, ETW |
| Scheduled execution | cron, systemd timers | Task Scheduler, services |
| Hardening framework | systemd sandboxing, seccomp, mount flags | ASR, CFA, AppLocker/WDAC |
| Script telemetry | shell history, audit `-S execve` | PowerShell 4104, AMSI |

The unifying principle: **both systems decide access by comparing a subject's attributes against an object's policy, with a mandatory layer above the discretionary one.** Once you see that, each OS is a vocabulary change, not a new mental model.

### 3.22.2 Integrated Lab Sequence (Own VM Only)

1. Create `<LAB_USER>`, add to a group, and inspect `id`, `/etc/passwd`, and `/etc/shadow`.
2. Create a file with mode `600`; change umask to `077` and `022`, create new files, and compare modes.
3. Locate setuid/setgid binaries and capabilities; baseline the list.
4. Configure a systemd service with `NoNewPrivileges=true`, `ProtectSystem=strict`, and `UMask=0077`; score it with `systemd-analyze security`.
5. Add an audit watch on `/etc/passwd`, trigger a benign change, and retrieve it with `ausearch -k identity`.
6. Harden SSH on a disposable VM, confirm `sshd -t`, then verify key-only login in a second terminal *before* closing the first.
7. On a Windows lab VM, inspect `whoami /priv`, enable PowerShell script block logging, run a benign script, and read Event ID 4104.
8. Install Sysmon with `<LAB_SYSMON_CONFIG>`; run a test process that makes a DNS query, and find event 22.

### 3.22.3 Detection and Defense Checklists

**Detection:**

- [ ] Alert on new UID-0/GID-0 accounts, empty-password accounts, and changes to `/etc/passwd`, `/etc/shadow`, `sudoers`, and `authorized_keys`.
- [ ] Alert on new setuid/setgid files, new capabilities, and files appearing in writable paths.
- [ ] Alert on new systemd units/timers, cron entries, Windows services (7045), and scheduled tasks.
- [ ] Correlate `auid` on Linux and `SubjectLogonId` on Windows to attribute actions to a person.
- [ ] Collect logs off-host; a local administrator can clear local logs on both OSes.

**Defense:**

- [ ] Key-only SSH, no root login, `AllowUsers`, short auth timeout, and verified config.
- [ ] Least-privilege sudo with no broad wildcards or blanket `NOPASSWD`.
- [ ] Capabilities and setuid binaries baselined; unnecessary ones removed.
- [ ] Services sandboxed with systemd directives or Windows service isolation.
- [ ] MAC enabled (AppArmor/SELinux) and ASR/CFA enabled in audit-then-enforce mode.
- [ ] Resource limits applied to untrusted processes and containers.

### 3.22.4 Knowledge Checks (Answers Included)

1. **A file is mode `664` under umask `002`. What was the requested mode?** 666; `666 & ~002 = 664`.
2. **Why is a setgid directory useful?** New files inherit the directory's group, enabling shared group ownership without `chown`.
3. **Which is more dangerous to miss in an audit: a setuid binary or a file capability `CAP_SETUID+ep`?** They are comparable; capability checks are often overlooked because `-perm -4000` does not find them.
4. **What does `auid` preserve across `sudo`?** The original login UID, allowing attribution to the human account.
5. **Why does `secure_path` matter in sudoers?** It prevents the invoking user's `PATH` from selecting which binary sudo executes.
6. **What does `NoNewPrivileges=true` block?** Acquisition of new privileges via setuid bits, file capabilities, and similar mechanisms by the unit and its children.
7. **Why did DAC allow a file but SELinux denied it?** DAC and MAC are independent checks; both must pass. Check `ausearch -m AVC`.
8. **What is the practical difference between a container and a VM?** A container shares the host kernel; a VM has its own kernel.
9. **Why is UAC a boundary rather than just a prompt?** Administrator sessions run with a filtered medium-integrity token; elevation creates a separate high-integrity process.
10. **Which PowerShell event contains deobfuscated script content?** Event ID 4104 (Script Block Logging).

### 3.22.5 Final Mastery Checklist

- [ ] I can compute effective modes from umask and explain where the kernel checks permissions.
- [ ] I can enumerate setuid/setgid/capability files and triage a finding.
- [ ] I can write and validate a sudoers rule, a hardened sshd config, and a sandboxed systemd unit.
- [ ] I can retrieve a specific event from journald, auditd, Windows Event Log, and Sysmon.
- [ ] I can explain, side by side, how Linux and Windows implement identity, discretionary access, and privilege elevation.

## 3.15 Key Takeaways

- Linux exposes system state through files; pipes and scripts let you compose powerful analysis workflows.
- Identity, permissions, capabilities, and MAC determine who can do what.
- Processes, services, logs, cron, and environment are both operational tools and escalation surfaces.
- Namespaces, cgroups, seccomp, and capabilities underpin containers and sandboxes.
- Kernel code is trusted; kernel bugs are high impact but a specialized target.
