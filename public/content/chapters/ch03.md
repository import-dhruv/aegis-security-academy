# Chapter 3: Linux Mastery for Security Researchers

> **Learning objectives.** Navigate and script the Linux shell fluently; manage users, permissions, processes, services, and packages; configure SSH and cron; use networking and logging commands; and explain Linux security mechanisms including capabilities, namespaces, and containers.

## 3.1 Why Linux Matters

Linux dominates security practice. It powers servers, cloud infrastructure, Android, and most security tooling. Kali Linux is a purpose-built penetration-testing distribution; Ubuntu is a common general-purpose and lab platform. A researcher who is fluent in Linux can work efficiently, understand the systems they test, and build reproducible labs.

Two distribution families matter here:

- **Debian-based:** Ubuntu, Kali, Linux Mint. Use `apt`/`dpkg`.
- **Red Hat-based:** RHEL, Fedora, CentOS Stream. Use `dnf`/`yum`/`rpm`.

Kali Linux is Debian-based and preloaded with hundreds of security tools. It is a good *toolbox*, not a daily-driver general OS, and should be used in labs and authorized engagements.

## 3.2 Linux Architecture

```
   +-----------------------------------------------------+
   | User applications (shell, tools, browsers, servers) |
   +-----------------------------------------------------+
   | Libraries (glibc, libssl, ...)                       |
   +-----------------------------------------------------+
   | System call interface                                |
   +=====================================================+
   | Kernel: process mgmt, memory, VFS, network, drivers  |
   +-----------------------------------------------------+
   | Hardware: CPU, RAM, disk, NIC                        |
   +-----------------------------------------------------+
```

The kernel exposes everything through system calls; user programs interact via libraries. The **Virtual File System (VFS)** layer abstracts file systems, and the **/proc** and **/sys** pseudo-filesystems expose kernel and process information as files. This "everything is a file" philosophy makes Linux introspection powerful: `cat /proc/cpuinfo`, `cat /proc/<pid>/maps`, etc.

## 3.3 Terminal Mastery

The shell is a command interpreter. Bash is the default on most distributions. Essential commands:

```
pwd                 print working directory
ls -la              list all files with details
cd /path            change directory
cp /a /b            copy; -r for directories
mv /a /b            move/rename
rm file             remove; -r recursive, -f force (dangerous)
mkdir -p a/b        create dirs including parents
cat file            print file
less file           page through file
head -n 10 file     first 10 lines
tail -f log         follow appended lines (great for logs)
grep -i "err" file  search case-insensitively
find . -name '*.py' search by name
locate file         fast search via updated database
wc -l file          count lines
sort / uniq         sort / deduplicate
cut -d: -f1 /etc/passwd   extract fields
sed 's/old/new/g'   stream editing
awk '{print $1}'    field extraction and processing
```

**Pipes and redirection** are the core of Unix power:

```
cmd1 | cmd2          pipe stdout of cmd1 into stdin of cmd2
cmd > file           redirect stdout to file (overwrite)
cmd >> file          append stdout
cmd 2> errors.log    redirect stderr
cmd &> all.log       redirect stdout and stderr
cmd < file           stdin from file
```

Combining tools is how real analysis happens:

```
cat access.log | grep " 404 " | awk '{print $1}' | sort | uniq -c | sort -rn | head
```

**Quoting:** single quotes preserve literally; double quotes allow variable expansion. Always quote variables in scripts to avoid word splitting and globbing bugs: `"$var"`.

## 3.4 Bash Scripting Fundamentals

```bash
#!/usr/bin/env bash
set -euo pipefail          # exit on error, unset var is error, pipe failures matter

target="${1:-localhost}"   # first arg or default
count=0

for port in 80 443 8080; do
  if timeout 1 bash -c "echo >/dev/tcp/target/port" 2>/dev/null; then
    echo "open: $port"
    ((count++))
  fi
done

echo "Checked 3 ports on target;count open."
```

Key constructs: variables (`x=1`, no spaces around `=`), conditionals (`if [ ... ]; then`, `[[ ]]` is more capable), loops (`for`, `while`), functions, arrays, and parameter expansion. Use `shellcheck` to find script bugs. Scripts are a superpower for repetitive security tasks — but always test them in a lab first.

## 3.5 Users, Groups, and Permissions

Linux is multi-user. Identity is defined by numeric UIDs/GIDs.

```
whoami                 current user
id                     uid, gid, groups
useradd -m alice       create user with home dir
passwd alice           set password
usermod -aG sudo alice add to sudo group
groupadd researchers   create group
su - alice             switch user
sudo command           run as root (or another user)
```

Important files:

- `/etc/passwd`: user accounts (name, UID, GID, home, shell). The password field is usually `x`, with hashes in `/etc/shadow`.
- `/etc/shadow`: password hashes (root-only readable). Offline password cracking targets this file.
- `/etc/group`: group definitions.
- `/etc/sudoers`: sudo policy (edit with `visudo`).

Permissions: `chmod 755 file` (rwxr-xr-x), `chown alice:staff file`, `umask 022` sets default permissions. Special bits: setuid (`chmod u+s`), setgid, sticky bit (`chmod +t` on `/tmp`). Setuid root binaries are a classic local privilege-escalation target.

**Capabilities** split root's privileges into fine-grained units (e.g., `CAP_NET_RAW` to craft packets, `CAP_NET_ADMIN` to configure interfaces). Inspect with `getcap -r / 2>/dev/null`. Misconfigured capabilities can be as dangerous as setuid.

## 3.6 Processes and Services

```
ps aux                 snapshot of processes
ps -ef                 full format
top / htop             interactive process viewer
jobs                   background jobs in current shell
bg / fg                background/foreground a job
kill -9 PID            force kill
pkill -f pattern       kill by command line
nohup cmd &            run immune to hangup
systemctl status ssh   service status (systemd)
systemctl start/stop/enable NAME
journalctl -u ssh -f   follow systemd logs for a unit
```

Signals: `SIGTERM` (15, graceful), `SIGKILL` (9, uncatchable), `SIGHUP` (1, hangup/reload), `SIGINT` (2, Ctrl-C). A process tree (`pstree`) shows parent/child relationships. Understanding process behavior is essential for debugging and for malware analysis.

## 3.7 Networking Commands

```
ip addr                 show interfaces and IPs (modern replacement of ifconfig)
ip route                routing table
ip neigh                ARP/ND cache
ss -tulpn               listening sockets and owning processes (replaces netstat)
ping host               ICMP echo test
traceroute host         path to host
dig example.com A       DNS query
nslookup example.com    DNS query (older)
curl -I https://site    HTTP headers only
wget URL                download
nc -lvnp 4444           listen on port (netcat)
tcpdump -i eth0 -nn port 80    capture packets
```

Netcat is the "Swiss Army knife" of networking: it can open connections, listen, transfer files, and serve as a simple backdoor in labs. Never use it to establish unauthorized access.

`/etc/hosts` provides static hostname mapping; `/etc/resolv.conf` configures DNS resolvers; `/etc/nsswitch.conf` defines lookup order.

## 3.8 Package Management

```
# Debian/Ubuntu
sudo apt update && sudo apt install nmap
apt-cache search keyword
dpkg -i package.deb

# Red Hat/Fedora
sudo dnf install nmap
rpm -i package.rpm
```

Keep systems patched: `apt upgrade`. Package repositories are a supply chain; use official sources and verify signatures. Python tooling should be isolated in virtual environments:

```
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
pip freeze > requirements.txt
```

## 3.9 SSH

SSH provides encrypted remote login. Key-based authentication is preferred over passwords.

```
ssh-keygen -t ed25519 -C "you@example.com"    generate key pair
ssh-copy-id user@host                          install public key
ssh -i ~/.ssh/key user@host                    connect with specific key
scp file user@host:/path                       copy file
rsync -avz dir/ user@host:/dir/                sync
```

Hardening `/etc/ssh/sshd_config`: disable root login (`PermitRootLogin no`), disable password auth (`PasswordAuthentication no`), use key-based auth, restrict users, change default port (minor), keep software updated. SSH keys must be protected (passphrase, restricted permissions `600`). Compromised private keys are a major attack vector.

## 3.10 Cron and Environment Variables

**Cron** schedules recurring tasks via crontabs:

```
# m h dom mon dow user  command
*/5 * * * *  root  /usr/local/bin/check.sh
0 2 * * *    root  /usr/local/bin/backup.sh
```

- System crontab: `/etc/crontab`; user crontabs via `crontab -e`; `/etc/cron.d/`.
- Security relevance: world-writable cron scripts, PATH hijacking, and insecure permissions can lead to privilege escalation. Cron runs with the privileges of the owner.

**Environment variables** configure process behavior: `PATH`, `HOME`, `SHELL`, `LANG`, `PWD`. `env` and `export` inspect/set them. Insecure `PATH` (including `.` or a writable directory) can cause a privileged script to execute an attacker-controlled binary — a classic escalation path.

## 3.11 Logs and Monitoring

Linux logs are concentrated in `/var/log/`:

- `/var/log/auth.log` (Debian) or `/var/log/secure` (RHEL): authentication events, sudo usage, SSH logins.
- `/var/log/syslog` or `/var/log/messages`: general system messages.
- `/var/log/kern.log`: kernel messages.
- Application logs in `/var/log/<app>/`.

Use `journalctl` for systemd logs, `grep`/`awk`/`tail -f` for analysis, `logrotate` for rotation. Security monitoring looks for patterns: repeated failed logins, unusual privileged commands, new accounts, unexpected cron entries, changes to `/etc/passwd` or `sudoers`.

## 3.12 Linux Security Mechanisms

- **Discretionary Access Control (DAC):** traditional owner/group/other permissions.
- **Mandatory Access Control (MAC):** SELinux (Red Hat) and AppArmor (Ubuntu/Debian) enforce policies regardless of owner. SELinux contexts (e.g., `unconfined_u:object_r:httpd_t:s0`) are a common source of "permission denied" puzzles.
- **Namespaces:** isolate kernel resources — PID, mount, network, user, IPC, UTS, cgroup. Containers are built on namespaces plus cgroups.
- **Control groups (cgroups):** limit and account for resource usage (CPU, memory, I/O).
- **Seccomp:** restricts which syscalls a process may make; used by sandboxes.
- **Capabilities:** fine-grained privilege subdivision (see above).
- **PAM (Pluggable Authentication Modules):** flexible authentication framework.

```
+-------------------------------------------+
| Container (namespaces: pid, net, mnt,...) |
|   +-------------------------------------+  |
|   | Process (seccomp filters syscalls)  |  |
|   +-------------------------------------+  |
|   cgroups limit CPU/memory                |
+-------------------------------------------+
                   |
             Linux kernel
```

Containers are **not** full virtual machines: they share the host kernel. A kernel vulnerability can break container isolation. This matters for cloud and infrastructure security (Chapter 19).

## 3.13 Kernel Fundamentals

The Linux kernel is monolithic but modular. Loadable kernel modules (`.ko`) extend it; they run in ring 0. Device drivers are a large source of kernel bugs. Kernel exploitation requires bypassing KASLR (kernel ASLR), SMEP/SMAP (prevent executing/accessing user memory from kernel), and other mitigations. The kernel's attack surface is exposed through syscalls, /proc, netlink, ioctl, and eBPF. For most web researchers, kernel exploitation is a specialization pursued later (Chapter 21).

## 3.14 Practical Exercises (Do These in a Lab)

1. Create a user, set a password, add to a group, and verify with `id` and `/etc/passwd`.
2. Create a file with mode `600`, then experiment with `chmod` values and observe who can read it.
3. Write a Bash script that takes a domain, resolves it with `dig`, and prints the A records.
4. Use `ss -tulpn` to identify which process listens on port 22 and 80 in your lab VM.
5. Set up an SSH key pair and disable password login in a disposable VM; confirm key-only login works.
6. Schedule a cron job that appends the date to a file every minute; verify with `tail -f`.
7. Inspect a process's maps with `cat /proc/<pid>/maps`; identify stack, heap, and library regions.

## 3.15 Key Takeaways

- Linux exposes system state through files; pipes and scripts let you compose powerful analysis workflows.
- Identity, permissions, capabilities, and MAC determine who can do what.
- Processes, services, logs, cron, and environment are both operational tools and escalation surfaces.
- Namespaces, cgroups, seccomp, and capabilities underpin containers and sandboxes.
- Kernel code is trusted; kernel bugs are high impact but a specialized target.
